# Блок управления показом целей на доске — дизайн

## Контекст

Доска команды (`web/static/tracker.js`, компонент `App`) рисует четыре горизонтальных
слоя: шапка команды (`.topbar`), степпер статусов (`.status-stepper`), область контента
(`.content`) и внутри неё — сводка по дочерним узлам, предупреждения и карточки целей.

Единственное средство управления показом целей — `PriorityFilter`, который сегодня
рендерится внутри `.topbar__main`, между лидом команды и прогрессом узла, с классами
`tb-pri*`. Префикс `tb-` означает top-bar, то есть сама вёрстка фиксирует неудачное
размещение.

Заметка к ключевому результату рисуется компонентом `KRNote` и управляется локальным
состоянием `showNote` внутри `KRRow`; включается она пунктом меню действий KR. Общего
управления по доске нет.

Серверная часть не участвует: `/api/v1/teams/{id}/okrs` отдаёт цели в пользовательском
порядке вместе с заметками KR, а порядок целей меняют отдельные эндпоинты
`move-up`/`move-down`.

## Решения

### 1. Один объект настроек вида доски, один ключ в `localStorage`

Настройки блока хранятся одним объектом под одним ключом:

```json
{ "sort": "custom", "pri": { "P1": true }, "notes": false, "hideZeroWeight": false }
```

Ключ не содержит ни id команды, ни id периода — именно поэтому смена команды и смена
периода настройки не сбрасывают, а перезагрузка страницы их восстанавливает (требование
«Сохранение настроек показа целей»).

Ключ **не** привязан к пользователю, в отличие от `STORAGE_KEYS.desc` и
`STORAGE_KEYS.sidebar`: он описывает вид, а не данные пользователя, и повторяет контракт
`TREE_EXPANDED_KEY` (`okr_tree_expanded`) — раскрытость дерева в сайдбаре хранится так же.
Привязка к пользователю здесь дала бы лишнюю зависимость от асинхронно загружаемого
`/api/v1/me`: настройки нужны на первом рендере, до того как `me` приедет.

Ключ объявляется в `web/static/storage.js` рядом с остальными, чтобы контракт хранилища
оставался в одном месте, и читается/пишется через существующие `readJSON`/`writeJSON` —
они уже глотают исключения квоты и приватного режима, что закрывает требование «отказ
хранилища не ломает доску».

### 2. Нормализация прочитанного значения вместо доверия к нему

Прочитанное значение прогоняется через нормализатор: неизвестный `sort` → `custom`, не
объект `pri` → `{}`, неизвестные ключи внутри `pri` отбрасываются, нечитаемый JSON →
дефолты целиком. Тот же подход, что в `readTreeExpanded` и `readFavorites`: неизвестное
значение игнорируется, а не ломает рендер. Это закрывает сценарий «Повреждённые
сохранённые настройки».

### 3. Фильтрация и сортировка — детерминированный конвейер над `allGoals`

`allGoals` (все цели периода) остаётся источником для всех расчётов: прогресса, суммы
весов, предупреждения о сумме, охвата выгрузки, `existingGoals` в окне цели. Показ
считается отдельно и в фиксированном порядке:

1. фильтр по приоритету;
2. скрытие целей с нулевым весом;
3. сортировка.

Порядок важен: сортировка последней означает, что она упорядочивает именно то, что
останется на экране, а фильтры не зависят друг от друга и от порядка.

Сортировка по приоритету — **стабильная**: `PRI_LEVELS.indexOf` как ключ, при равенстве
сохраняется исходный (пользовательский) порядок. `Array.prototype.sort` в ES2019+
стабилен, дополнительной индексации не нужно.

### 4. Перетаскивание целей отключается при сортировке по приоритету

`handleReorderGoals` вычисляет число шагов `move-up`/`move-down` по индексам в
**пользовательском** порядке (`teamOKR.goals`), а бросок пользователь делает по тому
порядку, что видит. При сортировке по приоритету это разные порядки, и результат броска
был бы непредсказуем.

Поэтому при `sort !== 'custom'` цель не получает `dragProps`: `GoalCard` сам выводит из их
отсутствия, что `canReorderGoal` ложно, и не рисует ручку перетаскивания. Отдельного
признака в `GoalCard` не добавляется.

Перетаскивание ключевых результатов внутри цели не затрагивается: порядок KR и порядок
целей — независимые величины, и сортировка доски на него не влияет.

### 5. Заметки KR: общий признак плюс индивидуальное перекрытие

`KRRow` получает проп `notesOpen` — общее значение с доски. Локальное состояние меняет
смысл: вместо «показана ли заметка» оно хранит **перекрытие** общего значения.

```js
const [visOverride, setVisOverride] = useState(null); // null — следовать доске
const noteShown = visOverride === null ? notesOpen : visOverride;
const [noteExpanded, setNoteExpanded] = useState(true);
useEffect(() => { setVisOverride(null); setNoteExpanded(true); }, [notesOpen]);
```

Три следствия, и все три нормативны в delta spec: включение птички показывает заметки
везде; пункт меню по-прежнему работает для одного KR; переключение птички сбрасывает
перекрытия, то есть возвращает доску к однородному состоянию.

Альтернатива «птичка просто выставляет локальные состояния всех строк» отвергнута: она
требует синхронизации состояния сверху вниз через эффекты в каждой строке и теряет
различие «следую доске» / «решил сам».

Заметка показывается **развёрнутой**: свёрнутая однострочная форма потребовала бы ещё
одного нажатия на каждый KR, то есть воспроизвела бы ровно ту проблему, из-за которой
блок и появляется.

Попутно разделяются два действия, которые сегодня слиты в одно. Нажатие на длинную
заметку в `KRNote` подписано «Свернуть», а по факту скрывает её целиком — подпись не
соответствует действию. Теперь нажатие на заметку сворачивает её до одной строки и
разворачивает обратно (`noteExpanded`), а скрывает заметку только пункт меню. `KRNote`
при этом не меняется: он уже принимает `open`/`onToggle` и рисует верные подписи
«Ещё» / «Свернуть».

### 6. Блок рендерится внутри `.content`, непосредственно над списком целей

Блок ставится не между `.topbar` и `.status-stepper` и не между степпером и `.content`, а
первым элементом непосредственно перед списком карточек целей — после сводки по дочерним
узлам (`ClusterView`), заголовка «Цели этого узла» и предупреждения о сумме весов.

Причина: у узла с дочерними командами выше списка целей лежит агрегат по детям, на который
настройки блока не влияют. Блок, поставленный над ним, читался бы как фильтр всего
содержимого. У листовой команды (большинство случаев) выше ничего нет, поэтому блок и
оказывается сразу под шапкой — то, что требует постановка задачи.

Одна точка рендера работает для обеих веток, отдельного ветвления по `hasChildren` не
нужно.

### 7. Пустой результат фильтрации получает собственное состояние

Сегодня при фильтре, под который не попала ни одна цель, `.content` не рисует ничего:
`goals` пуст, а пустые состояния завязаны на `allGoals.length === 0`. С двумя фильтрами и
сортировкой это состояние становится вероятным, а выглядит как «у команды нет целей».

Вводится отдельное состояние: `allGoals.length > 0 && goals.length === 0` → сообщение со
сбросом настроек. Предложение создать первую цель в нём не показывается — оно относится
только к команде без целей.

### 8. Классы: `tb-pri*` уходят, появляется общий `filter-bar`

Префикс `tb-` у фильтра приоритета перестаёт быть правдой, поэтому классы переименовываются,
а не переносятся как есть.

Блок объявляется в `web/static/components.css` (общие компоненты), а не в `tracker.css`:
точно такая же панель с чекбоксом и сбросом уже есть на странице графа целей
(`.gt-topbar`, `.gt-topbar__toggle`, `.gt-topbar__reset` в `goal_tree.css`), и общий блок
даёт ей путь миграции. Сама миграция графа в этот change не входит: она ничего не меняет в
поведении, а объём правок уводит change от его задачи. Расхождение фиксируется заметкой в
карточке дизайн-системы.

Состав блока:

| класс | назначение |
| --- | --- |
| `.filter-bar` | сам ряд |
| `.filter-bar__group` | группа «подпись + элемент управления» |
| `.filter-bar__cap` | подпись группы |
| `.filter-bar__seg` | сегментированный переключатель |
| `.filter-bar__btn`, `--on` | кнопка сегмента |
| `.filter-bar__btn--pri` | кнопка приоритета: цвет уровня через `--pc` |
| `.filter-bar__n` | счётчик целей у уровня приоритета |
| `.filter-bar__clear` | сброс одного фильтра (`×` у фильтра приоритета) |
| `.filter-bar__check` | подпись с нативным чекбоксом |
| `.filter-bar__spacer` | распорка перед сбросом |
| `.filter-bar__reset` | сброс настроек блока |

Сегментированный переключатель один и тот же для порядка и для приоритета — две кнопки и
четыре кнопки одного примитива. Существующий `.seg-group`/`.seg-btn` не переиспользуется:
он рассчитан на модалку (`flex: 1`, рамка 2px, высота ~38px) и в компактном ряду фильтров
выглядел бы как основное действие экрана.

Нативный `<input type="checkbox">` используется как есть — общего чекбокса в системе нет,
и карточка `toggles.html` это прямо фиксирует («Общий чекбокс — отсутствующий примитив»).
Вводить его в этом change не нужно: он потянет за собой все существующие места
(`transfer-modal__check`, `export-modal__check`, `gt-topbar__toggle`, `kr-stage-label`).

### 9. Значения по умолчанию не меняют текущее поведение доски

`sort: 'custom'`, `pri: {}`, `notes: false`, `hideZeroWeight: false`. Пользователь, который
не трогал блок, видит доску такой же, как до изменения, — появляется только сам ряд.

## Интерфейс

Переиспользуются:

- сегментированный переключатель и счётчики — та же механика, что у нынешнего фильтра
  приоритета (карточка `design-system/src/cards/topbar.html`, блок `.tb-pri`), перенесённая
  в новый блок;
- нативный чекбокс в подписи — паттерн `.gt-topbar__toggle` из карточки
  `design-system/src/cards/toggles.html`;
- кнопка сброса — паттерн `.gt-topbar__reset` из карточки
  `design-system/src/cards/goal-tree-panel.html`;
- пустое состояние — карточка `design-system/src/cards/empty-states.html`.

Добавляются:

- карточка `design-system/src/cards/board-filters.html` — блок управления показом целей:
  состояния по умолчанию, с выбранным приоритетом, с включёнными птичками, со сбросом;
  заметка о расхождении с `.gt-topbar` и о том, что граф целей ещё не переведён на общий
  блок;
- экран доски в `design-system/prototype/` получает блок управления показом: сортировку,
  фильтр приоритета, обе птички и сброс в рабочем виде.

Из карточки `design-system/src/cards/topbar.html` фильтр приоритета удаляется: в шапке его
больше нет.

Вид согласуется на прототипе до реализации (пункт в `tasks.md`), карточки обновляются
после.

## Риски

- **Переименование `tb-pri*`.** Классы встречаются в четырёх местах: `tracker.css`,
  `tracker.js`, карточка `topbar.html`, прототип (`prototype/app.js` и сборка
  `design-system/tracker.html`). Пропущенное место даёт нестилизованный элемент. Проверка —
  поиском по `tb-pri` после правок: ни одного вхождения не остаётся.
- **Сборка прототипа склеивает скрипты в один `<script>`**: дубликат `const` на верхнем
  уровне роняет всю страницу. После правок прототипа обязательна проверка собранного файла
  (`node --check`), а не только визуальный осмотр.
- **Автотестов frontend в проекте нет.** Проверка — ручная, по сценариям delta spec.
