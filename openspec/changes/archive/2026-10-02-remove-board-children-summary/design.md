## Context

Мотивация описана в `proposal.md`, раздел Why. Здесь — устройство удаляемой вертикали и границы
удаления.

Сводка по дочерним командам — это один вертикальный срез от UI до store, который больше ничего не
обслуживает:

- **UI** (`web/static/tracker.js`): компонент `ClusterView` рисует плашку `.cluster-overview` и
  сетку `.cluster-grid` из карточек `ChildCard`. Он монтируется по флагу
  `hasChildren = overview && overview.children_summary?.items?.length > 0`. Тот же флаг управляет
  заголовком «Цели этого узла» и тем, где показывается предупреждение о сумме весов целей
  (`goalWeightWarn` рендерится до блока, если потомков нет, и после него, если есть).
- **Загрузка данных**: состояние `overview` заполняется двумя запросами
  `GET /api/v1/teams/{id}/overview?period_id=…` — в эффекте при смене команды или периода и в
  `reload()`. Запрос делается только если у узла в иерархии есть потомки.
- **API**: пакет `internal/http/handlers/api/v1/teams/overview`. Маппинг —
  `teamscommon.TeamOverviewResponse` → `ChildrenSummaryResponse`, сбор UDID лидов —
  `CollectOverviewUserUDIDs`. DTO: `TeamOverviewResponse`, `TeamChildrenSummaryResponse`,
  `TeamChildSummaryResult`.
- **Usecase**: `okrboard.TeamOverviewFor` читает все команды, строит иерархию за период, берёт
  прямых потомков (`teamsvc.FindDirectChildren`) и всех потомков (`CollectDescendantIDs`), грузит
  цели подчинённой иерархии одним батчем и считает средний прогресс. Строки карточек строит
  `buildDirectChildrenSummary`, которому нужны статусы команд в периоде и моменты последнего
  обновления. Публичный `DirectChildrenSummary` — та же сборка без батча целей, и у него нет
  вызовов.
- **Service / store**: `goal.Service.ListTeamLastUpdateInPeriod` → порт
  `goal.Repo.ListTeamLastGoalUpdateInPeriod` → реализация в `internal/store/goals` (CTE
  `goal_updates`). Единственный вызов — из `buildDirectChildrenSummary`.

Дерево навигации слева живёт на другом эндпоинте (`GET /api/v1/hierarchy`) и показывает по каждому
узлу тип, название, звезду избранного и прогресс с подсветкой отставания. Оно не зависит от сводки
и остаётся как есть.

Остальная часть доски берёт данные из `GET /api/v1/teams/{id}/okrs`: прогресс узла в топбаре,
статус в степпере, список целей. Собственный прогресс узла с экрана не исчезает.

## Goals / Non-Goals

**Goals:**

- Убрать сводку по дочерним командам из интерфейса целиком, вместе с агрегированной плашкой.
- Не оставить после удаления ни мёртвого эндпоинта, ни мёртвого кода ниже по слоям.
- Сохранить дерево навигации, прогресс узла в топбаре, степпер статуса, фильтры и список целей
  без изменений.
- Снять с открытия узла с потомками все запросы, которые делались только ради сводки.

**Non-Goals:**

- Переносить что-либо из карточек дочерних команд в дерево навигации: ни статус, ни счётчики
  целей, ни момент последнего обновления, ни лида. Дерево остаётся в текущем виде.
- Менять `GET /api/v1/hierarchy`, `GET /api/v1/teams/{id}/okrs` и любые другие эндпоинты.
- Менять расчёт прогресса, темпа, здоровья цели и пороги настроек пространства.
- Менять обзор периода (`/api/v1/periods/{id}/overview`) и метрики в админке: это другая
  возможность, другой эндпоинт, он остаётся.
- Трогать исторические документы (`docs/old_specs`, `docs/superpowers`) и исторический макет
  `design-system/tracker.html`.

## Decisions

### 1. Блок удаляется целиком, включая агрегированную плашку

Рассматривался вариант оставить плашку и убрать только сетку карточек. Отклонён:

- Плашка живёт на том же эндпоинте, поэтому вся вертикаль всё равно осталась бы в коде, а
  сокращение экрана было бы минимальным.
- Её подпись «N из M с целями» складывает две разные величины: `N` — команды с целями по всей
  подчинённой иерархии, `M` — число прямых потомков. Без карточек, по которым можно пересчитать
  `M`, дробь становится совсем непрозрачной.
- Собственный прогресс узла уже есть в топбаре, а прогресс каждой дочерней команды — в дереве.
  Средний прогресс по подчинённой иерархии — третья, самая редко используемая величина.

### 2. Эндпоинт удаляется вместе с UI, а не остаётся «на всякий случай»

Решение пользователя. `GET /api/v1/teams/{teamID}/overview` вызывался только из `tracker.js`,
публичного API у продукта нет, поэтому оставленный эндпоинт был бы кодом без потребителя и без
теста, который бы его защищал от расхождения с остальной доской. В proposal он помечен как
**BREAKING** на случай внешних скриптов.

### 3. Мёртвая цепочка срезается до слоя, где у символа появляется другой потребитель

Удаление сводки обнуляет потребителей сразу у нескольких символов ниже. Правило остановки:
символ удаляется, если после удаления сводки у него не остаётся вызовов из production-кода; тест,
который проверяет только этот символ, удаляется вместе с ним.

Под правило попадают:

| символ | почему удаляется |
| --- | --- |
| `okrboard.TeamOverviewFor`, `DirectChildrenSummary`, `buildDirectChildrenSummary` | единственные потребители — удаляемый handler и несуществующие вызовы |
| `okrboard.TeamOverview`, `okrboard.TeamChildSummary` | типы только этих методов |
| `teamscommon.TeamOverviewResponse`, `ChildrenSummaryResponse`, `CollectOverviewUserUDIDs` | маппинг только этого эндпоинта |
| `dto.TeamOverviewResponse`, `TeamChildrenSummaryResponse`, `TeamChildSummaryResult` | формат только этого ответа |
| `goal.Service.ListTeamLastUpdateInPeriod` и `goal.Repo.ListTeamLastGoalUpdateInPeriod` | вызывались только из `buildDirectChildrenSummary` |
| `teamsvc.FindDirectChildren`, `teamsvc.CollectDescendantIDs` | после удаления остаются только в собственных тестах |

Правило останавливается на: `teamscommon.TeamOKRResponse`, `okrboard.TeamSummary` и
`GetTeamsWithPeriodSummary`, `teamsvc.HierarchyFromTeams`, `statuses.List`,
`goals.ListByTeamPeriod` / `ListByTeamsPeriod`, `v1.BuildProgressBarInfo`,
`common.TeamTypeLabel` / `TeamPeriodStatusLabel`, `progress.PeriodProgress` — у всех остаются
другие вызовы.

Store-метод `ListTeamLastGoalUpdateInPeriod` покрыт `TestKRActivityTimestampsUsedForGoalAndTeamUpdates`
вместе с `listGoalLastKRActivity`. Удаляется только половина теста, относящаяся к команде;
проверка момента обновления цели остаётся — она обслуживает предупреждение «нет обновлений» на
карточке цели.

### 4. Пустое состояние у узла без собственных целей показывается всем узлам одинаково

Сейчас условия обоих пустых состояний содержат `!overview`, поэтому у узла с потомками и без своих
целей не показывалось ничего — место занимала сводка. После удаления `overview` из состояния
компонента узел с потомками и без целей попадает в обычное «Цели не добавлены» с кнопкой создания
первой цели (кнопка по-прежнему скрывается, когда статус периода запрещает создание).

Рассматривался вариант завести для таких узлов отдельное состояние вида «у этого узла нет
собственных целей, дочерние команды — в дереве слева». Отклонён: это новая сущность ради подсказки
про дерево, которое и так постоянно на экране, и она противоречит цели изменения — узлы перестают
делиться на «родительские» и «листовые».

Условия пустых состояний переписываются на `allGoals.length === 0` и признак доступа
(`hierarchy.length`), без участия `overview`.

### 5. Маршрут стережёт существующий golden-тест, отдельный тест не нужен

В репозитории уже есть `TestRoutesGolden`: он обходит собранный боевой роутер и сверяет каждую
пару (метод, шаблон) с `internal/http/testdata/routes.golden`. Удаление эндпоинта проявляется
там как одна убранная строка, причём без Postgres и без поднятия сервера.

Поэтому отдельный тест «overview отвечает 404» не заводится. Вариант с проверкой в
`teams/routes_test.go` был бы вырожденным: этот тест монтирует только пакеты `teams` и `status`,
поэтому 404 получался бы и без удаления. Вариант с интеграционным тестом на боевом роутере
работает, но стоит контейнера Postgres ради того, что golden-тест уже проверяет бесплатно.

### 6. Порядок удаления — сверху вниз

Сначала UI, затем маршрут и handler, затем usecase, затем service и store. На каждом шаге
приложение собирается и работает: удаляемый слой к этому моменту уже никому не нужен. Обратный
порядок потребовал бы ломать сборку.

### 7. Предупреждение о сумме весов целей рендерится один раз

Сейчас `goalWeightWarn` вставляется в двух местах — до сводки и после неё — по взаимно
исключающим условиям. Со сводкой исчезает и ветвление: предупреждение рендерится один раз, перед
блоком управления показом целей. Поведение предупреждения не меняется.

### 8. Поведение `ListTeamLastGoalUpdateInPeriod` сохраняется на уровне цели

Store-тест проверял на одном наборе данных две вещи: что правка метаданных ключевого результата
(только `updated_at`, без `progress_updated_at`) обновлением не считается, и что момент обновления
видят и команда-владелец, и команда, которой цель расшарена.

Первое правило действует и на уровне цели — на нём держится предупреждение «нет обновлений» на
карточке цели, — но проверялось только через удаляемый командный запрос. Поэтому проверка
переносится на `ListGoalsByTeamPeriod`, а не удаляется вместе с ним. Вторая проверка уходит: она
относилась к охвату удаляемого запроса. Тест переименовывается в
`TestKRActivityTimestampsUsedForGoalUpdates`.

## Интерфейс

Новых компонентов нет. Изменение только удаляет.

- **Дизайн-система.** Удаляется карточка `design-system/src/cards/child-cluster-cards.html`
  («Карточки команд» — сводка кластера и сетка дочерних команд): описанного ею компонента в
  продукте не остаётся. Остальные карточки не меняются; `sidebar-tree.html` (дерево навигации)
  остаётся как есть, потому что дерево не меняется.
- **Прототип.** `design-system/prototype` уже рендерит доску без блока сводки: функция `childCard`
  в `app.js` объявлена, но не вызывается. То есть целевой вид доски — ровно то, что прототип
  показывает сейчас, и согласовывать нужно именно его. Функция `childCard` удаляется как мёртвая,
  вид прототипа от этого не меняется.
- **Стили.** Блоки `.child-card*` и `.cluster-*` удаляются из `web/static/tracker.css`.
  Общие компоненты (`ProgressBar`, `UserInfo`, бейджи) не затрагиваются — они переиспользуются
  другими экранами.

## Производительность

Открытие узла с потомками делало, помимо запроса целей самого узла, ещё один запрос, внутри
которого: чтение всех команд пространства, построение иерархии за период, батч целей по всем
потомкам, батч статусов команд и батч моментов последнего обновления. Все они уходят.

Циклов с запросами в удаляемом коде нет (батчи уже были батчами), новых запросов изменение не
добавляет. Кеширование не вводится: ничего нового не считается.

## Слои

Удаление не создаёт новых зависимостей и не меняет направление существующих. Порт `goal.Repo`
сужается на один метод — это сужение контракта service → store, протекания абстракций не
возникает. UI перестаёт знать про `children_summary`, то есть связей становится меньше.

## Риски

- **Внешние потребители эндпоинта.** Публичного API у продукта нет, но эндпоинт мог использоваться
  в чьих-то скриптах. Помечено как BREAKING в proposal; в `docs/old_specs/040-api-contract.md`
  описание остаётся как исторический документ.
- **Пользователи, которые смотрели статус и счётчики целей дочерних команд именно в сводке.** После
  изменения в дереве видны только название, тип и прогресс. Это принятый компромисс: см.
  Non-Goals — переносить показатели в дерево в этом change не нужно. Если потребность подтвердится,
  это отдельный change про дерево.
- **Регрессия пустых состояний.** Самое тонкое место изменения — условия в `App`, где участвует
  `overview`. Покрывается ручной проверкой на узле с потомками и без собственных целей
  (решение 4).
