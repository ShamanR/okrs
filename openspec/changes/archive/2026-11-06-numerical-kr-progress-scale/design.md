## Context

Мотивация — в `proposal.md`, требования — в delta spec `team-okr-board`.

Весь change во фронтенде, и сейчас устроено так:

- `calcKRProgress` (`web/static/tracker.js`) считает прогресс числового результата для окна
  обновления: точки «старт = 0%, промежуточные, цель = 100%» сортируются по значению, между
  соседними — линейная интерполяция, результат округляется. Тот же алгоритм на бэкенде
  (`internal/core/progress`), и строка на доске показывает уже посчитанный бэкендом
  `kr.progress`.
- `KRScale` ставит всё по значению: `posOf(v) = (v − start) / (target − start)`. Подписи —
  абсолютно позиционированные `.kr-scale__lbl` в одну строку высотой 30px, без учёта
  соседей.
- `krMeasureTip` собирает текст подсказки для `.has-tip` (`content: attr()`, поэтому только
  текст с переводами строк, без разметки). `KRTargetLabel` выводит `fmtNum(cur) → fmtNum(target)`.
- В прототипе дизайн-системы (`design-system/prototype/app.js`) эти функции продублированы
  строковыми шаблонами: `calcKRProgress`, шкала в `krModal` и её живое обновление по вводу в
  обработчике поля текущего значения, `krMeasureTip`, `krTargetText`.

Автоматических тестов фронтенда нет. Проверяемыми делаются чистые функции: их можно вырезать и
выполнить в node.

## Goals / Non-Goals

**Goals:**

- Одна функция интерполяции для расчёта процента в окне и для положения на шкале: шкала не
  может разойтись с числом.
- Раскладка подписей шкалы — чистая функция от позиций и ширин, проверяемая без браузера.

**Non-Goals:**

- Расчёт прогресса на бэкенде и сохраняемые данные не меняются.
- Ступенчатая зависимость прогресса от значения (разрыв в точке) — отдельное изменение модели,
  если понадобится. Здесь пороговая метрика задаётся как сейчас: промежуточным значением рядом с
  целью.
- Редактор ключевого результата не меняется.

## Decisions

### 1. Интерполяция выносится в одну функцию, шкала строится по ней

Из `calcKRProgress` выделяется построение точек и неокруглённая интерполяция
`progressAt(points, value)`. `calcKRProgress` округляет её результат и ведёт себя как прежде.
`KRScale` ставит всё через неё же: старт — 0%, цель — 100%, промежуточное значение — в точке
своего процента, текущее значение и заливка — в `progressAt(points, current)`.

Для позиционирования берётся неокруглённое значение: текущее значение, равное промежуточному,
встаёт ровно на его отметку, а не рядом из-за округления. От процента в окне оно отличается
меньше чем на 0,5% — глазом не различимо.

Если у промежуточных значений проценты не растут вместе с продвижением к цели (валидация этого
не запрещает), отметки на шкале встанут не в порядке значений. Это верно: шкала показывает
прогресс, а прогресс в таком случае действительно идёт назад. Раскладка подписей сортирует их по
позиции, так что наложения это не создаёт.

*Альтернатива:* оставить ось по значению и только развести подписи. Отклонена: проблема
«ползунок у цели при 50%» остаётся, а она хуже наложения — шкала противоречит числу.

*Альтернатива:* две оси — значение сверху, прогресс снизу. Отклонена: для окна на 480px это
вдвое больше подписей ради сведения, которое и так видно по подписям у отметок.

### 2. Подписи раскладываются по ярусам чистой функцией по измеренным ширинам

`layoutScaleLabels(items, trackWidth)` получает подписи с позицией в процентах и шириной в
пикселях, возвращает для каждой ярус: 0, 1 или «скрыта». Старт и цель всегда на ярусе 0:
старт выравнивается по левому краю, цель — по правому, промежуточные — по центру, как сейчас.
Промежуточные значения по порядку позиции жадно встают на ярус 0, если не пересекаются с уже
поставленными там подписями с зазором 6px, иначе на ярус 1, иначе скрываются.

Ширины измеряются в браузере: `KRScale` рендерит подписи, в `useLayoutEffect` читает
`getBoundingClientRect` и сохраняет раскладку в состояние — до отрисовки кадра, без мигания.
Пересчёт — при изменении старта, цели, промежуточных значений и единицы. От текущего значения
подписи не зависят, ввод в поле раскладку не пересчитывает. Ширина окна фиксирована
(`.modal-box--w480`), поэтому подписка на изменение размера не нужна.

Скрытая подпись получает `visibility: hidden` и не участвует в раскладке. Её отметка
`.kr-scale__cp` уже несёт `title` со значением и процентом — этого достаточно для требования
«доступно по наведению».

*Альтернатива:* оценивать ширину по числу символов. Отклонена: зависит от шрифта и ломается на
единицах вида «пользователей».

*Альтернатива:* поворачивать подписи под углом. Отклонена: хуже читается и непривычно для
остальных элементов приложения.

### 3. Подсказка: путь к цели вместо отдельного списка промежуточных значений

Для числового результата с промежуточными значениями тело подсказки:

```
Было: 5 000 000 ₽
Стало: 3 000 001 ₽ · 50% прогресса
Цель: 3 000 000 ₽

Путь к цели:
0% — 5 000 000 ₽ · старт
50% — 3 000 001 ₽
100% — 3 000 000 ₽ · цель
Прогресс зависит от значения нелинейно.
```

Процент стоит первым: подсказка рисуется пропорциональным шрифтом, и колонку значений не
выровнять, а короткий процент в начале строки читается как колонка. Промежуточные значения
проходят через существующий `tipList` (восемь плюс «…и ещё N»), старт и цель добавляются вокруг
него и в лимит не входят. Порядок — по направлению метрики, как и сейчас. Процент в строке
«Стало» — `kr.progress`, то же число, что в строке результата; так подсказка не может
разойтись со строкой, под которой показана. Пометка «прогресс ещё не обновляли» остаётся в
строке «Стало» как есть, процент тогда не выводится: он заведомо 0%.

Без промежуточных значений подсказка не меняется.

### 4. Краткая запись чисел в свёрнутой подписи

Рядом с `fmtNum` появляется `fmtCompact(n)`: при |n| < 10 000 — `fmtNum(n)`; иначе деление на
1e3 / 1e6 / 1e9 с разрядом «тыс» / «млн» / «млрд» и не больше одного знака после разделителя,
незначащий ноль отбрасывается. Разделитель дробной части — точка, как у `fmtNum`, чтобы числа
в приложении не расходились по виду.

`KRTargetLabel` форматирует оба числа через `fmtCompact`; если значения различаются, а краткие
записи совпали — оба через `fmtNum`. Подсказка всегда выводит полные числа.

*Альтернатива из обсуждения:* при совпадении кратких записей показывать ближайшую
непройденную отметку («до 100%: ≤ 3 000 000 ₽»). Отклонена: подпись перестаёт значить
«текущее → цель» в части строк, а полная цель и так есть в подсказке.

### 5. Прототип повторяет то же самое строковыми шаблонами

В `design-system/prototype/app.js` переносятся `progressAt`, `layoutScaleLabels`,
`fmtCompact` и новые тела `krMeasureTip` / `krTargetText`. Раскладка подписей в прототипе
выполняется после вставки окна в DOM, там же, где сейчас живое обновление шкалы по вводу;
живое обновление переходит на `progressAt`. Прототип склеивается в один script — новые
функции НЕОБХОДИМО называть так, чтобы не задублировать `const` с уже существующими.

## Интерфейс

Переиспользуются без новых компонентов:

- шкала `.kr-scale` / `.kr-scale__labels` / `.kr-scale__cp` / `.kr-scale__cur` — меняется только
  способ позиционирования;
- подсказка `.has-tip` с `data-tip-title` / `data-tip` — меняется только текст;
- подпись `.kr-target__val`.

Добавляются модификаторы в `web/static/tracker.css`: `.kr-scale__labels--tiers` (высота под
второй ярус), `.kr-scale__lbl--tier1` (смещение вниз на высоту яруса),
`.kr-scale__lbl--hidden` (`visibility: hidden`).

Вид согласуется на прототипе: окно «Обновить прогресс» для метрики «старт 5 000 000 ₽, цель
3 000 000 ₽, промежуточное 3 000 001 ₽ → 50%» и для метрики с близкими отметками 95% и 98%;
строка этих результатов с подсказкой. Карточки дизайн-системы: `progress.html` и
`kr-editor.html` — шкала, `kr-row.html` и `goal-card.html` — подпись и подсказка.

## Risks / Trade-offs

- [Привычный вид шкалы меняется: у метрик с промежуточными значениями подписи значений
  распределяются неравномерно] → это и есть способ показать нелинейность; пояснение под шкалой
  остаётся.
- [Раскладка по измеренным ширинам зависит от загрузки шрифта: до загрузки Inter ширины
  другие] → окно открывается по действию пользователя, когда шрифт страницы уже загружен;
  если нет, раскладка с ширинами системного шрифта остаётся читаемой, лишь чуть иначе
  распределённой.
- [Строки «Было / Стало / Цель» частично дублируют путь к цели] → оставлены намеренно: требование
  о подсказке их называет, и они отвечают на вопрос «где мы сейчас» без чтения всего списка.
- [Архивация зависит от `clarify-kr-measure-values`] → в задачах явная проверка порядка.

## Migration Plan

Только статические файлы фронтенда: выкатываются вместе с приложением, откат — откат
`tracker.js` / `tracker.css`. Данные и API не меняются.
