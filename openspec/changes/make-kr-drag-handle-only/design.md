## Context

Мотивация — см. proposal.md, требования — delta spec `team-okr-board`.

В `GoalCard` (`web/static/tracker.js`) сейчас два разных способа перетаскивания:

- **Карточка цели** — `draggable` только на время жеста от ручки: `onMouseDown` на
  `.drag-handle` взводит состояние `goalDraggable`, снимается оно по `dragend` карточки и по
  `mouseup` на `window` (эффект). По `mouseleave` ручки признак намеренно не снимается:
  ручка мала, и указатель покидает её раньше, чем браузер решает, что это перетаскивание
  (см. архивный change `2026-10-01-add-board-filter-bar`).
- **Строка KR** — `.kr-item` с `draggable={!!canReorderKR}` постоянно. Чтобы нажатия на
  вложенные элементы не начинали перетаскивание, `onMouseDownCapture` записывает в ref
  `krPressNoDrag`, было ли нажатие внутри `[data-no-drag]` или `.modal-overlay`, а
  `onDragStart` по этому флагу отменяет жест. Пометки `data-no-drag` стоят на точке
  статуса, меню «···», блоке действий, `CollapsibleMarkdown` и др. Название KR пометки
  не имеет, а пометить его нельзя без потери выделения: у `draggable`-предка браузер
  начинает drag вместо выделения ещё до `dragstart`, так что отмена в `onDragStart`
  выделение не возвращает.

Прототип (`design-system/prototype/app.js`) повторяет ту же асимметрию: у KR
`draggable="true"` в разметке, у цели — взведение по `mousedown` на `[data-goal-handle]`.

## Goals / Non-Goals

**Goals:**

- Строка KR перетаскиваемая только во время жеста, начатого на её ручке.
- Один механизм «взвести по ручке — снять по `mouseup`/`dragend`» для цели и KR.

**Non-Goals:**

- Внешний вид ручки, её размер и положение — не меняются.
- Условия доступности перетаскивания KR (`canEdit && onReorderKR`) и логика
  `dragover`/`drop`/`onReorderKR` — не меняются.
- Клавиатурное изменение порядка и touch-жесты — вне рамок.

## Decisions

### 1. Строка KR становится `draggable` только на время жеста от ручки

`GoalCard` хранит id взведённого KR (`null` — ни один). `onMouseDown` на
`.kr-item__drag-handle` взводит id этого KR; строка получает
`draggable={canReorderKR && armedKrId === kr.id}`. Снимается признак по `dragend` строки и
по `mouseup` на `window`, как у цели; по `mouseleave` ручки — не снимается.

Альтернативы:

- *Ручка сама `draggable`, строка — нет.* Тогда изображение при перетаскивании — сама
  ручка 18×26 px, а не строка; пришлось бы вызывать `setDragImage` со строкой, что даёт
  разное поведение браузеров и расходится с тем, как сделано у цели. Отклонено.
- *Оставить строку `draggable` и пометить название `data-no-drag`.* Не работает: выделение
  текста у `draggable`-предка браузер подменяет на drag до `dragstart` (см. Context).
  Отклонено.

### 2. Общий хук для взведения по ручке

Логика «взвести по `mousedown` на ручке, снять по `mouseup` на `window`» выносится в
маленький хук в `tracker.js` (рабочее имя `useHandleDragArm`), возвращающий текущее
взведённое значение, функцию взведения и функцию сброса. Им пользуются и карточка цели
(значение `true`), и строки KR (id KR). Хук один на `GoalCard`, а не на каждую строку KR:
одновременно взвести можно только одну ручку, поэтому id достаточно, и слушатель `mouseup`
висит на `window`, только пока что-то взведено.

Альтернатива — скопировать эффект для KR рядом с эффектом цели. Отклонено: два
экземпляра неочевидной логики (почему не `mouseleave`) разойдутся при следующей правке.

### 3. Удаляется механизм `krPressNoDrag` / `data-no-drag`

Когда строка не `draggable` вне жеста от ручки, нажатие на вложенный элемент перетаскивание
начать не может, и отмена в `onDragStart` больше не нужна. Удаляются: ref `krPressNoDrag`,
`onMouseDownCapture` строки KR, проверка в `onDragStart`, атрибуты `data-no-drag` и
поясняющий комментарий в `markdown.js`. Перед удалением атрибутов проверяется, что других
читателей `[data-no-drag]` (CSS, JS) нет. Заодно исчезает и случай из #140 — перетаскивание
открытого из строки KR модального окна (`.modal-overlay`): строка не `draggable`, пока ручка
не нажата.

### 4. Прототип повторяет продукт

В `design-system/prototype/app.js` у `.kr-item` убирается постоянный `draggable="true"`,
ручка KR получает пометку `data-kr-handle`, а существующие обработчики `mousedown`/`mouseup`/
`dragend` взводят и снимают `draggable` у `[data-kr-item]` так же, как у `[data-goal-item]`.
Карточка `design-system/src/cards/goal-card.html` статична и атрибута `draggable` не несёт —
её разметка не меняется.

## Интерфейс

Новых компонентов нет, внешний вид не меняется: переиспользуется существующая ручка
`.kr-item__drag-handle` (курсор `grab`, подсветка по наведению). Поведение согласуется на
экране доски в прототипе `design-system/prototype/` (карточка цели в режиме редактирования).

## Risks / Trade-offs

- [Указатель уходит с ручки до того, как браузер начал drag, и жест теряется] → признак не
  снимается по `mouseleave`, только по `mouseup`/`dragend` — проверено на карточке цели.
- [Нажатие на ручку без перетаскивания оставляет строку `draggable`] → снимается по
  `mouseup` на `window`.
- [Кнопку отпустили за пределами окна, не начав перетаскивания: ни `mouseup`, ни `dragend`
  не приходят, и строка остаётся `draggable` — следующее выделение её названия начнёт
  перетаскивание] → взведение снимается также по первому `mousemove` без нажатых кнопок
  (`buttons === 0`) и по `blur` окна. Указатель обязан вернуться на страницу, прежде чем
  нажать на название, поэтому такой `mousemove` всегда приходит раньше. Во время
  нативного перетаскивания `mousemove` не приходит, так что начатый жест не прерывается.
  Прототип повторяет то же правило.
- [Взведение ручки KR всплывает к карточке цели] → обработчик ручки KR взводит только KR;
  ручка цели — отдельный элемент вне `.kr-section`, `dragstart` строки KR по-прежнему
  вызывает `stopPropagation`.
- [Автоматических JS-тестов во фронтенде нет] → проверка синтаксиса через вендорный
  babel и A/B-проверка в браузере (подмена `/static/tracker.js` версией из git).

## Migration Plan

Только статический фронтенд: выкатывается вместе с образом, откат — откат образа. Данных
и API изменение не касается.
