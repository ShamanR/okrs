# Design: longer-slugs-and-demo-seeding

## Context

Мотивация — в proposal.md. Текущее состояние, важное для решений:

- Грамматика slug живёт в одном месте: `domain.ValidTenantSlug`
  (`internal/core/domain/tenant.go`), max 32. В БД slug — `TEXT UNIQUE`, длина не зажата,
  миграция схемы не нужна. Slug участвует в поддоменной маршрутизации → потолок 63
  (DNS label, RFC 1035).
- `provisioning.Service.CreateTenant` (`internal/service/provisioning/provisioning.go`)
  делегирует в `tenants.TenantRepository.Create`, который выполняет один `INSERT` через
  `pgxpool.Pool` напрямую — транзакции нет.
- Демо-данные существуют только как `seed_demo.sql` (~2700 строк): захардкожены `tenant_id=1`
  (через хак `ALTER TABLE ... SET DEFAULT 1`), id всех сущностей (teams 2..27, 100..112;
  goals 9..38, 100..116; KR 7..60, 100..132 — все перекрёстные ссылки по этим id), даты
  периодов 2025–2026, и глобальный `TRUNCATE ... CASCADE` всех таблиц.
- Приложение работает на pgx/v5 — psql-переменные (`-v tenant_id=...`) недоступны.
- Деплой — несколько реплик в Kubernetes; функция живёт в базе, рассыпания по инстансам нет.

## Goals / Non-Goals

**Goals:**

- Единственный источник правды о демо-данных, исполняемый и приложением, и `psql` локально.
- Периоды демо всегда вычисляются от даты создания, без литеральных дат.
- Создание пространства и его наполнение атомарны: нет состояния «пустой тенант + занятый
  slug» после сбоя.
- Повторный вызов сидера для того же пространства не плодит дубликаты (нужно для
  пере-применения в локальном окружении).

**Non-Goals:**

- Обновление/«освежение» демо-данных в уже существующих пространствах (периоды со временем
  устареют — принимается).
- Отдельный CLI-команда или HTTP-эндпоинт для сидирования произвольного существующего
  пространства из приложения (локально это решается вызовом функции через psql).
- Кастомное сообщение «нет доступа» — не трогаем.
- Миграция существующих пространств на новые лимиты slug — старые slug остаются валидными
  автоматически (грамматика только расширяется).

## Decisions

### 1. Демо-сидер — SQL-функция `seed_demo_data(tenant_id bigint)`, создаваемая миграцией

Миграция `051_seed_demo_function.sql` определяет plpgsql-функцию со всем содержимым нынешнего
`seed_demo.sql`. И приложение (`SELECT seed_demo_data($1)`), и локальное окружение
(`psql -c "SELECT seed_demo_data(1)"`) вызывают один и тот же код.

**Почему не Go-сидер:** отклонён в обсуждении — содержимое демо читается и дорабатывается
как SQL, второй источник правды нежелателен.

**Почему не параметризованный SQL-файл:** pgx не поддерживает psql-переменные; пришлось бы
читать файл через `go:embed` и делать строковую подстановку плейсхолдеров — самодельный
хрупкий механизм. Функция в базе устраняет подстановку вообще.

**Изменение демо = новая миграция** с `CREATE OR REPLACE FUNCTION` — стандартный механизм
проекта. Файл с телом функции держим в миграции как есть; `CREATE OR REPLACE` позволяет
обновлять определение без удаления.

### 2. Динамические id через временный маппинг

Захардкоженные id (и все перекрёстные ссылки на них) заменяются на выдачу из sequence с
маппингом «старый id → новый id»:

- Временная таблица `id_map(kind text, old_id bigint, new_id bigint)` (или набор plpgsql-
  переменных/массивов — реализация на усмотрение исполнителя, контракт один: каждая вставка
  сущности с захардкоженным ранее id регистрирует соответствие).
- Вставки идут через `INSERT ... SELECT ... FROM (VALUES (old_id, ...)) v RETURNING id`,
  соответствие пишется в маппинг; ссылки (`parent_id`, `goal_id`, `key_result_id`,
  `team_period_statuses`, `goal_shares`, `goal_links`, мета-таблицы KR, комментарии,
  уведомления) резолвятся джойном к маппингу.
- `teams.parent_id` требует два прохода: сначала все команды без `parent_id`, затем
  простановка родителей по маппингу.
- `setval` по sequence больше не нужен — id берутся из sequence естественно.

### 3. Периоды относительно `now()`, с фиксированными ролями

Литеральные даты заменяются выражениями от `date_trunc`:

| Роль в демо            | Период                                        |
|------------------------|-----------------------------------------------|
| Годовые цели           | `date_trunc('year', now())` .. конец года     |
| Кварталы               | Q1..Q4 текущего года                          |
| «Текущий квартал»      | `date_trunc('quarter', now())`                |
| «История» (закрытый)   | предыдущий квартал (`- interval '3 months'`)  |
| «Планирование»         | следующий квартал (`+ interval '3 months'`)   |
| Прошлый год            | годом раньше + его кварталы                   |

Цели привязываются к периодам по роли, а не по номеру: «исторические» цели (сейчас Q1 2026)
уходят в предыдущий квартал, цели «текущего квартала» — в текущий, «планирования» — в
следующий. Краевой случай Q1 (предыдущий квартал — Q4 прошлого года) решается сам собой:
предыдущий квартал считается арифметикой, а не поиском внутри текущего года.

### 4. Идемпотентность вместо TRUNCATE

Глобальный `TRUNCATE ... CASCADE` и хаки `ALTER TABLE ... SET DEFAULT 1` из функции убираются.
Для повторного применения к тому же пространству функция в начале удаляет свои же данные,
скоупленные на `tenant_id` (DELETE по таблицам в FK-безопасном порядке,
`WHERE tenant_id = $1` / по цепочке от команд и целей тенанта). Для нового пространства это
no-op. Демо-пользователь `demo:requester` и его заявка (membership requested + уведомление)
входят в клон демо и сидируются функцией — пользователи глобальны, вставка идёт с
`ON CONFLICT DO NOTHING`; настройки уведомлений демо-пользователей пишутся так же идемпотентно.

### 5. Атомарность: CreateTenant в транзакции

`TenantRepository.Create` получает вариант, принимающий `pgx.Tx` (или меняет сигнатуру на
работу в переданной транзакции — по слоистости store принимает executor, решение о
транзакции остаётся в service-слое). `provisioning.CreateTenant` открывает транзакцию:
`INSERT tenants` → `SELECT seed_demo_data(id)` → commit. Ошибка сидера откатывает и вставку
тенанта — slug остаётся свободным, API отвечает 500, повторный POST возможен. Длинный сид
(десятки вставок в одной транзакции) не блокирует других: все вставки идут в таблицы нового
tenant_id, конфликтов с конкурентными созданиями нет.

### 6. Slug: точечное расширение

`ValidTenantSlug`: `len(s) > 32` → `len(s) > 63` (комментарий о грамматике обновить).
Зарезервированные поддомены не меняются. Проверить UI: если в системной панели есть
подсказка/валидация «32» — синхронизировать. Тесты `internal/core/domain/tenant_test.go`
расширить граничными случаями 33/63/64.

## Risks / Trade-offs

- [Демо-контент в миграции увеличивает её размер (~2700 строк SQL)] → принимается: это цена
  единственного источника правды; правка контента через `CREATE OR REPLACE` не создаёт новых
  таблиц и безопасна для повторного применения миграций.
- [Функция в базе — логика вне Go, слабее покрыта юнит-тестами] → смягчение: интеграционный
  тест уровня store/service, который создаёт тенант через `provisioning` на реальной базе
  (как существующие `*_isolation_test.go`) и проверяет наличие периодов текущего года,
  команд и целей.
- [Идемпотентный DELETE внутри функции может нечаянно задеть недемо-данные тенанта] →
  функция по контракту вызывается только для свежесозданного пространства и для локального
  дефолтного; в design и в комментарии функции фиксируем: удаление скоуплено на tenant_id и
  предназначено для пере-применения демо, а не для произвольных пространств с живыми данными.
- [Демо со временем устаревает в созданных пространствах] → осознанный non-goal, зафиксирован
  в proposal.
- [Транзакция на время сидирования держит соединение] → объём вставок мал (десятки строк),
  длительность — миллисекунды; N+1 нет, все вставки массовые через VALUES.

## Migration Plan

1. Миграция 051: `CREATE FUNCTION seed_demo_data(bigint)` — безопасна, ничего не ломает.
2. Код: транзакционный CreateTenant + вызов функции; slug-валидация.
3. `seed_demo.sql` переписывается в обёртку: `SELECT seed_demo_data(1);` (плюс удаление
   демо дефолтного тенанта перед повторным применением обеспечивает сама функция).
4. Rollback: откат кода; функцию удалять не обязательно (миграция обратная —
   `DROP FUNCTION`).
