# Design

## Context

Мотивация — [proposal.md](proposal.md); контракт — [database-migrations](specs/database-migrations/spec.md).

Исходная точка исследования: `58fbf14f93a98c32fb33d8bb99d96dfab20de531`. В `migrations/` находятся 49 пар SQL, последняя — `049_kr_current_value_null`. Сервер использует golang-migrate v4.17.1 через `database/sql` и pgx, вызывает `Up` до seed и сборки приложения, допускает `ErrNoChange`. Docker копирует каталог в `/app/migrations`. Go — 1.25.0, локальный PostgreSQL — 15.

Запуск миграций повторён в store/API test helpers. Тесты миграций используют переходы к заданной версии в обе стороны; например, тест 048 проверяет удаление уведомлений нового типа при откате. SQL включает backfill и удаления, поэтому повторное применение старых файлов нельзя считать безвредным.

## Goals / Non-Goals

**Goals:** одна инфраструктурная реализация запуска для сервера и тестов; автоматический перенос служебной истории; доказуемая эквивалентность прикладной схемы и SQL-преобразований; согласование миграций между процессами.

**Non-Goals:** собственный универсальный мигратор, переопределение стандартного хранилища goose, изменение путей доставки SQL, глобальный рефакторинг test helpers, автоматическое лечение повреждённых БД. Приложение не получает HTTP API для управления миграциями.

## Decisions

### 1. Goose Provider в инфраструктурном пакете

Создать `internal/platform/migrations`, принимающий контекст, `*sql.DB` и файловую систему SQL. Использовать `github.com/pressly/goose/v3` Provider без глобального реестра и глобальных настроек. Конкретную стабильную версию закрепить в `go.mod` при реализации после проверки совместимости с Go 1.25; обновление Go не входит в change.

Пакет предоставляет применение всех доступных версий и переход к целевой версии для тестов. Переход выбирает `UpTo` или `DownTo` по текущей версии; совпадение версий — успех. Сервер использует только применение вперёд. Владение `sql.DB` остаётся у вызывающей стороны; соединение мигратора освобождается при любом результате.

Существующие функции разрешения пути сохраняют свои правила и передают `os.DirFS` общего каталога. Доменные пакеты и repositories не импортируют goose. Альтернатива с отдельной обязательной CLI-командой меняет деплой и отвергнута; глобальный API goose усложняет изоляцию тестов.

### 2. Преобразование файлов без изменения SQL

Каждую пару `NNN_name.up.sql` / `NNN_name.down.sql` объединить в `NNN_name.sql` с `-- +goose Up` и `-- +goose Down`. Сохранить тела, порядок и номера 001–049; в production-каталоге остаётся один файл на версию. Оставить стандартные транзакции goose. Проверить парсинг всех секций и реальные переходы на PostgreSQL; при необходимости аннотации `StatementBegin/End` лишь сохраняют границы исходного SQL.

Схлопывание истории в baseline отвергнуто: оно теряет проверяемые промежуточные состояния и обратные преобразования. Новые версии 50+ не добавляются в релиз замены мигратора.

### 3. Единственная блокировка для перехода и применения

Использовать PostgreSQL session advisory lock с тем же ключом, что в golang-migrate v4.17.1 для фактических `current_database()`, `current_schema()` и `schema_migrations`. Алгоритм совместимости зафиксировать тестовым вектором из старого драйвера; сохранить атрибуцию при переносе кода. Стандартный goose lock ID не подходит для смешанного запуска.

Runner резервирует `sql.Conn` вызывающего пула и в пределах `Conn.Raw` создаёт внутренний `sql.DB` с единственным соединением через небольшой адаптер `driver.Connector`. Адаптер делегирует запросы и транзакции исходному driver.Conn, не закрывает его и не допускает подключения к другой сессии. Внутренний пул закрывается до выхода из Raw; исходный sql.Conn освобождается runner, исходный sql.DB остаётся у вызывающей стороны.

До любых операций Provider runner на этой сессии берёт совместимый advisory lock и выполняет bootstrap. Provider использует внутренний пул без дополнительного SessionLocker; одна внешняя блокировка охватывает bootstrap, определение версии, HasPending и все up/down. Это необходимо для goose v3.26.0: Up/UpTo вызывают HasPending, который инициализирует таблицу истории без SessionLocker. Bootstrap только в SessionLocker не обеспечивает контракт. Для перехода к целевой версии после bootstrap под блокировкой получить текущую версию и выбрать UpTo или DownTo; совпадение — no-op.

При ошибке bootstrap, Provider либо отмене контекста runner освобождает уже взятую блокировку с отдельным контекстом очистки. При невозможности подтвердить unlock исходное driver.Conn исключается из пула через driver.ErrBadConn. Не брать вторую блокировку на другом соединении; транзакцию bootstrap начинать на выделенной сессии. Ожидание блокировки ограничить пятью минутами и контекстом; этот срок не ограничивает длительность уже начатой миграции. Ошибка освобождения соединения/блокировки не должна скрывать исходную ошибку. Интеграционные тесты проверяют непрерывное владение lock, отсутствие повторного подключения и сохранение владения исходным пулом.

Обычный запуск goose CLI обходит bootstrap и совместимую блокировку, поэтому не является поддерживаемым способом первоначального перехода или параллельного управления миграциями работающего приложения.

### 4. Классификация состояния до изменений

Классификация выполняется после lock и до DDL/DML. Использовать существующую схему подключения, не жёстко заданный `public`. Проверки каталога и истории выполняются пакетно; не опрашивать по одной таблице или версии в цикле.

| Состояние | Действие |
| --- | --- |
| Нет истории и прикладных объектов | Новая БД: штатная инициализация goose и выполнение цепочки |
| Пустая `schema_migrations`, прикладных объектов нет | Эквивалент новой БД после раннего прерывания старого запуска |
| Только корректная старая история `version=N`, `dirty=false`, N=1–49 | Атомарный импорт 1–N, затем применение отсутствующих версий |
| Корректная история goose | Использовать goose; повторно старую историю не импортировать |
| Только начальная версия goose 0 и нет прикладных объектов | Продолжить чистую установку после раннего прерывания |
| Незавершённая старая миграция, неподдерживаемая версия, некорректная структура/записи истории | Отказ без изменения состояния |
| Прикладные объекты есть, достоверной истории нет | Отказ; не выводить версию по наличию отдельных таблиц |

Наличие таблицы goose само по себе не доказывает успешный bootstrap: валидировать её структуру и эффективный набор применённых версий, учитывая штатный формат истории выбранной версии goose. Проверять начальную запись, отсутствие неизвестных версий и непрерывность применённого префикса. История с пропусками не принимается; выполнение out-of-order не включается. Старую историю с `dirty=true` отклонять и при наличии goose. Корректную старую запись после перехода считать замороженной: равенство её версии текущей goose не требуется, в том числе после легитимного `DownTo` в тестах. Это не проверка полного schema drift — достоверная история остаётся основанием доверия к прикладной схеме.

### 5. Атомарный импорт истории

В одной транзакции создать стандартную `goose_db_version`, начальную запись 0 и записи об успешном применении всех известных версий до N. Использовать стандартное хранилище goose с транзакционным интерфейсом выбранной версии; если требуется явный bootstrap SQL, его схема должна точно соответствовать закреплённой версии и проверяться тестом с Provider. Версии импортировать одним пакетным запросом, без запроса на каждую версию. Недостаточно записать только N: потеряется полная история.

После commit история goose становится действующей. `schema_migrations` сохраняется без записи и удаления. Отдельного маркера завершения и дополнительной служебной таблицы не требуется: создание полной истории атомарно. Сбой до commit оставляет прежнюю историю; сбой после commit допускает продолжение штатных goose-миграций. Начальный bootstrap и отдельные миграции — разные транзакции, но одна session lock охватывает всё.

### 6. Ошибки, логирование и тестовые настройки

Сохранить событие `migration` и порядок `app_start` → миграции → seed/сборка → `app_ready`. При ошибке возвращать её в composition root для единственной записи `error` и кода 1. Исключить сырой DSN и неконтролируемый текстовый вывод библиотеки; технические причины пропускать через существующие правила редакции логов.

Для транзакционных миграций goose ошибка откатывает текущую миграцию вместе с её записью версии; это отличается от старого `dirty`, и README описывает восстановление раздельно. Автоматического `force`, очистки dirty или догадок о версии нет.

Test helpers вызывают общий пакет, а последующее восстановление `tenant_id DEFAULT 1` оставляют только в fixtures. Seed demo не требует изменения: прикладная схема сохраняется. Проверить его запуск как регрессию.

### 7. Доказательство совместимости

До удаления старого runner получить эталоны с настоящим golang-migrate v4.17.1 из исходной ревизии: схемы версии 49 и воспроизводимые fixtures с данными на версиях 22, 47, 48, 49. Зафиксировать происхождение и способ генерации fixtures; не генерировать ожидаемый результат новым goose-кодом. Сравнивать нормализованные каталоги PostgreSQL: таблицы, столбцы/default/nullability, ограничения, индексы, определения и принадлежность последовательностей. Исключить только служебные объекты миграторов, OID и прочие нестабильные идентификаторы.

Для перехода 49 сравнить все прикладные строки и состояние последовательностей до/после. Для 22, 47 и 48 сравнить итог с оставшимися миграциями старого runner, включая преобразование KR и уведомления. Различающиеся между независимыми установками часы/случайные значения нормализовать только там, где они порождены самим SQL; проверка сохранности одной существующей БД остаётся точной.

Старый runner нужен как внешний эталон при реализации и проверке отката; в основном `go.mod`, production и обычных helpers зависимость golang-migrate удалить после перевода. Воспроизводимые fixtures остаются тестовыми данными, а исходный старый релиз доступен по зафиксированной ревизии. Интеграционные проверки должны реально выполняться на PostgreSQL 15: успешный `go test` со skipped DB tests не является доказательством.

## Risks / Trade-offs

- Разные миграторы используют разные lock IDs → совместимый ключ и проверка взаимного ожидания обоих порядков запуска.
- Прерывание bootstrap или ошибка прав → одна транзакция и тесты повторного запуска, включая освобождение lock после ошибки.
- Замороженная старая версия устаревает после применения оставшихся миграций → смешанный деплой и возврат на старый runner поддерживаются только при исходной версии 49; обновление с N<49 выполняется при остановленных старых экземплярах.
- Старый runner не знает о будущих версиях goose → запрет обещаний совместимости после 50+; сохранённая старая таблица не является общей двунаправленной синхронизацией.
- Новый парсер SQL и другие границы записи версии → проверка всех файлов, существующих down-сценариев и отката транзакции.
- Валидатор служебной истории может ошибочно отклонить штатный down/up → тестировать фактический формат записей goose после `49 → 48 → 49`.

## Migration Plan

1. Реализовать change и выполнить матрицу проверок на изолированных БД; релиз содержит ту же конечную прикладную версию 49.
2. Перед обновлением действующей установки сохранить резервную копию; проверить старую версию и отсутствие dirty. Никаких ручных изменений истории не требуется.
3. На исходной версии 49 допустимо последовательное обновление реплик: первая новая реплика импортирует историю, остальные используют goose. Старые реплики используют сохранённую прежнюю историю и общий lock.
4. Для исходной N<49 остановить старые экземпляры и запустить новый релиз: импорт N и оставшиеся преобразования выполняются автоматически. Этот путь не обещает возврат к старому runner без отдельной процедуры восстановления.
5. Возврат из переходного релиза на непосредственно предыдущий разрешён в проверенном сценарии: исходно версия 49, после перехода не было прикладных up/down. Старый релиз видит свою неизменённую историю; повторное обновление использует goose. Для новой БД, созданной goose, эта гарантия не даётся.
6. При dirty/повреждённой истории исправление — отдельная диагностическая операция; новый релиз не меняет проблемное состояние. При ошибке транзакционной goose-миграции устранить причину и повторить запуск.
