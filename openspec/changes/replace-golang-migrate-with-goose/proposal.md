# Proposal

## Why

Необходимо перейти с golang-migrate на goose, сохранив прикладную схему, данные и автоматическую подготовку БД при запуске. Переход должен работать на существующих установках без ручной команды и повторного выполнения исторических миграций.

## What Changes

- Заменить механизм миграций на goose с сохранением последовательности существующих версий 001–049 и поведения их прямых и обратных преобразований.
- Автоматически переносить учёт выполненных миграций при первом запуске новой версии; поддержать новую БД и обновление с промежуточной версии.
- Обеспечить повторный запуск после прерывания перехода и согласованную работу нескольких экземпляров, включая старый и новый миграторы в переходном релизе.
- Останавливать запуск при недостоверной истории или ошибке миграции, сохраняя диагностику жизненного цикла.
- Выпустить замену отдельно от новых изменений прикладной схемы; проверить возврат на предыдущий релиз для БД, уже имевшей версию 49 перед переходом.

## Capabilities

### New Capabilities

- `database-migrations`: автоматическая подготовка БД до готовности приложения, перенос существующей истории, сохранность данных, конкурентный запуск и восстановление после ошибок. Новое наблюдаемое поведение — автоматический переход между механизмами миграций и отказ от запуска при неоднозначной истории.

### Modified Capabilities

Нет. Требования `observability-logging` к событиям жизненного цикла и ошибкам сохраняются; требования предметных capabilities не меняются.

## Impact

- Зависимости `go.mod` / `go.sum`, каталог `migrations/`, запуск в `cmd/server/main.go`, общий инфраструктурный механизм миграций.
- Подготовка БД в `internal/store/store_test.go`, `internal/store/testutil/testutil.go`, `internal/http/handlers/api/v1/testutil/integration.go`, тесты `internal/store/migration_*_test.go`.
- README: формат миграций, автоматический переход, диагностика и границы отката. Доставка каталога миграций в Docker сохраняется.
- Изменяется служебный учёт мигратора; прикладные таблицы, API, UI и правила seed demo сохраняются.

### Согласованность с текущим проектом

Противоречий между рассмотренными требованиями, кодом и тестами в затронутой области не обнаружено. README и сервер предусматривают миграции при старте, `observability-logging` требует логировать их результат. Отдельной спецификации жизненного цикла миграций сейчас нет. Тестовые helpers намеренно восстанавливают `tenant_id DEFAULT 1` после миграций для старых fixtures; это тестовая настройка, которую нельзя переносить в production.

## Non-goals

Изменение прикладной схемы и бизнес-логики, объединение истории в baseline, новые миграции версии 50+, новый обязательный этап деплоя, UI, изменение seed demo и поддержка произвольного отката на старый мигратор после будущих изменений схемы.
