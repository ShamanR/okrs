# Spec Delta

## Purpose

Подготовка базы данных к запуску приложения и безопасный переход между механизмами миграций с сохранением прикладной схемы, данных и истории выполненных преобразований.

## ADDED Requirements

### Requirement: Подготовка базы до готовности приложения

При запуске сервер ОБЯЗАН (MUST) автоматически применить отсутствующие миграции в порядке версий до готовности принимать запросы и выполнения необязательного заполнения демонстрационными данными. Отсутствие новых миграций ОБЯЗАН (MUST)О считаться успешным результатом.

#### Scenario: Новая база
- **WHEN** сервер запускается на новой БД с необходимыми правами
- **THEN** применяются все миграции релиза
- **AND** приложение становится готовым только после успешного завершения подготовки

#### Scenario: Повторный запуск
- **WHEN** все миграции релиза уже выполнены
- **THEN** прикладные преобразования повторно не выполняются
- **AND** сервер успешно продолжает запуск

### Requirement: Автоматический переход существующей базы

Сервер ОБЯЗАН (MUST) автоматически принять корректную историю прежнего механизма и выполнить только отсутствующие миграции. Для уже актуальной БД переход ОБЯЗАН (MUST) сохранять прикладную схему и данные, включая идентификаторы, значения последовательностей и связи. Для промежуточной версии результат ОБЯЗАН (MUST) соответствовать прежней последовательности оставшихся преобразований.

#### Scenario: Переход актуальной базы
- **WHEN** БД содержит данные и успешно применённые версии 001–049 прежнего механизма
- **THEN** запуск переносит учёт выполненных миграций без ручной команды
- **AND** все прикладные данные и схема сохраняются

#### Scenario: Переход промежуточной версии
- **WHEN** БД содержит корректную историю до версии N, где 1 <= N < 49
- **THEN** версии до N включительно не выполняются повторно
- **AND** применяются только версии N+1–49 с прежним результатом преобразования данных

#### Scenario: Эквивалентность чистой установки
- **WHEN** новые БД создаются старым и новым механизмами до версии 49
- **THEN** их прикладные таблицы, столбцы, ограничения, индексы и определения последовательностей совпадают
- **AND** различия служебного учёта миграций допустимы

### Requirement: Возобновление после прерывания

Переход ОБЯЗАН (MUST) сохранять целостную историю после прерывания процесса. Повторный запуск ОБЯЗАН (MUST) продолжить подготовку без повторения успешно завершённых преобразований. Неуспешная транзакционная миграция ОБЯЗАН (MUST)А откатываться без регистрации успешного выполнения.

#### Scenario: Прерывание переноса истории
- **WHEN** процесс прерывается до завершения переноса истории
- **THEN** следующему запуску доступна исходная корректная история
- **AND** следующий запуск успешно повторяет переход

#### Scenario: Прерывание после переноса
- **WHEN** история перенесена, но процесс прерывается до завершения оставшихся миграций
- **THEN** следующий запуск использует перенесённую историю
- **AND** выполняет только ещё не завершённые миграции

#### Scenario: Ошибка внутри миграции
- **WHEN** одна из транзакционных миграций завершается ошибкой после выполнения части SQL
- **THEN** её прикладные изменения откатываются и версия не отмечается выполненной
- **AND** после устранения причины следующий запуск может повторить эту миграцию

### Requirement: Согласованность нескольких экземпляров

Экземпляры приложения ОБЯЗАН (MUST)Ы согласовывать перенос истории и применение миграций одной БД. Ожидающий экземпляр ОБЯЗАН (MUST) перечитать состояние после завершения работы предыдущего. Для переходного релиза НЕОБХОДИМО (MUST) обеспечить совместный запуск старой и новой версии приложения на БД, уже имевшей версию 49.

#### Scenario: Два новых экземпляра
- **WHEN** два экземпляра одновременно запускаются на новой или существующей БД
- **THEN** изменения выполняются последовательно без повторного применения завершённых миграций
- **AND** оба экземпляра могут продолжить запуск после завершения подготовки

#### Scenario: Смешанный запуск на версии 49
- **WHEN** старая и новая версии одновременно запускаются на БД с корректной прежней историей до версии 49
- **THEN** перенос истории не пересекается с работой старого мигратора
- **AND** обе версии успешно запускаются без изменения прикладных данных

### Requirement: Отказ при недостоверном состоянии

Сервер ОБЯЗАН (MUST) остановить запуск до готовности при незавершённой прежней миграции, неподдерживаемой версии, некорректной истории либо наличии прикладных таблиц без достоверной истории. Сервер ОБЯЗАН (MUST) сохранить это состояние для диагностики, не выполнять автоматическое исправление и не начинать новые прикладные преобразования.

#### Scenario: Незавершённая прежняя миграция
- **WHEN** прежняя история сообщает о незавершённой или ошибочной миграции
- **THEN** сервер завершает запуск с ошибкой, сохранив историю и прикладные данные

#### Scenario: Неизвестная версия или повреждённая история
- **WHEN** история содержит версию выше доступной в релизе, неизвестную версию либо недопустимый пропуск применённых версий
- **THEN** сервер отказывается от миграций и сообщает причину

#### Scenario: Таблицы без истории
- **WHEN** прикладные таблицы существуют, а достоверная история отсутствует
- **THEN** сервер не считает БД новой и завершает запуск с ошибкой

### Requirement: Диагностика подготовки базы

Сервер ОБЯЗАН (MUST) отражать успешный результат и ошибку подготовки БД через существующее событие `migration` в соответствии с `observability-logging`. При ошибке подключения, недостаточных правах, ошибке миграции или исчерпании времени ожидания блокировки сервер ОБЯЗАН (MUST) завершиться с ненулевым кодом до готовности, указав причину без секретов подключения.

#### Scenario: Недостаточно прав
- **WHEN** учётная запись БД не позволяет выполнить необходимую подготовку
- **THEN** сервер логирует ошибку и завершается с ненулевым кодом
- **AND** событие готовности не появляется

#### Scenario: Не удалось дождаться другого экземпляра
- **WHEN** время ожидания доступа к миграциям исчерпано
- **THEN** сервер логирует причину отказа и завершается без готовности

### Requirement: Возврат к предыдущему релизу при смене мигратора

Переходный релиз ОБЯЗАН (MUST) допускать возврат к непосредственно предыдущему релизу на прежнем миграторе, если БД уже находилась на версии 49 до перехода и после него прикладные миграции не применялись и не откатывались. Такой возврат ОБЯЗАН (MUST) сохранять данные без ручной правки истории.

#### Scenario: Возврат и повторное обновление
- **WHEN** актуальная прежняя БД проходит запуск нового релиза, возврат к предыдущему релизу и повторный запуск нового
- **THEN** все три запуска успешны
- **AND** прикладные данные сохраняются, а исторические преобразования не выполняются повторно
