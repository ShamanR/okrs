# Delta: tenancy

## MODIFIED Requirements

### Requirement: Резолв и переключение активного пространства

Система ОБЯЗАНА определять активное пространство каждого API-запроса по заголовку
`X-Tenant-ID`, переданному клиентом, и ОБЯЗАНА валидировать указанное пространство против
активных членств пользователя. Система ОБЯЗАНА позволять пользователю переключаться между
пространствами, в которых у него есть активное членство; переключение НЕ должно изменять
серверное состояние сессии и НЕ должно влиять на контекст других вкладок браузера. Сессия
НЕОБХОДИМО освободить от роли носителя выбранного пространства: она описывает только
идентичность пользователя.

#### Scenario: Запрос с валидным пространством

- GIVEN пользователь с активным членством в пространствах A и B
- WHEN он отправляет API-запрос с заголовком `X-Tenant-ID: B`
- THEN запрос обрабатывается в контексте пространства B

#### Scenario: Запрос с чужим пространством

- GIVEN пользователь без активного членства в пространстве X
- WHEN он отправляет API-запрос с заголовком `X-Tenant-ID: X`
- THEN запрос отклоняется и данные пространства X не раскрываются и не изменяются

#### Scenario: Независимость контекста вкладок

- GIVEN пользователь работает в двух вкладках браузера
- WHEN в первой вкладке выбрано пространство A, а во второй — пространство B
- THEN запросы каждой вкладки обрабатываются в её собственном пространстве,
  и переключение в одной вкладке не меняет контекст другой

#### Scenario: Переключение на своё пространство

- GIVEN пользователь с активным членством в двух пространствах
- WHEN он переключает активное пространство на второе
- THEN последующие запросы этой вкладки возвращают данные второго пространства,
  и серверное состояние сессии не изменяется

#### Scenario: Переключение на пространство без членства

- GIVEN пользователь без активного членства в пространстве X
- WHEN он пытается сделать X активным
- THEN переключение отклоняется и активное пространство не меняется

#### Scenario: Запрос без заголовка пространства

- GIVEN авторизованный пользователь с ровно одним активным членством
- WHEN он отправляет API-запрос без заголовка `X-Tenant-ID`
- THEN запрос обрабатывается в контексте единственного доступного пространства

### Requirement: Расширяемость стратегии резолва пространства

Система ОБЯЗАНА позволять подключать альтернативные стратегии резолва пространства выбором по
имени в конфигурации, без изменения остального поведения. В коробочной поставке доступна
стратегия резолва по заголовку запроса.

#### Scenario: Коробочная стратегия

- GIVEN коробочная поставка без дополнительных стратегий
- WHEN пользователь авторизован и передал пространство в заголовке запроса
- THEN активное пространство определяется этим заголовком после валидации членства

## ADDED Requirements

### Requirement: Клиентское хранение контекста пространства

Клиент ОБЯЗАН хранить выбранное пространство текущей вкладки в хранилище, изолированном между
вкладками, и ОБЯЗАН хранить последнее выбранное пространство в долговременном хранилище,
переживающем перезапуск браузера. При старте вкладки клиент ОБЯЗАН восстанавливать контекст по
приоритету: контекст вкладки, затем последний выбранный, затем единственное или первое доступное
пространство из списка членств.

#### Scenario: Восстановление последнего выбора

- GIVEN пользователь ранее выбрал пространство B и закрыл браузер
- WHEN он открывает приложение в новой вкладке
- THEN активным становится пространство B

#### Scenario: Дублирование вкладки

- GIVEN вкладка с выбранным пространством B
- WHEN пользователь дублирует вкладку или открывает ссылку в новой вкладке
- THEN новая вкладка стартует в пространстве B и далее независима от исходной

#### Scenario: Последнее выбранное пространство недоступно

- GIVEN в долговременном хранилище сохранено пространство B, доступ к которому отозван
- WHEN пользователь открывает приложение
- THEN клиент переключается на доступное пространство и обновляет сохранённое значение

### Requirement: Первый рендер без знания о пространстве

Серверный шелл ОБЯЗАН отдаваться без требования активного пространства: определение контекста —
ответственность клиента после загрузки. Отсутствие активных членств НЕОБХОДИМО сигналить
отдельным ответом API, а клиент ОБЯЗАН показывать экран no-access на основании этого ответа,
а не серверного перенаправления.

#### Scenario: Первая загрузка авторизованного пользователя

- GIVEN авторизованный пользователь без сохранённого клиентского контекста
- WHEN он открывает приложение
- THEN получает шелл, клиент резолвит пространство из списка членств и загружает данные

#### Scenario: Пользователь без членств

- GIVEN авторизованный пользователь без активных членств
- WHEN клиент запрашивает список членств
- THEN API сигналит отсутствие членств отдельным ответом и клиент показывает экран no-access
