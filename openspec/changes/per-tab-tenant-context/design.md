# Design: per-tab-tenant-context

## Context

Активное пространство хранится в `auth_sessions.active_tenant_id` и резолвится
`SessionStrategy` (internal/auth/resolve_strategy.go) на каждый запрос. Сессия одна на
браузер, поэтому контекст общий для всех вкладок. Браузерные GET, оставшиеся без членства,
редиректятся на `/no-access` в `RequireMembershipMiddleware` (internal/auth/middleware.go:162);
API в той же ситуации получает 403. Sidebar переключает пространство через
`POST /api/v1/session/tenant` (запись в БД на каждое переключение) и перезагружает страницу.

## Goals / Non-Goals

Goals:
- независимый контекст пространства в каждой вкладке;
- переключение пространства без серверной записи и без reload всей страницы, где это дёшево;
- tenant-agnostic первый рендер;
- сессия описывает только идентичность.

Non-Goals:
- не меняем модель изоляции данных и гранты — меняется только способ доставки tenant-id;
- не вводим tenant в URL (`/t/{slug}/...`) — отдельный шаг, если потребуется шаринг ссылок
  с пространством; текущий change закрывает только независимость вкладок;
- не трогаем system-плоскость (`/api/v1/system/*`): она адресует пространства явно по id в пути.

## Decisions

### 1. Источник истины — заголовок `X-Tenant-ID`

Новая `HeaderStrategy` в `TenantResolver` (цепочка стратегий уже есть): читает
`X-Tenant-ID`, валидирует против активных членств пользователя, при успехе возвращает
tenant+role. Невалидное/чужое значение → стратегия возвращает «не resolved», дальше запрос
получает 403 от `RequireMembershipMiddleware`. Заголовок отсутствует → fallback: ровно одно
членство — оно и есть контекст; несколько членств — «не resolved» (клиент обязан выбрать).

Почему заголовок, а не query: не засоряет адреса и закладки, естественно покрывается
единой точкой в api-клиенте фронта, и даёт корректный HTTP-кеш через `Vary: X-Tenant-ID`.

Альтернативы: tenant в path-префиксе URL — сильнее (шаринг ссылок), но это миграция всех
адресов приложения; оставлено за пределами change.

### 2. Хранение на клиенте: sessionStorage + localStorage

- `sessionStorage["tenant"]` — контекст вкладки. Изолирован между вкладками по построению
  (в отличие от localStorage, который общий и синхронизируется событием `storage` —
  использовать его для контекста вкладки нельзя).
- `localStorage["tenant"]` — последний выбранный, переживает перезапуск браузера.
- Порядок восстановления: sessionStorage → localStorage → `GET /api/v1/session/tenants`
  (первый доступный). При переключении пишем в оба.
- Дубликат вкладки наследует sessionStorage родителя — это желаемое поведение.

### 3. Tenant-agnostic шелл и клиентский no-access

- Серверные страницы (`/`, трекер, настройки, админка) перестают стоять за
  `RequireMembershipMiddleware`: шелл отдаётся любому авторизованному пользователю.
  Страница `/no-access` остаётся как адрес, но переход на неё выполняет клиент.
- Клиент после bootstrap запрашивает `/api/v1/session/tenants`: пустой список → экран
  no-access; недоступное сохранённое значение → тихий перебор на доступное с обновлением
  хранилищ.
- API-ответ «нет членств» должен быть отличим от «чужой tenant»: отдельный код ошибки
  (например, `no_membership` с 409/403 — решить в реализации, поведение зафиксировано в spec).

Нужна ревизия server-side мест, где tenant читается до JS: `web/shell` handler,
`web/noaccess`, `web/openlink`, `web/invite`. Openlink/invite уже работают со slug/token,
а не с сессионным tenant — проверить и зафиксировать.

### 4. Удаление серверного состояния

- Колонка `auth_sessions.active_tenant_id` удаляется миграцией; `SetActiveTenant`,
  `POST /api/v1/session/tenant` и `SessionStrategy` упраздняются. Sidebar-переключатель
  перестаёт делать POST и reload — просто пишет хранилища и перезагружает данные приложения.
- Миграция безопасна на нескольких репликах: колонка перестаёт читаться до её удаления
  (две миграции не нужны — чтение колонки убирается кодом в том же релизе, что и удаление,
  порядок «код, потом миграция» обеспечиваем деплоем).

### 5. Кеширование и мульти-инстанс

- `setAPICacheControl` дополняется `Vary: X-Tenant-ID` на всех tenant-scoped API-ответах:
  браузерный кеш становится корректным по построению, «старая иерархия после переключения»
  исключается на уровне HTTP.
- Серверных кешей контекста вкладки не существует — состояние живёт на клиенте, поэтому
  multi-instance Kubernetes не добавляет проблем согласования.

### Интерфейс

Затрагивает существующие компоненты: переключатель пространств в шапке сайдбара
(`SidebarTenant`, web/static/sidebar.js) — поведение меняется (без POST и полного reload),
разметка и классы — нет; экран no-access — становится клиентским состоянием, разметка
существующая. Новых переиспользуемых компонентов не появляется, карточки дизайн-системы
не меняются. Вид согласуем в прототипе до реализации: сценарий «переключение пространства
без перезагрузки» и «пустой шелл до резолва контекста» (loading-состояние).

## Risks / Trade-offs

- Двухфазный первый рендер (шелл → резолв → данные) может выглядеть как «пустое
  пространство» → отдельный loading-стейт шелла, согласованный в прототипе.
- Клиент может подставить любой `X-Tenant-ID` → валидация против memberships на каждый
  запрос обязательна; это дёшево (memberships уже в TTL-кеше на hot path).
- Машинные клиенты без заголовка при нескольких членствах получат 403, где раньше молча
  попадали в первое пространство → fallback «ровно одно членство» покрывает типичный случай;
  для многопространственных машинных вызовов документируем обязательность заголовка.
- Режим `AUTH_MODE=disabled`: `AnonymousUserMiddleware` подставляет tenant напрямую и не
  зависит от заголовка → оставляем как есть, отдельный сценарий в тестах.
- Пока tenant не в URL, скопированная из адресной строки ссылка не несёт пространства →
  осознанный non-goal; `openlink` продолжает работать по slug.

## Migration Plan

1. Код: HeaderStrategy, клиентское хранение, снятие RequireMembership со страниц шелла,
   упразднение session/tenant endpoint. Всё ещё читающее `active_tenant_id` — ничего.
2. Миграция БД: drop `auth_sessions.active_tenant_id` (вместе с релизом кода).
3. Откат: вернуть код; колонку восстанавливать не нужно — новый код её не пишет,
   старый при откате просто начнёт писать заново (пересоздать колонку обратной миграцией).

## Open Questions

- Точный код/статус ответа «нет членств» vs «чужой tenant» (409 vs 403 с телом-кодом) —
  выбирается в реализации, на спеки и разбивку задач не влияет.
