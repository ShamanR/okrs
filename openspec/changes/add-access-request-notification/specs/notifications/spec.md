## MODIFIED Requirements

### Requirement: Закрытый набор типов уведомлений

Система ОБЯЗАНА поддерживать ровно пять типов уведомлений: комментарий к цели, решение моего
замечания, изменение цели, чек-ин ключевого результата и заявка на доступ к пространству.
Набор ОБЯЗАН быть закрытым: неизвестный тип в настройках отклоняется. Ответ с настройками
ОБЯЗАН содержать все типы, доступные пользователю по его роли в пространстве:
администратору — все пять, остальным — четыре, без заявки на доступ.

#### Scenario: Полный перечень в настройках

- GIVEN пользователь не является администратором пространства
- WHEN он открывает настройки уведомлений
- THEN перечень содержит ровно четыре типа, заявки на доступ среди них нет

#### Scenario: Полный перечень в настройках администратора

- GIVEN пользователь — администратор пространства
- WHEN он открывает настройки уведомлений
- THEN перечень содержит ровно пять типов, включая заявку на доступ

### Requirement: Какие действия порождают уведомления

Система ОБЯЗАНА порождать уведомления только по закрытому перечню действий:

- добавление замечания и добавление ответа — тип «комментарий к цели»;
- отметка замечания решённым — адресный тип «решение моего замечания»;
- создание, копирование, перенос и удаление цели, изменение полей цели, смена владельца цели, а
  также создание, изменение и удаление ключевого результата — тип «изменение цели»;
- чек-ин ключевого результата, включая чек-ин, изменивший только заметку или только
  health-статус, — тип «чек-ин ключевого результата»;
- подача новой заявки на доступ к пространству по slug — тип «заявка на доступ».

Расширение этого перечня НЕОБХОДИМО считать продуктовым решением, а не деталью реализации.

#### Scenario: Удаление цели уведомляет как изменение цели

- GIVEN пользователь удаляет цель
- WHEN определяются получатели
- THEN они получают уведомление типа «изменение цели»

#### Scenario: Чек-ин только с заметкой

- GIVEN пользователь меняет только заметку ключевого результата
- WHEN определяются получатели
- THEN они получают уведомление типа «чек-ин ключевого результата»

#### Scenario: Подача заявки на доступ

- GIVEN пользователь не состоит в пространстве
- WHEN он подаёт заявку на доступ по slug этого пространства
- THEN администраторы пространства получают уведомление типа «заявка на доступ»

#### Scenario: Обработка заявки уведомлений не порождает

- GIVEN в очереди пространства есть заявка
- WHEN администратор одобряет или отклоняет её, либо заявитель отменяет её сам
- THEN новые уведомления не создаются ни у кого

### Requirement: Охват неприменим к адресным типам

Система НЕ ДОЛЖНА предлагать выбор охвата для адресных типов уведомлений и ОБЯЗАНА помечать их
как адресные. Заявка на доступ — адресный тип: её получатели определяются ролью в
пространстве, а не деревом команд.

#### Scenario: Настройка адресного типа

- GIVEN пользователь открывает настройки уведомлений
- WHEN он смотрит на адресный тип
- THEN у него нет выбора охвата, а сам тип помечен как адресный

#### Scenario: Настройка заявки на доступ

- GIVEN администратор пространства открывает настройки уведомлений
- WHEN он смотрит на тип «заявка на доступ»
- THEN у типа нет выбора охвата, а сам тип помечен как адресный

### Requirement: Отсутствие настройки означает значение по умолчанию

Система ОБЯЗАНА считать отсутствие сохранённой настройки нормой и подставлять
значения по умолчанию как при чтении настроек, так и при определении получателей.
По умолчанию уведомления категории «Цели» включены с охватом «только моя команда»,
а уведомления категории «Системные» выключены: их получатель включает сам. Значение
по умолчанию для каждого канала ОБЯЗАНО браться из настройки этого канала, заданной
администратором пространства; канал «в приложении» по умолчанию включён.
Предзаполнение настроек для всех пользователей выполняться НЕ ДОЛЖНО.

#### Scenario: Новый пользователь открывает настройки

- GIVEN пользователь ни разу не менял настройки уведомлений
- WHEN он открывает раздел настроек
- THEN он видит все типы уведомлений со значениями по умолчанию, а каналы —
  в положении, заданном администратором пространства

#### Scenario: Новый сотрудник в пространстве с настроенным каналом

- GIVEN администратор включил внешний канал по умолчанию
- WHEN в пространстве появляется новый пользователь, ни разу не открывавший настройки
- THEN уведомления доставляются ему в этот канал без каких-либо действий с его стороны

#### Scenario: Системный тип выключен по умолчанию

- GIVEN администратор пространства ни разу не менял настройку типа «заявка на доступ»
- WHEN он открывает настройки уведомлений
- THEN тип «заявка на доступ» показан выключенным

#### Scenario: Администратор не включал системный тип

- GIVEN администратор пространства ни разу не менял настройку типа «заявка на доступ»,
  а внешний канал пространства включён по умолчанию
- WHEN в пространство подаётся заявка
- THEN уведомление о ней администратору не создаётся: его нет ни в ленте, ни во внешнем канале

## ADDED Requirements

### Requirement: Получатели уведомления о заявке на доступ

Система ОБЯЗАНА доставлять уведомление о новой заявке на доступ каждому активному
администратору пространства, в которое подана заявка, если он сам включил этот тип.
Администраторы других пространств, обычные участники и системные администраторы без
членства-администратора в этом пространстве уведомление получать НЕ ДОЛЖНЫ. Администраторы
НЕОБХОДИМО определять пакетно для группы событий, без отдельного запроса на каждое событие.

#### Scenario: В пространстве несколько администраторов

- GIVEN в пространстве два активных администратора, оба включили тип «заявка на доступ», и несколько обычных участников
- WHEN пользователь подаёт заявку на доступ в это пространство
- THEN уведомление получает каждый из двух администраторов, а обычные участники не получают

#### Scenario: Администратор не включал тип

- GIVEN один администратор включил тип «заявка на доступ», а другой не менял эту настройку
- WHEN пользователь подаёт заявку
- THEN уведомление получает только тот, кто включил тип

#### Scenario: Администратор другого пространства

- GIVEN пользователь — администратор другого пространства и не состоит в пространстве заявки
- WHEN в пространство подаётся заявка
- THEN он уведомления не получает

### Requirement: Повторная заявка не порождает нового уведомления

Система ОБЯЗАНА порождать уведомление только при подаче новой заявки. Повторная отправка
заявки, которая уже ожидает решения, уведомлений порождать НЕ ДОЛЖНА. Заявка, поданная
снова после отмены или отклонения, считается новой.

#### Scenario: Повторная отправка ожидающей заявки

- GIVEN заявка пользователя уже ожидает решения
- WHEN он отправляет заявку в то же пространство ещё раз
- THEN новое уведомление не создаётся, и счётчик повторов существующего не растёт

#### Scenario: Заявка после отклонения

- GIVEN администратор отклонил заявку пользователя
- WHEN пользователь подаёт заявку снова
- THEN администраторы получают уведомление о новой заявке

### Requirement: Заявитель в уведомлении назван по имени

Система ОБЯЗАНА показывать в уведомлении о заявке имя и аватар заявителя, пока его заявка
ожидает решения, хотя активным участником пространства он ещё не является. Если заявка
была отклонена или отменена, заявитель НЕОБХОДИМО показывать по общему правилу для
бывших участников.

Исключение ОБЯЗАНО действовать только в уведомлении о самой заявке. В остальных
уведомлениях, где заявитель является автором события, поданная заявка правила не меняет:
бывший участник остаётся скрытым, пока не получит активное членство.

#### Scenario: Заявка ожидает решения

- GIVEN пользователь подал заявку, и она ещё не обработана
- WHEN администратор открывает ленту
- THEN в уведомлении указано имя заявителя

#### Scenario: Заявка одобрена

- GIVEN заявку одобрили, и заявитель стал участником
- WHEN администратор открывает ленту
- THEN в уведомлении по-прежнему указано имя заявителя

#### Scenario: Заявка отклонена

- GIVEN заявку отклонили
- WHEN администратор открывает ленту
- THEN вместо имени заявителя показан признак «бывший участник»

#### Scenario: Прежние уведомления бывшего участника

- GIVEN бывший участник подал новую заявку, и она ожидает решения
- WHEN получатель открывает ленту, где есть прежние уведомления о его действиях
- THEN в них по-прежнему показан признак «бывший участник», а по имени он назван только в уведомлении о заявке

### Requirement: Уведомление о заявке ведёт в очередь заявок

Система ОБЯЗАНА вести из уведомления о заявке в раздел администрирования пространства,
открытый на очереди заявок. Уведомление ОБЯЗАНО называть пространство, в которое подана заявка.

#### Scenario: Переход из ленты

- GIVEN администратор видит в ленте уведомление о заявке
- WHEN он нажимает на уведомление
- THEN открывается раздел пользователей админки пространства с фильтром «Заявки»

#### Scenario: Заявка уже обработана другим администратором

- GIVEN заявку одобрил или отклонил другой администратор
- WHEN администратор переходит по уведомлению
- THEN открывается очередь заявок, где этой заявки уже нет, и ошибка не показывается

### Requirement: Категории в настройках уведомлений

Система ОБЯЗАНА группировать типы в настройках уведомлений по категориям и показывать
категории в фиксированном порядке: «Цели», затем «Системные». Комментарий к цели, решение
моего замечания, изменение цели и чек-ин ключевого результата ОБЯЗАНЫ относиться к
категории «Цели», заявка на доступ — к категории «Системные». Категорию каждого типа
НЕОБХОДИМО сообщать сервером. Категория без единого доступного пользователю типа
показываться НЕ ДОЛЖНА. Группировка на сохранение не влияет: матрица сохраняется целиком,
как и прежде.

#### Scenario: Настройки администратора

- GIVEN пользователь — администратор пространства
- WHEN он открывает настройки уведомлений
- THEN он видит категорию «Цели» с четырьмя типами и категорию «Системные» с типом «заявка на доступ», который выключен, пока администратор его не включит

#### Scenario: Настройки участника

- GIVEN пользователь не является администратором пространства
- WHEN он открывает настройки уведомлений
- THEN он видит только категорию «Цели», а категории «Системные» нет

### Requirement: Настройку заявки на доступ сохраняет только администратор

Система ОБЯЗАНА отклонять как ошибку валидации сохранение настройки типа «заявка на доступ»
пользователем, который не является администратором пространства. Сохранённая настройка
администратора, который потом утратил роль, НЕОБХОДИМО оставлять без изменений: она снова
действует, если роль вернётся.

#### Scenario: Участник передаёт тип заявки

- GIVEN пользователь не является администратором пространства
- WHEN он сохраняет матрицу, содержащую тип «заявка на доступ»
- THEN операция отклоняется как ошибка валидации, и ни одна строка не сохраняется

#### Scenario: Роль администратора возвращена

- GIVEN администратор отключил тип «заявка на доступ», затем лишился роли, а позже получил её снова
- WHEN он открывает настройки уведомлений
- THEN тип «заявка на доступ» показан отключённым
