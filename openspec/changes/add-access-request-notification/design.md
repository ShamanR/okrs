## Context

Мотивация — в proposal.md, требования — в `specs/notifications` и `specs/notification-delivery`.

Текущее устройство, которое определяет подход:

- **Конвейер уведомлений.** Доменные события идут через `eventbus.Bus`. Подписчик
  `usecase/notification.Handle` (async, `SubscribeAll`) группирует события по
  (пространство, тип) и резолвит получателей одним запросом на группу. Затем он пишет строки
  через `CreateBatch` и передаёт `Delivery` во внешние каналы (`usecase/notificationdelivery`).
  Сопоставление событий с типом, якорем и payload лежит в `usecase/notification/mapping.go`.
- **Стратегии получателей.** Их сейчас две:
  - scoped — обход дерева команд, `notificationprefs.Resolve`; событие без `TeamID`
    отбрасывается;
  - addressed — один адресат из события, `ResolveAddressed`; признак задаёт `IsAddressed(t)`.
- **Каталог типов.** Константы и `AllTypes` лежат в `store/notificationprefs`. Туда же
  зашиты CHECK-ограничения миграции 044 на `notifications.type` и
  `notification_preferences.type`.
- **Онбординг.** `service/onboarding.Service.RequestAccess` делает upsert членства со
  статусом `requested` и не публикует событий: порта публикации у сервиса нет.
- **Журнал активности.** Он подписан на все события (`SubscribeAll`, sync). На неизвестный
  Kind `toRows` возвращает пустой результат. Тесты журнала и eventlog перебирают
  `event.AllKinds()` и требуют запись для каждого Kind.
- **Правило «бывшего участника».** Лента (`store/notifications.List`) и контакты для
  доставки (`store/users.ContactsByIDs`) маскируют автора, у которого нет активного
  членства. Заявитель с членством `requested` попал бы под маску.
- **Ссылки.** `render/notify.TargetURL` умеет строить только ссылку на цель, для остальных
  случаев возвращает пустую строку. Очередь заявок в админке — раздел «Пользователи»
  (`/admin?section=users`) с локальным фильтром-чипом «Заявки», который из адреса не читается.
- **Экран настроек** (`settings.js`, `NotificationsSettings`) — плоская таблица по
  `items`. Подписи типов берутся из `NOTIF_TYPE_LABELS` на клиенте.

## Goals / Non-Goals

**Goals:**

- Ввести третью стратегию получателей — «администраторы пространства» — не ломая две
  существующие и не добавляя запросов в цикле.
- Свести знание о типе (категория, адресность, стратегия получателей, видимость по роли)
  в один каталог, чтобы не размазывать `if type == ...` по слоям.
- Сохранить единый путь для ленты и доставки: запись уведомления остаётся источником для обоих.

**Non-Goals:**

- Переключать активное пространство по ссылке из внешнего канала. У ссылок на цели сейчас
  та же особенность, и решать её надо отдельно для всех типов.
- Хранить подписи категорий на сервере и локализовать их.
- Менять журнал активности: подача заявки в него не пишется.

## Decisions

### 1. Каталог типов в `store/notificationprefs`

Вместо `AllTypes` и `IsAddressed` появляется упорядоченный каталог. Каждая запись содержит:
- `Type`;
- `Category` (`goals` | `system`);
- `Audience` (`team_tree` | `addressee` | `tenant_admins`);
- `AdminOnly bool`;
- `DefaultEnabled bool` — `true` у типов категории «Цели», `false` у «Системных».

`defaultPreference(t)` берёт `Enabled` из `DefaultEnabled`. Выключенное значение по
умолчанию защищает от массовой рассылки при выкатке: без явного выбора администратор
уведомлений о заявках не получает.

*Альтернатива:* выключить по умолчанию только внешние каналы для системного типа, оставив
колокольчик. Отклонена: продуктовое решение — выключить системные уведомления целиком, и
одно значение «включено» проще объяснить на экране настроек, чем комбинацию типа и канала.

Производные функции:
- `IsAddressed(t)` — «нет охвата», то есть `Audience != team_tree`;
- `TypesFor(isAdmin)`;
- `CategoryOf(t)`;
- `AudienceOf(t)`.

`AllTypes` остаётся как полный перечень: на него опираются валидация и тесты.

Порядок каталога — порядок экрана. Типы одной категории идут подряд: «Цели», затем «Системные».

*Альтернатива:* держать категорию только на клиенте. Отклонена: спецификация требует, чтобы
категорию сообщал сервер. Кроме того, клиент уже не хардкодит адресность, и категория
должна прийти тем же путём.

*Почему в store, а не в domain:* типы и `IsAddressed` уже живут здесь, и от них зависят
SQL резолва и сервис настроек. Перенос каталога в `core/domain` — отдельный рефакторинг,
к этому изменению он не относится.

### 2. Доменное событие `AccessRequested`

В `core/event` добавляется Kind `access_requested` со структурой
`AccessRequested{Meta; TenantTitle string}`:
- `Meta.Scope` — пространство заявки;
- `Meta.ActorID` — заявитель;
- `TeamID` и `PeriodID` пустые;
- `OccurredAt` = now.

Kind добавляется в `AllKinds()`.

`onboarding.Service` получает consumer-side порт `Publisher{Publish(ctx, ev)}`. Порт
передаётся через конструктор, в `internal/http/server.go` в него подключается тот же bus.
Для тестов используется `servicetest.FakeBus`. `RequestAccess` создаёт заявку новым
методом хранилища `memberships.CreateRequest`
(`INSERT … ON CONFLICT (user_id, tenant_id) DO NOTHING`). Метод атомарно сообщает, была
ли вставка, и событие публикуется только при реальной вставке. Так при одновременных
отправках одной заявки уведомление уходит один раз, а членство, одобренное в тот же
момент, не понижается обратно до заявки (прежний `Upsert` мог это сделать). Название
пространства есть в `tn`, который загружен по slug.

*Альтернатива:* создавать уведомления прямо из `RequestAccess`. Отклонена: сервис
онбординга начал бы зависеть от конвейера уведомлений, и у доставки появился бы второй
вход в обход шины.

Журнал: в `toRows` добавляется явная ветка `AccessRequested → nil` с комментарием, почему
событие не журналируется. Тест покрытия получает запись с ожиданием нуля строк. Eventlog
получает образец события. Логировать `TenantTitle` безопасно: это не пользовательский текст
внутри пространства. Решение о теге `log` принимается по правилам `observability-logging`.

### 3. Стратегия получателей «администраторы пространства»

`mapping.go`: `notifyType(AccessRequested) = access_requested`; `anchorOf` возвращает `title = TenantTitle`.

`notification.Handle` вместо развилки `IsAddressed / TeamID` смотрит на `AudienceOf(typ)`:
- `team_tree` — как сейчас, без `TeamID` событие отбрасывается;
- `addressee` — как сейчас;
- `tenant_admins` — без дополнительных условий. Автор отсекается в SQL.

`resolve` получает третью ветку: `prefs.ResolveTenantAdmins(ctx, scope, typ, actorIDs)`.

Новый метод репозитория — один запрос на группу:

```sql
SELECT src.ord - 1, m.user_id, COALESCE(p.channel_overrides, '{}'::jsonb)
  FROM unnest($1::bigint[]) WITH ORDINALITY AS src(actor_id, ord)
  JOIN memberships m ON m.tenant_id = $2 AND m.role = 'admin' AND m.status = 'active'
  LEFT JOIN notification_preferences p
         ON p.tenant_id = $2 AND p.user_id = m.user_id AND p.type = $3
 WHERE m.user_id <> src.actor_id AND COALESCE(p.enabled, $4)
```

`$4` — `DefaultEnabled` типа из каталога. Для `access_requested` это `false`, поэтому
администратор без сохранённой строки настроек не отбирается. Жёсткое `TRUE` в этом запросе
разошлось бы с экраном настроек, который показывает тип выключенным. Запросы стратегий
`team_tree` и `addressee` не меняются: у их типов значение по умолчанию остаётся `true`.

Порт `PrefResolver` расширяется этим методом.

`coalesceKey` для `access_requested` использует сущность `tenant:<id>`, а не `goal:0`:
ключ становится читаемым, а схлопывание остаётся в пределах одного заявителя.

*Альтернатива:* передавать список администраторов в событии и использовать addressed-путь.
Отклонена: сервису онбординга пришлось бы знать, кто получатели, а `ResolveAddressed`
рассчитан на одного адресата на событие.

### 4. Формулировка и ссылка

`render/notify.wording`: для `KindAccessRequested` — заголовок «Заявка на доступ», тело
«<Имя> просит доступ к пространству «<TenantTitle>»». Контекст ленты для этого типа
пустой (нет команды и цели), поэтому пространство называется в теле.

`notify.LinkInput` получает поле `Kind`. `TargetURL` для `access_requested` возвращает
`/admin?section=users&filter=requests`, для остальных Kind логика прежняя. Это не ломает
вызывающих: `Kind` есть и у записи ленты (`n.Kind`), и у `Delivery` (`it.Kind`). Оба места
вызова (`targetURL` в обработчике ленты и `render` в доставке) дописывают поле. Абсолютизация
и правило «нет адреса — нет ссылки» переиспользуются без изменений.

`admin.js`: `UsersSection` берёт начальное значение фильтра из `?filter=` (допустимо только
`requests`) и сохраняет существующий `readSectionFromURL`. Отдельный маршрут не нужен.

Нужно проверить, что клик по уведомлению в колокольчике переходит по `url` как есть,
а не собирает ссылку на цель из полей. Если собирает — клиент должен предпочитать `url`.

### 5. Имя заявителя

В `store/notifications.List` условие «не бывший» расширяется: `m.status IN
('active','requested')`. Решение принимается на уровне SQL, одним запросом, без отдельных
обращений на каждого человека.

В `store/users.ContactsByIDs` признак `Removed` сохраняет прежний смысл («нет активного
членства»): по нему доставка отсекает получателей, и заявитель получателем быть не должен.
Добавляется отдельный признак `Requested` (заявка ожидает решения). Рендер доставки
называет автора по имени при `!Removed || Requested`, как и лента.

*Альтернатива:* учитывать статус `requested` только для строк типа `access_requested`.
Отклонена: у `ContactsByIDs` нет контекста типа, а два разных правила для ленты и внешнего
канала противоречили бы требованию об одинаковом PII-правиле.

### 6. Настройки: видимость по роли и категории

- **Сервис** `notificationpref`. `GetAll(scope, userID, isAdmin)` отдаёт типы из
  `TypesFor(isAdmin)`. `SetAll(..., isAdmin)` отклоняет `AdminOnly`-тип у не-администратора
  с `ErrInvalidType`. Проверка выполняется до записи, поэтому матрица не сохраняется
  частично. Сохранённые строки при потере роли не трогаются. Для типа без сохранённой
  строки `GetAll` отдаёт `DefaultEnabled`, то есть «заявка на доступ» показана выключенной.
- **Обработчик.** Он берёт `isAdmin` из роли членства текущего принципала в активном
  пространстве — из того же источника, что и доступ к админке. Проверки роли в сервисе или
  хранилище не дублируются. Предел `len(items) > len(AllTypes)` остаётся.
- **DTO.** К элементу добавляется `category` (`goals` | `system`).
- **Клиент** (`settings.js`):
  - `NOTIF_CATEGORIES = [{id:'goals', title:'Цели'}, {id:'system', title:'Системные'}]`;
  - в `tbody` перед типами каждой непустой категории выводится строка-заголовок группы
    (`notif-prefs__group`, `colSpan` на всю ширину);
  - `NOTIF_TYPE_LABELS.access_requested`: подпись «Заявка на доступ к пространству»,
    подсказка «Приходит администраторам пространства»;
  - вводный текст секции дополняется упоминанием системных уведомлений для администраторов.

  Новый компонент не вводится: таблица та же, добавляются только строки групп и стиль
  в общем CSS настроек.

### 7. Миграция 048

`048_access_request_notification.up.sql` пересоздаёт CHECK-ограничения `notifications_type`
и `notification_preferences_type`, добавляя в них `access_requested`.

`down` удаляет строки этого типа из обеих таблиц и восстанавливает прежние ограничения.

Seed demo (`seed_demo.sql`) содержит демо-уведомления и настройки. Он дополняется:
- включённой настройкой `access_requested` у демо-пользователя;
- демо-заявителем с поданной заявкой (он виден в очереди «Заявки»);
- уведомлением о его заявке, чтобы в колокольчике был пример с именем заявителя.

### 8. Кеширование

Новое кеширование не вводится. Резолв администраторов — один индексируемый запрос на
группу событий. Заявки подаются редко. Кеш членств (`MembershipCache`) инвалидируется
в `RequestAccess`, как и прежде. Роль для настроек берётся из уже закешированного
принципала, поэтому в многоэкземплярном развёртывании новых проблем согласованности нет.

## Risks / Trade-offs

- [Бывший участник, у которого снова есть поданная заявка, снова показывается по имени и
  в своих старых уведомлениях] → Это приемлемо: он сам раскрыл себя пространству новой
  заявкой. Одно правило для ленты и внешнего канала важнее.
- [Ссылка из внешнего канала открывает админку в текущем активном пространстве получателя,
  а не в пространстве заявки] → Ограничение уже действует для ссылок на цели и вынесено
  в Non-Goals. Название пространства в тексте позволяет администратору переключиться вручную.
- [Уведомление остаётся в ленте после того, как заявку обработали] → Переход ведёт
  в очередь, где заявки уже нет, без ошибки: это отражено в сценарии спецификации.
  Автоудаление вне scope.
- [Изменение сигнатур `GetAll`, `SetAll` и `LinkInput`] → Вызывающих мало. Перед правкой
  выполнить `change(operation:"verify")`.
- [Событие публикуется, а асинхронный подписчик упал] → Поведение то же, что у остальных
  типов: ошибка логируется шиной, заявка при этом сохранена.

## Migration Plan

1. Выкатить миграцию 048 вместе с кодом. Ограничение только расширяется, поэтому старые
   экземпляры во время rolling update продолжают работать.
2. Тип выключен по умолчанию, поэтому сразу после выкатки уведомления о заявках никому
   не создаются и не рассылаются. Администраторы включают тип в настройках профиля сами.
3. Старые экземпляры не публикуют `AccessRequested`. Заявки, поданные через них во время
   раскатки, уведомления не породят — это допустимо.
4. Откат: откатить код, затем выполнить `048 down`. Уведомления и настройки нового типа
   при этом удаляются.
