## Why

Когда пользователь подаёт заявку на подключение к пространству по slug, заявка молча
попадает в очередь администратора: узнать о ней можно, только открыв админку. Заявки
висят днями, а человек всё это время остаётся на странице «нет доступа». Администратору
нужно получать сигнал о новой заявке там же, где он получает остальные уведомления, —
в колокольчике и во внешних каналах (Mattermost и другие подключённые).

## What Changes

- Новый тип уведомления «заявка на доступ к пространству». Порождается, когда пользователь
  подаёт новую заявку на доступ по slug. Получатели — все активные администраторы
  пространства, в которое подана заявка.
- Уведомление отображается в ленте (колокольчик) и доставляется во внешние каналы по
  тем же правилам, что и остальные типы: с учётом каналов получателя, накопления и окна
  отправки.
- Уведомление ведёт в очередь заявок админки пространства: в ленте — нажатием, во внешнем
  канале — абсолютной ссылкой.
- Повторная отправка заявки, которая уже ожидает решения, нового уведомления не порождает.
- В ленте и в сообщении внешнего канала заявитель называется по имени, хотя активным
  участником пространства он ещё не является.
- Настройки уведомлений в профиле группируются по категориям. Существующие четыре типа
  попадают в категорию «Цели», новый тип — в категорию «Системные».
- Тип «заявка на доступ» показывается в настройках и сохраняется только у администратора
  пространства. Охват дерева команд к нему неприменим.
- Уведомления категории «Системные» по умолчанию выключены: администратор включает их
  сам. После выкатки никому ничего не приходит, пока администратор не включит тип, —
  массовой рассылки всем администраторам не будет.
- Закрытый набор типов расширяется с четырёх до пяти. Ответ с настройками зависит от роли
  пользователя в пространстве. Это меняет контракт настроек (**BREAKING** для клиентов,
  которые ожидают ровно четыре типа; других клиентов, кроме собственного UI, нет).

Вне scope:
- автоматическое скрытие или удаление уведомления после того, как заявку одобрили или
  отклонили;
- уведомление заявителю о решении по его заявке;
- уведомления системным администраторам.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `notifications`: новый тип «заявка на доступ» и правило, какое действие его порождает.
  Получатели — администраторы пространства, а не дерево команд. Настройки группируются
  по категориям, а набор типов в них зависит от роли. Закрытый набор типов расширяется до
  пяти. Правило охвата для адресных типов распространяется на новый тип. Значение по
  умолчанию для системных типов — «выключено».
- `notification-delivery`: ссылка во внешнем сообщении теперь бывает не только ссылкой на
  цель. Уведомление о заявке ведёт в очередь заявок пространства.

`membership-and-onboarding` не меняется: подача заявки, очередь и её обработка остаются
прежними. Новое поведение (уведомление) описывается в `notifications`.

## Impact

- **Домен и события**: новое доменное событие «заявка на доступ подана». Его публикует
  сервис онбординга, которому для этого нужен порт публикации. Журнал активности это
  событие не пишет.
- **Уведомления**: сопоставление событий с типами, новая стратегия получателей
  «администраторы пространства» (пакетный резолв), ключ схлопывания, формулировки
  (`render/notify`), ссылка на очередь заявок.
- **Настройки**: `store/notificationprefs` (типы, категории, видимость по роли),
  `service/notificationpref`, HTTP-обработчик настроек (поле `category` в ответе,
  фильтрация по роли, валидация), `web/static/settings.js` (группировка по категориям).
- **Правило показа имени**: лента (`store/notifications`) и контакты для доставки
  (`store/users.ContactsByIDs`) считают участника с поданной заявкой не «бывшим».
- **Админка**: `web/static/admin.js` открывает раздел «Пользователи» сразу с фильтром
  «Заявки», если он передан в адресе.
- **БД**: миграция 048 расширяет CHECK-ограничения `notifications.type` и
  `notification_preferences.type`. Seed demo дополняется примером настройки и
  уведомления нового типа.
- **Тесты**: тесты, которые перебирают `event.AllKinds()` (журнал, eventlog); тесты
  настроек, которые ожидают ровно четыре типа.

Противоречий между кодом, тестами и текущими specs не обнаружено.
