# Дизайн: уведомления об общих целях

## 1. Контекст

Сегодня конвейер уведомлений адресует событие ровно одной командой. Путь такой:

- событие несёт `event.Meta.TeamID` — для цели, её ключевых результатов и замечаний это
  всегда команда-владелец (`goals.team_id`);
- `usecase/notification.Handle` группирует события по `(tenant_id, type)` и для командных
  типов строит по одному `notificationprefs.Target{TeamID, ActorID}` на событие;
- `store/notificationprefs.ResolveRecipients` одним рекурсивным запросом поднимается от
  `Target.TeamID` к корню дерева, берёт руководителей (`teams.lead_udid`), отсекает автора
  и фильтрует по `enabled`/`scope` каждого получателя;
- `Recipient{Ord, UserID, ChannelOverrides}` возвращается пакетом, `Ord` — индекс исходного
  события; запись уведомления получает `team_id = Meta.TeamID`, и из него же строится
  переход.

Состав команд общей цели (`goal_shares`) в этом пути не участвует нигде. Отсюда обе дыры:
команда-участник не получает уведомлений об общей цели, а изменение самого состава команд
не порождает уведомлений вообще (`notifyType` возвращает `""` для `goal_shared` и
`goal_unshared`).

Новых типов уведомлений change не вводит: набор типов остаётся закрытым, матрица настроек
не меняется, `notifications.type` и `notification_preferences.type` остаются в прежних
множествах значений. Столбец `notifications.kind` CHECK-ограничения не имеет, поэтому
значения `goal_shared` и `goal_unshared` в нём допустимы без миграции.

## 2. Аудитория события об общей цели

### 2.1 Откуда берётся состав команд

Аудитория вычисляется в `usecase/notification`, а не в каждом месте публикации события.
Иначе пришлось бы загружать состав команд в десятке use case'ов и протащить его через
`event.Meta`, где он нужен единственному подписчику.

Новый порт use case'а:

```go
// GoalTeamsResolver returns, for each goal, the owning team and every team the
// goal is shared with.
type GoalTeamsResolver interface {
    TeamIDsByGoalIDs(ctx context.Context, scope domain.TenantScope, goalIDs []int64) (map[int64][]int64, error)
}
```

Реализация — в `store/shares`, одним запросом на всю группу событий (правило «не запрашивать
БД в цикле»):

```sql
SELECT g.id, g.team_id   FROM goals       g  WHERE g.id      = ANY($1) AND g.tenant_id = $2
UNION
SELECT s.goal_id, s.team_id FROM goal_shares s WHERE s.goal_id = ANY($1) AND s.tenant_id = $2
```

Запрос идёт один раз на группу `(tenant_id, type)` по списку уникальных `goal_id` группы.

### 2.2 Почему состав читается на обработке, а не на публикации

Обработчик уведомлений асинхронный, поэтому состав на момент обработки может отличаться
от состава на момент публикации. Это **принятая гонка**, а не её отсутствие, и стоит
назвать её честно.

Что именно может разойтись. Обычное событие — правка цели, замечание, чек-ин — своих
команд не несёт, восстановить их `composedTeamIDs` не из чего. Если команду B сняли с
цели между публикацией такого события и его обработкой, резолв её уже не вернёт, и
руководитель B пропустит событие, случившееся, пока цель была на его доске. Симметрично,
команда, добавленная в эту же щель, получит чуть более раннее событие.

Почему это приемлемо:

- щель — один переход между горутинами. `Publish` кладёт событие в буферизованный канал,
  на котором подписчик уже стоит в receive; отдельного таймера или интервала флаша нет.
  Чтобы гонка проявилась, снятие команды должно попасть ровно в эти миллисекунды;
- потерянное уведомление — об уже чужой цели. В том же батче руководитель B получит
  `goal_unshared` и узнает, что команду сняли: он не остаётся в неведении, а лишь не
  видит одной правки по цели, которой у него больше нет;
- обратный случай безвреден: команда, которую только что добавили, видит одно событие,
  случившееся незадолго до её появления в цели.

Чем пришлось бы платить за точность. Снимок состава в событии означает чтение
`goal_shares` в каждом месте публикации — то есть дополнительный запрос к БД на каждую
мутацию цели, KR и обсуждения, на горячем пути HTTP-ответа. Плюс поле в `event.Meta`,
которое обязаны заполнить все места публикации, с тихой деградацией при забытом: пустой
снимок читается как «участников нет», и уведомление не дойдёт вообще — то есть лекарство
отказывает в ту же сторону, что и болезнь, но уже постоянно, а не в миллисекундной щели.

Отдельно: гонки «цель удалена, состав исчез, уведомлять некого» не существует. Общая цель
жёстко не удаляется — `goal.Delete` для цели с участниками передаёт владение первой
команде-участнику, а `GoalDeleted` публикуется только для цели без участников.

### 2.3 Команды из самого события

К составу из 2.1 добавляются команды, которых в нём уже (или ещё) нет:

| событие | поле | что добавляется |
| --- | --- | --- |
| `GoalShared` | `SharedWithTeamIDs` | добавленные команды |
| `GoalUnshared` | `UnsharedTeamIDs` | снятые при полной замене состава |
| `GoalUnshared` | `UnsharedTeamID` | снятая одиночным удалением |
| `GoalUnshared` | `DeclinedByTeamID` | команда, отказавшаяся от участия |
| `GoalOwnerChanged` | `BeforeTeamID` | прежний владелец |

Прежний владелец в этом списке не ради симметрии. `goal.Delete` для общей цели не
удаляет её, а передаёт владение первому участнику и снимает его участие — прежний
владелец остаётся без цели вовсе: ни владельцем, ни участником. Из всех задетых команд
именно она гарантированно теряет цель с доски, и состав на момент обработки о ней уже
не помнит.

Три поля у `GoalUnshared` — существующая особенность: три места публикации пишут разную
форму payload, и нормализация в scope этого change не входит. Чтение закрывается одной
функцией `composedTeamIDs(ev)`, которая читает все три.

Итоговый набор команд события:

```
teams(p) = dedup( {Meta.TeamID} ∪ ownerAndShares[goalID] ∪ eventTeams(ev) )
```

`Meta.TeamID` остаётся в наборе: для событий без цели (заявка на доступ не попадает сюда
вовсе, но правило должно быть полным) и как страховка от рассинхронизации.

## 3. Разворачивание и дедупликация

### 3.1 Target: одно событие — несколько команд

`Target` остаётся парой `{TeamID, ActorID}`, но на одно событие их теперь несколько.
`Ord`, который резолвер возвращает, перестаёт быть индексом события и становится индексом
*адресуемой пары*. Поэтому `resolve` строит рядом с `targets` карту `ordToItem []int` и
`Handle` берёт `items[ordToItem[rc.Ord]]`.

Это предпочтительнее, чем добавлять в `Target` список команд: рекурсивный запрос уже
принимает параллельные массивы с `WITH ORDINALITY`, и разворачивание пар не меняет ни форму
запроса, ни его план.

### 3.2 Recipient: через какую команду найден

`Recipient` получает два поля:

```go
type Recipient struct {
    Ord              int
    UserID           int64
    ChannelOverrides map[string]bool
    TeamID           int64 // команда-участник, от которой выполнен обход
    Distance         int   // её расстояние до команды получателя
}
```

Запрос добавляет в выборку `c.root_team` и `c.distance`. Из-за этого прежний
`SELECT DISTINCT` перестал бы схлопывать получателя, найденного двумя путями вверх от
одного target'а (человек руководит и командой, и её родителем), поэтому он заменён на
`DISTINCT ON (c.ord, u.id)` с `ORDER BY c.ord, u.id, c.distance, c.root_team`: строка
остаётся одна и это ближайший путь. Схлопывать обязательно — иначе
`notifications.Insert` с `ON CONFLICT` увеличит `coalesce_count`, и получатель увидит
«2 изменения» там, где изменение было одно.

Дублирование *между* target'ами одного события SQL снять не может: он не знает, что
несколько target'ов — это одно событие. Это делает `usecase/notification`, где правило
видно явно:

- ключ — `(индекс события, UserID)`;
- побеждает запись с минимальным `Distance`;
- при равенстве — наименьший `TeamID`, чтобы результат не зависел от порядка строк из БД.

`Distance` как критерий выбран не для красоты: записанная в уведомлении команда — это та,
на чью доску ведёт переход, и ближайшая к получателю команда — та, доступ к которой у него
заведомо есть.

### 3.3 Запись уведомления

`UseCase.row` берёт `TeamID` из `Recipient`, а не из `Meta`. Остальные поля не меняются.
`render/notify.TargetURL` уже строит переход из `team_id` записи, поэтому переход начинает
вести на нужную доску сам собой — и в ленте, и во внешнем канале. Исключение одно, см. §5.2.

Ключ схлопывания не меняется: сущность схлопывания для «изменения цели» — сама цель, и
`goal_shared` схлопывается с другими правками той же цели в том же окне, как и любое другое
изменение. Это соответствует действующему требованию «Сущность схлопывания».

## 4. Одно событие — несколько типов

`notifyType(ev) string` становится `notifyTypes(ev) []string`:

- `CommentResolved` → `my_comment_resolved` (адресный) **и** `goal_comment` (командный);
- `GoalShared`, `GoalUnshared` → `goal_changed`;
- остальные — как раньше, один тип.

`Handle` уже группирует по типу, так что одно событие просто попадает в две группы. Для
`CommentResolved` командная группа отбрасывается, если цель не расшарена ни в одну команду:
`len(ownerAndShares[goalID]) <= 1`. Это асимметрия, и она намеренная — решение замечания к
обычной цели остаётся личным делом автора замечания, а у общей цели его видят все команды,
которые с этой целью работают.

Автор действия отсекается уже существующим механизмом: `u.id <> c.actor_id` в запросе
резолва и проверка `addressee == ActorID` для адресного типа. Отдельного правила этот change
не добавляет.

## 5. Формулировки

`render/notify.Input` получает `TeamID *int64` — команду из записи уведомления. Она нужна
только для двух новых Kind: текст должен отличаться для команды, которой касается изменение,
и для соседней команды-участника.

Payload несёт **два раздельных ключа**: `added_team_ids` у `goal_shared` и
`removed_team_ids` у `goal_unshared` (все три формы `GoalUnshared` приводятся к одному
списку). Глагол живёт в самом ключе, а не выводится из Kind, и текст выбирается по payload:

| `TeamID` записи | текст |
| --- | --- |
| в `removed_team_ids` | «{Актор} убрал вашу команду из цели» |
| в `added_team_ids` | «{Актор} добавил вашу команду к цели» |
| ни там, ни там | «{Актор} изменил состав команд цели» |

Это не стилистика, а требование схлопывания. Upsert в `store/notifications` **замораживает
`kind`, но перезаписывает `payload_json`** последним событием: это задокументированный
компромисс («первое вхождение выигрывает по формулировке»). Вместе с payload change
начинает обновлять и `team_id` — он не формулировка, а маршрут, и обязан описывать то же
событие, что и payload. Иначе на общей цели, где два события одного окна могут найти
одного получателя через разные команды, строка соединит последний payload с первой
командой: после снятия команды очередная правка перезапишет payload на тот, который про
команды молчит, а ссылка продолжит вести на доску, с которой цель уже ушла. Расшаривание и снятие по одной
цели попадают в один ключ схлопывания — они одного типа, об одной цели, от одного актора, —
и достаточно двух операций в пределах окна, чтобы строка получила `kind = goal_shared` и
payload снятия. С одним общим списком и выбором текста по Kind команда, которую только что
убрали, прочитала бы «вашу команду добавили». С раздельными ключами строка читается по
последнему payload, что и соответствует семантике схлопывания.

Идентификаторы кладутся как `[]any` из `int64`: в ленте тот же payload приходит из JSONB
как `[]any` из `float64`, и рендер обязан принимать обе формы, иначе текст расходится
между лентой и внешним каналом. Рендер читает обе.

Отсутствующий, пустой или нечитаемый список, как и запись без команды, дают нейтральный
текст: утверждать что-то про команду получателя, не зная её, нельзя.

### 5.1 Решение замечания: две формулировки на один Kind

`CommentResolved` теперь порождает две записи с одним `kind`, но разными типами, и текст у
них разный: адресной копии автору — прежнее «решил ваш комментарий», командной копии
участникам — «решил замечание к цели». Участники этого замечания не писали, и назвать его
«вашим» значит соврать. Поэтому `notify.Input` получает поле `Type` рядом с `Kind`, а
`notification.Delivery` — такое же поле, чтобы внешний канал говорил то же, что лента.

### 5.1a Прежний владелец

`GoalOwnerChanged` — единственное событие, у которого «ушедшая команда» из самого
события не выводится: `goal.Delete` прежнего владельца с цели снимает, а
`UpdateOwnerAndShares` может оставить его участником. Различает их только состав,
поэтому пометка считается в шаге аудитории (`pending.departed`) и попадает в payload
тем же ключом `removed_team_ids`. Состав не прочитался — пометки нет: лучше нейтральный
текст, чем ложное «цель у вас забрали».

Текст для такого получателя — «передал цель другой команде», а не «сменил владельца
цели»: второе читается как новость про кого-то другого.

### 5.2 Куда ведёт уведомление снятой команды

У команды, участие которой сняли, цели на доске больше нет, поэтому ссылка на цель открыла
бы доску и не подсветила ничего. `LinkInput.GoalLeftTeam` обрывает путь на доске команды в
периоде цели. Признак вычисляют оба вызывающих — лента и доставка — через
`notify.TeamWasRemoved(payload, teamID)`, то есть из того же payload, что и текст.

Это не то же самое, что `GoalMissing`: там цель удалена для всех, и ссылки нет вовсе; здесь
цель жива и у остальных команд открывается как обычно.

Названия команд в тексте не используются: события несут только идентификаторы, а загрузка
названий ради одной строки добавила бы запрос на каждую группу. Цель названа — этого
достаточно, чтобы понять, о чём речь, а состав виден на её карточке.

Тест `render/notify`, требующий собственного текста для каждого уведомляющего Kind, покроет
оба новых Kind автоматически — достаточно добавить их в перечень уведомляющих.

## 6. Интерфейс

Новых компонентов интерфейса change не вводит и существующие не меняет: уведомление об
общей цели — обычная строка колокольчика с заголовком, телом и переходом, уже описанная
карточкой уведомления в дизайн-системе. Настройки уведомлений не меняются — ни строк, ни
колонок, ни категорий.

Поэтому согласование вида на прототипе не требуется, и карточки дизайн-системы обновлять
не нужно. Если при реализации выяснится, что текст уведомления о составе команд не влезает
в существующую карточку, вид согласуется на прототипе до правки вёрстки.

## 7. Производительность

На группу событий добавляется ровно один запрос — состав команд по списку целей. Резолв
получателей остаётся одним запросом, но его входной массив растёт пропорционально среднему
числу команд-участников: типичная цель не расшарена вовсе (одна пара на событие), общая —
несколько пар. Рекурсивный обход выполняется от каждой пары, то есть стоимость запроса
растёт линейно по числу команд-участников, а не по числу получателей.

Дедупликация в Go — проход по результату резолва, без дополнительных запросов.

## 8. Отвергнутые альтернативы

**Нести состав команд в `event.Meta`.** Требует правок во всех местах публикации событий о
целях, ключевых результатах и замечаниях, и загрузки состава там, где он не нужен никому,
кроме уведомлений. Забытое поле деградирует тихо.

**Отдельный тип уведомления «общая цель».** Прямо исключено постановкой: отдельной настройки
не нужно. Кроме того, это расщепило бы настройку: пользователь, отключивший «изменение цели»,
продолжал бы получать изменения общих целей.

**Резолвить участников внутри SQL резолва (`JOIN goal_shares`).** Потребовало бы передавать в
резолвер `goal_id` вместо `team_id` и сделало бы запрос зависимым от схемы целей. Резолвер
отвечает на вопрос «кто подписан на событие в команде T» и о целях знать не должен.

**Вести переход всегда на доску команды-владельца.** Ломается ровно там, где change и нужен:
у руководителя команды-участника может не быть доступа к команде-владельцу.
