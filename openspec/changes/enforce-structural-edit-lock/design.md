## Context

Мотивацию см. в `proposal.md` — «Why». Здесь только то, что определяет подход.

Сегодня ограничение по статусу существует в трёх местах и в двух разных видах: сценарии работы с
целью читают статус команды и сравнивают его с двумя значениями, а сценарий шаринга проверяет
статус каждой вновь добавляемой команды. Проверок нет ни в одном сценарии ключевых результатов —
слой сценариев ключевых результатов вообще не знает о статусах. Отказы приходят двумя разными
доменными ошибками и превращаются в два разных машинных кода ответа.

Существенные ограничения:

- статус хранится парой «команда и период», поэтому любая проверка требует знать обе величины; для
  операции над ключевым результатом их приходится выводить через родительскую цель;
- одна операция может затрагивать доски нескольких команд сразу (сохранение набора участников,
  перенос цели), и статус у них разный;
- приложение работает в нескольких экземплярах, статус меняется из интерфейса в любой момент;
- набор статусов после правки baseline — пять значений, блокирующих из них два.

## Goals / Non-Goals

**Goals:**

- одно правило вместо трёх независимых проверок, чтобы новые операции не расходились с ним по
  умолчанию;
- проверка по каждой затронутой доске, а не по одной «главной» команде операции;
- отказ, отличимый клиентом от ошибки доступа и ошибки валидации, одинаковый для всех операций
  блокировки;
- сохранение работоспособности всего, что относится к исполнению: прогресс, health-статус,
  заметка, описание, комментарии, связи, чтение, экспорт.

**Non-Goals:**

- правила переходов между статусами: кто и в какой статус может переводить команду — отдельная
  тема, здесь не трогается; смена статуса остаётся доступной как сейчас;
- ограничения для статуса «к валидации» — он остаётся полностью редактируемым;
- унификация конверта ошибок API — отдельное изменение;
- изменение состава и правил событий журнала активности.

## Decisions

### Решение 1. Правило — чистый предикат в доменном слое, чтение статуса — в слое сценариев

Признак «статус допускает изменение состава и структуры» выражается чистой функцией над значением
статуса и живёт в доменном слое рядом с самим перечислением статусов. Слой сценариев читает статус
через сервис статусов и вызывает предикат.

Почему так: правило — доменное знание, а не деталь сценария, и должно иметь ровно одно место
определения. Держать его в сервисе статусов нельзя: сервис сущности не должен решать за сценарий,
что именно тот собирается сделать. Держать его в обработчиках нельзя — там нет бизнес-логики.

Альтернативы:

- *сравнение со списком значений на месте каждой операции* — так сегодня; именно это и дало
  расхождение между целями и ключевыми результатами;
- *отдельный сервис политики* — лишний слой ради одной функции без состояния и без ввода-вывода.

### Решение 2. Проверяется каждая затронутая доска

Для операции определяется множество команд, чей состав целей или содержимое она меняет, и правило
применяется к каждой из них по её собственному статусу в соответствующем периоде. Отказ выдаётся,
если хотя бы одна из них заблокирована.

Это даёт единообразие в неочевидных случаях: снятие участия проверяется по статусу выходящей
команды, а не владельца; перенос — по обеим сторонам; сохранение набора участников — по всем
добавляемым и по всем снимаемым командам.

Альтернатива — проверять «команду операции» — не работает: у половины случаев такой команды просто
нет, а у остальных она не та, чей состав меняется.

### Решение 3. Ключевые результаты получают статус через родительскую цель

Сценарии ключевых результатов получают порт на сервис статусов и порт на чтение цели, чтобы вывести
пару «команда и период» из родительской цели. Один вызов чтения цели и один вызов чтения статуса на
операцию.

Запросов в цикле это не создаёт: все операции над ключевым результатом — точечные, над одним
объектом. Перестановка ключевых результатов тоже точечная. Массовых операций над ключевыми
результатами, где проверка попала бы в цикл, в контракте нет; если такая появится, статусы нужно
читать пакетно — это фиксируется как правило для будущих операций, а не как код сейчас.

### Решение 4. Одна доменная ошибка и один машинный код отказа

Все отказы по статусу выражаются одной доменной ошибкой и одним машинным кодом ответа со значением
конфликта. Сегодня используется код `PERIOD_STARTED` для шаринга и родовой код конфликта для
переноса и создания цели — расширяем `PERIOD_STARTED` на все случаи.

Почему один код: клиент различает не «какая именно операция запрещена», а «период уже начат, эту
правку сделать нельзя» — сообщение и предлагаемое действие для пользователя одинаковые во всех
случаях. Два кода потребовали бы от клиента различать их без пользы.

Существующая доменная ошибка шаринга становится псевдонимом общей — так уже написанные обработчики
и тесты не ломаются одномоментно.

Альтернатива — код на каждый класс операции — отвергнута: множит контракт без сценария применения.

### Решение 5. Статус для проверки читается на каждую операцию, без кеша

Кеширование статуса для этой проверки не вводится. Окно рассогласования между экземплярами
приложения здесь означает пропущенную структурную правку в уже начатом периоде — ровно то, что
изменение и должно исключить. Стоимость чтения — один точечный запрос на мутацию, мутации редки по
сравнению с чтениями, и на горячем пути чтения доски эта проверка не участвует вовсе.

### Решение 6. Возврат в «черновик» — штатный способ поправить цели

Отдельного механизма разблокировки не вводится. Если состав целей нужно изменить после начала
периода, руководитель возвращает команду в «черновик», правит и переводит обратно. Смена статуса
блокировкой не затронута, поэтому путь доступен без новых прав и без новых операций.

Это осознанный выбор в пользу явности: правка в начатом периоде становится видимым действием со
сменой статуса, которое попадает в журнал активности, вместо незаметной правки «мимо» правила.

### Решение 7. Интерфейс: отказ обрабатывается там, где операция ещё предлагается

Доска уже скрывает структурные правки при «в работе» и «закрыт», поэтому большинство операций до
сервера не доходит. Две операции интерфейс в этих статусах всё ещё предлагает — снятие цели с доски
текущей команды и удаление цели, у которой есть команды-участники. Для них добавляется обработка
отказа существующими общими средствами: подтверждение действия и показ причины рядом с формой, без
новых компонентов.

## Risks / Trade-offs

- **Команда, начавшая период, застревает с чужой общей целью.** Команда-участник не может снять с
  себя цель, пока находится в «в работе». → Это принятое продуктовое правило: состав целей начатого
  периода не меняется в одностороннем порядке. Выход — возврат команды в «черновик» её
  руководителем; путь описан в решении 6 и должен быть отражён в тексте отказа.
- **Цель с участниками нельзя удалить, пока владелец в «в работе».** Передача владения теперь
  запрещена по статусу владельца. → Тот же выход. Риск потери данных отсутствует: запрещается
  удаление, а не сохранение.
- **Массовая активация периода замораживает сразу много команд.** Существующая операция становится
  заметно более значимой. → Поведение самой операции не меняется; риск снимается текстом
  подтверждения массового перехода, а не кодом.
- **Клиенты, полагавшиеся на успешный ответ в «в работе», получат отказ.** → Ломающее изменение
  внешнего контракта, отмечено в предложении; собственный интерфейс правится в этом же изменении,
  внешних потребителей API у продукта нет.
- **Расширение кода `PERIOD_STARTED` на новые случаи.** Клиент, сопоставлявший этот код только с
  выбором команд в модалке цели, покажет неточное сообщение. → Обработка кода выносится в общее
  место, сообщение делается независимым от конкретной формы.

## Migration Plan

Изменений схемы нет, миграции не требуются, данные не трогаются. Развёртывание обычное; откат —
возврат предыдущей версии приложения, состояние базы совместимо в обе стороны.

Отдельно: существующие команды в «в работе» и «закрыт» после развёртывания сразу перестают
принимать структурные правки. Это и есть цель изменения; предварительной подготовки данных не
требуется.
