## ADDED Requirements

### Requirement: Инвариант неизменности состава целей команды

Система SHALL считать состав целей команды в периоде зафиксированным, если статус этой команды в
этом периоде — «в работе» или «закрыт». Ни одна операция MUST NOT добавить цель на доску такой
команды и MUST NOT убрать цель с её доски. Правило SHALL применяться независимо от способа
изменения состава и независимо от того, кто его инициировал.

Инвариант SHALL проверяться для каждой команды, чья доска затрагивается операцией, по её
собственному статусу в этом периоде.

#### Scenario: Создание цели

- GIVEN статус команды — «в работе» или «закрыт»
- WHEN кто-либо создаёт цель для этой команды в этом периоде
- THEN операция отклоняется как конфликт, состав целей команды не меняется

#### Scenario: Удаление собственной цели

- GIVEN статус команды — «в работе» или «закрыт», цель принадлежит ей и никому не расшарена
- WHEN кто-либо удаляет эту цель
- THEN операция отклоняется как конфликт

#### Scenario: Удаление цели владельцем с передачей владения

- GIVEN статус команды-владельца — «в работе» или «закрыт», цель расшарена другой команде
- WHEN кто-либо удаляет цель из представления команды-владельца
- THEN операция отклоняется как конфликт: цель ушла бы с доски команды-владельца

#### Scenario: Добавление команды-участника

- GIVEN статус команды D в периоде цели — «в работе» или «закрыт»
- WHEN кто-либо добавляет команду D участником цели
- THEN операция отклоняется как конфликт

#### Scenario: Самостоятельный выход команды-участника

- GIVEN цель расшарена в команду B, статус команды B — «в работе» или «закрыт»
- WHEN кто-либо снимает участие команды B в этой цели
- THEN операция отклоняется как конфликт: цель ушла бы с доски команды B

#### Scenario: Копирование или перенос цели в начавшую команду

- GIVEN статус целевой команды в целевом периоде — «в работе» или «закрыт»
- WHEN кто-либо копирует или переносит цель в эту пару
- THEN операция отклоняется как конфликт

#### Scenario: Перенос цели из начавшей команды

- GIVEN статус исходной команды — «в работе» или «закрыт»
- WHEN кто-либо переносит цель из неё в команду, статус которой допускает добавление
- THEN операция отклоняется как конфликт: цель ушла бы с доски исходной команды

#### Scenario: Проверка выполняется по статусу каждой затронутой команды

- GIVEN команда-владелец в статусе «черновик», а команда-участник — в «в работе»
- WHEN кто-либо снимает участие команды-участника
- THEN операция отклоняется по статусу команды-участника, а не команды-владельца

### Requirement: Запрет структурных правок содержимого целей

Система SHALL отклонять как конфликт следующие операции, когда статус команды в периоде — «в
работе» или «закрыт»: изменение полей цели, создание ключевого результата, изменение ключевого
результата, удаление ключевого результата, изменение порядка целей, изменение порядка ключевых
результатов.

#### Scenario: Изменение полей цели

- GIVEN статус команды — «в работе» или «закрыт»
- WHEN кто-либо меняет заголовок, описание, приоритет, вес, тип работы, фокус или драйверов цели
- THEN операция отклоняется как конфликт

#### Scenario: Создание ключевого результата

- GIVEN статус команды — «в работе» или «закрыт»
- WHEN кто-либо создаёт ключевой результат в цели этой команды
- THEN операция отклоняется как конфликт

#### Scenario: Изменение ключевого результата

- GIVEN статус команды — «в работе» или «закрыт»
- WHEN кто-либо меняет заголовок, вес, тип или измеримые параметры ключевого результата
- THEN операция отклоняется как конфликт

#### Scenario: Удаление ключевого результата

- GIVEN статус команды — «в работе» или «закрыт»
- WHEN кто-либо удаляет ключевой результат
- THEN операция отклоняется как конфликт

#### Scenario: Изменение порядка целей

- GIVEN статус команды — «в работе» или «закрыт»
- WHEN кто-либо перемещает цель вверх или вниз в представлении этой команды
- THEN операция отклоняется как конфликт

#### Scenario: Изменение порядка ключевых результатов

- GIVEN статус команды — «в работе» или «закрыт»
- WHEN кто-либо перемещает ключевой результат внутри цели
- THEN операция отклоняется как конфликт

### Requirement: Операции, доступные во всех статусах

Система SHALL разрешать независимо от статуса команды в периоде: обновление прогресса ключевого
результата, изменение его health-статуса, сохранение его заметки, изменение его описания, работу
с замечаниями и ответами, привязку и отвязку родительских целей, чтение и экспорт.

#### Scenario: Обновление прогресса в закрытом статусе

- GIVEN статус команды — «в работе» или «закрыт»
- WHEN пользователь обновляет прогресс ключевого результата, его health-статус или заметку
- THEN операция выполняется

#### Scenario: Правка описания ключевого результата

- GIVEN статус команды — «в работе» или «закрыт», полное редактирование ключевого результата закрыто
- WHEN пользователь сохраняет описание ключевого результата
- THEN операция выполняется

#### Scenario: Комментирование

- GIVEN статус команды — «в работе» или «закрыт»
- WHEN пользователь добавляет замечание, отвечает на него, отмечает решённым или удаляет своё
- THEN операция выполняется

#### Scenario: Связи целей

- GIVEN статус команды — «в работе» или «закрыт»
- WHEN пользователь привязывает цель к родительской цели или отвязывает её
- THEN операция выполняется

#### Scenario: Чтение и экспорт

- GIVEN статус команды — «в работе» или «закрыт»
- WHEN пользователь открывает доску, дерево целей или экспортирует цели
- THEN операции выполняются

### Requirement: Ограничения по статусу — серверная гарантия

Система SHALL применять ограничения по статусу на сервере. Скрытие операции в интерфейсе MUST NOT
считаться достаточным: прямой запрос в обход интерфейса SHALL получать тот же отказ.

#### Scenario: Прямой запрос в обход интерфейса

- GIVEN интерфейс не предлагает структурную правку при статусе «в работе»
- WHEN пользователь отправляет соответствующий запрос напрямую
- THEN сервер отклоняет его как конфликт

#### Scenario: Согласованный вид отказа

- GIVEN любая из запрещённых статусом операций запрошена
- WHEN сервер её отклоняет
- THEN отказ имеет вид конфликта и отличим клиентом от ошибки доступа и ошибки валидации

## MODIFIED Requirements

### Requirement: Область действия серверного ограничения статуса

Система SHALL применять ограничение статуса к операциям, меняющим состав целей команды в периоде,
и к структурным правкам содержимого целей этой команды. Операции, не относящиеся ни к тому, ни к
другому, SHALL оставаться доступными во всех статусах.

#### Scenario: Отказ от общей цели в статусе «в работе»

- GIVEN цель расшарена в команду, статус которой — «в работе»
- WHEN пользователь удаляет цель из представления этой команды
- THEN операция отклоняется как конфликт: состав целей этой команды изменить нельзя

#### Scenario: Передача владения в статусе «в работе»

- GIVEN цель принадлежит команде в статусе «в работе» и расшарена другой команде
- WHEN пользователь удаляет цель из представления команды-владельца
- THEN операция отклоняется как конфликт: цель ушла бы с доски команды-владельца

#### Scenario: Обновление прогресса в статусе «закрыт»

- GIVEN статус команды — «закрыт»
- WHEN пользователь обновляет прогресс ключевого результата
- THEN обновление сохраняется

#### Scenario: Комментирование в любом статусе

- GIVEN статус команды — «в работе» или «закрыт»
- WHEN пользователь добавляет замечание, отвечает на него или удаляет своё
- THEN операция выполняется

### Requirement: Серверное ограничение состава целей в статусах «в работе» и «закрыт»

Система SHALL отклонять как конфликт любую операцию, которая добавила бы цель на доску команды со
статусом «в работе» или «закрыт» либо убрала бы цель с её доски. Перечень таких операций и общее
правило описаны требованием «Инвариант неизменности состава целей команды».

#### Scenario: Создание цели в статусе «в работе»

- GIVEN статус команды в периоде — «в работе»
- WHEN пользователь создаёт цель для этой команды в этом периоде
- THEN операция отклоняется как конфликт, цель не создаётся

#### Scenario: Создание цели в статусе «закрыт»

- GIVEN статус команды в периоде — «закрыт»
- WHEN пользователь создаёт цель для этой команды в этом периоде
- THEN операция отклоняется как конфликт

#### Scenario: Удаление собственной цели в статусе «в работе»

- GIVEN статус команды — «в работе», цель принадлежит этой команде и никому не расшарена
- WHEN пользователь удаляет цель
- THEN операция отклоняется как конфликт

#### Scenario: Прямой запрос в обход интерфейса

- GIVEN интерфейс скрывает добавление цели при статусе «в работе»
- WHEN пользователь отправляет запрос на создание цели напрямую
- THEN сервер отклоняет его так же
