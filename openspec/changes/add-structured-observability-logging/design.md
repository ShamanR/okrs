## Context

Мотивация — см. `proposal.md` → «Why». Требования — см.
`specs/observability-logging/spec.md`.

Здесь фиксируются ограничения существующего кода, которые определяют подход:

- Логгер уже пронизывает всю сборку как `*slog.Logger`: создаётся
  в `cmd/server/main.go`, передаётся в `app.New`, оттуда в `httpserver.NewServer`,
  `eventbus.New` и в `common.Dependencies` обработчиков. Собственной абстракции
  логгера в проекте нет, и вводить её не требуется.
- Единственная существующая точка системного логирования — `AccessLogMiddleware`
  в `internal/auth/middleware.go`. Она уже оборачивает `http.ResponseWriter`
  в `responseWriter` со снятым статусом ответа.
- Ответы об ошибках пишут две свободные функции `WriteError` — в
  `internal/http/handlers/api/v1/errors.go` и в
  `internal/http/handlers/api/v1/admin/admincommon/admincommon.go`. У них порядка
  289 мест вызова, ни одно из них не имеет доступа ни к логгеру, ни к `context`.
  Менять сигнатуру на всех вызовах — неприемлемый по объёму и риску дифф.
- Доменных событий 21 тип, все реализуют `event.Event` (`Kind()` + `Context()`),
  список типов доступен через `event.AllKinds()`. Многие события несут
  пользовательский текст (`Title`, `Text`, `NoteBefore`, `GoalTitle`).
- `eventbus` уже поддерживает `SubscribeAll` и режим `Async` с ограниченным
  буфером и логированием потерь.
- Приложение работает в нескольких экземплярах в Kubernetes.

## Goals / Non-Goals

**Goals:**

- Один машиночитаемый поток логов в stdout с фиксированной схемой полей.
- Гарантированное покрытие ошибок и паник без правки сотен мест вызова.
- Автоматическое покрытие доменных событий, устойчивое к добавлению новых типов.
- Структурная, а не дисциплинарная, гарантия отсутствия пользовательского текста
  и секретов в логах.
- Возможность отката формата вывода без релиза кода.

**Non-Goals:**

- Метрики и трассировка (OpenTelemetry, Prometheus) — отдельная capability.
- Хранение, ротация, ретенция и сэмплирование логов — ответственность
  инфраструктуры.
- Аудит-журнал для пользователя: `activity-log` уже покрывает эту потребность
  и остаётся отдельной capability. Логи предназначены для эксплуатации,
  а не для продуктового отображения.
- Изменение состава и семантики доменных событий.

## Decisions

### Решение 1: `log/slog` + `slog.NewJSONHandler`, без новых зависимостей

Проект уже целиком построен на `log/slog`. Переход на `zap`/`zerolog` дал бы
выигрыш в аллокациях, но потребовал бы переписать все существующие вызовы
и ввести внешнюю зависимость ради нагрузки, которой у приложения нет.

Формат выбирается на старте: `json` → `slog.NewJSONHandler`,
`text` → `slog.NewTextHandler`. Состав атрибутов от формата не зависит.

### Решение 2: пакет `internal/platform/logging` как владелец схемы

Новый пакет платформенного слоя (рядом с `eventbus`, `entitlements`,
`secretbox`) владеет:

- сборкой `slog.Handler` из конфигурации;
- реестром констант поля `event` — стабильных машиночитаемых идентификаторов
  типов записей;
- редактирующим `ReplaceAttr`;
- контекстными хелперами (`WithRequestID`, `WithScope`, `FromContext`).

Пакет не зависит ни от `http`, ни от `usecase`, ни от `store`, поэтому
его может использовать любой слой без протекания абстракций. Транспортным
типом логгера остаётся `*slog.Logger` — вводить собственный интерфейс поверх
stdlib незачем.

Конфигурация читается **только** в `cmd/server/main.go` (composition root)
и передаётся в `app.Config`. `app.New` не читает окружение — это сохраняет
существующее свойство сборки: `app` собирается тестом без переменных среды.

### Решение 3: контекст добавляется в запись обработчиком, а не вызывающим кодом

`slog.Handler.Handle` получает `context.Context`. Поэтому `logging` оборачивает
базовый handler в `contextHandler`, который на каждой записи достаёт из `ctx`
`request_id`, `tenant_id`, `actor_id`, `team_id`, `period_id` и добавляет их
в запись.

Альтернатива — прокидывать обогащённый `*slog.Logger` через все слои —
отвергнута: она требует менять сигнатуры сервисов и хранилищ ради сквозной
заботы, то есть ровно то протекание, которого архитектура избегает.

Цена решения: поля появляются только у вызовов с контекстом
(`InfoContext`/`WarnContext`/`ErrorContext`). Существующие вызовы без контекста
в слоях `http` и `usecase` переводятся на контекстные варианты в рамках
этого change; вызовы без доступного `ctx` (lifecycle в `main.go`) остаются
как есть — им контекст запроса и не нужен.

### Решение 4: ошибка попадает в лог через writer, а не через сигнатуру `WriteError`

Ключевое ограничение — 289 мест вызова `WriteError` без доступа к логгеру.

Обёртка ответа, создаваемая middleware, реализует интерфейс

```
interface { RecordError(code string, cause error) }
```

`WriteError` делает type assertion переданного `http.ResponseWriter`
на этот интерфейс и, если он выполнен, записывает в обёртку код и причину.
Сигнатура `WriteError` **не меняется**, ни один из 289 вызовов не правится.
Для 5xx добавляется дополнительная форма записи ошибки, принимающая `error`
целиком, — она применяется точечно там, где сейчас в ответ уходит
`err.Error()`.

Итоговую запись пишет middleware — одну на запрос, с уровнем по статусу
(2xx/3xx → `info`, 4xx → `warn`, 5xx → `error`) и с кодом и причиной из
обёртки, если они были записаны. Это одновременно даёт требование
«каждая ошибка оставляет след» и требование «ровно одна запись на ошибку»:
запись физически одна, дублировать её неоткуда.

Альтернативы отвергнуты:

- добавить `ctx`/логгер в `WriteError` — 289 правок, высокий риск, нулевая
  архитектурная выгода;
- логировать в каждом слое — не даёт гарантии покрытия и порождает дубли
  одной ошибки на каждом уровне.

Побочное следствие: техническая причина уходит в лог, а не в тело ответа —
это закрывает существующую утечку `err.Error()` наружу в
`admincommon.WriteError`.

### Решение 5: access-логирование переезжает в `internal/http/middleware`

`AccessLogMiddleware` и `responseWriter` переносятся из `internal/auth`
в `internal/http/middleware` (там уже живёт CSRF). Логирование запроса —
не забота аутентификации, а теперь обёртка ответа ещё и несёт error sink
из решения 4, что делает соседство с `auth` окончательно неуместным.
Blast radius переноса мал: одна точка монтирования в `Server.Routes`
и тесты.

Порядок цепочки middleware:

```
RequestID → AccessLog(+error sink) → Recovery → Session → …
```

`Recovery` стоит **внутри** `AccessLog` намеренно: он превращает панику
в ответ 500, и внешний `AccessLog` видит статус 500 и пишет обычную запись
о завершении запроса. Обратный порядок оставил бы панику без записи
о запросе. Паника при этом даёт две записи разных типов — `http_panic`
со стеком и `http_request` со статусом 500; это разные события, а не дубль
одной ошибки.

Собственный recovery, а не `chi/middleware.Recoverer`: последний печатает
неструктурированный многострочный дамп напрямую в stdout, что ломает
построчный JSON.

### Решение 6: `request_id` — принять или сгенерировать, с валидацией

Заголовок `X-Request-Id`. Входящее значение принимается, только если оно
проходит валидацию (ограниченная длина и ограниченный набор символов);
иначе генерируется новое. Без валидации внешний клиент мог бы подставить
многострочное значение (порча JSON-строки и подделка соседних записей)
или значение неограниченной кардинальности.

Идентификатор кладётся в `context` и возвращается клиенту тем же заголовком —
пользователь может сообщить его в обращении, и по нему находится вся цепочка.

### Решение 7: доменные события логируются рефлексией с allowlist по типам полей

Подписка — `eventbus.SubscribeAll(bus, "logging", …)` в режиме `Async`.
Один подписчик покрывает все 22 типа и любой будущий, что и требует
спецификация.

Проблема: интерфейс `event.Event` даёт только `Kind()` и `Context()`,
идентификаторов сущностей в нём нет. Расширять интерфейс методом
`LogAttrs()` — значит обязать автора каждого нового типа не забыть его
реализовать; ровно та ручная доработка, которую требование запрещает.

Поэтому поля события извлекаются рефлексией по **allowlist типов**:
в лог попадают поля типов `int64`, `*int64`, `[]int64`, `bool`, `time.Time`
и именованных типов с базовым числовым/булевым представлением. Поля
строковых типов **не логируются никогда**, если не помечены тегом
`log:"safe"` (для служебных строк вроде списка изменённых имён полей).

Это структурная, а не дисциплинарная гарантия: чтобы пользовательский текст
попал в лог, автору нового события пришлось бы сознательно поставить тег.
Забывчивость приводит к недологированию, а не к утечке — правильное
направление отказа.

Дескрипторы полей строятся один раз на `reflect.Type` и кешируются
в `sync.Map`, так что рефлексия не выполняется на каждое событие.
Подписчик асинхронный, вне пути запроса.

Гард: тест проходит по `event.AllKinds()`, заполняет каждое строковое поле
уникальным маркером и проверяет, что ни один маркер не встречается
в результирующей записи.

### Решение 8: подписчик логирования не обращается к базе данных

Подписчик логирует только то, что уже лежит в событии. Обогащение события
названиями сущностей из БД дало бы запрос на каждое событие — то есть
N+1 на пути каждой мутации, и вдобавок нарушило бы запрет на пользовательский
текст в логах. Сопоставление идентификаторов с названиями — задача
исследователя инцидента, а не приложения.

### Решение 9: редакция — денайлист ключей в `ReplaceAttr`

`ReplaceAttr` базового handler'а заменяет значение на фиксированную маску,
если ключ атрибута совпадает с ключом из денайлиста (`password`, `token`,
`secret`, `authorization`, `cookie`, `api_key`, `email`, `webhook_url`
и производные). Проверка идёт по нормализованному имени ключа, поэтому
`user_email` и `Email` перекрываются одним правилом.

Это последний рубеж, а не единственный: основная защита — не передавать такие
значения в логгер вовсе. `ReplaceAttr` ловит то, что просочилось.

Секретные значения настроек уведомлений уже маскируются в API
(`NoSecretKeyMessage`, маска в форме) — правило редакции распространяет
ту же политику на логи.

Гард: тест на набор атрибутов с денайлист-ключами проверяет, что исходные
значения отсутствуют в выводе.

### Решение 10: реестр констант поля `event`

Значения поля `event` — константы в `logging`, а не литералы по месту:
`http_request`, `http_panic`, `domain_event`, `auth_login`, `auth_logout`,
`auth_failed`, `authz_denied`, `access_changed`, `app_start`, `app_ready`,
`app_shutdown`, `migration`, `background_task`, `external_call`,
`event_dropped`, `config_invalid`.

Дашборды и алерты в Kibana строятся на этих значениях, поэтому они —
внешний контракт: переименование ломает потребителя так же, как
переименование поля API.

## Risks / Trade-offs

- **Смена формата ломает существующий разбор в Logstash** → до выката
  приложения конфигурация collector'а переводится на разбор JSON; откат
  выполняется переменной окружения `LOG_FORMAT=text` без релиза кода
  (см. Migration Plan).

- **Рост объёма логов: 22 типа доменных событий на уровне `info`** → объём
  ограничен сверху числом мутаций, а не числом запросов (чтения событий
  не порождают). При необходимости уровень доменных событий понижается
  до `debug` одной константой; предпочтение отдано полноте, потому что
  именно потерянная история мутаций делает расследование невозможным.

- **Рефлексия на пути публикации события** → дескрипторы кешируются по типу,
  подписчик асинхронный и не блокирует публикацию. При переполнении буфера
  событие теряется и это фиксируется существующим механизмом `Dropped()`
  плюс записью `event_dropped`.

- **Контекстные поля появляются только у `*Context`-вызовов** → вызовы
  в слоях `http` и `usecase` переводятся на контекстные варианты в рамках
  change; для остальных отсутствие `request_id` не является ошибкой,
  так как они происходят вне запроса.

- **Перенос `AccessLogMiddleware` из `internal/auth`** → это экспортированный
  символ; поиск использований показывает одну точку монтирования и тесты.
  Риск ограничен компиляцией, которая обнаружит любое пропущенное место.

- **Type assertion в `WriteError` молча ничего не делает вне цепочки
  middleware** → в юнит-тесте обработчика с голым `httptest.ResponseRecorder`
  запись об ошибке не создаётся. Это приемлемо (тест обработчика проверяет
  ответ, а не логи), но покрывается отдельным тестом на связку
  middleware + обработчик, чтобы регресс в цепочке не остался незамеченным.

## Migration Plan

1. Согласовать и выкатить конфигурацию сбора логов, разбирающую JSON
   (`json` codec/filter вместо `grok` по текстовой строке). До выката
   приложения этот шаг безвреден: текстовые строки просто не разберутся
   новым правилом так же, как не разбирались бы старым JSON.
2. Выкатить приложение. Значение `LOG_FORMAT` по умолчанию — `json`.
3. Проверить в Kibana: наличие обязательных полей, поиск по `request_id`,
   наличие записей уровня `error` при искусственной ошибке.
4. Откат при проблеме с разбором: выставить `LOG_FORMAT=text` в окружении
   и перезапустить pod'ы — код не откатывается. Полный откат кода нужен
   только при дефекте самого приложения.

Схема базы данных не меняется, миграций и обновления seed demo не требуется.

## Open Questions

- Источник значений полей `service` и `env`: отдельные переменные окружения
  приложения или метки, проставляемые collector'ом из метаданных Kubernetes.
  Вопрос не влияет ни на спецификацию (поля обязаны присутствовать
  в конечной записи), ни на структуру задач; решается при подготовке
  манифеста развёртывания.
