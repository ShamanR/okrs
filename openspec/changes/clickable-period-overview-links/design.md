## Context

Мотивация — см. `proposal.md` → «Why». Требования — см. `specs/period-overview/spec.md`.

Существующее состояние, важное для подхода:

- `PeriodOverviewContent` (`web/static/period_overview_view.js`) — общий презентационный
  компонент. Его используют оба потребителя: страница `/period-overview`
  (`web/static/period-overview.js`) и модальное окно администрирования
  (`PeriodOverviewModal` в `web/static/admin.js`). Правка в одном месте покрывает оба.
- Оба shell-шаблона (`period_overview_shell.html`, `admin_shell.html`) уже подключают
  `web/static/ui.js` раньше `period_overview_view.js`, поэтому `buildTargetURL` доступен
  без изменения шаблонов.
- `buildTargetURL(target)` (`web/static/ui.js`) — уже существующий и единственный в проекте
  конструктор адреса доски целей из `{team_id, period_id, goal_id, kr_id, comment_id}`.
  На нём построены переход из журнала активностей (`EventRow`) и копирование ссылки на цель
  в трекере. Разбор этих параметров на стороне доски целей уже реализован.
- `computePeriodOverview` (`internal/usecase/period/overview.go`) — чистая функция без
  ввода-вывода. Она получает уже собранный `hcsvc.PeriodData` из кеша и агрегирует его в
  памяти.
- Ответ обзора уже содержит `period_id`, `teams[].id` и `goals[].team_id` — для переходов к
  команде и к цели новых полей не требуется. Не хватает только связей у ключевых
  результатов.

## Goals / Non-Goals

**Goals:**

- Переход к сущности строится на существующем `buildTargetURL`, без второго способа
  формировать адрес доски целей.
- Привязка цели к команде становится детерминированной и не выходит за охват.
- Изменение остаётся аддитивным по контракту API.

**Non-Goals:**

- Не меняется контракт доски целей и разбор параметров адреса на её стороне.
- Не вводится переход из плиток и полос балансов напрямую — точкой перехода остаётся строка
  раскрытого состава.
- Не пересматривается набор полей `PeriodGoalItem` и `PeriodTeamSummary` — они уже достаточны.
- Не меняются схема базы данных, миграции и demo-данные.

## Decisions

### Решение 1: детерминированный выбор команды с приоритетом владельца

`computePeriodOverview` обходит команды по `map[int64]domain.Team`, а цель дедуплицируется по
первому вхождению. Порядок обхода map в Go не определён, поэтому для общей цели команда
выбирается случайно от запроса к запросу.

Правило выбора команды цели:

1. если команда-владелец цели (`domain.Goal.TeamID`) входит в охват — берётся она;
2. иначе берётся первая по возрастанию идентификатора команда охвата, содержащая эту цель.

Для этого обход команд ведётся по отсортированному срезу идентификаторов, а не по map.

Приоритет владельца выбран потому, что доска команды-владельца — каноническое место цели:
там она доступна к редактированию, а не только к просмотру. Откат на команду охвата нужен для
случая, когда владелец вне охвата: правило «переход ведёт только в доступную команду» уже
зафиксировано для журнала активностей, и обзор не должен вести себя иначе.

Альтернативы:

- *Оставить первое вхождение, но сделать обход детерминированным.* Дешевле, но переход для
  общей цели уводил бы в произвольную команду-участника вместо владельца — пользователь
  попадал бы не туда, где цель редактируется.
- *Отдавать клиенту список всех команд цели и выбирать на клиенте.* Раздувает ответ и
  переносит правило доступа в презентационный слой.

Побочный эффект: рядом с общей целью в детализации перестаёт «мигать» название команды.

### Решение 2: `PeriodKRItem` дополняется `GoalID` и `TeamID`

Сейчас ключевой результат отдаётся только названиями цели и команды — по ним переход не
построить. Добавляются `goal_id` и `team_id`.

`TeamID` ключевого результата — та же команда, что выбрана для его цели по решению 1, чтобы
переход к ключевому результату и переход к его цели вели на одну доску.

Данные берутся из уже загруженного `PeriodData` в том же проходе цикла — новых обращений к
базе данных не появляется, N+1 не возникает.

Альтернатива — отдельная ручка «разрешить ключевой результат в адрес» — отклонена: это
дополнительный round-trip на каждый клик ради двух чисел, которые уже есть в памяти.

### Решение 3: кеш не затрагивается

`hcsvc.Cache` хранит `PeriodData` — доменные данные, а не сериализованный обзор.
`computePeriodOverview` выполняется на каждый запрос поверх этих данных. Поэтому новые поля
появляются сразу после выката, устаревших ответов в multi-instance развёртывании быть не
может, инвалидация кеша не нужна.

### Решение 4: переход как обычная ссылка в новом окне

Строка состава рендерится как `<a href={buildTargetURL(...)} target="_blank" rel="noopener">`,
а не как обработчик клика с программным открытием окна. Причины:

- обычная ссылка не блокируется как всплывающее окно;
- работают привычные средства браузера: открыть в фоне, скопировать адрес, средняя кнопка;
- ссылка доступна с клавиатуры и для программ чтения с экрана без дополнительной разметки.

`rel="noopener"` обязателен: без него открытая вкладка получает доступ к `window.opener`.

Оформление переходов делается одним локальным компонентом строки внутри
`period_overview_view.js`, переиспользуемым всеми тремя списками, — чтобы три списка не
разъехались по виду и поведению. Компонент остаётся в файле общего представления обзора, то
есть автоматически одинаков для страницы и для модального окна администрирования.

Если для строки адрес построить не удалось (нет идентификаторов), она рендерится как обычный
текст, как сейчас, — без «мёртвой» ссылки.

### Решение 5: границы слоёв

Правило выбора команды — доменная логика охвата и принадлежности, поэтому живёт в
`internal/usecase/period`. Клиент получает готовый `team_id` и не восстанавливает связь по
названиям. Презентационный слой знает только, как собрать адрес из идентификаторов
(`buildTargetURL`), и не знает правил доступа.

## Risks / Trade-offs

- **Переход ведёт на доску команды, где у пользователя нет прав на изменение** (охват «мои
  команды» как руководителя вышестоящей команды) → Ожидаемо: доска сама применяет свои
  правила доступа и режим только для чтения. Обзор не расширяет права, он лишь сокращает путь.
- **Смена команды у общей цели после выката** — та же цель может показать другое название
  команды, чем показывала до изменения → Разовое и в сторону предсказуемости: новое значение
  стабильно, старое было случайным. Пользовательских данных не затрагивает.
- **Много открытых вкладок при разборе большого списка** → Осознанный размен: не уводить
  пользователя из обзора важнее, это и есть исходная задача. Ссылка обычная, поэтому пользователь
  может открыть её и в текущей вкладке средствами браузера.
- **Строка состава становится и кликабельной, и обрезаемой по ширине** → Полный текст
  остаётся доступен через `title`, поведение обрезки не меняется.
- **Расхождение с уже существующей пустой заготовкой изменения**
  `openspec/changes/add-overview-drilldown-deep-links` (каталог `specs/period-overview` без
  файлов) → Заготовка не содержит артефактов и ни на что не влияет; её удаление вынесено в
  задачи как отдельный шаг для решения пользователя.
