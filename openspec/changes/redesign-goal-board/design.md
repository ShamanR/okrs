## Context

Мотивация — см. `proposal.md`, раздел «Why». Требования — см. дельты
`specs/team-okr-board/spec.md` и `specs/team-period-lifecycle/spec.md`.

Что важно знать о текущем состоянии:

- Доска целиком живёт в `web/static/tracker.js`: `GoalCard` рисует карточку, `KRRow` — строку
  ключевого результата, `StatusStepper` — переключатель статусов. Это клиентский React без
  сборки: JSX транспилируется в браузере, модулей нет, компоненты видны друг другу как глобальные
  функции.
- Режим редактирования выводится из статуса одной строкой в `App`: `editMode` принимает значения
  `full`, `progress_only`, `comments_only`. Компоненты получают его пропом и сами решают, что
  рисовать. Сейчас решение всегда одно и то же — «не рисовать».
- Оформление вынесено в классы `web/static/*.css` (`goal-card__*`, `kr-*`, `status-stepper__*`),
  но не полностью: кнопка «Обновить прогресс» в `KRRow` и часть цветов здоровья заданы
  инлайновыми стилями прямо в JSX.
- `truncate-goal-kr-descriptions` уже ввёл `CollapsibleMarkdown` для описаний цели и ключевого
  результата. Этот механизм сохраняется без изменений.

Серверная часть, контракты API и данные не затрагиваются: всё изменение — в представлении.

## Goals / Non-Goals

**Goals:**

- Уменьшить вертикальный размер карточки цели так, чтобы цель вместе со своими ключевыми
  результатами читалась без раскрытия и без прокрутки на типичной цели.
- Свести редактирование к одному элементу управления, одинаковому у цели и у ключевого результата.
- Сделать блокировку по статусу видимой в точке действия, а не только вверху страницы.
- Довести оформление доски до классов CSS: убрать инлайновые стили из `GoalCard` и `KRRow`, чтобы
  дизайн-система описывала фактический вид.

**Non-Goals:**

- Не меняем состав данных цели и ключевого результата, правила расчёта прогресса, здоровья,
  прогноза и порогов.
- Не меняем серверные ограничения по статусу — это предмет `enforce-structural-edit-lock`.
- Не трогаем сводку по дочерним командам, дерево команд, селектор периода, обзор периода и
  экспорт.
- Не переводим доску на сборку/бандлер и не вводим новых зависимостей.
- Не вводим вид «список-таблица с панелью деталей»: он рассматривался и отклонён (см. Decisions).

## Decisions

### Решение 1. Компактная карточка, а не список с панелью деталей

Рассматривались три формы доски: компактная карточка с ключевыми результатами внутри,
плотный список строк с боковой панелью деталей, и косметическая чистка текущей карточки.

Выбрана компактная карточка. Список с панелью деталей даёт больше целей на экран, но прячет
ключевые результаты за клик — то есть меняет один способ «раскрыть скрытое» на другой, а именно
это и названо проблемой. Кроме того, панель деталей — новый крупный компонент навигации, который
пришлось бы согласовывать с глубокими ссылками (`?goal/kr/comment`), перетаскиванием для
переупорядочивания и сводкой по дочерним командам. Косметическая чистка не решает главного:
ключевые результаты остаются свёрнутыми.

Плотность достигается схлопыванием, а не сокрытием:

- метаданные (приоритет, вес, тип работы, фокус, драйверы, признак общей цели, ссылки на связи,
  копирование ссылки, экспорт) — одна строка вместо трёх;
- прогресс — одна строка: процент, индикатор здоровья, прогноз, давность обновления; под ней
  полоса прогресса с отметкой ожидаемого темпа;
- ключевые результаты — сразу под карточкой цели, без переключателя;
- раскрываемым остаётся только обсуждение (и длинные описания — механизмом из
  `truncate-goal-kr-descriptions`).

### Решение 2. Дублирующие сигналы схлопываются в один элемент каждый

Свежесть сейчас нарисована дважды: бейдж «⚠ Nд без обновлений» в строке метаданных и строка
«Обновлено: Nд назад» в блоке прогресса. Они не противоречат друг другу, но занимают два места.

Остаётся один элемент давности обновления в строке прогресса. Он показывает давность всегда, а
при выполнении условий требования «Предупреждение „нет обновлений“ на карточке цели» принимает
вид предупреждения с числом дней. Так существующее требование остаётся выполненным: предупреждение
с числом дней по-прежнему есть — оно просто не отдельный второй элемент.

Здоровье сейчас нарисовано четырьмя способами: цвет процента, текстовый бейдж, цвет полосы,
отдельная строка «прогноз N%». Остаётся один текстовый индикатор; цвет процента и полосы
вычисляется из него же (источник — существующая `healthOf`), а прогноз переезжает в ту же строку.

Альтернатива «оставить только цвет, убрать текст» отклонена: цвет один не различает «отстаёт» и
«нет обновлений» и недоступен при нарушениях цветовосприятия.

### Решение 3. Единый компонент иконочной кнопки действия

Вводится один переиспользуемый компонент кнопки-иконки — назовём его `IconButton` — с
обязательной текстовой подписью действия (`title` и `aria-label`), опциональным признаком
блокировки и причиной блокировки.

Через него выражаются: редактирование цели, удаление цели, редактирование ключевого результата,
обновление прогресса ключевого результата, удаление ключевого результата, заметка ключевого
результата. Вариант с текстовой кнопкой везде отклонён: в строке ключевого результата текст
«Редактировать» съедает ширину, которая нужна под название и прогресс, а строк на экране — десятки.
Вариант «кнопки только при наведении» отклонён: на тач-устройствах действие становится
ненаходимым, а при беглом просмотре доски пользователь не видит, что вообще можно сделать.

Иконки различаются по действию: ✎ — редактировать, ↑ — обновить прогресс, × — удалить,
📝 — заметка. Позиция в строке фиксирована, порядок одинаковый у цели и у ключевого результата.

Заголовок цели перестаёт быть кнопкой. Это осознанная потеря удобной крупной цели для клика: взамен
исчезает неоднозначность «заголовок то кликабельный, то нет» в зависимости от статуса, из-за
которой связь статуса и редактирования и была неочевидной.

### Решение 4. Блокировка показывается на элементе, объясняется в баннере

Раньше `editMode` управлял тем, рисовать ли элемент. Теперь он управляет тем, в каком виде его
рисовать. Вместо разбросанных по компонентам проверок `editMode === 'full'` вводится одна функция,
которая по режиму и виду действия возвращает его доступность и причину блокировки — единственное
место, где знание «что при каком статусе можно» записано в интерфейсе.

Двухуровневое объяснение:

- в точке действия — признак блокировки на кнопке и подсказка с причиной по наведению и по
  фокусу с клавиатуры («Изменить состав целей нельзя: команда в статусе „В работе“»);
- над списком целей — баннер под переключателем статусов, описывающий режим целиком: что
  доступно, что заблокировано и каким статусом.

Баннер не показывается в режиме полного редактирования: там объяснять нечего, а постоянный баннер
на самом частом экране — шум.

Перечень действий, блокируемых в интерфейсе, держим согласованным с серверным перечнем из
`enforce-structural-edit-lock`. Интерфейс при этом не становится источником правды: он объясняет
правило, а обеспечивает его сервер.

### Решение 5. Оформление переносится в CSS

Инлайновые стили из `KRRow` (кнопка обновления прогресса) и `GoalCard` (цвета здоровья) заменяются
классами с CSS-переменной цвета здоровья, выставляемой на карточке. Это условие того, чтобы
карточки дизайн-системы, которые инлайнят реальные `web/static/*.css`, показывали фактический вид,
а не приблизительный.

## Интерфейс

Затрагиваемые компоненты дизайн-системы (`design-system/src/cards/`):

| карточка | что происходит |
| --- | --- |
| `goal-card.html` | переверстывается: метаданные в одну строку, строка прогресса, KR внутри |
| `kr-row.html` | переверстывается: единый блок действий справа |
| `buttons.html` | добавляется иконочная кнопка действия и её заблокированное состояние |
| `banners-warnings.html` | добавляется баннер режима редактирования |
| `badges.html` | сверяется: индикатор здоровья и элемент давности обновления |

В прототипе (`design-system/prototype/`) затрагивается экран доски целей: карточка цели, строка
ключевого результата, область под переключателем статусов. Вид согласуется на прототипе **до**
реализации — прототип собран на реальном CSS и не расходится со стилями приложения. Состояния,
которые нужно показать на прототипе: полное редактирование, «в работе» (заблокирован состав
целей), «закрыт» (только комментарии).

## Risks / Trade-offs

- **Карточка со многими ключевыми результатами станет длиннее, чем сейчас в свёрнутом виде.**
  Цель с 8–10 ключевыми результатами займёт больше вертикали, чем сегодняшняя свёрнутая карточка.
  → Схлопывание метаданных, свежести, здоровья и футера отыгрывает около половины высоты карточки
  цели; строка ключевого результата тоже уплотняется. Проверяем на реальных данных: сравниваем
  высоту доски до и после на команде с типичным и с максимальным числом ключевых результатов.

- **Заблокированные кнопки вместо их отсутствия делают доску визуально шумнее в статусах
  «в работе» и «закрыт».** → Заблокированный вид приглушённый и без рамки; баннер объясняет режим
  один раз сверху, так что подсказка на кнопке нужна только при целенаправленной проверке.

- **Потеря клика по заголовку цели — регресс для тех, кто к нему привык.** → Принято осознанно
  (Решение 3). Иконка редактирования стоит в той же строке заголовка, в предсказуемом месте.

- **Глубокие ссылки `?goal/kr/comment` опираются на автораскрытие блока ключевых результатов.**
  Блока-переключателя больше нет. → Ветка автораскрытия для ключевого результата становится
  ненужной и удаляется; прокрутка к цели и к ключевому результату сохраняется, автораскрытие
  обсуждения по ссылке на комментарий сохраняется. Покрываем тестом на переход по ссылке на
  ключевой результат.

- **Перетаскивание для переупорядочивания ключевых результатов работало внутри раскрытого блока.**
  → Механика перетаскивания сохраняется на строке ключевого результата; проверяем, что новая
  область действий справа не перехватывает начало перетаскивания (для этого уже есть механизм
  `data-no-drag`).

- **Дизайн-система разойдётся с приложением, если её не обновить.** → Обновление карточек и
  прототипа внесено в `tasks.md` отдельными пунктами: согласование вида — до реализации,
  обновление карточек — после.

## Migration Plan

Выкладка обычная: изменение целиком клиентское, без миграций БД и без изменения контрактов.
Откат — возврат предыдущей версии статики. Состояния, сохраняемые в браузере (место работы,
раскрытие дерева), не затрагиваются: карточка цели своего состояния между сеансами не хранила и
не начинает.
