# Дизайн: ясность измерения ключевого результата

## Контекст

Числовая мера ключевого результата лежит колонками на `key_results`: `start_value`,
`target_value`, `current_value`, `unit`, `checkpoints` (с `migrations/023`, до этого были
отдельные таблицы `kr_percent_meta` / `kr_linear_meta`). Все три числовые колонки допускают
`NULL`, и каждое место чтения само превращает `NULL` в 0:

- `internal/store/krs/krs.go::scanNumerical` — для `ListKeyResultsByGoal` и `GetKeyResult`;
- `internal/store/goals/goals.go::loadKRsForGoals` — та же разборка, выписанная заново;
- `internal/store/goals/goals.go::ListGoalsByTeamsPeriod` — и там же ещё раз.

Домен (`domain.KRNumerical`) держит `CurrentValue float64` — без признака «значения нет».
Признак «прогресс ни разу не обновляли» в системе уже есть и доходит до API отдельным полем:
`progress_updated_at` (`internal/http/dto/kr.go`), который двигает только чек-ин.

Писать текущее значение умеют три места:

- `UpsertNumericalMeta` — при создании и при каждом сохранении определения результата;
- `updateNumericalCurrent` / `ApplyCheckIn` — чек-ин (он же ставит `progress_updated_at`);
- `CopyGoal` — копирование и перенос цели.

## Решение 1. `NULL` означает «прогресс ещё не обновляли», чтение склеивает со стартом

Отсутствие текущего значения выражается `NULL` в `current_value` — колонка это уже допускает,
новых полей и таблиц не нужно. Наружу `NULL` не отдаётся: на границе хранилища действует
правило `current_value ?? start_value`.

Почему склейка именно на границе хранилища, а не в домене или в DTO:

- `domain.KRNumerical.CurrentValue` остаётся `float64`, и ни один расчёт не узнаёт о `NULL`.
  Сделать поле `*float64` означало бы протащить необязательность через `progress.NumericalProgress`,
  `progress.ForKR`, health-статус, выгрузку в Markdown и рендеринг уведомлений — везде с одним
  и тем же `?? start`;
- правило оказывается в одном месте, а не в DTO-мэппере каждого эндпоинта (их несколько: доска
  команды, дерево целей, обзор периода, выгрузка);
- расчёт прогресса сохраняет сегодняшнее поведение: `current == start` даёт 0% в линейном
  случае и 0% по шагам (ни одна отметка не пройдена).

Известное следствие, которое изменение не трогает: у результата с совпадающими стартом и целью
прогресс равен 100% («100, если цель достигнута, иначе 0» — `progress-tracking`), и это так же
верно до первого чек-ина, как и сейчас. Поведение не меняется, потому что и сейчас
`current == start == target`.

Признак «прогресс не обновляли» для интерфейса остаётся один — `progress_updated_at`. Второго
(например, `current_value: null` в ответе) не вводим: два источника одной истины расходятся,
а `progress_updated_at` уже используется фронтендом (`mapKR` → `progressDaysAgo`).

## Решение 2. Общая разборка числовой меры вместо трёх копий

`scanNumerical` становится экспортируемой функцией пакета `store/krs` и единственным местом,
где nullable-колонки превращаются в `domain.KRNumerical` — вместе с правилом склейки.
`loadKRsForGoals` и `ListGoalsByTeamsPeriod` переходят на неё; пакет `store/goals` уже
импортирует `store/krs` (использует `krs.ParseCheckpoints`), новой зависимости между слоями не
появляется.

Без этого правило `?? start_value` пришлось бы написать в трёх местах, и самое заметное из них
— доска команды (`loadKRsForGoals`, тот самый `GET /api/v1/teams/{teamID}/okrs` из дефекта).

Порядок внутри функции важен: старт присваивается до текущего, иначе склейка возьмёт ноль.

## Решение 3. Текущее значение уходит из определения результата

`NumericalMetaInput.CurrentValue` и `MetaInput.NumericalCurrent` убираются,
`UpsertNumericalMeta` перестаёт упоминать `current_value` в `UPDATE`. Следствия:

- при создании колонка остаётся `NULL` — ровно то, что нужно решению 1;
- при сохранении определения текущее значение не трогается — ни у нового результата, ни у
  того, где прогресс уже обновляли. Это вторая половина дефекта: сейчас редактор перезаписывает
  `current_value` при каждом сохранении, и значение переживает правку только потому, что
  клиент возвращает его обратно нетронутым;
- `numerical_current` уходит из `ParseNumericalMeta` и из `save` в `KREditModal`.

Альтернатива — оставить поле необязательным (`*float64`: `nil` значит «не менять») — отвергнута:
единственный сценарий, где текущее значение приходило в этих операциях, это копия старта при
создании, то есть ровно то, от чего избавляемся. Возможность задать прогресс в обход чек-ина
не нужна и противоречит уже зафиксированному требованию «Окно обновления прогресса не меняет
определение результата» в его обратную сторону.

Переданное `numerical_current` игнорируется, а не отклоняется ошибкой: разбор формы просто
перестаёт читать поле. Отклонять нечего — поля с таким смыслом в контракте больше нет.

## Решение 4. Копирование цели без прогресса пишет `NULL`

`CopyGoal` при `with_progress=false` сейчас пишет `current_value = start_value` («reset →
start»). После изменения пишет `NULL` — скопированный результат должен быть неотличим от
только что созданного, в том числе в том, что правка старта потянет за собой текущее значение.
При `with_progress=true` значение переносится как есть, включая `NULL`.

Читаемое значение при этом не меняется: и до, и после копирования без прогресса оно равно
старту.

## Решение 5. Миграция существующих строк с behaviour-preserving предикатом

```sql
UPDATE key_results
SET current_value = NULL
WHERE kind = 'NUMERICAL'
  AND progress_updated_at IS NULL
  AND current_value IS NOT NULL
  AND start_value IS NOT NULL
  AND current_value = start_value;
```

Оба условия нужны:

- `progress_updated_at IS NULL` — прогресс ни разу не обновляли. Одного этого условия мало:
  `progress_updated_at` появился позже числовых колонок, и у результата, прогресс которого
  обновляли до его появления, он может быть пустым при настоящем текущем значении;
- `current_value = start_value` — страховка от этого случая. Если значения равны, склейка
  вернёт то же число, поэтому миграция не меняет ни одного читаемого значения, ни одного
  процента прогресса и ни одного health-статуса. Меняется только то, что последующая правка
  старта теперь потянет за собой текущее значение.

Строки, где прогресс обновляли или где текущее значение отличается от стартового, не
затрагиваются.

Обратная миграция возвращает прежнее представление:

```sql
UPDATE key_results
SET current_value = start_value
WHERE kind = 'NUMERICAL' AND current_value IS NULL AND start_value IS NOT NULL;
```

Она переписывает и те строки, которые были созданы уже после изменения, — это и есть прежнее
поведение: до этого изменения `current_value` у числового результата всегда было заполнено.

`seed_demo.sql` приводится к тому же виду: у демонстрационных результатов, которые по сценарию
ещё не обновляли, `current_value` пустое. Демо-данные должны воспроизводить состояние, которое
получит пользователь, создав результат руками.

## Решение 6. Подсказка деталей измерения на существующем механизме

Используется уже работающий на доске механизм `.has-tip`: `data-tip-title` + `data-tip`,
раскрытие чистым CSS через `::after` с `content: attr(data-tip-title) "\A" attr(data-tip)` и
`white-space: pre-line`, срабатывает по `:hover` и по `:focus`. Тем же механизмом подписаны вес
цели и вес ключевого результата. Новый компонент подсказки не вводится: второй механизм на
той же доске разойдётся с первым по виду и по поведению с клавиатурой.

Два ограничения механизма определяют разметку:

- **подсказка вешается на колонку, а не на само значение.** У `.kr-target__val` стоит
  `overflow: hidden` для многоточия — абсолютно позиционированная подсказка внутри него
  обрезалась бы. Носителем `.has-tip` становится обёртка в `.kr-target-col`, как это уже
  сделано для `.kr-weight-chip`;
- **содержимое подсказки — текст в атрибуте.** Переносы строк задаются `\n` (атрибут +
  `pre-line`), разметки внутри подсказки быть не может. Отметки выполнения шагов поэтому
  текстовые символы (`✓` / `·`), а не элементы.

Содержимое по типам:

| Тип | Заголовок | Тело |
| --- | --- | --- |
| Метрика | `Метрика · повысить` либо `Метрика · снизить` | `Было: <старт> <ед.>`, `Стало: <текущее> <ед.>`, `Цель: <цель> <ед.>` |
| Проектный | `Шаги проекта · <закрыто> из <всего>` | по строке на шаг: `✓ <название> · <вес>%` либо `· <название> · <вес>%` |
| Бинарный | `Достижение · да или нет` | `Сейчас: не выполнено` либо `Сейчас: выполнено`, `Цель: выполнено` |

Направление метрики берётся оттуда же, откуда стрелка в свёрнутой подписи: `target >= start` —
«повысить», иначе «снизить». Слово и стрелка не могут разойтись, потому что считаются из одного
выражения.

Три решения о содержимом сверх буквального «было · стало · цель»:

1. **Если прогресс ни разу не обновляли, это сказано строкой** — `Стало: <старт> <ед.>
   (прогресс ещё не обновляли)`. Без этого «Было: 100 · Стало: 100» у нового результата
   читается как тот же сбой, от которого избавляется часть 1. Признак — `progressDaysAgo ===
   null` в `mapKR`, то есть `progress_updated_at` из ответа.
2. **Промежуточные значения метрики перечисляются** строкой на значение — `<значение> <ед.> →
   <процент>% прогресса` — и подсказка заканчивается строкой о нелинейности. Это выходит за
   буквальную формулировку задачи, но именно у таких результатов свёрнутая подпись и процент
   прогресса выглядят противоречиво («↑ 120 → 200» при 60%), а объяснение сейчас доступно
   только в окне обновления прогресса. Формулировка о нелинейности берётся той же, что уже
   принята для шкалы в требовании «Шкала прогресса с промежуточными значениями».
3. **Длинные перечисления ограничиваются.** Подсказка `.has-tip` не прокручивается и шире
   260px не становится: список из двадцати шагов превратится в полосу во весь экран. Шаги и
   промежуточные значения выводятся не более восьми, после чего добавляется `…и ещё <N>`.
   Порог общий для обоих списков.

Свёрнутая подпись не меняется: состав, порядок и ширина колонки те же, скрытых сведений не
появляется — подсказка показывает то, что уже загружено в строку, и ни одного запроса не
добавляет.

## Интерфейс

Переиспользуются существующие компоненты дизайн-системы:

- `.has-tip` — подсказка по наведению и по фокусу (карточка `design-system/src/cards/`,
  раздел подсказок);
- `.kr-target-col` / `.kr-target__val` / `.kr-target__dir` — свёрнутая подпись целевого
  значения в строке результата (`design-system/src/cards/kr-row.html`).

Новых компонентов нет: подсказка — применение `.has-tip` к колонке, которая его не имела.

Вид согласуется на прототипе: строки ключевого результата всех трёх типов в
`design-system/prototype/app.js` (`krTargetText`), включая метрику с промежуточными значениями,
метрику без обновлений прогресса и проектный результат с длинным списком шагов. Карточка
`design-system/src/cards/kr-row.html` обновляется после согласования.

## Риски

- **Подсказка обрезается контейнером.** `.has-tip::after` позиционируется абсолютно; если у
  какого-то предка строки окажется `overflow: hidden`, подсказка обрежется. Проверяется на
  последней строке последней цели на доске и в узкой раскладке. Соседний `.kr-weight-chip` с
  тем же механизмом работает в той же строке — это основание считать риск низким, но не
  основание не проверить.
- **Миграция и строки с прогрессом, сделанным до появления `progress_updated_at`.** Закрыто
  вторым условием предиката (решение 5); на этом месте есть тест.
- **Выгрузка и уведомления читают текущее значение через домен.** Склейка на границе
  хранилища (решение 1) оставляет их нетронутыми; проверяется тестами существующих сценариев,
  новых требований к ним изменение не вводит.
