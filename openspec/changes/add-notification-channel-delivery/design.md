## Context

Мотивация — см. `proposal.md` → Why. Требования — см. delta-спеки этого change.

Существенное для подхода состояние кода:

- `notifychannel` — публичный пакет-контракт: только типы, без ввода-вывода
  и без импортов `okrs/internal/**`. Это сделано намеренно, чтобы канал можно
  было написать в отдельном модуле: Go запрещает импорт `internal` извне.
  Любое решение обязано сохранить это ограничение.
- `internal/service/notificationchannel` — единственное место, где секрет канала
  существует в открытом виде. Оно же строит `Sender` и оборачивает его в
  маскирующую обёртку.
- `internal/usecase/notification` — подписчик шины, создаёт строки уведомлений.
  Резолв получателей уже пакетный и уже возвращает список каналов
  (`Recipient.Channels`), который сегодня отбрасывается.
- `notifychannel/mattermost` уже спроектирован как долгоживущий экземпляр: кэш
  идентификатора бота и коалесцирование одновременных резолвов не имеют смысла
  при построении нового экземпляра на каждую отправку.
- Приложение работает в нескольких экземплярах в Kubernetes.

## Goals / Non-Goals

**Goals:**

- Доставка уведомлений во внешние каналы без распределённого состояния
  и без новой инфраструктуры.
- Сохранение публичности контракта `notifychannel`: канал из чужого модуля
  должен собираться и работать.
- Отсутствие обращений к базе данных на каждое доставляемое сообщение.
- Явная и предсказуемая граница между «ядро решает, кому и что» и «канал решает,
  когда и в каком виде отправить».

**Non-Goals:**

- Гарантированная доставка. Потери при аварийном завершении экземпляра приняты
  как допустимые.
- Единый дайджест поверх нескольких экземпляров приложения.
- Повторные попытки с сохранением состояния между рестартами.
- Привязка внешнего аккаунта (account linking). Адресация остаётся через
  `Target`, как сегодня.
- Новые типы уведомлений и изменение правил их порождения.

## Decisions

### 1. Политика доставки принадлежит каналу, а не ядру

Ядро отдаёт каналу по одному сообщению и не знает ни про окно, ни про
накопление. `Send` меняет смысл на «принять к отправке»; когда именно уйдёт
сообщение и как будет выглядеть — решает канал.

**Почему так.** Политика отправки у разных каналов разная по своей природе:
мессенджеру уместно накапливать, а транспорт с дешёвой доставкой может слать
сразу. Формат склейки нескольких обновлений в одно сообщение — тоже дело канала:
Markdown у Mattermost, HTML у почты, собственный диалект у Telegram. Если ядро
склеивает текст, оно неизбежно начинает знать про формат конкретного канала.

**Альтернатива: ядро исполняет политику, канал её объявляет.** `Descriptor` несёт
признак «накапливает» и окно по умолчанию, буфер и таймер живут в ядре, канал
предоставляет только форматирование пачки через дополнительный интерфейс.
Плюс — буфер, потолок и выгрузка написаны один раз для всех каналов.
Минус — `Descriptor` растёт, ядро знает про существование окна, а канал теряет
право на собственную политику. Отклонено в пользу автономии канала; цена —
повторная реализация накопления в каждом следующем канале — принята осознанно.

### 2. Буфер — в памяти экземпляра приложения

**Почему так.** Альтернатива — считать буфером саму таблицу уведомлений и
раз в окно читать недоставленное. Она даёт честный единый дайджест между
экземплярами, переживает рестарт и переиспользует уже работающее схлопывание,
но требует выбора ведущего экземпляра (иначе реплики отправят один дайджест
несколько раз) и колонки состояния доставки.

Отклонено: важность этих уведомлений не оправдывает распределённого состояния
и блокировок. Прямое следствие — получатель при нескольких экземплярах может
получить несколько сообщений за окно. Это зафиксировано в спеке как поведение,
а не как дефект.

### 3. Новые методы идут в сам `Sender`, а не в необязательные интерфейсы

```go
type Sender interface {
	Send(ctx, target, msg) error      // принять к отправке
	SendNow(ctx, target, msg) error   // отправить немедленно, вернуть ошибку
	Flush(ctx) error                  // отправить накопленное
}
```

**Почему не отдельные необязательные интерфейсы** (как `Linker`). В
`internal/service/notificationchannel/secretmask.go` задокументировано проверенное
эмпирически ограничение: маскирующая обёртка встраивает `Sender`, а встраивание
интерфейса продвигает только его собственные методы. Приведение обёрнутого
значения к любому другому интерфейсу контракта проваливается — молча, без ошибки
компиляции.

Через эту обёртку проходит каждый канал с секретом. Значит необязательный
`SendNow` при проверочной отправке не нашёлся бы, произошёл бы откат на `Send`,
и кнопка проверки отвечала бы «успех» на неработающий канал. Необязательный
`Flush` не нашёлся бы при остановке, и буфер молча терялся бы при каждом
развёртывании. Оба отказа тихие и проявились бы через месяцы.

**Следствие, которое нельзя забыть.** Комментарий у обёртки гласит, что все
методы кроме `Send` проходят насквозь. `SendNow` возвращает ошибку прямо
в HTTP-ответ администратору, поэтому обёртка ОБЯЗАНА переопределить и его —
иначе секрет уйдёт наружу и требование спеки нарушится именно там, где оно
нужнее всего. Это отдельная задача в `tasks.md`, а не подразумеваемая деталь.

**Цена.** Добавление методов в интерфейс ломает все внешние реализации. Сегодня
это Mattermost и тестовые заглушки. Ограничение задокументированного долга по
`Linker` этим решением не ухудшается, но и не устраняется.

### 4. `Channel.New` принимает структуру зависимостей

```go
type Deps struct {
	Settings Settings
	Logger   *slog.Logger
	Now      func() time.Time
}
```

`Settings` — конфигурация канала внутри пространства; логгер и часы к ней
не относятся, поэтому расширять `Settings` нельзя. Структура вместо позиционных
параметров выбрана, чтобы следующая зависимость не ломала сигнатуру снова.

`Now` нужен ради тестируемости: канал теперь владеет таймером, и проверка
«накопил три обновления, по истечении окна отправил одно сообщение» без
управляемого времени превращается в ожидание реального интервала.

Ограничение пакета соблюдено: `log/slog` и `time` — стандартная библиотека,
импорта `okrs/internal/**` не появляется.

### 5. Логгер инжектится ядром уже с редактированием секрета

Как только канал начинает писать ошибки сам, маскирующая обёртка перестаёт быть
второй линией защиты: она видит только то, что возвращается из `Send`.

Поэтому ядро отдаёт каналу логгер, обработчик которого вырезает секрет этого
пространства. Ядро — единственное место, где секрет есть в открытом виде, значит
оно и должно применять редактирование. Канал об этом не знает и не может забыть.
Это та же логика, по которой маскирование ошибок живёт в ядре, а не в канале.

### 6. Реестр долгоживущих экземпляров каналов

Сегодня `Service.Sender` строит новый экземпляр на каждый вызов. С буфером
внутри канала это означало бы буфер, который создаётся и немедленно умирает.

Появляется реестр `(пространство, канал) → экземпляр`, владеемый слоем сервиса.
Он же чинит существующее противоречие: кэш идентификатора бота в Mattermost
наконец начинает работать.

**Актуальность конфигурации.** Экземпляр строится из настроек, которые могут
измениться. Реестр хранит версию конфигурации, из которой построен экземпляр,
и сверяет её с текущей через существующий кеш снапшота настроек пространства —
in-memory, поэтому сверка не порождает обращения к базе на каждое сообщение.
При расхождении: выгрузить накопленное старым экземпляром, затем построить новый.

Экземпляр, обслуживший проверочную отправку, и экземпляр, обслуживающий
доставку, — один и тот же объект: `SendNow` минует буфер по построению.

### 7. Трёхзначное состояние настройки пользователя

Настройка пары «тип × канал» имеет три состояния: явно включено, явно выключено
и «пользователь не высказывался». Третье необходимо, иначе значение по умолчанию
от администратора некуда применять.

Хранение — разреженная структура отклонений: записываются только ячейки,
отличающиеся от текущего значения по умолчанию; отсутствие ключа означает
«не высказывался». У большинства пользователей она пуста, поэтому отдельная
таблица со строкой на ячейку не окупается; структура живёт в уже существующей
строке настроек и приезжает тем же соединением, что и сейчас.

**Миграция дешёвая.** Существующая колонка списка каналов сегодня содержит ровно
одно значение — канал «в приложении»; реальных каналов там нет и быть не могло,
потому что доставки не существовало. Переносить, кроме него, нечего.

**Альтернатива: два списка** (включённые и выключенные). Отклонено: два источника
об одном факте допускают противоречивое состояние, когда канал попал в оба.

### 8. Сохранение матрицы целиком фиксирует выбор по всем её ячейкам

Форма сохраняется целиком, поэтому после первого сохранения все показанные
на экране ячейки становятся явным выбором. Это принято сознательно: пользователь
видел эти переключатели и нажал «Сохранить».

Существенно, что главное свойство при этом не теряется: канал, подключённый
позже, на экране не показывался, в сохранённые данные не попал и остаётся
в состоянии «не высказывался» — то есть доезжает до всех по значению
администратора. Затрагивается только смена значения по умолчанию у канала,
который на момент сохранения уже существовал.

### 9. Таблица уведомлений — журнал, а не лента

Запись уведомления создаётся, когда тип включён и охват совпадает, независимо
от каналов. Лента и доставка во внешние каналы — два её читателя, у каждого своя
ячейка в матрице.

Это следствие решения 2: если бы отключённый канал «в приложении» отменял
создание записи, внешнему каналу нечего было бы отправлять. Формулировка внесена
в спеку явно, иначе следующий читатель кода примет это за дефект.

### 10. Потолок буфера — на получателя

Ограничение объёма применяется к накопленному каждого получателя по
отдельности, а не к каналу целиком. При общем потолке один активный получатель
вытеснил бы накопленное всех остальных. При переполнении отбрасываются самые
старые обновления, приём новых продолжается.

## Границы слоёв

```
  usecase/notification     создаёт уведомления, знает получателей и их каналы
        |  узкий порт, объявленный на стороне потребителя
        v
  service/notificationchannel   реестр экземпляров, секрет, редактирующий
        |                       логгер, маскирование ошибок
        v
  notifychannel (контракт)  --> notifychannel/mattermost
                                буфер, окно, формат сообщения
```

`internal/usecase/notification` не импортирует `notifychannel`: он объявляет
собственный узкий порт («доставить эти уведомления этим получателям в эти
каналы») и получает его реализацию из слоя сервиса, как уже сделано для
хранилища уведомлений и резолвера настроек. Типы канала остаются за границей
сервиса, абстракция не протекает вверх.

## Производительность

Обработчик шины уже группирует события по паре «пространство, тип» и резолвит
получателей пакетно. Доставка обязана остаться в этой же дисциплине:

- **Каналы получателя** приезжают тем же запросом резолва, что и сегодня
  (`Recipient.Channels`). Дополнительных запросов не появляется.
- **Настройки канала и признак доступности** читаются один раз на группу,
  а не на получателя, и обслуживаются существующим кешем снапшота настроек
  пространства.
- **Адрес получателя** (почта) резолвится одним запросом на всю пачку
  получателей. Запрос на получателя в цикле недопустим — это ровно тот N+1,
  ради которого резолв получателей уже сделан пакетным.
- **Сама отправка** в буфер — операция в памяти, обращений к базе не делает.

## Risks / Trade-offs

- **Несколько сообщений за окно при нескольких экземплярах** → принято как
  поведение и зафиксировано в спеке; пользователю видно как несколько дайджестов
  подряд, содержимое при этом не дублируется.
- **Потеря накопленного при аварийном завершении** → принято; лента уведомлений
  не страдает, потому что запись создаётся независимо от доставки.
- **Устаревшая конфигурация на других экземплярах** после сохранения настроек
  администратором → сверка версии конфигурации через кеш снапшота настроек
  пространства; отставание ограничено временем жизни кеша.
- **Ломающее изменение публичного контракта** `Sender` и `Channel.New` → в сборке
  один внешний канал и тестовые заглушки; изменение выполняется одним заходом.
- **Секрет в журнале** при переходе логирования в канал → редактирующий логгер
  инжектится ядром, канал не может его обойти.
- **Секрет в ответе проверочной отправки** через непереопределённый `SendNow`
  → отдельная задача на обновление маскирующей обёртки и тест на неё.
- **Резкий рост трафика в канал** сразу после включения «по умолчанию у всех»
  → смягчается накоплением: даже при активном пространстве получатель получает
  не более одного сообщения на окно от экземпляра.
- **Рост числа живых экземпляров каналов** (пространства × каналы на каждом
  экземпляре приложения) → каждый экземпляр канала держит буфер и таймер;
  требуется потолок на получателя и освобождение экземпляров пространств,
  переставших порождать события.

## Migration Plan

1. Изменение структуры хранения настроек пользователя: разреженные отклонения
   по каналам. Существующее значение канала «в приложении» переносится как явный
   выбор. Обновляется seed demo.
2. Настройки канала пополняются признаком «включён по умолчанию» и окном
   отправки. Существующие каналы получают признак выключенным и окно по
   умолчанию — то есть после развёртывания поведение не меняется, пока
   администратор не включит канал сознательно.
3. Изменение контракта `notifychannel` и Mattermost выполняется одним заходом:
   промежуточного состояния, в котором интерфейс расширен, а канал не обновлён,
   не существует.
4. Откат: признак «включён по умолчанию» выключается администратором, доставка
   прекращается немедленно; лента уведомлений продолжает работать, потому что
   не зависит от доставки.
