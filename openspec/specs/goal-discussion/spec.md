# Goal Discussion Specification

## Purpose

Обсуждение цели — двухуровневый механизм замечаний: замечание (таска) с состоянием «решено» и
ответы на него. Возможность описывает создание, резолв и повторное открытие замечаний, ответы,
удаление, счётчики и авторство.

## Requirements

### Requirement: Комментарий всегда имеет автора

Система SHALL фиксировать автора у каждого замечания и ответа. В режиме без авторизации автором
SHALL выступать системный пользователь `anonymous-local`.

#### Scenario: Создание замечания

- GIVEN авторизованный пользователь
- WHEN он оставляет замечание к цели
- THEN замечание сохраняется с ним в качестве автора

#### Scenario: Режим без авторизации

- GIVEN система работает в режиме без авторизации
- WHEN оставляется замечание
- THEN его автором фиксируется системный пользователь `anonymous-local`

### Requirement: Ровно один уровень вложенности

Система SHALL допускать ответы только на замечание первого уровня. Ответ на ответ MUST NOT
создаваться.

#### Scenario: Ответ на замечание

- GIVEN у цели есть замечание
- WHEN пользователь отвечает на него
- THEN ответ сохраняется внутри этого замечания

#### Scenario: Попытка ответить на ответ

- GIVEN у замечания есть ответ
- WHEN пользователь пытается ответить на этот ответ
- THEN операция отклоняется

### Requirement: Состояние «решено» есть только у замечания

Система SHALL разрешать отмечать решённым только замечание первого уровня. Ответ MUST NOT иметь
состояния «решено».

#### Scenario: Резолв замечания

- GIVEN у цели есть нерешённое замечание
- WHEN пользователь отмечает его решённым
- THEN сохраняются момент решения и пользователь, отметивший его решённым

#### Scenario: Попытка резолва ответа

- GIVEN у замечания есть ответ
- WHEN кто-либо пытается отметить ответ решённым
- THEN операция не выполняется, состояние ответа не меняется

### Requirement: Согласованность полей решения

Система SHALL хранить момент решения и пользователя, отметившего решённым, всегда вместе: либо
оба заполнены, либо оба отсутствуют.

#### Scenario: Повторное открытие

- GIVEN замечание отмечено решённым
- WHEN пользователь открывает его заново
- THEN момент решения и пользователь, отметивший решённым, очищаются оба

### Requirement: Идемпотентность резолва и повторного открытия

Система SHALL изменять состояние и записывать событие журнала только при фактической смене
состояния. Повторный резолв уже решённого замечания и повторное открытие уже открытого MUST NOT
перезаписывать поля решения и MUST NOT создавать запись журнала.

#### Scenario: Повторный резолв

- GIVEN замечание уже решено с известным моментом решения
- WHEN пользователь отмечает его решённым ещё раз
- THEN момент решения и автор решения не меняются, новая запись журнала не создаётся

#### Scenario: Повторное открытие открытого замечания

- GIVEN замечание не решено
- WHEN пользователь открывает его заново
- THEN состояние не меняется, новая запись журнала не создаётся

### Requirement: Удаление замечания каскадно удаляет ответы

Система SHALL удалять вместе с замечанием все его ответы.

#### Scenario: Удаление замечания с ответами

- GIVEN у замечания есть два ответа
- WHEN замечание удаляется
- THEN оба ответа также удаляются

### Requirement: Порядок замечаний и ответов

Система SHALL сортировать замечания от ранних к поздним и ответы внутри замечания также от
ранних к поздним.

#### Scenario: Порядок отображения

- GIVEN у цели есть несколько замечаний, созданных в разное время
- WHEN пользователь раскрывает обсуждение
- THEN замечания отображаются от самого раннего к самому позднему

### Requirement: Счётчик комментариев считает только замечания

Система SHALL показывать на карточке цели число замечаний, решённых и нерешённых. Ответы MUST
NOT входить в счётчик.

#### Scenario: Замечание с ответами

- GIVEN у цели одно замечание и три ответа на него
- WHEN пользователь смотрит карточку цели
- THEN счётчик показывает одно замечание

### Requirement: Комментирование доступно во всех статусах

Система SHALL разрешать создание замечаний и ответов, резолв, повторное открытие и удаление
собственных комментариев независимо от статуса команды в периоде.

#### Scenario: Комментирование в закрытом периоде

- GIVEN статус команды в периоде — «закрыт»
- WHEN пользователь оставляет замечание и отвечает на него
- THEN обе операции выполняются

### Requirement: Проверка доступа к обсуждению на сервере

Система SHALL проверять на сервере доступ к команде, принадлежность комментария цели и право на
удаление. Проверки MUST NOT ограничиваться интерфейсом.

#### Scenario: Комментарий к недоступной цели

- GIVEN команда-владелец цели недоступна пользователю
- WHEN он пытается оставить к ней замечание
- THEN возвращается «не найдено»

#### Scenario: Комментарий не принадлежит цели

- GIVEN пользователь указывает идентификатор комментария другой цели
- WHEN он пытается его изменить или удалить в контексте своей цели
- THEN операция отклоняется

### Requirement: Загрузка обсуждения вместе с целями

Система SHALL загружать комментарии целей команды вместе с самими целями одним запросом,
без отдельного запроса на каждую цель.

#### Scenario: Открытие доски команды

- GIVEN у команды несколько целей с комментариями
- WHEN пользователь открывает доску команды
- THEN комментарии всех целей приходят вместе с целями
