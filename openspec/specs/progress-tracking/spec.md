# Progress Tracking Specification

## Purpose

Возможность определяет, как измеряется выполнение: обновление прогресса ключевых результатов по
типам, единые правила расчёта прогресса цели, команды и периода, а также ручной health-статус
ключевого результата. Это единственный источник правды по числам, которым пользуются доска,
обзор периода, health check-in, экспорт и дерево целей.

## Requirements

### Requirement: Прогресс бинарного ключевого результата

Система SHALL считать прогресс бинарного ключевого результата равным 100, если он отмечен
выполненным, и 0 в противном случае.

#### Scenario: Отметка выполнения

- GIVEN бинарный ключевой результат не выполнен
- WHEN пользователь отмечает его выполненным
- THEN его прогресс становится равен 100

### Requirement: Прогресс проектного ключевого результата

Система SHALL считать прогресс проектного ключевого результата суммой весов завершённых этапов
с ограничением диапазоном от 0 до 100.

#### Scenario: Сумма весов превышает 100

- GIVEN у проектного ключевого результата суммарный вес завершённых этапов больше 100
- WHEN вычисляется прогресс
- THEN прогресс равен 100

#### Scenario: Ни один этап не завершён

- GIVEN у проектного ключевого результата нет завершённых этапов
- WHEN вычисляется прогресс
- THEN прогресс равен 0

### Requirement: Прогресс числового ключевого результата без промежуточных значений

Система SHALL считать прогресс числового ключевого результата без промежуточных значений
линейно от стартового значения к целевому, в обоих направлениях изменения метрики, с
ограничением диапазоном от 0 до 100.

#### Scenario: Рост метрики

- GIVEN стартовое значение меньше целевого, текущее значение — ровно посередине
- WHEN вычисляется прогресс
- THEN прогресс равен 50

#### Scenario: Снижение метрики

- GIVEN стартовое значение больше целевого, текущее значение — ровно посередине
- WHEN вычисляется прогресс
- THEN прогресс равен 50

#### Scenario: Текущее значение хуже стартового

- GIVEN текущее значение выходит за стартовое в сторону, противоположную цели
- WHEN вычисляется прогресс
- THEN прогресс равен 0

#### Scenario: Текущее значение лучше целевого

- GIVEN текущее значение выходит за целевое
- WHEN вычисляется прогресс
- THEN прогресс равен 100

#### Scenario: Стартовое значение равно целевому

- GIVEN стартовое и целевое значения совпадают
- WHEN вычисляется прогресс
- THEN прогресс равен 100, если цель достигнута, иначе 0

### Requirement: Прогресс числового ключевого результата с промежуточными значениями

Система SHALL считать прогресс числового ключевого результата с промежуточными значениями
линейной интерполяцией между точками: стартовое значение соответствует 0 процентам, целевое —
100 процентам, промежуточные — своим процентам, точки упорядочиваются по значению метрики. Вне
диапазона SHALL применяться процент ближайшей крайней точки, результат SHALL ограничиваться
диапазоном от 0 до 100.

#### Scenario: Значение между двумя точками

- GIVEN задано промежуточное значение с известным процентом
- WHEN текущее значение находится между стартовым и этим промежуточным
- THEN прогресс интерполируется линейно между 0 и процентом промежуточной точки

#### Scenario: Значение ниже стартового

- GIVEN текущее значение ниже стартового
- WHEN вычисляется прогресс
- THEN прогресс равен 0

#### Scenario: Достигнуто целевое значение

- GIVEN текущее значение достигло целевого
- WHEN вычисляется прогресс
- THEN прогресс равен 100

### Requirement: Прогресс цели как взвешенное среднее

Система SHALL считать прогресс цели взвешенным средним прогресса её ключевых результатов.

#### Scenario: Цель без ключевых результатов

- GIVEN у цели нет ключевых результатов
- WHEN вычисляется её прогресс
- THEN прогресс равен 0

#### Scenario: Суммарный вес ключевых результатов равен нулю

- GIVEN у всех ключевых результатов цели вес равен 0
- WHEN вычисляется прогресс цели
- THEN прогресс равен 0

#### Scenario: Разные веса

- GIVEN у цели два ключевых результата с разными весами
- WHEN вычисляется прогресс
- THEN вклад каждого пропорционален его весу

### Requirement: Прогресс команды в периоде как взвешенное среднее целей

Система SHALL считать прогресс команды в периоде взвешенным средним прогресса её целей.

#### Scenario: Изменение веса цели

- GIVEN у команды две цели с разным прогрессом
- WHEN вес одной из целей меняется
- THEN прогресс команды пересчитывается с учётом нового веса

### Requirement: Единые правила расчёта

Система SHALL применять одни и те же правила расчёта прогресса во всех разделах: на доске
команды, в обзоре периода, в дереве целей, в экспорте и в health check-in.

#### Scenario: Согласованность разделов

- GIVEN цель с известным прогрессом
- WHEN пользователь видит её на доске, в дереве целей и в экспорте
- THEN во всех разделах отображается одно и то же значение прогресса

### Requirement: Обновление прогресса ключевого результата

Система SHALL позволять обновлять прогресс ключевого результата способом, соответствующим его
типу: числовое текущее значение, отметка выполнения, отметки завершённых этапов. Обновление
прогресса SHALL проверять доступ к команде-владельцу цели на сервере.

#### Scenario: Обновление прогресса в доступной команде

- GIVEN пользователю доступна команда-владелец цели
- WHEN он обновляет прогресс её ключевого результата
- THEN значение сохраняется и прогресс цели пересчитывается

#### Scenario: Обновление прогресса вне области видимости

- GIVEN команда-владелец цели недоступна пользователю
- WHEN он пытается обновить прогресс ключевого результата
- THEN возвращается «не найдено», значение не меняется

### Requirement: Способ обновления должен соответствовать типу ключевого результата

Система SHALL отклонять как конфликт обновление прогресса способом, не соответствующим типу
ключевого результата. Проверка SHALL выполняться до любой записи, поэтому отклонённое обновление
MUST NOT изменить ни прогресс, ни health-статус, ни заметку.

#### Scenario: Числовое обновление бинарного ключевого результата

- GIVEN ключевой результат бинарного типа
- WHEN пользователь обновляет его числовым текущим значением
- THEN операция отклоняется как конфликт

#### Scenario: Отметка выполнения у числового ключевого результата

- GIVEN ключевой результат числового типа
- WHEN пользователь обновляет его отметкой выполнения
- THEN операция отклоняется как конфликт

#### Scenario: Отметки этапов у непроектного ключевого результата

- GIVEN ключевой результат бинарного или числового типа
- WHEN пользователь обновляет его отметками завершённых этапов
- THEN операция отклоняется как конфликт

#### Scenario: Отклонение не оставляет следов

- GIVEN обновление отклонено из-за несоответствия типу, при этом в том же запросе переданы health-статус и заметка
- WHEN запрос обрабатывается
- THEN ни прогресс, ни health-статус, ни заметка не изменяются

### Requirement: Чек-ин — одна операция

Система SHALL применять прогресс, health-статус и заметку ключевого результата, переданные одним
запросом, как одну операцию чек-ина. Такой запрос SHALL порождать не более одного события
изменения.

#### Scenario: Прогресс, статус и заметка одним запросом

- GIVEN пользователь обновляет прогресс, health-статус и заметку одним запросом
- WHEN операция выполняется
- THEN изменения применяются вместе, а в журнале и уведомлениях они выглядят как один чек-ин, а не три

#### Scenario: Чек-ин без изменений

- GIVEN пользователь сохраняет те же значения, что уже записаны
- WHEN операция выполняется
- THEN событие изменения не порождается

#### Scenario: Чек-ин только с заметкой

- GIVEN пользователь меняет только заметку, не трогая прогресс
- WHEN операция выполняется
- THEN заметка сохраняется и чек-ин фиксируется как изменение

#### Scenario: Заметка сохраняется при частичном сбое

- GIVEN в одном запросе передана заметка и отметки этапов проекта
- WHEN применение отметок этапов не удалось
- THEN заметка всё равно сохраняется

### Requirement: Чек-ин сохраняет предшествующие значения

Система SHALL фиксировать в событии чек-ина значения прогресса и заметки, действовавшие до
операции, даже если соответствующее поле в этом запросе не передавалось.

#### Scenario: Обновление только прогресса

- GIVEN у ключевого результата есть заметка, пользователь обновляет только прогресс
- WHEN операция выполняется
- THEN событие несёт действующий текст заметки, а не пустое значение

### Requirement: Ручной health-статус ключевого результата

Система SHALL хранить у ключевого результата health-статус из закрытого справочника («не
начат», «в плане», «под риском», «выполнен») со значением по умолчанию «не начат». Значение вне
справочника SHALL отклоняться как ошибка валидации.

#### Scenario: Установка health-статуса

- GIVEN пользователь обновляет прогресс ключевого результата
- WHEN он одновременно передаёт допустимый health-статус
- THEN health-статус сохраняется

#### Scenario: Недопустимый health-статус

- GIVEN пользователь передаёт health-статус вне справочника
- WHEN запрос обрабатывается
- THEN операция отклоняется как ошибка валидации

### Requirement: Health-статус не влияет на расчёты

Система MUST NOT учитывать health-статус в расчёте прогресса ключевого результата, цели,
команды и периода. Health-статус — информационный сигнал.

#### Scenario: Смена health-статуса

- GIVEN у ключевого результата известный прогресс
- WHEN его health-статус меняется на «под риском»
- THEN прогресс ключевого результата, цели и команды не меняется

### Requirement: Однократный автоматический переход в «выполнен»

Система SHALL при переходе прогресса ключевого результата снизу вверх через 100 процентов
однократно выставлять health-статус «выполнен», если он ещё не «выполнен». Повторное сохранение
на 100 процентах и падение прогресса ниже 100 процентов health-статус MUST NOT менять. Явно
переданный статус SHALL иметь приоритет над автоматическим.

#### Scenario: Достижение 100 процентов

- GIVEN прогресс ключевого результата меньше 100 и health-статус не «выполнен»
- WHEN прогресс становится равен 100
- THEN health-статус автоматически становится «выполнен»

#### Scenario: Пользователь снял статус после автоперехода

- GIVEN health-статус был автоматически выставлен «выполнен», а затем изменён вручную
- WHEN прогресс сохраняется снова на 100 процентах
- THEN автоматический переход не повторяется и ручное значение сохраняется

#### Scenario: Падение прогресса ниже 100

- GIVEN health-статус «выполнен», прогресс равен 100
- WHEN прогресс уменьшается
- THEN health-статус остаётся «выполнен»

#### Scenario: Явный статус вместе с достижением 100 процентов

- GIVEN прогресс достигает 100 процентов
- WHEN в том же обновлении явно передан другой health-статус
- THEN сохраняется явно переданный статус

### Requirement: Ожидаемый темп периода

Система SHALL вычислять ожидаемый темп периода как долю прошедшего времени периода в процентах:
0 до даты начала периода, 100 после даты окончания, между ними — отношение прошедшего времени ко
всей длительности периода, ограниченное диапазоном от 0 до 100. Ожидаемый темп одинаков для всех
команд и целей в рамках одного периода.

#### Scenario: Период ещё не начался

- GIVEN дата начала периода в будущем
- WHEN вычисляется ожидаемый темп
- THEN он равен 0

#### Scenario: Период завершился

- GIVEN дата окончания периода уже прошла
- WHEN вычисляется ожидаемый темп
- THEN он равен 100

#### Scenario: Середина периода

- GIVEN прошла ровно половина длительности периода
- WHEN вычисляется ожидаемый темп
- THEN он равен примерно 50

#### Scenario: Нулевая или отрицательная длительность

- GIVEN период, у которого дата окончания не позже даты начала
- WHEN вычисляется ожидаемый темп в пределах периода
- THEN он равен 100, а для периода с датой окончания раньше даты начала — 0

#### Scenario: Одинаковый темп для всех команд

- GIVEN две команды с разным прогрессом в одном периоде
- WHEN для каждой вычисляется ожидаемый темп
- THEN значение совпадает

### Requirement: Отклонение от ожидаемого темпа

Система SHALL сопровождать показатель прогресса сводкой темпа: фактический прогресс, ожидаемый
темп, их разность и оценку. Разность SHALL вычисляться как фактический прогресс минус ожидаемый
темп.

#### Scenario: Сводка темпа у команды

- GIVEN прогресс команды равен 40, ожидаемый темп равен 55
- WHEN отображается сводка темпа
- THEN разность равна минус 15

### Requirement: Пороги оценки темпа

Система SHALL относить отклонение от ожидаемого темпа к одной из трёх оценок: «отстаёт», если
разность меньше минус 10; «опережает», если разность больше 10; «идёт по плану» в остальных
случаях, включая обе границы диапазона.

#### Scenario: Отставание

- GIVEN разность равна минус 15
- WHEN определяется оценка
- THEN она равна «отстаёт»

#### Scenario: Опережение

- GIVEN разность равна 15
- WHEN определяется оценка
- THEN она равна «опережает»

#### Scenario: Граница диапазона

- GIVEN разность равна ровно минус 10 или ровно 10
- WHEN определяется оценка
- THEN она равна «идёт по плану»

### Requirement: Порог «в плане» перекрывает оценку темпа

Система SHALL считать цель или команду «в плане» и выделять её соответствующим образом, если её
прогресс не ниже порога «в плане» из настроек пространства, независимо от оценки темпа.

#### Scenario: Высокий прогресс при отставании от темпа

- GIVEN прогресс команды выше порога «в плане», но оценка темпа — «отстаёт»
- WHEN команда отображается
- THEN она показывается как идущая по плану
