# Team Period Lifecycle Specification

## Purpose

Статус команды в периоде — продуктовый жизненный цикл работы над целями: от черновика к
валидации, работе и закрытию. Возможность описывает набор статусов, их смену вручную и массово,
режимы редактирования интерфейса, а также серверные ограничения, которые статус фактически
накладывает на операции с целями.

## Requirements

### Requirement: Набор статусов команды в периоде

Система SHALL поддерживать ровно пять статусов команды в периоде, в порядке жизненного цикла:
«нет целей», «черновик», «к валидации», «в работе», «закрыт». Значение вне этого набора SHALL
отклоняться как ошибка валидации.

#### Scenario: Смена статуса на допустимое значение

- GIVEN пользователю доступна команда
- WHEN он переводит её статус в периоде в «в работе»
- THEN статус сохраняется для пары «команда и период»

#### Scenario: Недопустимое значение статуса

- GIVEN пользователь отправляет статус вне набора
- WHEN запрос обрабатывается
- THEN операция отклоняется как ошибка валидации

#### Scenario: Отменённое историческое значение статуса

- GIVEN пользователь отправляет значение статуса, которое не входит в набор из пяти
- WHEN запрос обрабатывается
- THEN операция отклоняется так же, как любое другое неизвестное значение

### Requirement: Смысл шага «к валидации»

Система SHALL трактовать шаг «к валидации» как состояние, в котором руководитель команды
подготовил цели и передал их на проверку вышестоящему руководителю. Шаг SHALL находиться между
«черновиком» и «в работе».

#### Scenario: Передача целей на проверку

- GIVEN руководитель команды закончил оформлять цели в статусе «черновик»
- WHEN он переводит команду в «к валидации»
- THEN цели считаются переданными на проверку, а команда ещё не начала работу по ним

### Requirement: Отображение жизненного цикла

Система SHALL отображать в интерфейсе четыре явных шага жизненного цикла: «черновик»,
«к валидации», «в работе», «закрыты». Состояние «нет целей» SHALL отображаться отдельным
признаком, а не шагом.

#### Scenario: Команда без целей

- GIVEN у команды в периоде нет целей
- WHEN пользователь открывает доску команды
- THEN отображается признак «нет целей», а шаги жизненного цикла недоступны для выбора

#### Scenario: Текущий шаг

- GIVEN статус команды — «к валидации»
- WHEN пользователь открывает доску
- THEN этот шаг выделен как текущий, пройденные шаги показаны менее выраженно

### Requirement: Режимы редактирования выводятся из статуса

Система ОБЯЗАНА выводить режим редактирования доски из статуса команды в периоде: при «нет
целей», «черновик» и «к валидации» доступно полное редактирование; при «в работе» интерфейс
предлагает обновление прогресса и комментарии; при «закрыт» — только комментарии.

Действие, недоступное в текущем режиме, ОБЯЗАНО объяснять причину — текущий статус команды в
периоде. Объяснение ОБЯЗАНО быть доступно при наведении и при получении фокуса с клавиатуры.
Активировать недоступное действие НЕОБХОДИМО не допускать.

Пункты меню действий и кнопка создания цели ОБЯЗАНЫ оставаться на своих местах в недоступном
виде. Кнопку добавления ключевого результата внутри карточки цели при недоступности ОБЯЗАНО
скрывать: причина в этом случае объясняется баннером режима над списком целей.

#### Scenario: Режим полного редактирования

- GIVEN статус команды — «черновик»
- WHEN пользователь открывает доску
- THEN ему доступны создание, редактирование и удаление целей и ключевых результатов

#### Scenario: Режим «только комментарии»

- GIVEN статус команды — «закрыт»
- WHEN пользователь открывает доску
- THEN интерфейс предлагает только работу с комментариями

#### Scenario: Создание цели остаётся видимым

- GIVEN статус команды — «в работе»
- WHEN пользователь открывает доску
- THEN кнопка создания цели видна на своём месте в недоступном виде

#### Scenario: Добавление ключевого результата скрыто

- GIVEN статус команды — «в работе»
- WHEN пользователь смотрит карточку цели
- THEN кнопки добавления ключевого результата нет, а причина названа баннером режима

#### Scenario: Причина блокировки названа

- GIVEN статус команды — «в работе», на доске есть недоступное действие
- WHEN пользователь наводит указатель на это действие или переводит на него фокус с клавиатуры
- THEN отображается объяснение, называющее текущий статус команды причиной

#### Scenario: Недоступное действие не срабатывает

- GIVEN статус команды — «закрыт»
- WHEN пользователь активирует недоступное действие
- THEN окно не открывается и данные не изменяются

### Requirement: Баннер режима редактирования на доске

Система ОБЯЗАНА показывать на доске команды баннер текущего состояния — в одной строке с
переключателем статусов, справа от шагов жизненного цикла.

Баннер ОБЯЗАН называть текущий статус команды в периоде и сопровождать его пояснением:

- в «черновике» и «к валидации» — что сделать, чтобы перейти к следующему шагу;
- в «в работе» — что состав целей зафиксирован и доступны обновление прогресса и комментарии;
- в «закрыт» — что доступны только комментарии.

Баннер ОБЯЗАН обновляться при смене статуса команды и при переключении команды или периода —
без перезагрузки страницы.

#### Scenario: Черновик

- GIVEN статус команды — «черновик»
- WHEN пользователь открывает доску
- THEN в строке статусов виден баннер, называющий статус «черновик» и подсказывающий перейти
  к «к валидации», когда цели готовы

#### Scenario: Команда в работе

- GIVEN статус команды — «в работе»
- WHEN пользователь открывает доску
- THEN баннер называет статус «в работе» и указывает, что состав целей зафиксирован, а доступны
  обновление прогресса и комментарии

#### Scenario: Период закрыт

- GIVEN статус команды — «закрыт»
- WHEN пользователь открывает доску
- THEN баннер называет статус «закрыт» и указывает, что доступны только комментарии

#### Scenario: Смена статуса на доске

- GIVEN открыта доска команды в статусе «к валидации»
- WHEN пользователь переводит команду в «в работе»
- THEN баннер описывает новый режим без перезагрузки страницы

### Requirement: Серверное ограничение состава целей в статусах «в работе» и «закрыт»

Система SHALL отклонять как конфликт создание цели и удаление цели командой-владельцем, когда
статус этой команды в этом периоде — «в работе» или «закрыт». Ограничение SHALL проверяться на
сервере независимо от интерфейса.

#### Scenario: Создание цели в статусе «в работе»

- GIVEN статус команды в периоде — «в работе»
- WHEN пользователь создаёт цель для этой команды в этом периоде
- THEN операция отклоняется как конфликт, цель не создаётся

#### Scenario: Создание цели в статусе «закрыт»

- GIVEN статус команды в периоде — «закрыт»
- WHEN пользователь создаёт цель для этой команды в этом периоде
- THEN операция отклоняется как конфликт

#### Scenario: Удаление собственной цели в статусе «в работе»

- GIVEN статус команды — «в работе», цель принадлежит этой команде и никому не расшарена
- WHEN пользователь удаляет цель
- THEN операция отклоняется как конфликт

#### Scenario: Прямой запрос в обход интерфейса

- GIVEN интерфейс скрывает добавление цели при статусе «в работе»
- WHEN пользователь отправляет запрос на создание цели напрямую
- THEN сервер отклоняет его так же

### Requirement: Область действия серверного ограничения статуса

Система SHALL применять ограничение статуса только к операциям, меняющим состав целей команды в
периоде: создание цели, удаление цели командой-владельцем, добавление команды-участника в общую
цель и создание цели в целевой паре при копировании или переносе. Прочие операции SHALL
оставаться доступными во всех статусах.

#### Scenario: Отказ от общей цели в статусе «в работе»

- GIVEN цель расшарена в команду, статус которой — «в работе»
- WHEN пользователь удаляет цель из представления этой команды
- THEN участие команды в цели снимается: ограничение статуса на эту операцию не распространяется

#### Scenario: Передача владения в статусе «в работе»

- GIVEN цель принадлежит команде в статусе «в работе» и расшарена другой команде
- WHEN пользователь удаляет цель из представления команды-владельца
- THEN владение целью передаётся команде-участнику: ограничение статуса на эту операцию не распространяется

#### Scenario: Обновление прогресса в статусе «закрыт»

- GIVEN статус команды — «закрыт»
- WHEN пользователь обновляет прогресс ключевого результата
- THEN обновление сохраняется

#### Scenario: Комментирование в любом статусе

- GIVEN статус команды — «в работе» или «закрыт»
- WHEN пользователь добавляет замечание, отвечает на него или удаляет своё
- THEN операция выполняется

### Requirement: Массовая смена статуса команд периода

Система SHALL позволять переводить статусы команд периода массово: «активировать» переводит
команды в «в работе», «закрыть» — в «закрыт». Область действия операции SHALL совпадать с
разрешённым охватом вызывающего.

#### Scenario: Массовая активация

- GIVEN в охвате вызывающего несколько команд с целями в периоде
- WHEN он выполняет массовую активацию
- THEN все такие команды переводятся в статус «в работе»

#### Scenario: Команда вне охвата

- GIVEN в периоде есть команда за пределами охвата вызывающего
- WHEN он выполняет массовую операцию
- THEN статус этой команды не меняется

### Requirement: Массовая операция пропускает команды без целей

Система SHALL затрагивать при массовой смене статуса только команды, у которых в этом периоде
есть хотя бы одна цель. Команды без целей SHALL отмечаться как пропущенные.

#### Scenario: Команда без целей

- GIVEN у команды в периоде нет целей
- WHEN выполняется массовая смена статуса
- THEN её статус не меняется и она попадает в список пропущенных

### Requirement: Идемпотентность массовой смены статуса

Система MUST NOT затрагивать команду, уже находящуюся в целевом статусе: такая команда не
попадает ни в число затронутых, ни в число пропущенных, и не порождает записи журнала.

#### Scenario: Повторная активация

- GIVEN все команды охвата уже в статусе «в работе»
- WHEN выполняется массовая активация повторно
- THEN ни одна команда не отмечается затронутой и новые записи журнала не создаются

### Requirement: Журналирование массовой смены статуса

Система SHALL создавать отдельную запись журнала активности на каждую реально изменённую
команду и SHALL помечать такие записи как выполненные массовой операцией.

#### Scenario: Массовое закрытие трёх команд

- GIVEN три команды с целями находятся в статусе «в работе»
- WHEN выполняется массовое закрытие
- THEN в журнале появляются три отдельные записи смены статуса с признаком массовой операции
