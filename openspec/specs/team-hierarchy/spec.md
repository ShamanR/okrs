# Team Hierarchy Specification

## Purpose

Оргструктура команд — контекст, в котором существуют все OKR. Возможность описывает дерево
команд, его редактирование, руководителя команды, правила удаления и восстановления, а также
правила видимости команд в зависимости от выбранного периода.

## Requirements

### Requirement: Команда как узел дерева

Система SHALL хранить команды деревом с необязательным родителем. Дерево MUST NOT содержать
циклов.

#### Scenario: Создание вложенной команды

- GIVEN существует команда-родитель
- WHEN администратор пространства создаёт команду с указанием этого родителя
- THEN новая команда появляется в дереве как её потомок

#### Scenario: Попытка образовать цикл

- GIVEN команда A является предком команды B
- WHEN кто-либо назначает команду B родителем команды A
- THEN операция отклоняется, дерево остаётся ациклическим

### Requirement: Имя команды не является идентификатором

Система SHALL допускать одинаковые имена у разных команд. Команда SHALL адресоваться только
идентификатором; имя — отображаемый ярлык.

#### Scenario: Две команды с одинаковым именем

- GIVEN в разных ветках иерархии создаются две команды с именем «Платформа»
- WHEN обе команды сохраняются
- THEN обе существуют независимо и адресуются собственными идентификаторами

### Requirement: Тип команды — ярлык уровня оргструктуры

Система SHALL хранить тип команды как ярлык уровня из закрытого перечня (от широкого к узкому:
департамент, кластер, юнит, группа, команда, сквад, сотрудник). Вложенность SHALL определяться
только родителем и MUST NOT ограничиваться типом.

#### Scenario: Вложение вопреки порядку типов

- GIVEN команда типа «кластер»
- WHEN администратор делает её потомком команды типа «команда»
- THEN операция допускается: тип не ограничивает вложенность

### Requirement: Руководитель команды

Система SHALL хранить у команды руководителя как ссылку на пользователя. В режиме без
авторизации ссылка SHALL отсутствовать. При удалении пользователя ссылка SHALL сбрасываться, а
команда SHALL сохраняться.

#### Scenario: Удаление пользователя-руководителя

- GIVEN команда, у которой назначен руководитель
- WHEN учётная запись руководителя удаляется
- THEN команда остаётся, а ссылка на руководителя очищается

### Requirement: Наличие целей у команды учитывает и собственные, и расшаренные цели

Система SHALL считать, что у команды есть цели, если в каком-либо периоде существует хотя бы одна
цель, которой команда владеет, **либо** хотя бы одна цель другой команды, расшаренная в эту
команду. Оба признака SHALL применяться одинаково при выборе между мягким и полным удалением.

#### Scenario: Команда только с собственными целями

- GIVEN у команды есть собственные цели и нет расшаренных в неё
- WHEN проверяется наличие целей
- THEN считается, что цели есть

#### Scenario: Команда только с расшаренными целями

- GIVEN команда не владеет ни одной целью, но участвует в общей цели другой команды
- WHEN проверяется наличие целей
- THEN считается, что цели есть

### Requirement: Мягкое удаление команды с историей

Система SHALL выполнять мягкое удаление команды, если у неё есть цели хотя бы в одном периоде —
собственные или расшаренные в неё. Мягко удалённая команда SHALL сохраняться, чтобы не терять
исторические цели, общие цели и статусы периодов.

#### Scenario: Удаление команды с целями

- GIVEN у команды есть цели хотя бы в одном периоде
- WHEN администратор пространства удаляет команду
- THEN команда помечается удалённой, её исторические данные сохраняются

#### Scenario: Удаление команды-участника общей цели

- GIVEN команда не владеет ни одной целью, но участвует в общей цели другой команды
- WHEN администратор пространства удаляет команду
- THEN выполняется мягкое удаление, участие команды в общей цели сохраняется

### Requirement: Полное удаление только для команды без целей

Система SHALL допускать полное удаление команды, только если у неё нет ни собственных, ни
расшаренных в неё целей ни в одном периоде. Нарушение SHALL приводить к отказу уровня конфликта.

#### Scenario: Полное удаление команды без целей

- GIVEN у команды нет ни собственных, ни расшаренных в неё целей ни в одном периоде
- WHEN администратор пространства выполняет полное удаление
- THEN команда удаляется безвозвратно

#### Scenario: Полное удаление команды с целями

- GIVEN у команды есть цели хотя бы в одном периоде
- WHEN администратор пространства запрашивает полное удаление
- THEN операция отклоняется как конфликт, команда сохраняется

#### Scenario: Полное удаление команды-участника общей цели

- GIVEN команда не владеет целями, но участвует в общей цели другой команды
- WHEN администратор пространства запрашивает полное удаление
- THEN операция отклоняется как конфликт: участие в общей цели не должно исчезнуть вместе с командой

### Requirement: Перепривязка потомков при удалении

Система SHALL при удалении команды перепривязывать её дочерние команды к родителю удаляемой
команды. Если родителя не было, дочерние команды SHALL становиться корневыми.

#### Scenario: Удаление промежуточного узла

- GIVEN команда B является потомком A и имеет собственных потомков
- WHEN команда B удаляется
- THEN её потомки становятся прямыми потомками A

#### Scenario: Удаление корневого узла

- GIVEN корневая команда с потомками
- WHEN она удаляется
- THEN её потомки становятся корневыми

### Requirement: Восстановление мягко удалённой команды

Система SHALL позволять восстановить мягко удалённую команду. Восстановление SHALL возвращать
её в список активных и MUST NOT откатывать перепривязку потомков, выполненную при удалении.

#### Scenario: Восстановление после удаления

- GIVEN команда была мягко удалена, а её потомки перепривязаны к её родителю
- WHEN администратор пространства восстанавливает команду
- THEN команда снова активна, но её прежние потомки остаются на новом месте

### Requirement: Видимость команд с учётом периода

Система SHALL определять видимость команд на сервере с учётом мягкого удаления и выбранного
периода: активная команда SHALL быть видна всегда, в том числе без целей; мягко удалённая
команда SHALL быть видна только если в выбранном периоде у неё есть цели.

#### Scenario: Активная команда без целей

- GIVEN активная команда без целей в выбранном периоде
- WHEN пользователь открывает иерархию с этим периодом
- THEN команда отображается

#### Scenario: Мягко удалённая команда с целями в периоде

- GIVEN мягко удалённая команда, имеющая цели в выбранном периоде
- WHEN пользователь открывает иерархию с этим периодом
- THEN команда отображается

#### Scenario: Мягко удалённая команда без целей в периоде

- GIVEN мягко удалённая команда без целей в выбранном периоде
- WHEN пользователь открывает иерархию с этим периодом
- THEN команда не отображается

#### Scenario: Иерархия без указания периода

- GIVEN в пространстве есть мягко удалённые команды
- WHEN пользователь запрашивает иерархию без выбранного периода
- THEN мягко удалённые команды не отображаются

### Requirement: Иерархия ограничена областью видимости

Система SHALL возвращать пользователю только те узлы иерархии, которые входят в его область
видимости.

#### Scenario: Частичный доступ

- GIVEN пользователю выдан один узел с потомками
- WHEN он запрашивает иерархию
- THEN он получает лес из доступного узла и его потомков, без остальных ветвей

### Requirement: Чтение отдельной команды

Система SHALL предоставлять чтение отдельной команды по её идентификатору с её названием, типом,
отображаемым названием типа и родителем. Команда вне области видимости читателя SHALL отвечать
«не найдено», а некорректный идентификатор — ошибкой валидации.

#### Scenario: Чтение доступной команды

- GIVEN пользователю доступна команда
- WHEN он запрашивает её по идентификатору
- THEN он получает её название, тип, отображаемое название типа и родителя

#### Scenario: Команда вне области видимости

- GIVEN команда недоступна пользователю
- WHEN он запрашивает её по идентификатору
- THEN возвращается «не найдено»

#### Scenario: Некорректный идентификатор

- GIVEN пользователь передаёт нечисловой идентификатор команды
- WHEN запрос обрабатывается
- THEN возвращается ошибка валидации
