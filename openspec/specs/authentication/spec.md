# Authentication Specification

## Purpose

Возможность отвечает на вопрос «кто выполняет действие»: вход через внешних провайдеров
OAuth2/OIDC, идентичность пользователя, серверные сессии, режим работы без авторизации и
защита браузерных мутаций от подделки межсайтовых запросов.

## Requirements

### Requirement: Вход через внешних провайдеров

Система SHALL аутентифицировать пользователя через внешнего провайдера OAuth2/OIDC и SHALL
поддерживать несколько провайдеров одновременно. Набор доступных провайдеров SHALL расширяться
подключением нового провайдера по имени, без изменения поведения существующих.

#### Scenario: Успешный вход

- GIVEN неавторизованный посетитель и настроенный провайдер
- WHEN он проходит вход у провайдера и возвращается в приложение
- THEN создаётся сессия, профиль пользователя создаётся или обновляется, посетитель попадает в приложение

#### Scenario: Выбор провайдера

- GIVEN настроено несколько провайдеров
- WHEN неавторизованный посетитель открывает страницу входа
- THEN ему предлагается выбрать любой из настроенных провайдеров

### Requirement: Идентичность пользователя определяется парой «провайдер + субъект»

Система SHALL считать идентичностью пользователя пару «провайдер + идентификатор субъекта у
провайдера». Совпадение адреса электронной почты MUST NOT объединять учётные записи и MUST NOT
давать доступ.

#### Scenario: Один адрес почты у двух провайдеров

- GIVEN человек входит под одним адресом почты сначала через провайдера A, затем через провайдера B
- WHEN обе сессии созданы
- THEN это две независимые учётные записи с независимыми членствами и доступами

### Requirement: Обновление профиля при повторном входе

Система SHALL при повторном входе обновлять отображаемое имя, аватар и момент последнего входа
пользователя данными провайдера.

#### Scenario: Повторный вход после смены имени у провайдера

- GIVEN пользователь ранее входил и сменил имя у провайдера
- WHEN он входит снова
- THEN в приложении отображается новое имя, учётная запись остаётся прежней

### Requirement: Серверные сессии

Система SHALL хранить сессию на сервере и SHALL передавать клиенту только её идентификатор в
cookie. Cookie MUST быть недоступна скриптам страницы, MUST ограничивать межсайтовую отправку и
MUST помечаться как защищённая при работе по TLS.

#### Scenario: Содержимое cookie

- GIVEN пользователь авторизован
- WHEN он осматривает cookie сессии
- THEN cookie содержит только идентификатор сессии, без профиля, ролей и прав

#### Scenario: Истёкшая сессия

- GIVEN срок действия сессии истёк
- WHEN пользователь отправляет запрос с этим идентификатором сессии
- THEN сессия не резолвится и пользователь считается неавторизованным

#### Scenario: Выход

- GIVEN авторизованный пользователь
- WHEN он выполняет выход
- THEN сессия перестаёт резолвиться, а повторное использование её идентификатора не даёт доступа

### Requirement: Режим работы без авторизации

Система SHALL поддерживать режим, в котором вход не требуется. В этом режиме все действия
выполняются от имени системного пользователя `anonymous-local`, который имеет активную роль
администратора пространства.

#### Scenario: Действие в режиме без авторизации

- GIVEN система запущена в режиме без авторизации
- WHEN посетитель создаёт цель или комментарий
- THEN автором действия фиксируется системный пользователь `anonymous-local`

#### Scenario: Кросс-тенантная плоскость в режиме без авторизации

- GIVEN система запущена в режиме без авторизации
- WHEN посетитель обращается к кросс-тенантной плоскости управления
- THEN доступ не предоставляется: `anonymous-local` не является пользователем системного уровня

### Requirement: Начальная выдача системной привилегии

Система SHALL позволять назначить первого пользователя системного уровня конфигурацией
инстанса. Назначение SHALL срабатывать при первом совпавшем входе и только пока в инстансе нет
ни одного пользователя системного уровня.

#### Scenario: Первый вход назначенного пользователя

- GIVEN в инстансе нет ни одного пользователя системного уровня и задан кандидат
- WHEN кандидат впервые входит в систему
- THEN он получает системную привилегию

#### Scenario: Инстанс уже имеет системного пользователя

- GIVEN в инстансе уже есть пользователь системного уровня
- WHEN входит кандидат, заданный конфигурацией
- THEN привилегия ему не выдаётся; дальнейшая выдача возможна только явным действием

### Requirement: Защита браузерных мутаций от межсайтовой подделки

Система SHALL проверять токен защиты от межсайтовой подделки для всех изменяющих состояние
HTTP-действий, вызываемых из браузера.

#### Scenario: Мутация без токена

- GIVEN авторизованный пользователь
- WHEN из браузера отправляется изменяющий состояние запрос без валидного токена защиты
- THEN запрос отклоняется и состояние не меняется

#### Scenario: Чтение не требует токена

- GIVEN авторизованный пользователь
- WHEN он выполняет запрос только на чтение
- THEN токен защиты не требуется

#### Scenario: Мутация без парной cookie

- GIVEN у клиента отсутствует cookie с токеном защиты
- WHEN он отправляет изменяющий состояние запрос
- THEN запрос отклоняется, даже если токен передан в запросе

#### Scenario: Токен передаётся заголовком или полем формы

- GIVEN клиент отправляет изменяющий состояние запрос
- WHEN токен передан либо специальным заголовком, либо полем формы
- THEN оба способа принимаются, а значение сверяется с cookie

### Requirement: Ротация токена защиты от межсайтовой подделки

Система SHALL выдавать новый токен защиты на каждом безопасном запросе, обновляя cookie. Токен
MUST NOT быть постоянным; клиент SHALL подставлять в мутацию актуальное значение.

#### Scenario: Обновление токена при чтении

- GIVEN клиент выполняет безопасный запрос
- WHEN ответ получен
- THEN cookie с токеном защиты содержит новое значение

#### Scenario: Устаревший токен в мутации

- GIVEN клиент использует значение токена, которое уже было заменено
- WHEN он отправляет изменяющий состояние запрос
- THEN запрос отклоняется и состояние не меняется

### Requirement: Машинный вызов не требует токена защиты

Система SHALL пропускать без проверки токена защиты машинный вызов, аутентифицированный
инстанс-токеном, поскольку такой запрос не использует cookie браузера и не может быть подделан
межсайтовым способом.

#### Scenario: Provisioning-вызов

- GIVEN машинный вызывающий обращается с инстанс-токеном
- WHEN он выполняет изменяющий состояние запрос
- THEN токен защиты от межсайтовой подделки не требуется

### Requirement: Неавторизованный запрос обрабатывается по типу вызывающего

Система SHALL по-разному отвечать на неавторизованный запрос в зависимости от того, открывает ли
его человек в браузере или выполняет программный клиент. Запрос страницы SHALL перенаправляться
на вход, запрос к данным SHALL получать ответ «не авторизован» без перенаправления.

#### Scenario: Открытие страницы без авторизации

- GIVEN неавторизованный посетитель
- WHEN он открывает страницу приложения
- THEN он перенаправляется на страницу входа

#### Scenario: Запрос к данным без авторизации

- GIVEN неавторизованный клиент
- WHEN он обращается к данным приложения
- THEN он получает ответ «не авторизован» и MUST NOT получать перенаправление, которое клиент принял бы за успешный ответ

#### Scenario: Запрос, явно ожидающий данные

- GIVEN неавторизованный клиент запрашивает адрес страницы, но явно указывает, что ожидает данные, а не разметку
- WHEN запрос обрабатывается
- THEN он получает ответ «не авторизован», а не перенаправление

### Requirement: Возврат на исходную страницу после входа

Система SHALL сохранять адрес запрошенной страницы при перенаправлении на вход и возвращать
пользователя на него после успешного входа.

#### Scenario: Переход по ссылке в неавторизованном сеансе

- GIVEN пользователю прислали ссылку на конкретную команду и период
- WHEN он открывает её, не будучи авторизованным, и проходит вход
- THEN после входа он попадает на ту же страницу с теми же параметрами, а не на стартовую

#### Scenario: Адрес без параметров

- GIVEN неавторизованный посетитель открывает раздел без параметров
- WHEN он проходит вход
- THEN он попадает в этот раздел
