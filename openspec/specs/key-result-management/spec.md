# Key Result Management Specification

## Purpose

Ключевой результат (KR) — измеримая часть цели. Возможность описывает три типа KR, их поля и
справочники, промежуточные значения, порядок, заметку и описание KR.

## Requirements

### Requirement: Ключевой результат принадлежит одной цели

Система SHALL связывать ключевой результат ровно с одной целью. При удалении цели её ключевые
результаты SHALL удаляться вместе с ней.

#### Scenario: Удаление цели

- GIVEN у цели есть ключевые результаты
- WHEN цель удаляется
- THEN её ключевые результаты также удаляются

### Requirement: Три типа ключевого результата

Система SHALL поддерживать три типа ключевого результата: бинарный, проектный (этапы с весами) и
числовой. Иные типы MUST NOT приниматься.

#### Scenario: Создание проектного KR

- GIVEN пользователь создаёт ключевой результат проектного типа
- WHEN он задаёт этапы с весами
- THEN ключевой результат сохраняется с этими этапами

#### Scenario: Неизвестный тип

- GIVEN пользователь отправляет ключевой результат с типом вне перечня
- WHEN запрос обрабатывается
- THEN операция отклоняется как ошибка валидации

### Requirement: Единица измерения числового KR

Система SHALL требовать для числового ключевого результата единицу измерения из закрытого
справочника и SHALL отклонять значения вне справочника. Свободный ввод единицы измерения MUST
NOT поддерживаться.

#### Scenario: Единица из справочника

- GIVEN пользователь создаёт числовой ключевой результат
- WHEN он выбирает единицу измерения из справочника
- THEN ключевой результат сохраняется

#### Scenario: Произвольная единица

- GIVEN пользователь передаёт единицу измерения, отсутствующую в справочнике
- WHEN запрос обрабатывается
- THEN операция отклоняется как ошибка валидации

### Requirement: Значения числового KR

Система SHALL хранить у числового ключевого результата стартовое, целевое и текущее значения.

#### Scenario: Числовой KR со снижением метрики

- GIVEN стартовое значение больше целевого
- WHEN ключевой результат сохраняется
- THEN он принимается: направление изменения метрики не ограничивается

### Requirement: Промежуточные значения числового KR

Система SHALL позволять задавать числовому ключевому результату необязательные промежуточные
значения с указанием процента выполнения. Проценты SHALL быть в диапазоне от 0 до 100, значения
MUST NOT дублироваться. Промежуточные значения SHALL загружаться вместе с ключевым результатом.

#### Scenario: Дублирующее промежуточное значение

- GIVEN пользователь задаёт два промежуточных значения с одинаковым значением метрики
- WHEN он сохраняет ключевой результат
- THEN операция отклоняется как ошибка валидации

#### Scenario: Процент вне диапазона

- GIVEN пользователь задаёт промежуточному значению процент больше 100
- WHEN он сохраняет ключевой результат
- THEN операция отклоняется как ошибка валидации

### Requirement: Вес ключевого результата

Система SHALL хранить вес ключевого результата в диапазоне от 0 до 100 и SHALL отклонять
значения вне диапазона.

#### Scenario: Недопустимый вес

- GIVEN пользователь задаёт ключевому результату вес больше 100
- WHEN он сохраняет изменения
- THEN операция отклоняется как ошибка валидации

### Requirement: Порядок ключевых результатов внутри цели

Система SHALL поддерживать порядок ключевых результатов внутри цели независимо от порядка целей.

#### Scenario: Перестановка KR

- GIVEN у цели несколько ключевых результатов
- WHEN пользователь меняет их порядок
- THEN новый порядок сохраняется и отображается при следующем открытии цели

### Requirement: Критерий обнуления

Система SHALL позволять задать ключевому результату любого типа необязательный человекочитаемый
критерий обнуления. Критерий MUST NOT участвовать в расчётах.

#### Scenario: Критерий обнуления у бинарного KR

- GIVEN пользователь задаёт критерий обнуления бинарному ключевому результату
- WHEN ключевой результат сохраняется
- THEN критерий отображается, а расчёт прогресса не меняется

### Requirement: Заметка ключевого результата

Система SHALL хранить не более одной заметки на ключевой результат с указанием её автора.
Заметка MUST NOT удаляться через интерфейс приложения — её можно только перезаписать. При
удалении ключевого результата заметка SHALL удаляться.

#### Scenario: Перезапись заметки

- GIVEN у ключевого результата уже есть заметка
- WHEN пользователь сохраняет новый текст заметки
- THEN прежний текст заменяется, автором фиксируется текущий пользователь

#### Scenario: Автор заметки в режиме без авторизации

- GIVEN система работает в режиме без авторизации
- WHEN сохраняется заметка
- THEN её автором фиксируется системный пользователь `anonymous-local`

### Requirement: Описание ключевого результата в окне обновления прогресса

Система SHALL показывать описание ключевого результата в окне обновления прогресса как
нередактируемую справку. Если описания нет, SHALL предлагаться его добавить, и введённый текст
SHALL сохраняться вместе с прогрессом.

#### Scenario: Описание отсутствует

- GIVEN у ключевого результата нет описания
- WHEN пользователь открывает окно обновления прогресса
- THEN вместо блока описания отображается предложение добавить описание

### Requirement: Удаление ключевого результата требует подтверждения

Система SHALL запрашивать подтверждение перед удалением ключевого результата.

#### Scenario: Подтверждение удаления

- GIVEN пользователь нажал удаление ключевого результата
- WHEN отображается запрос подтверждения
- THEN ключевой результат удаляется только после явного подтверждения

### Requirement: Форматирование числовых значений в интерфейсе

Система SHALL отображать и принимать значения метрики числового ключевого результата с
группировкой разрядов по тысячам, сохраняя позицию курсора при вводе. Проценты и веса SHALL
отображаться без группировки. В данных обмена значения SHALL оставаться числами без
разделителей.

#### Scenario: Ввод большого значения

- GIVEN пользователь вводит целевое значение метрики
- WHEN он набирает число из шести знаков
- THEN значение отображается с разделением разрядов, а курсор остаётся на месте ввода

#### Scenario: Отображение веса

- GIVEN вес ключевого результата равен 100
- WHEN он отображается
- THEN он показывается без разделителей разрядов

### Requirement: Заметка в составе чек-ина

Система SHALL различать при чек-ине отсутствие поля заметки и переданную пустую строку.
Отсутствие поля означает «не трогать заметку». Пустая строка SHALL стирать текст заметки, сохраняя
саму запись с её автором и моментом изменения.

#### Scenario: Заметка не передана

- GIVEN у ключевого результата есть заметка, пользователь обновляет только прогресс
- WHEN операция выполняется
- THEN текст заметки остаётся прежним

#### Scenario: Передана пустая заметка

- GIVEN у ключевого результата есть заметка
- WHEN пользователь сохраняет чек-ин с пустой строкой в поле заметки
- THEN текст заметки становится пустым, но запись заметки сохраняется с новым автором и моментом изменения

### Requirement: Отдельное сохранение заметки требует непустого текста

Система SHALL отклонять как ошибку валидации отдельное сохранение заметки ключевого результата с
пустым или состоящим из пробелов текстом. Этим отдельное сохранение отличается от поля заметки в
чек-ине, где пустая строка допустима.

#### Scenario: Пустой текст при отдельном сохранении

- GIVEN пользователь сохраняет заметку отдельной операцией
- WHEN текст пуст или состоит только из пробелов
- THEN операция отклоняется как ошибка валидации
