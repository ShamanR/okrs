# Notifications Specification

## Purpose

Уведомления — персональная лента событий, касающихся пользователя: комментарии к целям, решение
его замечаний, изменения целей и обновления прогресса. Возможность описывает ленту и счётчик
непрочитанного, схлопывание повторов, определение получателей по дереву команд, персональные
настройки и срок хранения.

## Requirements

### Requirement: Уведомления доступны только своему получателю

Система SHALL определять получателя уведомлений исключительно по текущей сессии. Возможность
указать другого получателя MUST NOT существовать в контракте: ни лента, ни счётчик, ни пометка
прочитанным, ни настройки не принимают получателя из запроса.

#### Scenario: Чтение ленты

- GIVEN авторизованный пользователь
- WHEN он запрашивает ленту уведомлений
- THEN он получает только свои уведомления в своём активном пространстве

#### Scenario: Пометка чужого уведомления прочитанным

- GIVEN пользователь знает идентификатор уведомления другого человека
- WHEN он отправляет пометку прочитанным с этим идентификатором
- THEN ни одно чужое уведомление не изменяется

#### Scenario: Удаление чужого уведомления

- GIVEN пользователь знает идентификатор уведомления другого человека
- WHEN он пытается его удалить
- THEN возвращается «не найдено» — ответ неотличим от ответа для несуществующего уведомления

### Requirement: Лента и постраничная загрузка

Система SHALL отдавать ленту уведомлений от свежих к старым, с возможностью запросить только
непрочитанные и с постраничной загрузкой.

#### Scenario: Только непрочитанные

- GIVEN у пользователя есть прочитанные и непрочитанные уведомления
- WHEN он запрашивает только непрочитанные
- THEN в ленте отсутствуют прочитанные

### Requirement: Счётчик непрочитанного

Система SHALL отдавать число непрочитанных уведомлений пользователя как значение, вычисляемое по
самим записям, без отдельного накапливаемого счётчика.

#### Scenario: Удаление непрочитанного уведомления

- GIVEN у пользователя есть непрочитанное уведомление
- WHEN он удаляет его
- THEN счётчик непрочитанного уменьшается без рассинхронизации со списком

#### Scenario: Согласованность в многоинстансной среде

- GIVEN приложение развёрнуто в нескольких экземплярах
- WHEN пользователь запрашивает счётчик у разных экземпляров
- THEN он получает одинаковое значение

### Requirement: Открытие панели не помечает уведомления прочитанными

Система MUST NOT помечать уведомления прочитанными самим фактом загрузки ленты. Пометка SHALL
происходить только по явному действию пользователя.

#### Scenario: Просмотр панели

- GIVEN у пользователя есть непрочитанные уведомления
- WHEN он открывает панель и закрывает её, ничего не выбрав
- THEN уведомления остаются непрочитанными

#### Scenario: Отметить все прочитанными

- GIVEN у пользователя несколько непрочитанных уведомлений
- WHEN он отмечает все прочитанными
- THEN все они становятся прочитанными, счётчик обнуляется

#### Scenario: Идемпотентная пометка

- GIVEN уведомление уже прочитано
- WHEN пользователь помечает его прочитанным снова
- THEN операция завершается успешно и ничего не меняет

### Requirement: Различие пометки прочитанным и удаления

Система SHALL оставлять прочитанное уведомление в ленте до истечения срока хранения и SHALL
убирать удалённое уведомление немедленно.

#### Scenario: Прочитанное остаётся в ленте

- GIVEN пользователь пометил уведомление прочитанным
- WHEN он открывает ленту
- THEN уведомление отображается как прочитанное

### Requirement: Схлопывание повторов

Система SHALL схлопывать повторные уведомления одного типа об одной сущности от одного автора в
пределах фиксированного временного окна в одну запись со счётчиком повторов. Схлопывание SHALL
выполняться одной атомарной операцией, безопасной при одновременной работе нескольких
экземпляров приложения.

#### Scenario: Правка цели с двумя ключевыми результатами

- GIVEN автор в пределах одного окна изменяет цель и два её ключевых результата
- WHEN получатель открывает ленту
- THEN он видит одно уведомление со счётчиком повторов, а не три отдельных

#### Scenario: Повтор возвращает уведомление в непрочитанные

- GIVEN получатель уже прочитал уведомление
- WHEN в пределах того же окна происходит повтор того же события
- THEN уведомление снова становится непрочитанным, а счётчик повторов увеличивается

#### Scenario: Окно фиксировано, а не скользящее

- GIVEN события происходят по разные стороны границы окна
- WHEN формируются уведомления
- THEN они не схлопываются между собой, даже если интервал между ними меньше длины окна

### Requirement: Сущность схлопывания

Система SHALL использовать в качестве сущности схлопывания сам ключевой результат для
уведомлений об обновлении прогресса и цель — для всех остальных типов.

#### Scenario: Обновление двух ключевых результатов одной цели

- GIVEN автор обновляет прогресс двух ключевых результатов одной цели в пределах окна
- WHEN получатель открывает ленту
- THEN он видит два отдельных уведомления — по одному на ключевой результат

### Requirement: Автор события не получает уведомления о собственном действии

Система MUST NOT создавать уведомление, получателем которого был бы автор самого события.

#### Scenario: Комментарий к собственной цели

- GIVEN пользователь оставляет замечание к цели своей команды
- WHEN определяются получатели
- THEN сам автор уведомления не получает

### Requirement: Адресные уведомления

Система SHALL доставлять уведомление о решении замечания непосредственно автору этого замечания.
Охват дерева команд к адресным уведомлениям MUST NOT применяться.

#### Scenario: Замечание решено другим человеком

- GIVEN замечание пользователя решено другим человеком
- WHEN определяются получатели
- THEN уведомление получает автор замечания

### Requirement: Определение получателей по дереву команд

Система SHALL определять получателей уведомлений со скоупом обходом дерева команд вверх от
команды события к корню, по настройкам каждого получателя. Резолв SHALL выполняться пакетно для
группы событий, без отдельного запроса на каждое событие.

#### Scenario: Охват «только моя команда»

- GIVEN руководитель настроил охват «только моя команда»
- WHEN событие происходит в команде-потомке
- THEN он уведомления не получает

#### Scenario: Охват «моя команда и потомки»

- GIVEN руководитель настроил охват «моя команда и её непосредственные потомки»
- WHEN событие происходит в прямой дочерней команде
- THEN он получает уведомление

#### Scenario: Охват «всё поддерево»

- GIVEN руководитель настроил охват «всё поддерево»
- WHEN событие происходит в любой команде-потомке на любой глубине
- THEN он получает уведомление

### Requirement: Настройки уведомлений пользователя

Система SHALL предоставлять пользователю матрицу настроек по типам уведомлений: включение,
охват дерева команд (кроме адресных типов) и каналы доставки. Настройки SHALL сохраняться
целиком, а не по одной строке.

#### Scenario: Сохранение матрицы

- GIVEN пользователь изменил несколько строк настроек
- WHEN он сохраняет форму
- THEN сохраняется вся матрица целиком

#### Scenario: Повторное сохранение той же матрицы

- GIVEN пользователь сохраняет ту же матрицу дважды
- WHEN операция выполняется
- THEN итоговое состояние совпадает

#### Scenario: Неизвестный тип или охват

- GIVEN пользователь передаёт неизвестный тип уведомления или неизвестный охват
- WHEN запрос обрабатывается
- THEN операция отклоняется как ошибка валидации

### Requirement: Отсутствие настройки означает значение по умолчанию

Система SHALL считать отсутствие сохранённой настройки нормой и подставлять значения по
умолчанию — уведомления включены, охват «только моя команда», канал «в приложении» — как при
чтении настроек, так и при определении получателей. Предзаполнение настроек для всех
пользователей MUST NOT выполняться.

#### Scenario: Новый пользователь открывает настройки

- GIVEN пользователь ни разу не менял настройки уведомлений
- WHEN он открывает раздел настроек
- THEN он видит все типы уведомлений со значениями по умолчанию

### Requirement: Охват неприменим к адресным типам

Система MUST NOT предлагать выбор охвата для адресных типов уведомлений и SHALL помечать их как
адресные.

#### Scenario: Настройка адресного типа

- GIVEN пользователь открывает настройки уведомлений
- WHEN он смотрит на адресный тип
- THEN у него нет выбора охвата, а сам тип помечен как адресный

### Requirement: Срок хранения уведомлений

Система SHALL удалять фоновым процессом прочитанные уведомления, нетронутые дольше заданного
срока, и любые уведомления, нетронутые дольше большего срока. Возраст SHALL отсчитываться от
последнего изменения записи, а не от её создания.

#### Scenario: Давнее уведомление, продолжающее собирать повторы

- GIVEN уведомление создано давно, но недавно схлопнуло новый повтор и снова стало непрочитанным
- WHEN выполняется удаление по сроку хранения
- THEN уведомление не удаляется

#### Scenario: Удаление по сроку не управляется правами

- GIVEN истёк срок хранения уведомлений
- WHEN выполняется фоновая очистка
- THEN уведомления удаляются независимо от пространства и получателя, без участия пользователя

### Requirement: Закрытый набор типов уведомлений

Система SHALL поддерживать ровно четыре типа уведомлений: комментарий к цели, решение моего
замечания, изменение цели и чек-ин ключевого результата. Набор SHALL быть закрытым: неизвестный
тип в настройках отклоняется, а ответ с настройками всегда содержит все четыре типа.

#### Scenario: Полный перечень в настройках

- GIVEN пользователь открывает настройки уведомлений
- WHEN перечень загружается
- THEN он содержит ровно четыре типа

### Requirement: Какие действия порождают уведомления

Система SHALL порождать уведомления только по закрытому перечню действий:

- добавление замечания и добавление ответа — тип «комментарий к цели»;
- отметка замечания решённым — адресный тип «решение моего замечания»;
- создание, копирование, перенос и удаление цели, изменение полей цели, смена владельца цели, а
  также создание, изменение и удаление ключевого результата — тип «изменение цели»;
- чек-ин ключевого результата, включая чек-ин, изменивший только заметку или только
  health-статус, — тип «чек-ин ключевого результата».

Расширение этого перечня SHALL считаться продуктовым решением, а не деталью реализации.

#### Scenario: Удаление цели уведомляет как изменение цели

- GIVEN пользователь удаляет цель
- WHEN определяются получатели
- THEN они получают уведомление типа «изменение цели»

#### Scenario: Чек-ин только с заметкой

- GIVEN пользователь меняет только заметку ключевого результата
- WHEN определяются получатели
- THEN они получают уведомление типа «чек-ин ключевого результата»

### Requirement: Действия, намеренно не порождающие уведомлений

Система MUST NOT порождать уведомления при: расшаривании цели, снятии участия команды в цели,
привязке и отвязке родительской цели, смене статуса команды в периоде, повторном открытии
замечания, удалении замечания и удалении ответа.

#### Scenario: Смена статуса команды

- GIVEN руководитель переводит команду в другой статус
- WHEN событие обрабатывается
- THEN уведомления не создаются ни у кого

#### Scenario: Расшаривание цели

- GIVEN цель расшаривается в другую команду
- WHEN событие обрабатывается
- THEN уведомления не создаются

#### Scenario: Удаление замечания

- GIVEN автор удаляет своё замечание
- WHEN событие обрабатывается
- THEN уведомления не создаются, при том что добавление замечания их порождает

### Requirement: Длинный текст в уведомлении сокращается

Система SHALL сокращать длинный текст замечания или заметки в теле уведомления, обозначая
сокращение многоточием. Сокращение SHALL выполняться по границам символов, не разрывая их.
Полный текст SHALL оставаться доступным в самой сущности.

#### Scenario: Длинное замечание

- GIVEN пользователь оставляет замечание длиннее предела показа
- WHEN получатель видит уведомление
- THEN в теле уведомления показано начало текста с многоточием

#### Scenario: Короткое замечание

- GIVEN текст замечания короче предела показа
- WHEN получатель видит уведомление
- THEN текст показан целиком, без многоточия

#### Scenario: Текст с многобайтовыми символами

- GIVEN текст содержит символы, занимающие несколько байтов
- WHEN текст сокращается
- THEN сокращение не разрывает символ и текст остаётся читаемым

### Requirement: Обновление счётчика непрочитанного в интерфейсе

Система SHALL обновлять счётчик непрочитанного примерно раз в минуту, пока страница открыта, и
дополнительно при возвращении пользователя на вкладку.

#### Scenario: Уведомление пришло, пока страница открыта

- GIVEN пользователь держит страницу открытой
- WHEN ему приходит новое уведомление
- THEN счётчик обновляется в пределах примерно минуты без действий пользователя

#### Scenario: Возврат на вкладку

- GIVEN пользователь переключился на другую вкладку и вернулся
- WHEN вкладка снова активна
- THEN счётчик обновляется сразу, не дожидаясь очередного цикла

### Requirement: Ранее созданные уведомления сохраняют свой смысл и вид

Система SHALL продолжать читать и отображать уведомления, созданные до изменения правил их
формирования, с прежним смыслом и прежним текстом. Такие уведомления MUST NOT деградировать до
обобщённой подписи и MUST NOT менять свой тип при последующих чтениях.

#### Scenario: Уведомление, созданное по прежним правилам

- GIVEN в ленте есть уведомление, созданное до изменения правил формирования
- WHEN получатель открывает ленту
- THEN уведомление отображается с осмысленным заголовком и текстом, соответствующими действию, которое его породило

#### Scenario: Схлопывание не переписывает прежнее уведомление

- GIVEN уведомление создано по прежним правилам и повторяется в пределах окна схлопывания
- WHEN повтор схлопывается в ту же строку
- THEN уведомление сохраняет прежний вид, а счётчик повторов увеличивается

#### Scenario: Настройки применяются к прежним уведомлениям так же

- GIVEN у получателя есть прежние и новые уведомления одного смысла
- WHEN он отключает соответствующий тип в настройках
- THEN правило применяется к обоим одинаково: смысл прежнего уведомления не расходится с новым

#### Scenario: Прежние уведомления уходят по общему сроку хранения

- GIVEN прежние уведомления перестали обновляться
- WHEN наступает срок хранения
- THEN они удаляются по тем же правилам, что и остальные
