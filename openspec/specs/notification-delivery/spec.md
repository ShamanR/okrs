# Notification Delivery Specification

## Purpose

Доставка созданного уведомления во внешние каналы: выбор каналов получателя,
накопление обновлений и отправка их одним сообщением, поведение при остановке
экземпляра приложения, при переполнении накопленного и при недоступности
внешнего сервиса.

## Requirements

### Requirement: Доставка уведомления в каналы получателя

Система ОБЯЗАНА передавать созданное уведомление во все каналы, включённые у его
получателя для соответствующего типа уведомления. Канал, отключённый получателем
для этого типа, участвовать в доставке НЕ ДОЛЖЕН. Канал, недоступный
пространству или выключенный администратором, участвовать в доставке НЕ ДОЛЖЕН
независимо от настроек получателя.

#### Scenario: Канал включён получателем

- GIVEN у получателя включён внешний канал для типа «комментарий к цели»
- WHEN для него создаётся уведомление этого типа
- THEN уведомление доставляется в этот канал

#### Scenario: Канал отключён получателем для одного типа

- GIVEN получатель отключил внешний канал для типа «чек-ин ключевого результата»,
  оставив его включённым для остальных типов
- WHEN для него создаётся уведомление о чек-ине
- THEN в этот канал оно не доставляется, а уведомления остальных типов доставляются

#### Scenario: Администратор выключил канал

- GIVEN получатель не отключал канал, но администратор пространства выключил его
- WHEN для получателя создаётся уведомление
- THEN доставка в этот канал не выполняется

### Requirement: Накопленные обновления отправляются одним сообщением

Система ОБЯЗАНА накапливать уведомления получателя и отправлять их одним
сообщением по истечении окна отправки канала. Отдельное сообщение на каждое
уведомление отправляться НЕ ДОЛЖНО. Формирование текста накопленного сообщения
НЕОБХОДИМО относить к самому каналу, поскольку формат сообщения определяется
внешним сервисом.

#### Scenario: Несколько уведомлений за одно окно

- GIVEN за время одного окна получателю создано несколько уведомлений
- WHEN окно истекает
- THEN получатель получает одно сообщение, содержащее все накопленные обновления

#### Scenario: Одно уведомление за окно

- GIVEN за время окна получателю создано ровно одно уведомление
- WHEN окно истекает
- THEN получатель получает одно сообщение с этим обновлением

#### Scenario: За окно не создано ни одного уведомления

- GIVEN за время окна получателю не создано ни одного уведомления
- WHEN окно истекает
- THEN сообщение не отправляется

#### Scenario: Накопление раздельно по получателям

- GIVEN за время окна созданы уведомления для двух разных получателей
- WHEN окно истекает
- THEN каждый получает собственное сообщение только со своими обновлениями

### Requirement: Отправка накопленного при остановке и при изменении настроек

Система ОБЯЗАНА отправлять накопленные, но ещё не отправленные обновления при
штатной остановке экземпляра приложения и перед применением изменённых настроек
канала. Отправка при остановке ОБЯЗАНА быть ограничена по времени, чтобы не
задерживать остановку неограниченно.

#### Scenario: Штатная остановка экземпляра

- GIVEN в накопленном есть неотправленные обновления
- WHEN экземпляр приложения штатно останавливается
- THEN накопленное отправляется до завершения работы

#### Scenario: Администратор изменил настройки канала

- GIVEN в накопленном есть неотправленные обновления
- WHEN администратор сохраняет изменённые настройки канала
- THEN накопленное отправляется по прежним настройкам, после чего начинает
  действовать новая конфигурация

#### Scenario: Аварийное завершение экземпляра

- GIVEN в накопленном есть неотправленные обновления
- WHEN экземпляр приложения завершается аварийно
- THEN накопленное теряется, и это допустимое поведение: лента уведомлений
  получателя при этом не страдает

### Requirement: Ограничение объёма накопленного

Система ОБЯЗАНА ограничивать объём накопленного для одного получателя. При
достижении предела самые старые накопленные обновления ОБЯЗАНЫ отбрасываться,
а приём новых ОБЯЗАН продолжаться.

#### Scenario: Внешний сервис недоступен длительное время

- GIVEN внешний сервис недоступен, и накопленное для получателя достигло предела
- WHEN для этого получателя создаются новые уведомления
- THEN новые обновления принимаются, а самые старые отбрасываются

#### Scenario: Шумный получатель не вытесняет остальных

- GIVEN для одного получателя накоплено предельное количество обновлений
- WHEN создаётся уведомление для другого получателя
- THEN оно принимается в полном объёме

### Requirement: Доставка не влияет на ленту уведомлений

Система ОБЯЗАНА создавать уведомление и показывать его в ленте независимо от
того, удалась ли доставка во внешние каналы. Неудачная доставка изменять запись
уведомления, её признак прочитанности или счётчик непрочитанного НЕ ДОЛЖНА.

#### Scenario: Внешний сервис отверг отправку

- GIVEN внешний сервис отвечает отказом
- WHEN получателю создаётся уведомление
- THEN оно присутствует в ленте и учитывается в счётчике как обычно

### Requirement: Ошибка доставки не доходит до получателя и не раскрывает секрет

Система ОБЯЗАНА записывать ошибку доставки в журнал приложения. Ошибка доставки
показываться получателю или автору события НЕ ДОЛЖНА. Значение секрета канала
в журнале присутствовать НЕ ДОЛЖНО, в том числе если канал подставляет секрет
в адрес запроса.

#### Scenario: Отправка завершилась ошибкой

- GIVEN внешний сервис отверг отправку накопленного сообщения
- WHEN ошибка обрабатывается
- THEN она попадает в журнал приложения, и ни получатель, ни автор события её не видят

#### Scenario: Ошибка содержит секрет канала

- GIVEN канал формирует адрес запроса, включающий секрет
- WHEN ошибка доставки записывается в журнал
- THEN значение секрета в записи отсутствует

### Requirement: Ссылка в доставленном сообщении открывается извне продукта

Ссылка на цель в сообщении, отправленном во внешний канал, ОБЯЗАНА быть
абсолютной. Относительная ссылка в мессенджере не работает: она либо остаётся
текстом, который нельзя нажать, либо разрешается относительно адреса самого
мессенджера и ведёт не туда.

Если у развёртывания не настроен собственный адрес, ссылка отправляться НЕ
ДОЛЖНА — сообщение при этом уходит без неё. Ссылка, которую нельзя открыть,
хуже её отсутствия.

Внешний вид ссылки НЕОБХОДИМО относить к самому каналу: способ сделать её
нажимаемой определяется тем, как принимающая сторона отображает сообщения.

#### Scenario: Адрес продукта настроен

- GIVEN у развёртывания настроен собственный адрес
- WHEN получателю уходит сообщение об уведомлении, привязанном к цели
- THEN ссылка в сообщении абсолютная и открывает эту цель

#### Scenario: Адрес продукта не настроен

- GIVEN у развёртывания не настроен собственный адрес
- WHEN получателю уходит сообщение
- THEN сообщение доставляется без ссылки, а не со ссылкой, которую нельзя открыть

#### Scenario: Уведомление не привязано к цели

- GIVEN уведомление не указывает на цель
- WHEN формируется сообщение
- THEN ссылки в нём нет

### Requirement: Накопление выполняется в пределах одного экземпляра приложения

Система накапливает обновления в памяти экземпляра приложения. При нескольких
работающих экземплярах получатель за одно окно МОЖЕТ получить несколько
сообщений — по одному от каждого экземпляра, обработавшего события. Каждое такое
сообщение ОБЯЗАНО быть непротиворечивым и содержать только те обновления,
которые действительно произошли.

#### Scenario: События обработаны разными экземплярами

- GIVEN приложение развёрнуто в нескольких экземплярах
- WHEN за одно окно события получателя обработаны разными экземплярами
- THEN получатель получает несколько сообщений, и ни одно обновление
  не дублируется между ними и не теряется
