# Settings Specification

## Purpose

Настройки разнесены по трём уровням с разной ответственностью: глобальные настройки инстанса,
настройки пространства и личные настройки пользователя. Возможность описывает, кто что может
менять, как настройки попадают в интерфейс участника и как работает сбор обратной связи.

## Requirements

### Requirement: Три уровня настроек с разной ответственностью

Система SHALL разделять настройки на три уровня: глобальные настройки инстанса, изменяемые
пользователем системного уровня; настройки пространства, изменяемые администратором
пространства; личные настройки пользователя, изменяемые им самим.

#### Scenario: Участник меняет личные настройки

- GIVEN авторизованный участник
- WHEN он изменяет своё личное предпочтение
- THEN изменение сохраняется и не влияет на других пользователей

#### Scenario: Администратор пространства и глобальная настройка

- GIVEN администратор пространства без системной привилегии
- WHEN он пытается изменить глобальную настройку инстанса
- THEN операция отклоняется

### Requirement: Два класса настроек пространства

Система SHALL различать в настройках пространства продуктовые ключи, изменяемые администратором
пространства, и тарифные возможности, изменяемые только пользователем системного уровня или
машинным provisioning-вызовом.

#### Scenario: Продуктовая настройка

- GIVEN администратор пространства
- WHEN он меняет продуктовую настройку своего пространства
- THEN изменение сохраняется и применяется без перезапуска приложения

#### Scenario: Тарифная возможность через продуктовый путь

- GIVEN администратор пространства
- WHEN он пытается изменить тарифную возможность через настройки своего пространства
- THEN операция отклоняется

### Requirement: Политика доступа новых пользователей

Система SHALL позволять администратору пространства выбрать политику для новых участников: не
выдавать доступа либо выдавать грант на узел иерархии по умолчанию. Политика SHALL применяться
без перезапуска и MUST NOT изменять уже выданные гранты.

#### Scenario: Смена политики

- GIVEN политика была «без доступа», уже есть участники с грантами
- WHEN администратор переключает политику на «узел по умолчанию»
- THEN новые участники получают грант на этот узел, а существующие гранты не меняются

### Requirement: Общие настройки пространства

Система SHALL позволять администратору пространства задавать название пространства, ссылку на
документацию и текст, показываемый участнику без доступных команд. Название MUST быть непустым.
Ссылка на документацию SHALL быть либо пустой, либо абсолютной ссылкой http(s); пустое значение
SHALL скрывать соответствующий пункт меню.

#### Scenario: Пустое название

- GIVEN администратор пространства сохраняет общие настройки
- WHEN он передаёт пустое название
- THEN операция отклоняется как ошибка валидации

#### Scenario: Некорректная ссылка на документацию

- GIVEN администратор передаёт значение, не являющееся абсолютной ссылкой http(s) и не пустое
- WHEN он сохраняет настройки
- THEN операция отклоняется как ошибка валидации

#### Scenario: Очистка ссылки на документацию

- GIVEN ссылка на документацию задана
- WHEN администратор сохраняет пустое значение
- THEN пункт меню «Документация» перестаёт отображаться

### Requirement: Пространство регистрации по умолчанию

Система SHALL позволять пользователю системного уровня задать пространство, в которое попадает
новый пользователь без членства, либо оставить значение незаданным.

#### Scenario: Значение снято

- GIVEN пространство регистрации по умолчанию было задано
- WHEN пользователь системного уровня снимает значение
- THEN новые пользователи без членства попадают на страницу «нет доступа»

### Requirement: Текст страницы «нет доступа»

Система SHALL позволять пользователю системного уровня задать текст страницы «нет доступа» с
разметкой. Пустое значение SHALL означать текст по умолчанию.

#### Scenario: Свой текст

- GIVEN пользователь системного уровня задал текст страницы «нет доступа»
- WHEN пользователь без членства открывает эту страницу
- THEN отображается заданный текст с применённой разметкой

### Requirement: Производные настройки в интерфейсе участника

Система SHALL отдавать авторизованному участнику значения настроек его пространства, влияющие на
отображение: порог дней без обновлений, допустимое отставание от темпа, порог «в плане», ссылку
на документацию, текст для пустой иерархии и параметры сбора обратной связи. Это SHALL
обеспечивать единую трактовку порогов интерфейсом и сводкой Health Check-in.

#### Scenario: Согласованность порогов

- GIVEN администратор изменил порог «в плане»
- WHEN участник открывает доску команды
- THEN подсветка прогресса использует новое значение без изменения кода интерфейса

#### Scenario: Признаки плоскостей администрирования приходят тем же ответом

- GIVEN участник загружает клиентскую конфигурацию
- WHEN ответ формируется
- THEN тем же ответом приходят признаки доступности администрирования пространства и администрирования инстанса; их смысл и границы применимости определяет возможность разграничения доступа

### Requirement: Настройки читаются снимком

Система SHALL читать настройки пространства на горячем пути одним снимком всех ключей через кэш,
а не отдельным обращением на каждый ключ.

#### Scenario: Открытие доски

- GIVEN на доске требуется несколько настроек пространства
- WHEN страница загружается
- THEN значения берутся из одного снимка настроек

### Requirement: Настройки сбора обратной связи

Система SHALL позволять администратору пространства задать ссылку на опрос, включение
всплывающего окна, включение пункта меню и интервал охлаждения показа окна в днях. Интервал MUST
быть не меньше одного дня. Пустая ссылка SHALL скрывать и пункт меню, и окно.

#### Scenario: Некорректный интервал

- GIVEN администратор задаёт интервал охлаждения меньше одного дня
- WHEN он сохраняет настройки
- THEN операция отклоняется как ошибка валидации

#### Scenario: Опасная схема ссылки

- GIVEN администратор передаёт ссылку с потенциально опасной схемой
- WHEN он сохраняет настройки
- THEN операция отклоняется как ошибка валидации

### Requirement: Показ окна обратной связи

Система SHALL показывать окно сбора обратной связи только когда оно включено и ссылка задана, и
при этом с начала текущего периода вовлечения прошло не менее двух суток, а с момента последнего
закрытия окна прошло не менее заданного интервала охлаждения. Отсчёт SHALL вестись на стороне
клиента.

#### Scenario: Первый заход

- GIVEN пользователь впервые открывает приложение
- WHEN окно обратной связи включено
- THEN окно не показывается

#### Scenario: Повтор после закрытия

- GIVEN пользователь закрыл окно
- WHEN с момента закрытия прошло меньше интервала охлаждения
- THEN окно не показывается снова

#### Scenario: Возвращение после долгого перерыва

- GIVEN пользователь не заходил дольше интервала охлаждения
- WHEN он открывает приложение
- THEN отсчёт периода вовлечения начинается заново и окно показывается не раньше чем через двое суток

#### Scenario: Закрытие окна

- GIVEN окно обратной связи открыто
- WHEN пользователь закрывает его любым способом или переходит по ссылке опроса
- THEN момент закрытия фиксируется и начинается отсчёт интервала охлаждения

### Requirement: Личные настройки пользователя

Система SHALL хранить личные настройки пользователя отдельно от настроек пространства и SHALL
позволять изменять их только самому пользователю.

#### Scenario: Личная настройка не видна другим

- GIVEN пользователь задал личное предпочтение
- WHEN другой пользователь того же пространства открывает свои настройки
- THEN он видит собственное значение, а не чужое
