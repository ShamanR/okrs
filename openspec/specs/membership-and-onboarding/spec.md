# Membership and Onboarding Specification

## Purpose

Возможность описывает, как человек попадает в пространство, как он там числится и как выходит:
активное членство как условие доступа, три примитива онбординга (авторегистрация,
пригласительная ссылка, заявка по slug), очередь заявок у администратора и раздел «Мои
пространства».

## Requirements

### Requirement: Доступ к приложению требует активного членства

Система SHALL пропускать в приложение только пользователя с активным членством в пространстве.
Членство в состоянии «заявка подана» доступа MUST NOT давать.

#### Scenario: Авторизованный пользователь без членства

- GIVEN пользователь авторизован, но не имеет активного членства ни в одном пространстве
- WHEN он открывает приложение
- THEN он попадает на страницу «нет доступа» с возможностью запросить доступ

#### Scenario: Пользователь с поданной заявкой

- GIVEN у пользователя есть членство в состоянии «заявка подана»
- WHEN он открывает приложение
- THEN он остаётся на странице «нет доступа»; заявка доступа не открывает

#### Scenario: Страница «нет доступа» не зацикливается

- GIVEN пользователь без активного членства
- WHEN он открывает страницу «нет доступа»
- THEN страница отображается без перенаправления на саму себя

### Requirement: Автоматическая регистрация в пространстве по умолчанию

Система SHALL при первом входе пользователя без активного членства автоматически создавать
активное членство с ролью обычного участника в пространстве регистрации по умолчанию, если оно
задано настройкой инстанса. Если пространство регистрации по умолчанию не задано, пользователь
SHALL попадать на страницу «нет доступа».

#### Scenario: Пространство по умолчанию задано

- GIVEN настроено пространство регистрации по умолчанию
- WHEN новый пользователь впервые входит в систему
- THEN ему создаётся активное членство с ролью обычного участника и применяется политика новых пользователей этого пространства

#### Scenario: Пространство по умолчанию не задано

- GIVEN пространство регистрации по умолчанию не задано
- WHEN новый пользователь впервые входит в систему
- THEN членство не создаётся и он попадает на страницу «нет доступа»

### Requirement: Пригласительная ссылка

Система SHALL позволять администратору пространства создавать пригласительную ссылку с
одноразовым или многоразовым использованием и SHALL привязывать активное членство только по
валидному токену ссылки.

#### Scenario: Приглашённый принимает ссылку будучи авторизованным

- GIVEN авторизованный пользователь открывает валидную пригласительную ссылку
- WHEN ссылка обрабатывается
- THEN токен погашается, пользователю создаётся активное членство в пространстве ссылки, активное пространство переключается на него

#### Scenario: Приглашённый не авторизован

- GIVEN неавторизованный посетитель открывает валидную пригласительную ссылку
- WHEN он проходит вход через любого провайдера
- THEN токен погашается после входа и членство привязывается к текущей идентичности

#### Scenario: Ограничение числа использований

- GIVEN ссылка создана с ограничением в N использований
- WHEN ссылку принимают в N+1-й раз
- THEN приглашение не срабатывает и членство не создаётся

#### Scenario: Недействительный токен

- GIVEN токен истёк, отозван, исчерпан или неизвестен
- WHEN посетитель открывает ссылку
- THEN он мягко перенаправляется без выдачи доступа и без сообщения об ошибке

#### Scenario: Совпадение адреса почты не даёт доступа

- GIVEN приглашение создано администратором
- WHEN посетитель без валидного токена входит под адресом почты, известным пространству
- THEN членство ему не создаётся

### Requirement: Хранение токена приглашения

Система SHALL хранить токен пригласительной ссылки в необратимом виде и MUST NOT возвращать его
в списке приглашений.

#### Scenario: Просмотр списка приглашений

- GIVEN администратор пространства создал несколько ссылок
- WHEN он открывает список приглашений
- THEN он видит роль, состояние, лимит и число использований, но не сам токен

### Requirement: Отзыв приглашения

Система SHALL позволять администратору пространства отзывать выданную ссылку. Операция SHALL
быть идемпотентной и SHALL действовать только в пределах его пространства.

#### Scenario: Повторный отзыв

- GIVEN ссылка уже отозвана
- WHEN администратор отзывает её снова
- THEN операция завершается успешно, состояние не меняется

### Requirement: Заявка на доступ по slug

Система SHALL позволять авторизованному пользователю запросить доступ к пространству по его
slug, создавая членство в состоянии «заявка подана». Публичный каталог пространств MUST
отсутствовать.

#### Scenario: Заявка по известному slug

- GIVEN авторизованный пользователь знает slug пространства
- WHEN он отправляет заявку
- THEN создаётся членство в состоянии «заявка подана» и заявка попадает в очередь администратора

#### Scenario: Заявка по неизвестному slug

- GIVEN slug не соответствует ни одному пространству
- WHEN пользователь отправляет заявку
- THEN возвращается «не найдено»

#### Scenario: Заявка при действующем членстве

- GIVEN пользователь уже является активным участником пространства
- WHEN он отправляет заявку в это же пространство
- THEN операция отклоняется как конфликт

### Requirement: Обработка заявок администратором пространства

Система SHALL предоставлять администратору пространства очередь заявок с действиями «одобрить»
и «отклонить». Одобрение SHALL переводить членство в активное, отклонение SHALL удалять
поданную заявку.

#### Scenario: Одобрение заявки

- GIVEN в очереди есть заявка
- WHEN администратор одобряет её
- THEN членство становится активным и пользователь получает доступ к пространству

#### Scenario: Отклонение заявки

- GIVEN в очереди есть заявка
- WHEN администратор отклоняет её
- THEN поданное членство удаляется и доступ не выдаётся

### Requirement: Единый базовый доступ новому участнику

Система SHALL применять политику новых пользователей пространства при автоматической
регистрации, при принятии приглашения, при одобрении заявки и при прямом подключении участника
пользователем системного уровня. Политика SHALL применяться только если у пользователя ещё нет
ни одного гранта в этом пространстве.

#### Scenario: Политика «узел по умолчанию»

- GIVEN пространство настроено выдавать новому участнику узел по умолчанию
- WHEN участник получает членство любым из способов и не имеет грантов в этом пространстве
- THEN ему выдаётся грант на узел по умолчанию

#### Scenario: У участника уже есть гранты

- GIVEN участнику ранее уже был выдан узел иерархии в этом пространстве
- WHEN он получает членство повторно
- THEN политика новых пользователей не применяется и существующие гранты не меняются

### Requirement: Раздел «Мои пространства»

Система SHALL показывать любому авторизованному пользователю список его членств во всех
состояниях и SHALL позволять из этого раздела отправить заявку по slug, выйти из пространства
или отменить собственную заявку.

#### Scenario: Просмотр списка

- GIVEN у пользователя есть активные членства и поданные заявки
- WHEN он открывает раздел «Мои пространства»
- THEN он видит все свои членства с их состоянием и ролью, отсортированные по названию пространства

#### Scenario: Выход из пространства

- GIVEN пользователь — активный участник пространства и не является его последним администратором
- WHEN он выходит из пространства
- THEN его членство и все его гранты в этом пространстве удаляются

#### Scenario: Отмена собственной заявки

- GIVEN пользователь подал заявку в пространство
- WHEN он отменяет её
- THEN поданное членство удаляется

#### Scenario: Идемпотентный выход

- GIVEN пользователь не является участником пространства
- WHEN он выполняет выход из него
- THEN операция завершается успешно и ничего не меняет

#### Scenario: Выход последнего администратора

- GIVEN пользователь — единственный активный администратор пространства
- WHEN он выходит из пространства
- THEN операция отклоняется как конфликт

### Requirement: Отвязка участника администратором

Система SHALL позволять администратору пространства отвязать участника: удалить его членство
любого состояния и все его гранты иерархии в этом пространстве. Операция SHALL быть
идемпотентной.

#### Scenario: Отвязка участника

- GIVEN участник состоит в пространстве и имеет гранты
- WHEN администратор пространства отвязывает его
- THEN членство и гранты в этом пространстве удаляются, доступ прекращается

### Requirement: Приглашение имеет приоритет над автоматической регистрацией

Система SHALL при первом входе пользователя без активного членства сначала пытаться применить
действующее приглашение и только при его отсутствии или недействительности применять
автоматическую регистрацию в пространстве по умолчанию.

#### Scenario: Вход по приглашению при заданном пространстве по умолчанию

- GIVEN задано пространство регистрации по умолчанию, и пользователь пришёл по действующему приглашению в другое пространство
- WHEN он проходит вход
- THEN он получает членство в пространстве приглашения, а не в пространстве по умолчанию, и активным становится пространство приглашения

#### Scenario: Недействительное приглашение при заданном пространстве по умолчанию

- GIVEN пользователь пришёл по истёкшему, отозванному или исчерпанному приглашению, и задано пространство регистрации по умолчанию
- WHEN он проходит вход
- THEN приглашение не срабатывает, и применяется автоматическая регистрация в пространстве по умолчанию

#### Scenario: Недействительное приглашение без пространства по умолчанию

- GIVEN пользователь пришёл по недействительному приглашению, пространство регистрации по умолчанию не задано
- WHEN он проходит вход
- THEN членство не создаётся и он попадает на экран «нет доступа»

### Requirement: Сбой онбординга не отменяет вход

Система SHALL завершать вход пользователя успешно, даже если применить онбординг не удалось.
Пользователь SHALL получить сеанс и попасть на экран «нет доступа», а не на ошибку входа.

#### Scenario: Онбординг не удалось применить

- GIVEN пользователь успешно прошёл проверку у внешнего провайдера
- WHEN применение онбординга завершается ошибкой
- THEN сеанс создаётся, вход считается успешным, пользователь попадает на экран «нет доступа»

#### Scenario: Повторный вход после сбоя

- GIVEN при предыдущем входе онбординг не применился
- WHEN пользователь входит снова
- THEN онбординг применяется повторно, и при успехе он получает членство
