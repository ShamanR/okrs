# observability-logging Specification

## Purpose

Capability описывает наблюдаемость приложения через логи: в каком формате
приложение выдаёт лог-записи во внешнюю систему сбора, какие ключевые события
и ошибки обязаны оставлять след, как записи одного запроса связываются между
собой и какие данные запрещено выводить в лог.

## Requirements

### Requirement: Формат и транспорт лог-записи

Приложение SHALL выводить каждую лог-запись в stdout одной строкой
в формате JSON, пригодном для машинного разбора системой сбора логов.
Приложение MUST NOT устанавливать сетевые соединения с системой сбора логов:
доставка является ответственностью инфраструктуры.

Формат вывода SHALL быть конфигурируемым: значение `json` (по умолчанию)
выдаёт машиночитаемый JSON, значение `text` выдаёт человекочитаемый текст
для локальной разработки.

Приложение MUST NOT прерывать обработку запроса или фоновой задачи из-за
невозможности записать лог.

#### Scenario: Вывод в режиме по умолчанию

- **WHEN** приложение запущено без явной настройки формата логов
- **THEN** каждая лог-запись выводится в stdout отдельной строкой
- **AND** строка является валидным JSON-объектом

#### Scenario: Многострочные значения не ломают запись

- **WHEN** в лог-запись попадает значение, содержащее переводы строк
  (например, стек паники)
- **THEN** запись остаётся одной строкой stdout
- **AND** переводы строк экранированы внутри JSON-значения

#### Scenario: Человекочитаемый формат для разработки

- **WHEN** формат логов явно переключён на `text`
- **THEN** записи выводятся в человекочитаемом текстовом виде
- **AND** состав полей записи не меняется

### Requirement: Обязательные поля лог-записи

Каждая лог-запись SHALL содержать поля: временную метку, уровень,
человекочитаемое сообщение, стабильный идентификатор типа события,
имя сервиса и окружение развёртывания.

Стабильный идентификатор типа события MUST быть машиночитаемым
и не зависеть от текста сообщения, чтобы записи можно было фильтровать
и агрегировать без разбора текста.

Записи, порождённые обработкой HTTP-запроса, SHALL дополнительно содержать
идентификатор запроса. Записи, относящиеся к действию в контексте
организации, SHALL дополнительно содержать идентификатор организации,
а при наличии — идентификатор действующего пользователя, команды и периода.

#### Scenario: Базовый набор полей присутствует

- **WHEN** приложение выводит любую лог-запись
- **THEN** запись содержит временную метку, уровень, сообщение,
  идентификатор типа события, имя сервиса и окружение

#### Scenario: Контекст организации в записи о действии пользователя

- **WHEN** записывается событие, произошедшее в контексте организации
- **THEN** запись содержит идентификатор организации
- **AND** содержит идентификатор действующего пользователя, если он известен

#### Scenario: Отсутствующий контекст не подменяется

- **WHEN** событие произошло вне контекста организации или без известного
  действующего пользователя
- **THEN** соответствующие поля отсутствуют в записи
- **AND** приложение не подставляет вместо них нулевые или фиктивные значения

### Requirement: Корреляция записей одного запроса

Приложение SHALL присваивать каждому входящему HTTP-запросу идентификатор
запроса и включать его во все лог-записи, порождённые обработкой этого
запроса, включая запись о завершении запроса и записи об ошибках.

Если входящий запрос уже содержит идентификатор запроса, установленный
вышестоящим компонентом, приложение SHALL использовать его; иначе приложение
SHALL сгенерировать новый уникальный идентификатор.

Приложение SHALL возвращать идентификатор запроса клиенту в ответе,
чтобы по нему можно было найти записи в системе логов.

#### Scenario: Идентификатор генерируется

- **WHEN** приходит запрос без идентификатора запроса
- **THEN** приложение генерирует уникальный идентификатор
- **AND** все лог-записи этого запроса содержат один и тот же идентификатор
- **AND** идентификатор возвращается в ответе

#### Scenario: Идентификатор наследуется

- **WHEN** приходит запрос с уже установленным идентификатором запроса
- **THEN** приложение использует полученный идентификатор без изменений
- **AND** возвращает его же в ответе

#### Scenario: Разные запросы не смешиваются

- **WHEN** приложение параллельно обрабатывает несколько запросов
- **THEN** записи каждого запроса несут собственный идентификатор
- **AND** идентификаторы разных запросов не совпадают

### Requirement: Логирование завершения HTTP-запроса

Приложение SHALL записывать в лог завершение каждого обработанного
HTTP-запроса с указанием метода, пути, статуса ответа, длительности
обработки и признака аутентифицированности.

Записываемый путь MUST быть безопасным для агрегации: приложение
MUST NOT включать в лог строку запроса (query string) целиком.

#### Scenario: Успешный запрос

- **WHEN** запрос обработан со статусом 2xx
- **THEN** в лог выводится запись уровня `info`
- **AND** запись содержит метод, путь, статус, длительность и идентификатор
  запроса

#### Scenario: Строка запроса не попадает в лог

- **WHEN** запрос содержит параметры в строке запроса
- **THEN** записанный путь не содержит строку запроса

#### Scenario: Значение параметра маршрута не попадает в лог

- **WHEN** запрос пришёл на маршрут, параметр которого является учётными
  данными — например, токеном приглашения
- **THEN** в записи указан шаблон маршрута
- **AND** значение параметра в записи отсутствует

### Requirement: Обязательное логирование ошибок

Каждый ответ приложения, сообщающий об ошибке, SHALL порождать лог-запись.
Ответы со статусом 5xx SHALL логироваться на уровне `error`, ответы
со статусом 4xx — на уровне `warn`.

Запись об ошибке SHALL содержать статус ответа, машиночитаемый код ошибки
и техническую причину ошибки. Техническая причина, попадающая в лог,
MUST NOT добавляться в тело ответа пользователю.

Ошибка, обнаруженная в слое доступа к данным или в слое сценариев
и приводящая к ответу 5xx, SHALL быть залогирована ровно один раз —
дублирование записи об одной ошибке не допускается.

#### Scenario: Внутренняя ошибка

- **WHEN** обработка запроса завершается ответом 500
- **THEN** в лог выводится запись уровня `error`
- **AND** запись содержит статус, код ошибки, техническую причину
  и идентификатор запроса

#### Scenario: Ошибка валидации

- **WHEN** обработка запроса завершается ответом 400
- **THEN** в лог выводится запись уровня `warn`
- **AND** запись содержит статус и код ошибки

#### Scenario: Техническая причина не утекает пользователю

- **WHEN** внутренняя ошибка залогирована с технической причиной
- **THEN** тело ответа пользователю не содержит эту техническую причину

#### Scenario: Ошибка логируется однократно

- **WHEN** одна ошибка проходит через несколько слоёв и приводит
  к одному ответу об ошибке
- **THEN** в логе присутствует ровно одна запись об этой ошибке

### Requirement: Логирование необработанной паники

Приложение SHALL перехватывать необработанную панику при обработке
HTTP-запроса, записывать её в лог на уровне `error` вместе со стеком вызовов
и идентификатором запроса, после чего возвращать клиенту ответ 500.

Паника в обработчике одного запроса MUST NOT приводить к остановке
приложения и MUST NOT влиять на обработку других запросов.

Если паника случилась после отправки заголовка ответа, приложение MUST NOT
завершать такой ответ штатно: ответ SHALL прерываться, а запись
о завершении запроса SHALL отмечать его как несостоявшийся на уровне
`error` — иначе усечённый ответ неотличим от успешного.

Паника в фоновой задаче, выполняющейся вне запроса, MUST NOT приводить
к остановке приложения и MUST NOT останавливать цикл, которому эта задача
принадлежит: следующий запуск SHALL выполняться штатно. Запись о такой
панике SHALL нести имя задачи.

#### Scenario: Паника в обработчике

- **WHEN** обработчик запроса паникует
- **THEN** в лог выводится запись уровня `error` со стеком вызовов
  и идентификатором запроса
- **AND** клиент получает ответ 500
- **AND** приложение продолжает обслуживать последующие запросы

#### Scenario: Паника после начала ответа

- **WHEN** обработчик паникует после того, как заголовок ответа уже отправлен
- **THEN** ответ прерывается, а не завершается штатно
- **AND** запись о завершении запроса имеет уровень `error` и отмечает
  ответ как несостоявшийся

#### Scenario: Паника в фоновой задаче по расписанию

- **WHEN** паникует фоновая задача, выполняющаяся по расписанию
- **THEN** в лог выводится запись уровня `error` со стеком и именем задачи
- **AND** приложение продолжает работу
- **AND** следующий запуск этой задачи выполняется штатно

#### Scenario: Паника в фоновом обработчике

- **WHEN** паникует обработчик доменного события
- **THEN** в лог выводится запись уровня `error`
- **AND** приложение продолжает работу

### Requirement: Логирование доменных событий как фактов

Каждое опубликованное доменное событие SHALL порождать лог-запись уровня
`info`, фиксирующую факт события: тип события, идентификаторы затронутых
сущностей и контекст события (организация, действующий пользователь,
команда, период, время наступления).

Запись о доменном событии MUST NOT содержать пользовательское содержимое
события — названия целей и ключевых результатов, тексты комментариев,
тексты заметок чек-инов и иные текстовые поля, введённые пользователем.

При добавлении нового типа доменного события оно SHALL логироваться
автоматически, без отдельной доработки на каждый тип.

#### Scenario: Событие изменения фиксируется

- **WHEN** публикуется доменное событие о создании цели
- **THEN** в лог выводится запись с типом события, идентификатором цели
  и контекстом события

#### Scenario: Пользовательский текст не логируется

- **WHEN** публикуется доменное событие, несущее пользовательский текст
  (название цели, текст комментария, заметка чек-ина)
- **THEN** этот текст отсутствует в лог-записи о событии

#### Scenario: Новый тип события покрыт автоматически

- **WHEN** в систему добавлен новый тип доменного события
- **THEN** его публикация порождает лог-запись без изменения кода
  логирования событий

#### Scenario: Потеря события фиксируется

- **WHEN** доменное событие не доставлено подписчику
- **THEN** в лог выводится запись уровня `warn` с типом события
  и причиной потери

### Requirement: Логирование событий аутентификации и авторизации

Приложение SHALL логировать факты входа пользователя, выхода пользователя,
неуспешной аутентификации и отказа в доступе.

Запись об отказе в доступе SHALL содержать причину отказа, запрошенный
ресурс и идентификатор пользователя, если он известен. Отказ в доступе
SHALL логироваться на уровне `warn`, неуспешная аутентификация — на уровне
`warn`.

Приложение SHALL логировать изменения прав доступа: изменение роли участника,
выдачу и отзыв прав, изменение административных настроек организации.

#### Scenario: Успешный вход

- **WHEN** пользователь успешно аутентифицирован
- **THEN** в лог выводится запись уровня `info` с идентификатором
  пользователя и использованным провайдером

#### Scenario: Отказ в доступе

- **WHEN** аутентифицированный пользователь запрашивает ресурс,
  на который у него нет прав
- **THEN** в лог выводится запись уровня `warn` с причиной отказа,
  запрошенным ресурсом и идентификатором пользователя

#### Scenario: Изменение прав

- **WHEN** администратор изменяет роль участника или выдаёт права
- **THEN** в лог выводится запись уровня `info` с идентификатором
  администратора, идентификатором затронутого пользователя
  и характером изменения

### Requirement: Логирование жизненного цикла приложения

Приложение SHALL логировать этапы своего жизненного цикла: старт, результат
применения миграций базы данных, готовность принимать запросы, получение
сигнала остановки, завершение обслуживания запросов, завершение обработки
отложенных событий и завершение работы.

Отказ на этапе запуска, приводящий к невозможности продолжить работу,
SHALL логироваться на уровне `error` с причиной отказа до завершения
процесса.

Приложение SHALL логировать запуск, завершение и ошибки фоновых задач
и планировщиков.

#### Scenario: Штатный запуск

- **WHEN** приложение успешно стартовало
- **THEN** в логе присутствуют записи о применении миграций
  и о готовности принимать запросы

#### Scenario: Отказ при запуске

- **WHEN** приложение не может подключиться к базе данных при старте
- **THEN** в лог выводится запись уровня `error` с причиной отказа
- **AND** запись выводится до завершения процесса

#### Scenario: Штатная остановка

- **WHEN** приложение получает сигнал остановки
- **THEN** в логе присутствуют записи о получении сигнала, о завершении
  обслуживания запросов и о завершении обработки отложенных событий

#### Scenario: Незавершённая остановка

- **WHEN** отложенные события не удалось обработать за отведённое время
- **THEN** в лог выводится запись уровня `warn` с указанием причины

### Requirement: Логирование обращений во внешние системы

Приложение SHALL логировать результат каждого обращения во внешнюю систему,
включая доставку уведомлений во внешние каналы: целевую систему, исход
(успех или ошибка) и длительность обращения.

Неуспешное обращение SHALL логироваться на уровне `error` с причиной отказа.
Повторная попытка обращения SHALL логироваться с указанием номера попытки.

Запись об обращении во внешнюю систему MUST NOT содержать учётные данные,
токены и адрес подключения с встроенными учётными данными.

#### Scenario: Успешная доставка уведомления

- **WHEN** уведомление доставлено во внешний канал
- **THEN** в лог выводится запись уровня `info` с названием канала
  и длительностью обращения

#### Scenario: Неуспешная доставка

- **WHEN** доставка уведомления во внешний канал завершилась ошибкой
- **THEN** в лог выводится запись уровня `error` с названием канала
  и причиной отказа

#### Scenario: Учётные данные канала не логируются

- **WHEN** обращение во внешний канал использует токен или пароль
- **THEN** это значение отсутствует в лог-записи

### Requirement: Редакция секретов и персональных данных

Приложение MUST NOT выводить в лог секреты: пароли, токены доступа,
ключи шифрования, значения сессионных cookie, значения заголовка
авторизации и значения настроек, помеченных как секретные.

Приложение MUST NOT выводить в лог адрес электронной почты и отображаемое
имя пользователя в открытом виде. Пользователь SHALL идентифицироваться
в логах по числовому идентификатору.

Значение параметра маршрута может быть учётными данными, поэтому любая
запись, называющая запрошенный ресурс, SHALL указывать шаблон совпавшего
маршрута, а не конкретный путь. Правило действует для всех таких записей,
а не только для записи о завершении запроса: одно правило в трёх копиях
уже приводило к тому, что закрытой оказывалась лишь одна из них.

Если значение всё же должно быть упомянуто, оно SHALL заменяться
на фиксированную маску, не позволяющую восстановить исходное значение.

#### Scenario: Секретная настройка замаскирована

- **WHEN** логируется изменение настройки, помеченной как секретная
- **THEN** значение настройки заменено маской
- **AND** исходное значение отсутствует в записи

#### Scenario: Заголовки авторизации не логируются

- **WHEN** логируется обработка запроса с заголовком авторизации
  или сессионной cookie
- **THEN** их значения отсутствуют в записи

#### Scenario: Ни одна запись не раскрывает параметр маршрута

- **WHEN** запрос к маршруту, параметр которого является учётными данными,
  порождает записи о завершении запроса, о панике и об отказе в доступе
- **THEN** ни одна из этих записей не содержит значение параметра
- **AND** каждая из них указывает шаблон маршрута

#### Scenario: Пользователь идентифицируется по идентификатору

- **WHEN** логируется событие входа пользователя
- **THEN** запись содержит числовой идентификатор пользователя
- **AND** не содержит его адрес электронной почты в открытом виде

### Requirement: Конфигурация уровня логирования

Уровень логирования SHALL задаваться через окружение развёртывания
и поддерживать значения `debug`, `info`, `warn`, `error`. По умолчанию
SHALL применяться уровень `info`.

Записи с уровнем ниже настроенного MUST NOT выводиться. Записи уровней
`warn` и `error` MUST NOT скрываться значениями настройки `debug`, `info`
и `warn`.

Некорректное значение настройки MUST NOT препятствовать запуску приложения:
приложение SHALL применить уровень по умолчанию и записать об этом
предупреждение.

Диагностика некорректной настройки логирования SHALL выводиться независимо
от настроенного уровня — это единственное исключение из правила выше.
Без него некорректное значение скрывало бы сообщение о самом себе: при уровне
`error` предупреждение о недопустимом формате вывода отфильтровывалось бы тем
самым значением, о соседе которого сообщает, и опечатка в манифесте
развёртывания молча меняла бы наблюдаемость приложения.

#### Scenario: Уровень по умолчанию

- **WHEN** уровень логирования не задан
- **THEN** применяется уровень `info`
- **AND** отладочные записи не выводятся

#### Scenario: Понижение до отладочного уровня

- **WHEN** уровень логирования задан как `debug`
- **THEN** выводятся записи всех уровней, включая отладочные

#### Scenario: Некорректное значение

- **WHEN** уровень логирования задан недопустимым значением
- **THEN** приложение стартует с уровнем `info`
- **AND** в лог выводится предупреждение о некорректном значении настройки

#### Scenario: Диагностика настройки видна при любом уровне

- **WHEN** уровень логирования задан как `error`, а формат вывода задан
  недопустимым значением
- **THEN** предупреждение о некорректном формате выводится
- **AND** обычные записи уровней ниже `error` по-прежнему не выводятся
