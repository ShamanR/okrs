# Дизайн-система

Источник для проекта в [Claude Design](https://claude.ai/design): standalone-превью
реальных компонентов интерфейса.

## Принцип

CSS здесь не дублируется. Каждое превью при сборке инлайнит реальные файлы из
`web/static/`, перечисленные в директиве `@dsCss`. Дизайн-система физически не может
разойтись с продуктовым кодом — достаточно пересобрать.

Разметка в `src/cards/` написана вручную по фактическим именам классов, потому что
интерфейс собирается React-компонентами в `web/static/*.js` без отдельного шаблонного
слоя. При изменении разметки компонента карточку нужно поправить руками; при изменении
только стилей — ничего делать не нужно.

## Сборка

```sh
./design-system/build.sh
```

Собирает `design-system/dist/`:

- `components/<name>.html` — самодостаточные страницы, их и заливаем в Claude Design;
- `cards.json` — метаданные карточек (имя, группа, подпись, размер).

`dist/` не коммитится: это артефакт сборки.

## Формат исходника

`src/cards/<name>.html` — фрагмент разметки с директивами в начале:

| директива | назначение |
| --- | --- |
| `@dsCard group="..."` | группа в панели Design System, попадает первой строкой в результат (обязательна) |
| `@dsName` | подпись карточки |
| `@dsSubtitle` | что показано на карточке |
| `@dsCss` | какие `web/static/*.css` инлайнить |
| `@dsViewport` | размер карточки, `ШИРИНАxВЫСОТА` |
| `@dsTheme dark` | тёмная подложка превью (сайдбар, панели уведомлений) |

`src/preview.css` — обвязка страницы превью (сетка, подписи образцов). Всё под
префиксом `.ds-`, продуктовые классы не переопределяются.

## Проверка

Разметка не должна ссылаться на классы, которых нет в заинлайненном CSS:

```sh
python3 - <<'PY'
import re, glob, os
for p in sorted(glob.glob('design-system/dist/components/*.html')):
    style, body = open(p, encoding='utf-8').read().split('</style>', 1)
    css = set(re.findall(r'\.([A-Za-z0-9_-]+)', style))
    used = {c for m in re.findall(r'class="([^"]+)"', body) for c in m.split()}
    miss = sorted(c for c in used if not c.startswith('ds-') and c not in css)
    if miss:
        print(os.path.basename(p), '->', ', '.join(miss))
PY
```

## Загрузка в Claude Design

Проект: **«OKRs — дизайн-система»**, `12e552f0-1aaf-4d84-9013-9cef887d4dd2`.

Требуется авторизация design-system: один раз выполнить `/design-login` в
интерактивной сессии Claude Code в терминале. После этого порядок такой:

1. `list_projects` — найти проект или `create_project` для нового;
2. `list_files` — сравнить со списком в `dist/`;
3. `finalize_plan` с `localDir = design-system/dist` и `writes = ["components/**/*.html"]`;
4. `write_files` с `localPath` по каждой карточке;
5. при необходимости `register_assets` из `cards.json` — если панель не подхватила
   имена карточек из маркеров `@dsCard`.

Синхронизация инкрементальная: заливаем изменённые карточки, а не весь набор.

## Кликабельный прототип

`design-system/prototype/` — прототип приложения на тех же продуктовых стилях:
экраны трекера и обзора периода, вымышленные данные, живая навигация и модалки.

```sh
./design-system/prototype/build.sh
```

Собирает две копии одной страницы:

- `dist/prototype.html` — для публикации. Без `<!DOCTYPE>`, `<html>` и `<body>`:
  их добавляет артефактный движок. Первой строкой маркер `@dsCard`, по нему прототип
  становится карточкой в проекте Claude Design. **Локально этот файл не открывать** —
  браузер разберёт его в quirks mode.
- `dist/prototype.local.html` — полноценный документ для локального просмотра:

```sh
open design-system/dist/prototype.local.html
```

Сервер не нужен: всё инлайн, внешних запросов нет.

CSS инлайнится с диска тем же способом, что и в карточках, поэтому прототип не
расходится с приложением.

Свои файлы только три: `overlay.css` (обвязка прототипа, префикс `.pt-`),
`data.js` (тестовые данные) и `app.js` (рендер и поведение). Разметка намеренно
повторяет продуктовые классы, чтобы утверждённый вид переносился в React-компоненты
почти дословно.

Прототип не приложение: нет бэкенда, прав доступа и сохранения — изменения живут до
перезагрузки страницы.


## Когда обновлять

Дизайн-система — рабочий инструмент, а не нормативный документ: поведение
продукта описывает только `openspec/specs/`. В OpenSpec её описывать не нужно.

Превью инлайнят реальные `web/static/*.css` при сборке, поэтому:

| что изменилось | что делать |
| --- | --- |
| только стили в `web/static/*.css` | ничего, достаточно пересобрать |
| разметка существующего компонента | обновить его карточку в `src/cards/`, а если компонент есть в прототипе — и `prototype/` |
| появился новый переиспользуемый компонент | завести карточку, иначе он выпадет из системы |
| компонент удалён | удалить карточку |

После правок:

```sh
./design-system/build.sh
./design-system/prototype/build.sh
```

и залить результат в проект Claude Design.

Разметка карточек и прототипа повторяет продуктовые классы. Собственные
классы для продуктовых элементов там не заводятся: всё, что не является
частью продукта, помечается префиксом `.ds-` (карточки) или `.pt-`
(прототип) — по этому признаку видно, где прототип отходит от приложения.


### Связь с OpenSpec

Если OpenSpec change затрагивает интерфейс:

- в `design.md` — раздел «Интерфейс»: какие компоненты переиспользуются, какие
  добавляются, и ссылка на карточку или экран прототипа, по которому согласован вид;
- в `tasks.md` — пункт на согласование вида в прототипе **до** реализации и пункт
  на обновление дизайн-системы **после**;
- вид согласуется на прототипе, а не на скриншотах: прототип собран на реальном
  CSS и не расходится со стилями приложения.

Скриншоты добавляются только как историческая фиксация при архивации change,
когда важно сохранить, как решение выглядело на момент принятия.

## Состав

30 карточек в группах: Foundations, Actions, Forms, Data display, Navigation,
Overlays, Goals, Goal tree, Activity, Settings, Content.

Карточки фиксируют и расхождения, найденные при сборке, — они вынесены в заметки
прямо на превью:

- две параллельные системы кнопок (`.btn` и `.set-btn`) с одинаковыми ролями;
- три реализации полосы прогресса (`.progress-bar`, `.gt-panel__bar`, `.gt-card__bar`);
- четыре реализации аватара с инициалами;
- пять наборов пилюль с радиусами 4 / 6 / 12 / 20 / 999;
- два диалога подтверждения с разной геометрией;
- `TEAM_TYPE_COLOR` объявлен дважды с разными цветами (`ui.js` и `goal_tree.js`),
  поэтому одна команда в трекере и в графе целей окрашена по-разному;
- радиусы 7, 9, 10, 14, 16, 20 px мимо шкалы токенов;
- английские подписи статусов KR в русском интерфейсе.
