# User Flows

## Основные пользовательские сценарии

### 1. Управление командами

Пользователь открывает `/teams`, где:

- просматривает список команд;
- видит отдельный основной список активных команд;
- видит отдельный список soft-deleted команд внизу страницы;
- создаёт новую команду;
- редактирует существующую команду;
- удаляет команду;
- восстанавливает soft-deleted команду;
- окончательно удаляет soft-deleted команду только если у неё нет goals ни в одном периоде;
- задаёт parent-child структуру через `parent_id`.

Удаление команды работает так:

- если у команды нет goals ни в одном периоде, она удаляется полностью;
- если goals когда-либо были, команда переводится в soft-deleted состояние;
- дочерние команды при любом варианте удаления не удаляются и поднимаются на уровень выше.

### 2. Управление периодами

Пользователь открывает `/periods`, где:

- просматривает список периодов;
- создаёт новый период;
- редактирует период;
- меняет порядок периодов через move up / move down.

### 3. Просмотр OKR команды

Пользователь открывает `/teams/{teamID}/okr` или `/teamOkrs`.

Текущая реализация `/teamOkrs` работает как:

- SSR отдаёт каркас страницы;
- данные подгружаются через API (`/api/v1/hierarchy`, `/api/v1/teams/{teamID}/okrs`, `/api/v1/teams/{teamID}/overview`);
- пользователь видит двухколоночный layout:
  - слева: иерархический sidebar с командами;
  - справа: цели выбранной команды и блок дочерних команд;
- выбранная команда синхронизируется с URI (`team` query param) без full page reload;
- для прогресса используется `progress_meta` (actual/forecast/delta/status), возвращаемый backend.

Текущая реализация `/teams/{teamID}/okr` работает как:

- SSR отдаёт shell страницы и стартовый breadcrumb;
- после API hydration breadcrumb перестраивается в формат `teamOkrs / Cluster / Unit / Team · Period` (полная цепочка от корня до выбранной команды);
- клик по любой команде в breadcrumb ведёт на `/teamOkrs` с сохранением `period_id` и применением фильтра `team`;
- в верхней части страницы остаётся только заголовок «Цели» и action-кнопки;
- кнопка «Добавить цель» отображается только если `team period status` не равен `validated` и не равен `closed`;
- якоря вида `#goal-{id}` обрабатываются после загрузки данных и корректно скроллят к карточке цели;
- блок Key Results внутри каждой цели рендерится как collapse и по умолчанию закрыт;
- если в URI есть якорь `#goal-{id}`, то у соответствующей цели блок Key Results раскрывается автоматически;
- после создания новой цели URI обновляется на `#goal-{new_id}`, что автоматически прокручивает страницу к новой карточке после перезагрузки данных.

Правила видимости команд по периодам:

- в актуальном периоде отображаются все активные команды, а soft-deleted команды показываются только если в этом периоде у них уже есть OKR / goals;
- актуальный период определяется сервером как период, в диапазон дат которого попадает текущая дата;
- активная команда без goals остаётся видимой и в историческом периоде;
- soft-deleted команда показывается только если у неё есть OKR / goals в выбранном периоде;
- soft-deleted команда без goals не показывается в актуальном периоде;
- soft-deleted команда с goals остаётся видимой в тех периодах, где у неё есть goals, включая актуальный период.

### 4. Работа с целью

Пользователь может:

- создать goal для команды в периоде;
- редактировать поля goal;
- менять вес goal;
- менять порядок goal;
- комментировать goal;
- расшаривать goal на другие команды;
- менять weight goal для owner team или shared team.

### 5. Работа с key result

Пользователь может:

- создать KR для goal;
- редактировать KR;
- менять порядок KR;
- комментировать KR;
- обновлять прогресс KR в зависимости от типа:
  - `PERCENT`
  - `LINEAR`
  - `BOOLEAN`
  - `PROJECT`

### 6. Обновление статуса периода команды

Пользователь может обновить `team period status` для команды и периода.

Поддерживаемые значения:

- `no_goals`
- `forming`
- `in_progress`
- `validated`
- `closed`

## Текущее UX-поведение

На текущий момент UI и backend устроены так:

- часть страниц рендерится через SSR;
- данные и действия выполняются через `/api/v1` (legacy `/api/*` эндпоинты удалены);
- team OKR page использует SSR-shell + API hydration;
- goal / KR actions доступны через API и формы.
- для team OKR страницы обновление статуса периода, прогресса KR и reorder выполняются через `/api/v1`, а не через legacy form-endpoints.

## Важное ограничение текущей реализации

На текущий момент lifecycle-ограничения периода описаны в домене, но не зафиксированы сервером как строгие правила доступа.

Это означает:

- статус периода хранится и обновляется;
- значение статуса валидируется;
- но backend пока не запрещает structural edits goal / KR только на основании `validated` или `closed`.

Поэтому любые UX-ограничения для `validated` / `closed` сейчас должны считаться целевым поведением интерфейса, а не полной серверной гарантией.

## Требование к новым UX-фичам

Любая новая UX-фича должна явно указывать:

- на какой странице она живёт;
- работает ли она через SSR refresh, API hydration или API mutation;
- какие empty / error / loading states обязательны;
- зависит ли поведение от `team period status`;
- проверяется ли ограничение только в UI или ещё и на сервере.

Для удаления/восстановления команд:

- страница `/teams` работает через SSR + form POST;
- visibility rules для `/teamOkrs` и `/api/v1/teams` проверяются на сервере;
- запрет hard delete команды с goals проверяется на сервере, а UI только отражает результат.
