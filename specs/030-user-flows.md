# User Flows

## Основные пользовательские сценарии

### 0. Авторизация

**При `AUTH_MODE=enabled`:**

1. Неавторизованный пользователь открывает любую страницу приложения.
2. Сервер редиректит на `/login?next=<original_url>`.
3. Если включён один провайдер — браузер сразу редиректит на него. Если несколько — страница выбора.
4. После успешного OAuth callback сервер создаёт или обновляет локального пользователя, создаёт сессию.
5. Пользователь попадает на исходную страницу (или `/teamOkrs`).

**При `AUTH_MODE=disabled`:**

- `/login` немедленно редиректит на `/teamOkrs`.
- Все страницы доступны без входа.
- Все операции выполняются от имени `anonymous-local`.

**Выход:**

- Пользователь нажимает «Выйти» в гамбургер-меню (`☰` слева вверху → нижний блок «Аккаунт»).
- POST `/logout` удаляет серверную сессию и очищает cookie.
- Редирект на `/login`.

**Новый пользователь без гранта:**

- При первом логине сервер применяет политику новых пользователей (хранится в `system_settings.new_user_policy`):
  - `empty` (по умолчанию) — пользователь видит пустую иерархию, доступа нет.
  - `default_node` — пользователю автоматически выдаётся грант на узел из `system_settings.default_hierarchy_node_id`.
- Если грантов нет — `GET /api/v1/hierarchy` возвращает пустой список; трекер показывает заглушку «Нет доступа к командам. За доступом обратитесь к администратору» в sidebar и в основной области контента.
- Все write/read endpoints на конкретные команды/цели/KR недоступному scope возвращают `404 NOT_FOUND`.

### 1. Управление командами — `/admin/teams`

Доступно только администраторам (при `AUTH_MODE=enabled`). При `AUTH_MODE=disabled` доступно всем.

Пользователь открывает `/admin/teams`, где:

- просматривает активные команды в виде полноширинного дерева иерархии (drill-down);
- видит отдельный список soft-deleted команд внизу страницы;
- создаёт новую команду;
- редактирует существующую команду; поле «Руководитель» использует компонент `UserSelector` (single-select, suggest): всегда показывает input, при фокусе открывает список всех пользователей, при вводе фильтрует по имени и команде, выбранный пользователь отображается с аватаркой слева и кнопкой очистки справа; поле «Расположение в иерархии» (родительская команда) использует `TeamCombobox` (single-select по дереву);
- удаляет команду;
- восстанавливает soft-deleted команду;
- окончательно удаляет soft-deleted команду только если у неё нет goals ни в одном периоде;
- задаёт parent-child структуру через `parent_id`.

**Поведение дерева (клиент):**

- По умолчанию дерево свёрнуто — видны только корневые узлы (кластеры). Раскрытие хранится на клиенте как множество id раскрытых узлов; смена структуры (появление/удаление команд) не вызывает ошибок — неизвестные id просто игнорируются, новые узлы свёрнуты по умолчанию.
- Узел с детьми раскрывается/сворачивается по клику на ▶/▼ — по одному уровню за раз.
- Кнопка «Раскрыть всё» разворачивает дерево целиком и переключается в «Свернуть всё».
- Поиск показывает все совпадения вместе с их путём в иерархии, игнорируя текущее сворачивание.
- В шапке отображается счётчик «Иерархия · N» (число активных команд), у узлов — счётчик прямых детей.
- Создание (кнопка «+ Новая команда» и «+» в строке узла для дочерней) и редактирование (клик по строке или «✎») открываются в модальном окне; «×» в строке деактивирует команду.

GET `/teams` и GET `/teams/*` отдают редирект 302 на `/admin/teams` и `/admin/teams/*` соответственно.

Удаление команды работает так:

- если у команды нет goals ни в одном периоде, она удаляется полностью;
- если goals когда-либо были, команда переводится в soft-deleted состояние;
- дочерние команды при любом варианте удаления не удаляются и поднимаются на уровень выше.

### 2. Управление периодами — `/admin/periods`

Доступно только администраторам (при `AUTH_MODE=enabled`). При `AUTH_MODE=disabled` доступно всем.

Пользователь открывает `/admin/periods`, где:

- просматривает список периодов;
- создаёт новый период;
- редактирует период;
- меняет порядок периодов через move up / move down.

GET `/periods` отдаёт редирект 302 на `/admin/periods`.

### 3. Управление доступом — `/admin/access`

Доступно только администраторам (при `AUTH_MODE=enabled`). При `AUTH_MODE=disabled` доступно всем.

Пользователь открывает `/admin/access`, где:

- видит список всех пользователей с аватаром, именем, флагом admin и числом узлов доступа («N узл» / «полный доступ» для админов / «нет доступа»);
- фильтрует список тремя чипами со счётчиками: «Все пользователи», «Админы», «Без доступов» (последний — пользователи без admin-прав и без единого выданного узла иерархии, т.е. `is_admin=false` и `GrantedNodeCount=0`);
- ищет по имени, email, провайдеру **и названиям команд, в которых пользователь является руководителем** (lead команды по `lead_udid`); напр. ввод названия команды находит её руководителя, даже если этого слова нет в имени/роли;
- открывает карточку пользователя в модальном окне (клик по строке или «✎»): учётная запись (read-only), переключатель admin-прав, список команд-руководства с переходом «Открыть →», редактор доступа к иерархии (`TeamCombobox`); изменения admin-прав и грантов применяются пакетно по кнопке «Сохранить», «Отмена» отменяет;
- выдаёт или снимает права администратора через API;
- выдаёт или отзывает доступ к узлу иерархии через API.

**Правила видимости для не-администраторов:**

- Доступны только команды, на которые выдан явный грант (и все их дочерние узлы).
- Отсутствие гранта = нет доступа ни к одной команде (пустая иерархия).
- Администраторы видят всю иерархию без ограничений.

Изменения доступа вступают в силу немедленно без перезапуска приложения.

### 3а. Настройки — вкладка «Настройки» в admin-панели

Политика для новых пользователей вынесена в отдельную вкладку «Настройки» (⚙) в навигации admin-панели.

- `Нет доступа` (`empty`) — при первом логине пользователь не получает никакого доступа; администратор выдаёт гранты вручную.
- `Доступ к узлу по умолчанию` (`default_node`) — при первом логине пользователь автоматически получает грант на выбранный узел иерархии (и всех его потомков); применяется однократно, если у пользователя ещё нет ни одного гранта.

Политика сохраняется в БД (`system_settings`) и применяется без перезапуска приложения.

### 3б. Навигация admin-панели (SPA)

Admin-панель — единое React-приложение (`admin.js`), все web-маршруты `/admin*` отдают один и тот же shell.

- Активный раздел отражается в URL как `/admin?section={id}`, где `id` ∈ `periods | teams | users | settings | health-checkin`.
- Переключение раздела вызывает `history.pushState`, поэтому кнопки «Назад»/«Вперёд» браузера переходят между ранее открытыми разделами (через событие `popstate` приложение восстанавливает раздел из URL без перезагрузки).
- При загрузке приоритет выбора раздела: параметр `?section=` → legacy path-маршрут (`/admin/teams` → teams, `/admin/periods` → periods, `/admin/access` → settings) → `localStorage` (`okr_admin_section`) → `periods`.
- Последний открытый раздел дополнительно сохраняется в `localStorage`, неизвестные значения игнорируются с откатом на `periods`.

### 3в. Персональные настройки — `/settings`

Доступно любому авторизованному пользователю (при `AUTH_MODE=disabled` — всем). Это **не** часть admin-панели: отдельный React SPA (`settings.js`), открывается из меню пользователя (аватар в сайдбаре трекера → «Настройки»). Полноэкранная страница с тёмной боковой навигацией и двумя разделами; визуальный язык команд (бейдж типа, цвета) совпадает с трекером и админкой.

Загрузка данных: `GET /api/v1/me` (нужен `udid`), `GET /api/v1/periods`, `GET /api/v1/hierarchy?period_id=` (текущий период по дате, иначе первый). Только API hydration, без серверных мутаций.

Структура страницы повторяет admin-панель: тёмный сайдбар с заголовком «OKR Tracker / Настройки», список разделов под лейблом «Разделы», кнопка «← Вернуться к OKR Tracker» внизу сайдбара; в контентной области — верхний бар с пилюлей «← OKR Tracker» и breadcrumbs «Настройки / {раздел}».

Активный раздел отражается в URL как `/settings?section={id}`, где `id` ∈ `descriptions | sidebar`. Переключение раздела вызывает `history.pushState` (кнопки «Назад»/«Вперёд» переходят между разделами через `popstate`); при загрузке приоритет: `?section=` → `localStorage` (`okr_settings_section`) → `descriptions`. Раздел `descriptions` доступен только лиду; для остальных он скрыт и не выбирается.

**Раздел «Описание команд»** (виден только если пользователь — лид хотя бы одной команды в своём scope):

- редактируемыми считаются команды, где `node.lead.udid == me.udid`, и все вложенные в них команды;
- показываются отступной иерархией: бейдж типа + название + лид + текущее описание; кнопка «Изменить» (если описание есть) / «Добавить» разворачивает Markdown-редактор (`MarkdownEditor`) с предпросмотром и кнопками «Сохранить»/«Отмена»;
- текущее описание = локальный override (если задан) поверх `description` из `/api/v1/hierarchy`;
- если пользователь не лид ни одной команды — блок-заглушка «Редактирование недоступно».

**Раздел «Мой сайдбар»** — дерево-пикер выбора отображаемых в сайдбаре трекера узлов:

- у каждого узла 3 состояния чекбокса: пусто (ничего в поддереве не выбрано), галочка (выбрано всё поддерево: узел + все потомки), минус/indeterminate (выбрана только часть);
- клик по чекбоксу циклирует: пусто → вся ветвь → только сам узел → пусто (для листа — вкл/выкл);
- поиск по названию (показывает совпадения с путём, форсирует разворот), «Выбрать все», «Снять все», сворачивание/разворот веток;
- счётчик «Выбрано N · в сайдбаре M узлов» (M учитывает родительские узлы) и per-node «N из M» (сколько прямых детей затронуто выбором).

**Правило отображения в сайдбаре трекера:** узел виден, если он выбран или содержит выбранного потомка (родительские узлы остаются для навигации). Текущая открытая команда всегда видна. Если выбор никогда не настраивался — показываются все доступные узлы.

**Персистентность:** описания (override-слой) и выбор сайдбара хранятся в `localStorage` отдельно по каждому пользователю (`okr_team_desc_overrides:<userID>`, `okr_sidebar_nodes:<userID>`) и восстанавливаются при перезагрузке; трекер читает те же ключи. Серверные данные и схема БД не меняются.

**Empty/error/loading states:** «Загрузка…» при инициализации; заглушка ошибки при сбое загрузки; «Редактирование недоступно» для не-лида; «Ничего не найдено» при пустом поиске.

Поведение не зависит от `team period status`. Ограничение доступа к разделу «Описание команд» проверяется только на клиенте (по `lead.udid` в пределах выданного scope); серверная запись описаний здесь не выполняется.

### 3г. Глобальная навигация (гамбургер-меню)

Во всех страницах (трекер, настройки, админка, заглушки) слева вверху sidebar есть кнопка `☰`, открывающая выезжающий слева drawer — единый компонент `HeaderNavMenu` из `header.js`. Drawer закрывается по клику на фон, крестику или клавише Esc.

- **Разделы:** «Цели команд» → `/`, «Лог активностей» → `/activity-log`, «Дерево целей» → `/goal-tree`. Активный раздел подсвечивается по текущей странице (на `/settings` и `/admin*` не подсвечен ни один).
- **Аккаунт (низ):** карточка профиля (аватар + имя + email) с кнопкой ⚙ → `/settings`; «Документация» (только если задан `documentation_url` из `GET /api/v1/config`); «Администрирование» → `/admin` (только для `is_admin`); «Выйти» (POST `/logout`).

**Страницы-заглушки.** `/activity-log` и `/goal-tree` доступны любому авторизованному пользователю (как `/settings`) и отдают общий shell `stub-shell` + `stub.js`: тёмный sidebar с тем же гамбургер-меню и контент-плейсхолдер «Раздел в разработке». Реальная функциональность — вне текущего scope.

### 4. Просмотр OKR команды

Пользователь открывает `/teamOkrs` (основной маршрут) или `/teams/{teamID}/okr` (редиректит на `/teamOkrs`).

При `AUTH_MODE=enabled` пользователь видит только команды в пределах выданных ему гранта и их потомков. Прямой запрос к недоступной команде через URL не даёт данных по этой команде.

**Реализация `/teamOkrs` — React SPA:**

- SSR (`tracker_shell.html`) отдаёт пустой каркас и загружает `tracker.js` + `tracker.css`;
- SPA получает данные через: `GET /api/v1/me`, `GET /api/v1/periods`, `GET /api/v1/hierarchy?period_id=`, `GET /api/v1/teams/{id}/okrs?period_id=`, `GET /api/v1/teams/{id}/overview?period_id=`;
- layout: тёмный sidebar слева (гамбургер-меню `☰` + иерархия команд + выбор периода) и основная область справа;
- основная область содержит: topbar с названием команды и общим прогрессом, status stepper, список goal-карточек;
- для узлов с дочерними командами над списком целей отображается cluster overview;
- смена команды не вызывает перезагрузки страницы.

**Навигация и прямые ссылки:**

- Текущий узел иерархии и период всегда отражаются в URL: `/teamOkrs?team={teamID}&period={periodID}`. Первый разрешённый выбор подменяет текущую запись истории (`history.replaceState`), каждая последующая смена команды/периода добавляет новую запись (`history.pushState`).
- Кнопки «Назад»/«Вперёд» браузера возвращают к ранее открытым узлам: по событию `popstate` приложение восстанавливает узел и период из URL без перезагрузки страницы.
- Можно скопировать URL и отправить коллеге — получатель откроет ровно тот же узел и период.
- При загрузке приоритет выбора: URL-параметры → cookie `okr_last` → первый доступный.
- Последний открытый узел и период сохраняются в cookie `okr_last` (TTL 30 дней). Повторное открытие приложения восстанавливает последнее место без необходимости искать его заново.
- Состояние раскрытия узлов дерева команд в sidebar сохраняется на клиенте в `localStorage` (ключ `okr_tree_expanded`) как карта `nodeId → false` (свёрнут); отсутствие записи означает раскрытый узел по умолчанию. Закрытие и повторное открытие вкладки не сбрасывает раскрытие дерева. Хранение по `id` устойчиво к изменению структуры команд: неизвестные `id` (удалённые команды) игнорируются, новые команды раскрыты по умолчанию.

**Status stepper:**

- отображает 4 шага: Черновик (`forming`), К валидации (`ready`), В работе (`in_progress`), Закрыты (`closed`);
- при `no_goals` показывает специальный badge «Нет целей» и деактивирует все кнопки шагов;
- текущий шаг подсвечен акцентным цветом, пройденные — слабее;
- смена шага вызывает `POST /api/v1/teams/{id}/status`.

**Карточка цели:**

- заголовок, приоритет (P0–P3), вес, тип работы (Delivery/Discovery), фокус, владелец;
- прогресс-бар с forecast-отметкой, индикатор здоровья (ahead / on track / below / stale);
- для общих целей — баннер «Общая с:» со списком команд; текущая команда помечается суффиксом «· Вы»;
- badge «Общая · N команд» в мета-строке не учитывает текущую команду в счётчике (только внешние partners);
- в режиме редактирования (editMode=full) — карандаш-иконка при клике на заголовок открывает GoalModal; красный крестик рядом с заголовком — удаление цели через ConfirmModal;
- раскрывающийся блок KR; раскрывающийся блок комментариев.

**Режимы редактирования (editMode), определяемые клиентом по статусу:**

| Статус                         | editMode        | Доступные действия                         |
| ------------------------------ | --------------- | ------------------------------------------ |
| `no_goals`, `forming`, `ready` | `full`          | создание/редактирование/удаление goal и KR |
| `in_progress`                  | `progress_only` | обновление прогресса KR, комментарии       |
| `validated`, `closed`          | `comments_only` | только комментарии                         |

**Правила видимости команд по периодам:**

- в актуальном периоде отображаются все активные команды, а soft-deleted команды — только если в этом периоде у них уже есть OKR / goals;
- актуальный период определяется сервером как период, в диапазон дат которого попадает текущая дата;
- активная команда без goals остаётся видимой и в историческом периоде;
- soft-deleted команда показывается только если у неё есть OKR / goals в выбранном периоде.

### 5. Работа с целью

Пользователь может:

- создать goal для команды в периоде;
- редактировать поля goal, включая поле `owner_text` — мульти-селект владельцев через компонент `UserSelector`; выбор из таблицы users с поиском по имени и команде; хранится как строка через запятую (например `"Ivan, Maria"`);
- менять вес goal;
- менять порядок goal (drag-and-drop в editMode=full);
- комментировать goal (комментарий фиксирует author_user_id);
- расшаривать goal на другие команды;
- менять weight goal для owner team или shared team;
- удалить goal (только в editMode=full) — появляется красный крестик справа от заголовка; требует подтверждения в ConfirmModal; если goal была owner — удаляется полностью; если goal была shared — удаляется только share текущей команды.

**Авто-переход в `no_goals`:** сервер при любом удалении goal проверяет, остались ли у команды цели в данном периоде; если нет и статус не `no_goals` — автоматически сбрасывает его в `no_goals`. Это серверная гарантия, не зависящая от UI.

### 6. Работа с key result

Пользователь может:

- создать KR для goal;
- редактировать KR;
- менять порядок KR (drag-and-drop в editMode=full);
- комментировать KR (комментарий фиксирует author_user_id);
- обновлять прогресс KR в зависимости от типа: `NUMERICAL`, `BOOLEAN`, `PROJECT`;
- в модалке «Обновить прогресс» под заголовком показывается нередактируемый блок «Описание» (Markdown) — справка для контекста; если описания нет, вместо блока выводится кнопка «Добавить описание», которая раскрывает поле ввода, а введённый текст сохраняется вместе с прогрессом через `POST /api/v1/krs/{krID}/description`;
- удалить KR (только в editMode=full) — красный крестик справа от кнопки «Редактировать»; требует подтверждения в ConfirmModal.

### 7. Обновление статуса периода команды

Пользователь может обновить `team period status` для команды и периода.

Поддерживаемые значения:

- `no_goals`
- `forming`
- `in_progress`
- `validated`
- `closed`

## Текущее UX-поведение

На текущий момент UI и backend устроены так:

- `/teamOkrs` — React SPA: SSR-shell отдаёт HTML-каркас, `tracker.js` загружает данные через API и рендерит компоненты;
- `/admin/*` — SSR с Go-шаблонами + `admin.js` для динамических элементов (access management);
- все данные и мутации идут через `/api/v1`;
- гамбургер-меню (`☰`) слева вверху sidebar открывает drawer с разделами навигации («Цели команд», «Лог активностей», «Дерево целей») и аккаунт-блоком (аватар, имя, ⚙ «Настройки», «Документация», «Администрирование» для админов, «Выйти»); идентично на всех страницах;
- комментарии к goals загружаются батчевым запросом вместе с целями команды (в рамках одного GET `/api/v1/teams/{id}/okrs`).

## Важное ограничение текущей реализации

На текущий момент lifecycle-ограничения периода описаны в домене, но не зафиксированы сервером как строгие правила доступа.

Это означает:

- статус периода хранится и обновляется;
- значение статуса валидируется;
- но backend пока не запрещает structural edits goal / KR только на основании `validated` или `closed`.

Поэтому любые UX-ограничения для `validated` / `closed` сейчас должны считаться целевым поведением интерфейса, а не полной серверной гарантией.

## Требование к новым UX-фичам

Любая новая UX-фича должна явно указывать:

- на какой странице она живёт;
- работает ли она через SSR refresh, API hydration или API mutation;
- какие empty / error / loading states обязательны;
- зависит ли поведение от `team period status`;
- зависит ли поведение от auth mode и роли пользователя;
- проверяется ли ограничение только в UI или ещё и на сервере.
