# Контекст уведомления и удаление записи — план

**Цель:** в карточке уведомления видно, к какой команде (с иерархией) и к какой цели оно относится; у каждой записи есть кнопка удаления.

**Откуда задача.** Пользователь: «добавь контексты — команду с иерархией и название цели, если доступно; это нужно, чтобы легче ориентироваться». И: «пропала кнопка удаления конкретного уведомления».

**Важно про вторую половину.** Кнопки удаления НИКОГДА не было: проверено по всей истории `web/static/notifications.js` (файл существует в одном коммите `6685a7d`), эндпоинта `DELETE` нет ни в `routes.golden`, ни в спеках, единственный `DELETE FROM notifications` — очистка по сроку хранения. Это не регресс, а новая функция. Формулировка пользователя ошибочна, поведение — нет: кнопка нужна.

## Глобальные ограничения

- **Коммиты запрещены** (правило 8 `CLAUDE.md`). Файлы дерева застейджены, `HEAD` — `6685a7d`; индекс не трогать. Диффы смотреть `git diff HEAD`, не `git diff`.
- **Никаких N+1** (правило 9 `CLAUDE.md`). Список отдаёт до 100 записей; контекст резолвится в том же запросе, что и остальное, — так уже сделан актор («The actor is joined here rather than looked up per row: one query, no N+1»).
- **Пакет на URI**, `RegisterRoutes` — в `routes.go`.
- **CSRF** обязателен для браузерных DELETE.
- Данные с сервера рендерятся как текст; `dangerouslySetInnerHTML` запрещён (правило 8 `specs/010`).
- Комментарии в production-коде Go — английский; в `*_test.go` и JS — русский.
- Спеки — на русском, файлы в CRLF, целиком не переписывать.
- `go test ./...` сейчас зелёный (158 пакетов) и обязан таким остаться.
- `gofmt -l internal/` НЕ запускать (дерево в CRLF) — точечно; если файл в CRLF, нормализовать, форматировать, вернуть окончания.
- Проверять парсинг JS вендоренным Babel.

## Task 1: Контекст — команда с иерархией и цель

**Файлы:** `internal/store/notifications/notifications.go` (+тест), `internal/http/dto/notification.go`, `internal/http/handlers/api/v1/notifications/handler.go` (+тест), `web/static/notifications.js`, `web/static/sidebar.css`, `specs/040-api-contract.md`.

**Решение: резолв на чтении, в том же запросе.** Не денормализовать в строку уведомления. Причины: не нужна миграция; названия остаются актуальными — переименованная команда показывается своим текущим именем, что и помогает ориентироваться; это же соглашение уже принято для актора. Цена: рекурсивный CTE по небольшому набору команд на запрос списка.

**Путь команды.** Строка вида `Компания / Платформа / Биллинг` — от корня к листу, разделитель ` / `. Строится рекурсивным подъёмом по `teams.parent_id` **только для тех команд, что встретились в выборке**, а не по всему дереву тенанта. Обязательно ограничить рекурсию по `tenant_id` на каждом шаге: `parent_id` без этого условия увёл бы в чужой тенант при повреждённых данных.

**Название цели.** `LEFT JOIN goals` по `n.goal_id`. Если цели нет (удалена) или `goal_id` пуст — поле не отдаётся.

**DTO.** Добавить необязательное поле контекста, например:
```go
// Context is where the notification happened: the team path from the root
// ("Компания / Платформа") and the goal title when the notification has one.
// Both are resolved at read time, so a renamed team or goal shows its current
// name — that is what makes the list scannable. Omitted when empty.
type NotificationContext struct {
    Team string `json:"team,omitempty"`
    Goal string `json:"goal,omitempty"`
}
```
и `Context *NotificationContext \`json:"context,omitempty"\`` в `Notification`.

**Клиент.** Отдельная строка в карточке под телом, приглушённым стилем; команда и цель разделены — предложи разделитель, консистентный с соседними элементами. Не показывать строку, когда контекста нет. Существующие классы переиспользовать; новые правила — в `sidebar.css`, рядом с остальными `notif__`.

**Внимание на пересечение.** У уведомления о чек-ине уже есть поле `subject` — название ключевого результата. Цель в контексте его не дублирует (KR и цель — разные сущности), но проверь глазами, что карточка не выглядит как три строки одного и того же.

## Task 2: Удаление уведомления

**Файлы:** `internal/store/notifications/notifications.go` (+тест), `internal/service/notification/` (+тест), новый пакет хендлера, `internal/http/server.go`, `web/static/notifications.js`, `internal/http/testdata/routes.golden`, `specs/040-api-contract.md`, `specs/070-code-structure.md`.

**Маршрут:** `DELETE /api/v1/notifications/{id}` — новый пакет по правилу «пакет на URI», `RegisterRoutes` в `routes.go`.

**Безопасность — главное в этой задаче.** Удаление обязано быть ограничено И тенантом, И пользователем-получателем: `WHERE id = $1 AND tenant_id = $2 AND user_id = $3`. Без условия по `user_id` любой участник тенанта удалял бы чужие уведомления, зная id. Чужое или несуществующее уведомление отвечает `404` — одинаково, чтобы по коду ответа нельзя было проверить существование чужой записи.

**Счётчик непрочитанных.** Удаление непрочитанного уведомления обязано уменьшать счётчик. Проверь, как считается `unread-count`, и покрой тестом сценарий: непрочитанное удалено → счётчик уменьшился.

**Клиент.** Кнопка на каждой записи, справа. Требования:
- клик по кнопке НЕ должен переходить по ссылке уведомления и НЕ должен помечать прочитанным — остановить всплытие;
- запись исчезает из списка сразу, счётчик обновляется;
- кнопка доступна с клавиатуры и имеет `aria-label`;
- стиль — как у существующих управляющих элементов карточки, свои цвета не заводить.
