## 1. Обязательно закрыть в фазе 1b

### 1.1. Graceful shutdown в `cmd/server/main.go`

`App.Close` (а значит и `bus.Close`) **никогда не выполняется**. `main` не ловит сигналы: `http.ListenAndServe` либо блокируется навсегда, либо возвращает ошибку в `os.Exit(1)`, а тот пропускает `defer`. Та же дыра у соседнего `defer pool.Close()` — она пре-существующая, не регрессия фазы 1a.

**Почему нельзя тянуть:** в фазе 1b появляется воркер доставки уведомлений, и дренаж очереди при остановке перестаёт быть теоретическим. Сейчас терять нечего — единственный подписчик синхронный.

**Что сделать:** `signal.NotifyContext` на `SIGINT`/`SIGTERM`, `srv.Shutdown(ctx)` вместо голого `ListenAndServe`, порядок остановки — HTTP → шина → пул БД.

## 3. Ловушка на будущее: реестр `event.AllKinds()`

Реестр поддерживается руками, поэтому **23-я `Kind`-константа, не внесённая в него, не уронит ни один тест**. Проверено мутацией при ревью. Дыра шире, чем кажется: `internal/core/event/event_test.go` тоже перечисляет 22 структуры руками за литералом `len(all) != 22`, то есть новый тип проходит мимо **обоих** тестов.

Сейчас это безопасно: фазы 1a и 1b новых видов событий не добавляют. Риск возникает в фазе 2 (Slack, почта, вебхуки) или при любом расширении домена.

**Закрывается дешевле, чем казалось.** При планировании я записал, что альтернатива — только codegen; это неверно. Хватит ~15 строк теста в `internal/core/event`, который `go/parser`-ом собирает const-блок `Kind = "…"` из `events.go` и сверяет его с `AllKinds()`. Это закрывает связку «константы ↔ реестр» полностью и без генерации, оставляя незакрытым только «новая структура без новой константы» — а это `TestKindsAreUniqueAndNonEmpty` уже делает неудобным пропустить.

**Когда:** вместе с первым же добавлением нового вида события.

## 4. Известные несоответствия спек и кода, не входящие в скоуп уведомлений

### 4.1. `specs/010`, раздел «OSS / SaaS split» описывает нерабочий путь расширения

Сказано, что приватный `okrs-saas` «импортирует `okrs/app`, blank-import'ит пакеты с SaaS-регистрациями, выбирает их по имени в `Config`». Регистрирующие функции (`auth.Register`, `auth.RegisterResolveStrategy`, `entitlements.Register`, `nomembership.Register`) при этом лежат в `internal/`, а `okrs/internal/...` по правилу видимости Go импортируется только кодом внутри модуля `okrs`. Из отдельного модуля вызвать их **нельзя**.

Значит описанный путь расширения работает только для кода внутри того же модуля. Обнаружено при проектировании уведомлений; в фазе 2 каналы уведомлений намеренно строятся **иначе** — публичный пакет-контракт `notifychannel` плюс опция `app.Config.NotificationChannels`, — чтобы требование «расширять каналы из внешнего репозитория» вообще было выполнимо.

**Что делать:** отдельная задача — либо переделать сеймы auth/entitlements/nomembership по образцу каналов, либо переписать раздел спеки под то, как оно работает на самом деле. К уведомлениям отношения не имеет, тянуть в их план не следует.

**Закрыто фазой 2a-1** ровно в части каналов уведомлений: `notifychannel` (публичный контракт) и `app.Config.NotificationChannels` реализованы и описаны в `specs/010-architecture-constraints.md`. Сам системный вопрос — auth/entitlements/nomembership остаются нерасширяемыми извне — не закрыт, см. «Что делать» выше.

### 4.2. Шесть файлов переписаны из CRLF в LF

Правки фазы 1a сохранили в LF шесть ранее-CRLF файлов; git вернёт им CRLF при следующем касании. На дифф это не повлияло (изменения содержательные, не переписывание целиком), но при коммите стоит убедиться, что не прилетает whitespace-шум.

### 4.3. Нормализация окончаний строк во всём дереве

Рабочее дерево преимущественно CRLF, из-за чего `gofmt -l internal/` выдаёт ~450

## 6. Долг фазы 2a-1: публичный сейм каналов уведомлений

**Источник:** исполнение фазы 2a-1 — публичный контракт `notifychannel`, канал Mattermost, шифрование секретов (`internal/platform/secretbox`), экран настроек тенант-админа и панель system-admin. **Статус:** ничего из перечисленного не блокирует 2a-1; каждый пункт осознанно отложен с обоснованием.

### 6.1. Ротация `NOTIFICATIONS_SECRET_KEY`

Перешифровки сохранённых секретов нет: смена ключа развёртывания сегодня ломает все настроенные каналы (`secretbox.Open` вернёт ошибку, `Sender` собрать не выйдет). Не входило в скоуп 2a-1 — первый набор каналов. **Что сделать:** отдельная задача на batch re-encrypt при ротации (напр. поддержка второго, «предыдущего», ключа на переходный период).

### 6.2. `notification_identities` заведена, но не заполняется

Таблицу пишут только каналы, реализующие `notifychannel.Linker`; ни один канал в 2a-1 (Mattermost) его не реализует — он адресует по email. Хранилище тем не менее живёт в ядре уже сейчас: иначе `Linker`, часть публичного контракта `notifychannel`, было бы нечем пользоваться в момент появления первого канала с привязкой аккаунта (Telegram, 2a-2+).

### 6.3. Привязки каналов к тарифам нет

Решение продукта, а не забытая работа: гейт доступа канала тенанту сегодня — только entitlement (`entitlement.notifications.<канал>`), без отдельного слоя биллинг-плана.

### 6.4. Нет ограничения частоты обращений к внешнему API канала

В 2a-1 неважно: единственный вызывающий внешний API — кнопка «Проверить» на форме настроек, дёргает вручную один раз за клик. Воркер доставки 2a-2 обязан завести лимитер — иначе всплеск уведомлений может упереться в rate limit самого канала (Mattermost, будущий Telegram). Отдельно: `POST .../admin/settings/notifications/{channel}/test` тоже ничем не ограничен — администратор может дёргать внешний API кнопкой без предела; риск невелик (нужны права tenant-admin), но в 2a-2 разумно закрыть заодно общим лимитером.

### 6.5. SSRF-поверхность

Администратор пространства задаёт `base_url` Mattermost-сервера, по которому сервер делает исходящие запросы. Схема ограничена `http`/`https` (`notifychannel/mattermost`), но приватные и кластерные адреса (RFC1918, `169.254.169.254` и т.п.) сегодня достижимы. Открытый вопрос продукта, не техническая недоделка: нужен ли allowlist/запрет приватных диапазонов, или доверия tenant-admin (уже привилегированная роль в своём пространстве) достаточно.

### 6.6. Обёртка маскирования секрета не продвигает интерфейсы контракта

`secretMaskingSender` (`internal/service/notificationchannel/secretmask.go`) встраивает `notifychannel.Sender`; приведение обёрнутого значения к `notifychannel.Linker` не проходит — Go продвигает через встраивание методы только встроенного интерфейса, не другие интерфейсы, которым удовлетворяет исходное значение. Проверено эмпирически, задокументировано в коде рядом с типом. Сегодня безопасно: приведений к `Linker` в модуле нет. Перед фазой account-linking (Telegram) нужно решить конструкцию иначе — например, сателлитный метод у `Service`, продвигающий `Linker` приведением исходного (ещё не обёрнутого) `Sender`, а не самой маскирующей обёртки.

### 6.7. `Service.Sender()` строит новый экземпляр на каждый вызов

Сегодня безопасно: единственный вызывающий (`POST .../test`) отправляет одно сообщение за раз. Воркер доставки 2a-2 обязан получать `Sender` один раз на пачку сообщений, а не пересобирать на каждое — иначе внутриканальный кэш (напр. resolve «email → user id» в Mattermost) бесполезен: каждое сообщение платит за резолв заново.

### 6.8. `Get`→`Upsert` в `Save` неатомарны

В K8s-среде на много инстансов два одновременных сохранения дают lost update: сохранение с пустым `secret` (по контракту — «не менять сохранённый») перезаписывает секрет данными, прочитанными до чужого параллельного сохранения, — новее записанный чужой секрет теряется (правило 10 CLAUDE.md о консистентности при много-инстансном развёртывании). Частота обращений к админской форме настроек низкая, поэтому отложено.

**Рецепт (предложен сквозным ревью фазы 2a-1, дешевле обоих ранее записанных вариантов).** Не транзакция и не версионирование, а перенос самого правила «пустой секрет = оставить прежний» в SQL: сервис отправляет в репозиторий `NULL` вместо прочитанного `prev.SecretEnc`, а `Upsert` пишет

```sql
secret_enc  = COALESCE(EXCLUDED.secret_enc,  notification_channels.secret_enc),
secret_hint = COALESCE(EXCLUDED.secret_hint, notification_channels.secret_hint)
```

Read-modify-write исчезает целиком: `Save` перестаёт читать строку ради секрета, а решение «оставить прежний» принимает база в момент записи. Ни транзакции, ни блокировки, ни колонки версии.

**Почему не в эту волну:** правка меняет контракт репозитория (`Config.SecretEnc == nil` начинает означать «не трогать», а не «нет секрета»), а с ним — проверку `case hadPrev && len(prev.SecretEnc) > 0` в `Save` и её тесты. Это не единицы строк, и одна из них — семантика поля, которую читает не только `Save`.

### 6.10. `notificationpref.AvailableChannels` не подключён к `Service.EnabledNames`

`internal/service/notificationpref/notificationpref.go` держит `var AvailableChannels = []string{"in_app"}` с комментарием «фаза 2 заменит это списком выданных тенанту каналов». Фаза 2a-1 построила ровно нужный метод — `notificationchannel.Service.EnabledNames`, чей доккомментарий прямо называет пользовательский экран настроек одним из потребителей, — и **не подключила** его: `AvailableChannels` по-прежнему статичен, а `EnabledNames` остаётся продовым кодом без единого вызывающего.

**Решение осознанное, а не забытое.** Доставщика ещё нет: канал, включённый тенант-админом, сегодня ничего не отправляет — воркер доставки появляется в фазе 2a-2. Показать пользователю колонку «Mattermost» в матрице настроек значило бы предложить ему выбрать канал, который молча ничего не сделает. Пустой чекбокс, который ничего не меняет, — та же болезнь, что и тумблер, не меняющий ничего наблюдаемого (см. 6.11 про панель).

**Условие снятия:** фаза 2a-2, в один change set с воркером доставки. Тогда `AvailableChannels` заменяется на `EnabledNames(ctx, scope)` (значит, и валидация в `Set`, и поле `channels` в `GET /api/v1/notifications/preferences` становятся тенант-зависимыми), а требование дизайн-спеки §13.3 «колонки каналов появляются, только если в тенанте включён больше одного канала» получает наконец настоящий источник данных.

**Чего стоит ожидание:** до тех пор `EnabledNames` покрыт только тестами и не проверен ни одним продовым сценарием.

### 6.11. Отзыв entitlement оставляет осиротевшую строку `notification_channels`

Системный администратор снимает `entitlement.notifications.<канал>` у пространства. Строка в `notification_channels` остаётся как была: `enabled = true`, зашифрованный секрет на месте. Добраться до неё после этого не может никто:

- тенант-админ — канал пропал из `GET /api/v1/admin/settings/notifications` (`Service.Available` фильтрует по entitlement), а `PUT` и `POST .../test` по нему отвечают `404`;
- системная панель — read-only и работает с entitlements, а не с конфигурацией канала: эндпоинта, стирающего чужую настройку, в ней нет и по замыслу не было.

Повторная выдача того же entitlement **молча воскрешает включённый канал** со старым секретом — без действия администратора пространства и без следа в интерфейсе.

**Решение: храним, не чистим.** Отзыв entitlement — это «пространству больше нельзя пользоваться каналом», а не «пространство отказалось от канала». Отзыв бывает временным (ошибка биллинга, пересмотр тарифа, тестовое снятие), и уничтожение конфигурации при нём означало бы, что администратор пространства при возврате канала заново вводит токен, которого у него может уже не быть под рукой. Это разрушительное действие в ответ на обратимое событие. Сохранение данных — то же правило, что уже записано в §10.3 дизайн-спеки для канала, выпавшего из сборки: «данные не теряются, при возврате канала всё оживает».

**Что за это заплачено — и это должно быть видно:**

1. **Зашифрованный секрет живёт в БД дольше, чем право им пользоваться.** Он недостижим (ключ у сервера, `Sender` для неразрешённого канала не собирается), но он есть. Для пространства, у которого канал отобрали навсегда, это хранение данных без основания.
2. **Возврат entitlement включает канал молча.** Ожидание «вернули доступ → канал в состоянии, в котором его оставили» защитимо, но администратор пространства об этом не уведомляется, и отправка возобновляется без его участия. В фазе 2a-2, когда появится доставка, это станет наблюдаемым: уведомления снова поедут в Mattermost.
3. **В K8s отзыв доезжает до других подов не мгновенно.** `Service.SetTenantEntitlement` инвалидирует `TenantSettingsCache` **того инстанса, который обработал запрос**; на остальных подах снимок живёт до истечения TTL — `defaultTenantSettingsCacheTTL = 5 * time.Minute` (`internal/store/tenantsettings/cache.go`). До пяти минут после отзыва часть реплик продолжает считать канал выданным. Для фазы 2a-1 потолок ущерба — тенант-админ видит карточку канала и может нажать «Проверить»; в 2a-2 в это окно попадут реальные доставки. Свойство не новое и не про уведомления — так работают все entitlements, — но именно у каналов оно впервые управляет исходящим трафиком наружу.

**Что сделать (не в 2a-1):**

- к моменту 2a-2 решить, достаточно ли пятиминутного окна для канала, управляющего внешней отправкой, или отзыв должен инвалидировать снимок на всех инстансах (широковещательная инвалидация или сквозная проверка entitlement перед отправкой пачки);
- дать системной панели видеть, что у пространства осталась конфигурация отозванного канала, — хотя бы отметкой в списке. Сегодня этот факт не показан нигде, и «храним» на практике неотличимо от «потеряли»;
- отдельно решить судьбу секрета у пространства, удалённого или приостановленного насовсем. `ON DELETE CASCADE` от `tenants` закрывает удаление; приостановку — нет.

### 6.12. Формат deep-link продублирован между Go и JS

Ссылка на цель в трекере (`/?team=&period=&goal=&kr=&comment=`) собирается в двух
местах: клиентским `buildTargetURL` (`web/static/ui.js`) и серверным `targetURL`
(`internal/http/handlers/api/v1/notifications/handler.go`). Автоматической связи
между ними нет — только комментарии, ссылающиеся друг на друга.

Эта пара уже разъезжалась: сервер отдавал `goal_id`/`team_id`/`period_id`, которых
трекер не читает вовсе, и каждый клик по уведомлению открывал трекер без перехода
к цели. Дефект пережил восемь поштучных ревью и сквозное, потому что `targetURL`
не была покрыта тестом, а план фазы сам зафиксировал неверный формат как образец.
Нашёл его пользователь руками. Сейчас формат закреплён тестом
`TestTargetURL`, сверяющим полную строку, включая порядок параметров.

**Что делать в 2a-2, а не раньше.** Воркер доставки будет слать ссылку во внешние
каналы, где нужен АБСОЛЮТНЫЙ адрес и нет ни браузера, ни `ui.js`. Не писать третью
реализацию: вынести `targetURL` в переиспользуемую функцию, принимающую сырые
идентификаторы (team/period/goal/kr/comment) и базовый адрес — пустой для
колокольчика (текущее поведение и формат ответа API не меняются), настроенный для
каналов. Тогда в Go-рантайме формат живёт в одном протестированном месте,
симметрично тому, как в JS он живёт в одном `buildTargetURL`.

Переводить API уведомлений на выдачу сырых идентификаторов вместо готовой строки
рассматривалось и отклонено: это устранило бы дублирование только для браузерных
потребителей, а внешним каналам клиент недоступен — то есть для сценария, ради
которого вопрос и поднят, выигрыша нет.

## 7. Долг задачи «Чек-ин по KR: одно событие, одно уведомление»

**Источник:** исполнение плана [2026-08-31-kr-checkin-notifications.md](2026-08-31-kr-checkin-notifications.md) — `KRProgressUpdated` и `KRNoteUpdated` заменены одним событием `KRCheckedIn`, чек-ин стал одной операцией `usecase/keyresult.CheckIn`. **Статус:** ничего из перечисленного не блокирует задачу; каждый пункт осознанно отложен с обоснованием.

### 7.1. Изменение health-статуса KR не порождает строки журнала активности

Чек-ин, в котором изменился только health-статус, даёт уведомление, но **ни одной** строки журнала: `toRows` для `KRCheckedIn` (`internal/service/activity/journal.go`) возвращает строку `kr_progress` только при изменении прогресса и строку `kr_note_updated` только при изменении заметки.

**Почему отложено:** это сознательное решение задачи, а не пробел. Главное её утверждение — «вывод журнала не меняется», а до неё смена статуса KR событий не порождала вообще, и журнал о ней никогда не знал. Завести новую строку значило бы изменить вывод всех четырёх табов и счётчиков ровно в той задаче, которая обещала их не трогать.

**Условие снятия:** отдельная задача, если продукт решит, что смена health-статуса KR должна быть видна в журнале. Тогда нужны новый `action` (сегодня `status_changed` занят статусом команды), его место в категориях/фильтрах UI и правка перечня `action` в `specs/020-domain-model.md` — данные для строки в событии уже есть (`HealthBefore`/`HealthAfter`).

### 7.2. Legacy-ветка рендерера для сохранённого `kind = 'kr_progress'`

`internal/render/notify/notify.go` держит ветку `legacyKindKRProgress` со старым текстом «обновил прогресс» и старым телом.

**Почему нельзя удалить сейчас:** рендер идёт по `kind`, **сохранённому в строке** `notifications`, а не по текущему коду. Уже записанные строки несут `kind = 'kr_progress'` навсегда: upsert схлопывания намеренно не переписывает `kind` (`internal/store/notifications/notifications.go`), а миграции этих значений нет и не будет — в отличие от `domain.ActionKRProgress` в журнале, константа которого поэтому и сохранена. Удаление ветки превратило бы каждую такую строку в заглушку «Обновление по цели». (Проверено попутно: если старая строка всё-таки схлопнётся с новым чек-ином в том же десятиминутном бакете, ей обновится `payload_json` в новом формате — legacy-ветка читает из него `before.progress`/`after.progress`, которые там есть, и рендерится корректно.)

**Условие снятия:** истечение срока хранения уведомлений после выката. Ретенция — `notificationReadRetentionDays = 90` и `notificationAnyRetentionDays = 180` (`internal/scheduler/scheduler.go`), проход раз в сутки, возраст считается по `updated_at`. То есть **через 180 дней** после выката строк с `kind = 'kr_progress'` в таблице не останется; перед удалением ветки — убедиться запросом `SELECT count(*) FROM notifications WHERE kind = 'kr_progress'`. Эквивалента для `kr_note_updated` держать не нужно: `mapping.go` такого `kind` никогда не записывал.

### 7.3. `POST /api/v1/krs/{krID}/note` остался без известных клиентов

После перехода на чек-ин одним запросом интерфейс правит заметку полем `note` в теле запроса прогресса; отдельный маршрут не зовёт больше никто (`rg` по `web/` и `internal/` — только регистрация маршрута, golden-таблица и собственные тесты).

**Почему отложено:** маршрут — часть публичного API, а не внутренняя функция. Удалять его по факту «в этом репозитории вызывающих нет» рано: внешний потребитель (скрипт, интеграция) виден не из кода. Он к тому же уже идёт через `CheckIn`, то есть ничего не дублирует и не расходится в поведении — цена сохранения близка к нулю.

**Условие снятия:** решить судьбу маршрута, когда появится уверенность, что внешних потребителей нет (например, после наблюдения за логами доступа за период). Тогда — либо удалить вместе со строкой в `specs/040`, `specs/070` и golden-таблицей маршрутов, либо оставить осознанно и убрать из спеки оговорку «нет известных клиентов».

### 7.4. Фейковый стор `servicetest.Store` связан наполовину: заметку видит только одиночное чтение

`internal/service/servicetest/store.go`: `UpsertKeyResultNote` пишет в `Notes`, `GetKeyResultNote` читает оттуда же, а `BatchLoadNotes` по-прежнему возвращает `nil` — записанную заметку он не видит.

**Почему отложено:** связывание сделано ровно под нужду задачи — доказать, что `CheckIn` читает заметку **до** записи (мутация с перестановкой этих шагов переживала весь набор тестов, пока стор был парой независимых no-op). Потребителей `BatchLoadNotes` у этого фейка сегодня нет, а расширение фейка без теста, который бы его требовал, — код без вызывающего.

**Чего стоит ожидание:** будущий тест, записавший заметку и прочитавший её батчем, получит рассинхрон: одиночное чтение вернёт текст, батчевое — пусто. Ошибка выглядит как дефект продового кода, а не фейка.

**Условие снятия:** первый же тест, которому нужен батчевый путь; связать `BatchLoadNotes` с той же картой `Notes` (три строки), заодно — с `GoalStore.BatchLoadNotes`, где заглушка такая же.
