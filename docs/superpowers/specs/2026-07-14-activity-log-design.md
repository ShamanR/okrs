# Дизайн: Лог активности (Activity Log)

Дата: 2026-07-14
Ветка: `activity-log`

## Цель

Наполнить раздел `/activity-log` реальной функциональностью. Сейчас это
заглушка (`stub_shell` + `stub.js`, «Раздел в разработке»). Нужна лента
событий по OKR с фильтрами, переходами к цели/KR/комментарию и отображением
состояния БЫЛО→СТАЛО, а также контекстный сайдбар (период, разделы, избранное,
дерево команд), в котором **вместо прогресса показывается число лог-сообщений**.

## Мотивация / проблема

В БД сегодня нет истории изменений: прогресс KR, статусы команд и состав
целей/KR хранятся только как текущее состояние. Таймстемпы есть лишь у
комментариев. Значит, ленту активности нельзя вывести из существующих данных —
события нужно **фиксировать в момент действия** в отдельном append-only
журнале.

## Требования (из задачи)

1. Логируем типы событий:
   - изменение состава целей и/или KeyResult;
   - изменение статуса целей команды;
   - обновление прогресса KeyResult (ссылка на цель, прогресс, комментарий к цели);
   - комментарии к цели (новый комментарий, отметка РЕШЕНО).
2. Каждое сообщение содержит ссылку с переходом к цели/комментарию/KR и
   состояние БЫЛО→СТАЛО.
3. Сайдбар страницы: выбор периода, выбор разделов, избранные команды и
   иерархия команд. В иерархии вместо прогресса — число лог-сообщений (rollup по
   поддереву, как прогресс в трекере).
4. Выбор периода в сайдбаре меняет логи на относящиеся к целям этого периода;
   есть опция «Все периоды».
5. Табы-категории, «Все авторы», «Избранное», диапазон времени (Всё
   время / Сегодня / 7 дней / 30 дней), поиск по событиям — как на макете.
6. **Разграничение доступа.** Разделение по тенантам обязательно. Видимость
   ограничена командами, доступными пользователю (тот же scope, что в трекере):
   нет доступа к команде → не видно ни её целей, ни её событий, ни её вклада в
   счётчики дерева.
7. **Edge-case «пользователя убрали из пространства».** Не приводит к ошибкам;
   не показываем старого пользователя (ни email, ни аватар).
8. **Накопление и очистка.** Журнал растёт со временем. Нужна ручная очистка с
   выбором глубины: удалить всё старше квартала / старше года / всё. Кнопка — и в
   админке (в контексте своего пространства, tenant-admin), и в system-панели
   (как элемент управления пространством, system-admin).

## Принятые решения

- **Запись событий — явно в service-слое** (не триггеры БД, не async-outbox).
  Новая append-only таблица `activity_events` + `ActivityRepository`. Каждый
  инструментируемый метод `service.go` захватывает состояние ДО, делает мутацию,
  затем пишет событие.
  - _Почему не триггеры Postgres:_ триггер не знает actor'а и семантической
    категории, не строит человекочитаемое БЫЛО→СТАЛО, тянет бизнес-логику в БД,
    плохо тестируется в Go.
  - _Почему не outbox+worker:_ лишний процесс и координация в K8s, eventual
    consistency, которая тут не нужна. Таблица остаётся forward-compatible с
    этим подходом, если понадобится масштаб.
- **Best-effort запись.** Событие фиксируется **после** успешной мутации,
  отдельным вызовом `ActivityRepository`. Ошибка записи логируется, но **не
  пробрасывается** наверх — лента активности не должна ронять действие
  пользователя. Событие — побочный эффект, источник правды — сама мутация.
  (Компромисс: краш между мутацией и записью теряет одну строку лога — приемлемо
  для журнала активности, не для ledger.)
- **Actor — явный параметр** `actorUserID int64` в инструментируемых методах
  (как уже сделано для `AddGoalComment`). Service **не импортирует** `auth`,
  слои остаются чистыми; хендлер достаёт actor через `auth.UserIDFromContext`.
- **Правки полей — отдельные события** `goal_fields_changed` / `kr_fields_changed`
  с БЫЛО→СТАЛО по изменившимся полям (по решению «состав целей + правки полей»).
- **Share-aware видимость.** Событие видно тем, у кого есть доступ к любой команде
  из **audience цели** = {owner team} ∪ {команды, которым цель расшарена}, а не
  только владельцу. «Вижу цель → вижу её лог». Событие остаётся **одной строкой**
  (без дублей в хранении); audience и предикат видимости резолвятся на чтении из
  текущих `goal_shares`. Подробности и семантика счётчиков — в «Доступ».
- **Ссылки — структурный target, не URI.** В БД **не** храним готовый URL. Храним
  структурные id (`goal_id`/`kr_id`/`comment_id` + контекст), а URL собирает одна
  фронт-функция `buildTargetURL(target)`. Причины: роуты меняются (готовый URI
  замораживает схему и ломается на «router fix»); goal-permalink/goal-anchor
  сегодня **не существуют**, а `/goal-tree` — заглушка (нечего вмораживать);
  ссылка зависит от зрителя (scope), а не только от события; при
  удалении/переименовании/смене владельца по id деградируем корректно; URL — это
  presentation-слой, его нельзя протаскивать в доменную строку.
- **Deep-link в трекер (необходимое дополнение).** Сегодня трекер линкуется только
  `?team=&period=`, якоря на цель нет. Добавляем параметры `goal` (скролл +
  подсветка карточки), `kr` (раскрыть/подсветить KR), `comment` (открыть
  обсуждение) — иначе «переход к цели/KR/комментарию» из требования не работает.
- **Навигационный target резолвится на чтении:** ведём на **текущий** owner-team
  цели, если он доступен зрителю; иначе — на любую доступную зрителю команду из
  audience (детерминированный выбор). Так sharee-зритель, не имеющий доступа к
  owner-команде, попадает на свою sharee-доску, где цель тоже видна.
- **Счётчики дерева реагируют только на период + диапазон времени** (не на
  категорию/автора/поиск) — так число стабильно и дёшево считается; фронт
  агрегирует по поддереву. При share-aware событие расшаренной цели засчитывается
  каждой команде из audience (см. «Доступ» — оговорка про дубли в поддереве).
- **Bell / непрочитанные, ретеншн, бэкфилл истории — вне scope** (см. ниже).
- **Демо-seed наполняем** богатой лентой; forward-only для реальных тенантов.

## Доменная модель и миграция

Новая сущность `ActivityEvent`. Миграция создаёт таблицу `activity_events`:

| Поле | Тип | Смысл |
|---|---|---|
| `id` | bigserial PK | |
| `tenant_id` | bigint NOT NULL | тенант (scope); FK → tenants.id |
| `actor_user_id` | bigint NOT NULL | кто сделал; FK → users.id. В `auth=disabled` — `anonymous-local` (id=1) |
| `category` | text NOT NULL | `progress` \| `composition` \| `status` \| `discussion` |
| `action` | text NOT NULL | конкретное действие (список ниже) |
| `team_id` | bigint | команда-контекст (для дерева/scope/фильтра). FK → teams.id ON DELETE SET NULL |
| `period_id` | bigint | период-контекст (для фильтра по периоду). FK → periods.id ON DELETE SET NULL |
| `goal_id` | bigint | ссылка на цель (nullable) |
| `kr_id` | bigint | ссылка на KR (nullable) |
| `comment_id` | bigint | ссылка на комментарий (nullable) |
| `entity_title` | text | снапшот заголовка цели/KR на момент события (ссылка читается даже после удаления/переименования) |
| `payload_json` | jsonb NOT NULL DEFAULT '{}' | `{ before, after, ... }` + доп. поля (проценты, unit, текст) |
| `created_at` | timestamptz NOT NULL DEFAULT now() | |

Индексы:

- `(tenant_id, created_at DESC, id DESC)` — основной feed + курсорная пагинация;
- `(tenant_id, period_id, created_at DESC)` — фильтр по периоду;
- `(tenant_id, team_id, created_at DESC)` — фильтр по команде и tree-counts;
- `(tenant_id, actor_user_id)` — фильтр по автору.

`payload_json` — расширяемое хранилище без миграций (по образцу
`attributes_json` / `key_results.checkpoints`). FK на сущности не каскадят
удаление события: журнал append-only, ссылки становятся «висячими», но
`entity_title` сохраняет читабельность. Хранимые `team_id`/`period_id` — это
**контекст на момент события** (owner-team тогда, период цели): используются для
scope, счётчиков и бейджа периода. **Навигационный** target (куда ведёт ссылка)
резолвится на чтении от текущего состояния цели (см. Read API) — при
удалении/недоступности цели `target = null`.

### Значения `action` по категориям

- **progress:** `kr_progress`.
- **composition:** `goal_created`, `goal_deleted`, `kr_created`, `kr_deleted`,
  `goal_shared`, `goal_unshared`, `goal_owner_changed`, `goal_fields_changed`,
  `kr_fields_changed`.
- **status:** `status_changed`.
- **discussion:** `comment_added`, `comment_resolved`, `comment_reopened`.

Категория (`progress`/`composition`/`status`/`discussion`) совпадает с табами на
макете (Прогресс / Состав целей / Статусы и риски / Обсуждения).

## Слои: store и service

- `internal/domain` — тип `ActivityEvent`, enum `ActivityCategory`, `ActivityAction`.
- `internal/store/activity` — новый `ActivityRepository`:
  - `Record(ctx, scope, event) error` — INSERT одной строки;
  - `List(ctx, scope, accessibleTeamIDs []int64, filter) ([]ActivityEvent, nextCursor, error)` —
    feed с фильтрами и курсорной пагинацией; видимость по audience (джойн
    `goals → goal_shares`) ∩ `accessibleTeamIDs`;
  - `TreeCounts(ctx, scope, accessibleTeamIDs []int64, periodID *int64, since time.Time) (map[int64]int, error)` —
    прямые счётчики по команде (audience-раскрытие ∩ доступные команды).
  - `Purge(ctx, scope, olderThan *time.Time) (deleted int64, err error)` —
    tenant-scoped удаление (см. «Очистка журнала»).
  - Регистрируется в `store.Store` (поле `Activity`), как остальные репозитории.
  - `accessibleTeamIDs` вычисляется тем же путём, что и в трекере/`GET /api/v1/hierarchy`
    (набор доступных команд из `PolicyEvaluator`), и передаётся из сервиса.
- `internal/service` — интерфейс `ActivityRepo` в `Deps`; метод-хелпер
  `recordActivity(ctx, ev)` (best-effort, логирует ошибку). Инструментируемые
  методы получают `actorUserID` и вызывают `recordActivity` после мутации.
  Публичные read-методы: `ListActivity(ctx, scope, filter)` и
  `ActivityTreeCounts(ctx, scope, ...)` — применяют scope-фильтр (см. «Доступ»).
  Очистка: `PurgeActivity(ctx, scope, olderThan)` — проверяет tenant-admin
  authority; system-плоскость — отдельный метод (в provisioning/system-сервисе)
  с проверкой system-admin, tenant-id из пути.

### Точки инструментирования (service.go)

| Метод | action | before → after / payload |

| `UpdateKRProgressNumerical/Boolean/Project` | `kr_progress` | значение и % до/после, unit; текст комментария к цели, если задан в том же действии |

`team_id` / `period_id` заполняются из агрегата цели (цель → owner team + period;

## Read API

Scope: только команды, доступные пользователю по grants (`PolicyEvaluator`), в
пределах активного тенанта.

### `GET /api/v1/activity`

Query-параметры:

- `period_id` (int, опц.) — фильтр по периоду; отсутствует → «Все периоды»;
- `team_ids[]` (int, опц.) — клик по дереву/разделу; фильтр по **audience**: событие
  проходит, если выбранная команда ∈ audience его цели (owner **или** sharee);
- `category` (опц.) — `progress` \| `composition` \| `status` \| `discussion`;
- `actor_udid` (опц.) — фильтр по автору;
- `range` (опц.) — `today` \| `7d` \| `30d` \| `all` (по умолчанию `all`);
- `q` (опц.) — поиск по `entity_title`, тексту payload и имени автора (case-insensitive);
- `cursor`, `limit` (по умолчанию 50, максимум 100) — курсорная пагинация по `(created_at, id)`.

Ответ: `{ items: [...], next_cursor }`. Каждый `item`:

```json
{
  "id": 123,
  "category": "progress",
  "action": "kr_progress",
  "actor": { "udid": "...", "display_name": "...", "avatar_url": "...", "removed": false },
  "team": { "id": 42, "name": "Платформа" },
  "period": { "id": 7, "name": "Q1 · 2026" },
  "goal_id": 900, "kr_id": 555, "comment_id": null,
  "entity_title": "P95 latency API gateway",
  "target": { "section": "tracker", "team_id": 42, "period_id": 7, "goal_id": 900, "kr_id": 555 },
  "before": { "value": 320, "progress": 40 },
  "after":  { "value": 278, "progress": 61 },
  "created_at": "2026-07-14T09:12:00Z"
}
```

`actor` резолвится tenant-scoped (см. «Доступ»): для не-участника —
`{ "removed": true, "display_name": "Бывший участник" }` без `avatar_url`/email.

`target` — структурный дескриптор перехода (без готового URL), собранный на
чтении: `team_id` = текущий owner-team цели, если доступен зрителю, иначе
доступная зрителю команда из audience; `period_id` = период цели; `goal_id` +
опц. `kr_id`/`comment_id` — якорь. Если цель удалена/недоступна → `target: null`
(фронт покажет `entity_title` без ссылки). URL строит `buildTargetURL(target)` на
фронте; `section` оставляет задел на другие разделы (напр. будущий goal-tree).

### `GET /api/v1/activity/tree-counts`

Query: `period_id` (опц.), `range` (опц.). Ответ: `{ "counts": { "<team_id>": <int> } }`
— прямые счётчики событий по команде за период+диапазон, в рамках доступного
scope. Счётчик команды T = число событий, у которых T ∈ audience цели (owner
**или** sharee) — согласовано с фильтром ленты по команде. Фронт агрегирует по
поддереву (дерево у него уже есть) → число в сайдбаре = rollup по потомкам.
Категория/автор/`q` на дерево не влияют.

Оговорка (share-aware): цель, расшаренная между двумя командами **внутри одного
поддерева**, может быть посчитана в rollup этого поддерева более одного раза
(событие реально видно под каждой из команд). Приемлемая аппроксимация для v1;
точный dedup по поддереву — вне scope. Шаринг обычно кросс-веточный, поэтому на
практике почти не проявляется.

Оба эндпоинта — read-only, под membership-гейтом, tenant-scoped.

## Очистка журнала (ручной retention)

Автоматического retention нет — очистка запускается вручную с выбором глубины.
Глубина `older_than` (закрытый справочник):

- `quarter` — удалить события старше 3 месяцев (`created_at < now() - interval '3 months'`);
- `year` — старше 12 месяцев (`created_at < now() - interval '12 months'`);
- `all` — удалить все события пространства.

### Store / service

- `ActivityRepository.Purge(ctx, scope, olderThan *time.Time) (deleted int64, err error)`
  — `DELETE FROM activity_events WHERE tenant_id = $scope AND (olderThan IS NULL OR created_at < olderThan)`.
  Всегда tenant-scoped (нельзя задеть чужой тенант). `all` → `olderThan = nil`.
- Cutoff считается в сервисе из `older_than` (`quarter`/`year`/`all`), не приходит
  «сырым» временем с клиента.
- Операция **не логируется** сама в журнал (без мета-рекурсии); v1.

### API

- **Tenant-admin (своё пространство):**
  `POST /api/v1/admin/activity/purge`, body `{ "older_than": "quarter"|"year"|"all" }`
  → `200 { "deleted": <int> }`. Tenant-id из контекста; write-authority — **admin**
  тенанта (проверка в service-слое, как у прочих admin-действий). CSRF обязателен.
- **System-admin (управление пространством):**
  `POST /api/v1/system/tenants/{id}/activity/purge`, тело то же → `200 { "deleted": <int> }`.
  По образцу `suspend`/`restore`/`entitlements`. Authority — **system-admin**;
  tenant-id из пути. `404`, если тенант не найден. CSRF обязателен.
- `422` при неизвестном `older_than`.

### UI (консистентные контролы, CLAUDE.md rule 12)

- **Админка (`admin.js`):** в разделе управления пространством — контрол «Очистить
  лог активности» с выбором глубины (Старше квартала / Старше года / Всё) и
  **подтверждением** (действие деструктивно и необратимо). Успех показывает число
  удалённых.
- **System-панель (`system.js`):** тот же контрол в карточке управления тенантом,
  рядом с suspend/restore/entitlements. Переиспользуем один и тот же
  select-глубины + confirm-паттерн, чтобы контролы были одинаковы на обеих
  плоскостях.

## Доступ и безопасность

- **Тенант.** Все запросы фильтруются по `tenant_id` из `TenantScope`. Событие
  одного тенанта недоступно из другого.
- **Team scope (share-aware).** Видимость события определяется его **audience** =
  {owner team цели} ∪ {команды, которым цель расшарена}; для событий без цели
  (`status_changed`) audience = {команда события}. Событие видно, если audience ∩
  доступные пользователю команды (`PolicyEvaluator`) ≠ ∅. Нет доступа ни к одной
  команде из audience → событие не попадает ни в ленту, ни в счётчики; обойти
  через прямой запрос эндпоинта нельзя. Событие остаётся **одной строкой** —
  audience раскрывается на чтении джойном `activity_events → goals → goal_shares`;
  в ленте событие не дублируется (widened-предикат видимости), в `TreeCounts`
  засчитывается каждой команде из audience (см. оговорку в tree-counts).
- **Fail-closed по `team_id`.** Событие с `team_id IS NULL` (например, команда
  была hard-deleted) в scoped-ленту и счётчики **не попадает** — видимы только
  события с известной доступной командой. (Hard delete команды разрешён лишь при
  отсутствии goals во всех периодах, т.е. таких событий практически не бывает;
  правило — на всякий случай, чтобы не протечь.)
- **Edge-case «пользователь убран из пространства».**
  - Событие остаётся (append-only). При рендере actor резолвится через
    tenant-scoped путь: активный участник → имя + аватар; **не участник /
    не резолвится → нейтральный плейсхолдер** (`removed: true`,
    «Бывший участник», инициалы-фолбэк) **без email и без аватара**.
  - Резолв actor'а никогда не бросает: отсутствие/удаление пользователя даёт
    плейсхолдер, а не 500. Батч-резолв авторов не падает на одном отсутствующем.
  - `avatar_url` и email не участвуют в ответе для не-участников — PII бывшего
    участника не утекает.
- **CSRF/экранирование.** Эндпоинты read-only (GET) — CSRF неприменим. Все
  пользовательские данные (заголовки, тексты, имена) рендерятся через безопасное
  экранирование, без raw HTML.

## Тесты

- **service:** запись события на каждую категорию (progress/composition/status/
  discussion), корректный before→after, best-effort (ошибка записи не роняет
  мутацию), заполнение team_id/period_id.
- **store:** `List` с фильтрами (period, team, category, actor, range, q),
  курсорная пагинация; `TreeCounts` по периоду+диапазону.
- **доступ (share-aware):** sharee-зритель видит событие расшаренной цели; зритель
  без доступа к любой команде из audience — не видит (ни в `List`, ни в
  `TreeCounts`); изоляция по тенанту; fail-closed при `team_id IS NULL`;
  actor-резолв для не-участника отдаёт плейсхолдер без PII и не падает.
- **target:** резолв ведёт на текущий owner-team, если доступен; иначе на
  доступную sharee-команду; `target: null` при удалённой/недоступной цели.
- **handler:** query-параметры, пагинация, membership-гейт.
- **очистка:** `Purge` удаляет только события своего тенанта (не задевает чужой);
  `quarter`/`year` режут по cutoff, `all` — всё; возвращает число удалённых;
  authority — admin (tenant-эндпоинт) и system-admin (system-эндпоинт), отказ
  не-админу; `422` на неизвестный `older_than`; CSRF на обоих.
