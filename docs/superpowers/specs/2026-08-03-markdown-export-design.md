# Экспорт целей в Markdown — дизайн

Дата: 2026-08-03

## Проблема и цель

Пользователю нужно выгружать OKR в Markdown — для внешних документов, вики, ревью.
Экспорт запускается из трекера, отдаёт готовый Markdown, который можно посмотреть в
превью, скопировать в буфер или скачать файлом.

## Scope фичи

Три уровня выгрузки:

1. **Одна цель** (`goal`) — конкретная цель с её KR.
2. **Цели команды** (`team`) — все цели команды-контекста в выбранном периоде.
3. **С вложенными командами** (`tree`) — цели команды + цели всего доступного поддерева.

Два вида детализации:

- **Краткий** (`short`) — команда (с путём иерархии), список целей, их описания и KR-чеклист.
- **Полный** (`full`) — краткий + метаданные цели + детали KR + описания KR + заметки KR.

Независимый флаг **Комментарии** — добавляет к целям блок обсуждений (таски + ответы).

Выгрузка: **в буфер обмена** или **файлом** `.md`.

Точка входа: меню «···» у цели (рядом с 🔗 «копировать ссылку»). Расширить scope до команды
или поддерева можно прямо в модалке.

## Архитектура и слои

Генерация Markdown — **на сервере**. Клиент запрашивает готовый текст, показывает превью и
по этому же тексту копирует/скачивает. Единый источник форматирования (не дублируется на
клиенте), эффективный batched-доступ к БД для поддерева, покрытие Go-тестами.

- **`internal/export`** (новый пакет) — чистые функции форматирования:
  на вход доменные агрегаты (дерево команд, goals, key results, comments), на выход — `string`.
  Без SQL и HTTP. Прогресс KR/цели берётся из `internal/okr` (единый источник расчётов).
- **`internal/service`** — оркестрация экспорта: по `scope` грузит нужные данные
  (со scope-фильтрацией по правам), вызывает форматтер. Никакой бизнес-логики в handler.
- **`internal/store`** — переиспользуем существующие batch-загрузчики OKR команды; для `tree`
  список команд поддерева фильтруется по scope **до** загрузки целей, цели грузятся batched
  (без N+1).
- **`internal/http/handlers/api/v1/teams`** — тонкий handler: парсинг/валидация параметров,
  вызов сервиса, сериализация ответа.

Слои не протекают: handler не ходит в БД напрямую, форматтер не знает про HTTP/SQL,
расчёты прогресса не дублируются.

## API-контракт

### `GET /api/v1/teams/{teamID}/export`

Отдаёт Markdown-выгрузку целей для выбранного scope в выбранном периоде.

**Method + path:** `GET /api/v1/teams/{teamID}/export`

**Request (query-параметры):**

- `period_id` (int64, **обязателен**) — период выгрузки.
- `scope` (**обязателен**) — `goal` | `team` | `tree`.
- `goal_id` (int64, обязателен **при `scope=goal`**) — цель для выгрузки.
- `format` — `short` | `full`, по умолчанию `short`.
- `comments` — `0` | `1`, по умолчанию `0`.

**Validation rules:**

- `period_id` отсутствует/невалиден → `400 VALIDATION_ERROR`.
- `scope` не из набора → `400 VALIDATION_ERROR`.
- `scope=goal` без `goal_id` (или невалидный) → `400 VALIDATION_ERROR`.
- `format`/`comments` вне набора → `400 VALIDATION_ERROR`.
- `teamID` вне tenant/scope запрашивающего → `404 NOT_FOUND`.
- `scope=goal`: цель не принадлежит команде-контексту (как владелец) и не расшарена в неё,
  либо команда-владелец вне scope → `404 NOT_FOUND`.

**Success response (`200 application/json`):**

```json
{
  "filename": "okr-y26q1-u1.md",
  "markdown": "<!-- OKR export · Q1 · 2026 -->\n\n# Платформа\n\n## ...",
  "lines": 41
}
```

- `filename` — предлагаемое имя файла (см. «Имя файла»).
- `markdown` — готовый текст.
- `lines` — число строк в `markdown` (для футера модалки).

**Error cases:** `400 VALIDATION_ERROR`, `404 NOT_FOUND`, `500 INTERNAL`. Shape ошибок — как у
остального контракта.

**Idempotency:** read-only, без side effects, идемпотентен. CSRF не требуется (safe GET).

**Side effects on aggregates:** нет. Прогресс/агрегаты не изменяются, только читаются.

Скачивание файла делает клиент: создаёт Blob из `markdown` с именем `filename`. Отдельного
download-эндпоинта нет.

## Права доступа (server-enforced)

Ограничение доступа — жёсткое серверное правило, не косметика UI.

- **Tenant / пространство** — endpoint работает только в активном тенанте запрашивающего
  (`TenantScopeFromContext`), как все `/api/v1/teams/*`. Данные другого пространства недостижимы.
- **Scope (hierarchy grants)** — применяется `PolicyEvaluator`:
  - `scope=goal` / `scope=team` — `teamID` (или команда-владелец цели) вне scope → `404`.
  - `scope=tree` — в вывод попадают только доступные потомки: пересечение поддерева со scope.
    Недоступные ветки молча исключаются из Markdown **и** из счётчиков.
  - Расшаренные цели — доступны, если пользователь видит команду-владельца или одну из
    shared-команд из своего scope (существующая audience-логика).
- **Admin / `AUTH_MODE=disabled`** — полный доступ в рамках тенанта, как везде.
- Проверка — в service/handler-слое на сервере. Клиент дополнительно не показывает недоступное,
  но полагаться на это нельзя.

Следствие для запросов: список команд поддерева фильтруется по scope до загрузки целей, чтобы
не тянуть лишние данные.

## Формат Markdown

Каждая выгрузка начинается с комментария-заголовка периода:

```
<!-- OKR export · Q1 · 2026 -->
```

### Краткий вид (`short`)

Для `scope=team`:

```
<!-- OKR export · Q1 · 2026 -->

# Платформа

## Снизить P95 latency до 200ms

Оптимизировать критические пути запросов

- [ ] P95 latency API gateway
- [ ] P95 latency auth service
- [ ] Миграция на HTTP/2
```

- `#` — команда. Для `scope=goal` — та же структура, но одна цель.
- Для `scope=tree` — каждая команда отдельным блоком; иерархия отражается путём в заголовке
  команды (`# A / B / Платформа`). Уровень заголовка целей внутри блока — `##`.
- `##` — заголовок цели.
- Под заголовком цели — её **описание** (Markdown как есть). Описание цели входит и в краткий
  вид (ключевой контекст).
- KR — чеклист: `- [ ]` для невыполненного, `- [x]` если KR выполнен (`progress == 100`;
  для BOOLEAN — is_done; для NUMERICAL — достигнута цель; для PROJECT — 100% этапов).

### Полный вид (`full`)

Дополняет краткий:

- Под заголовком цели — строка метаданных: приоритет (`P0`–`P3`), вес (`вес N%`), тип работы
  (Delivery/Discovery), фокус (Title Case, как в UI), драйверы (владельцы), прогресс `N%`.
- KR — помимо чеклист-строки: тип KR; для `NUMERICAL` — `start → current / target unit`;
  вес KR; критерий обнуления (если задан); прогресс `N%`.
- **Описания KR** (Markdown как есть).
- **Заметки KR** (`KeyResultNote`) — текст + автор.

Точная типографика строк метаданных фиксируется в плане реализации и закрепляется тестами;
принцип — компактно, человекочитаемо, стабильно между вызовами.

### Комментарии (`comments=1`)

Независимо от `short`/`full`. Под целью:

```
**Комментарии**
- Алексей Иванов (21 апр): Начали профилирование. Нашли узкое место в middleware auth.
- Дмитрий Петров (20 апр): Нужно учесть зависимость от PaaS/Infra по HTTP/2-конфигурации nginx.
```

- Выводятся таски (замечания первого уровня) по возрастанию `created_at`; решённые помечаются.
- Ответы — с отступом под своей таской.
- Автор + дата у каждой записи.

### Общие цели (дедуп)

В `scope=tree` одна и та же расшаренная цель может относиться к нескольким командам. В выгрузке
цель показывается в блоке команды-владельца; в командах, куда она расшарена, помечается как
общая без дублирования тела (в кратком — строкой-ссылкой/пометкой; детали типографики — в плане).
В `scope=team` цель отображается на доске команды-контекста по правилам board (owner + shared-in),
консистентно с `GET /api/v1/teams/{id}/okrs`.

### Экранирование

Пользовательский текст (заголовки, описания, комментарии) — валидный Markdown-контент; спецсимволы
не должны ломать структуру документа. Правила экранирования фиксируются тестами.

### Имя файла

Схема: `okr-y<YY>q<Q>-<code>.md`, где `<YY>` — две цифры года периода, `<Q>` — квартал (если
период квартальный; иначе слаг периода), `<code>`:

- `g<goalId>` — одна цель;
- `<типная-буква><teamId>` — команда (буква из `team.type`);
- `<типная-буква><teamId>-tree` — с вложенными командами.

Имя формирует сервер и возвращает в `filename`. Схема — предмет уточнения, при необходимости
правится в реализации.

## UI (tracker.js)

Живёт на странице трекера (`/teamOkrs`). Работает через **API hydration** (запрос готового
Markdown к новому endpoint); мутаций нет.

- В меню «···» у цели (рядом с кнопкой 🔗) — пункт **«Экспорт в Markdown»**. Открывает модалку
  `ExportModal` с предвыбранным scope `goal`.
- Модалка:
  - шапка: «Экспорт целей в Markdown» + подзаголовок `<период> · <путь команды>`;
  - три карточки-скоупа (Одна цель / Цели команды / С вложенными командами) со счётчиками;
  - два чекбокса: «Полный экспорт» (`format`), «Комментарии» (`comments`);
  - область превью с моноширинным Markdown;
  - футер: имя файла + число строк слева; кнопки «Закрыть» / «Скопировать» / «Скачать .md».
- Смена scope/чекбоксов → debounced-запрос к endpoint, превью обновляется. «Скачать»/«Скопировать»
  используют уже полученный `markdown`.
- Счётчики карточек: «цели команды» — из данных доски (уже загружены); «команд в структуре» — из
  hierarchy (клиент уже имеет, с учётом scope); число целей для nested — из ответа endpoint при
  выборе этого scope.
- Копирование — через `navigator.clipboard` с fallback на `textarea+execCommand` (как в
  существующем «копировать ссылку»). Скачивание — Blob + `download`-ссылка.
- Общие компоненты и стиль — консистентно с существующими модалками трекера (переиспользуем
  каркас модалки, кнопки, `Markdown`-стили где уместно).

### Empty / error / loading states

- **loading** — «Загрузка превью…» в области превью при каждом запросе.
- **error** — заглушка ошибки запроса с возможностью повторить.
- **copied** — кнопка «Скопировать» кратко показывает ✓ «Скопировано».
- Скоуп `goal` предвыбран (вход из меню цели).

### Зависимости от статуса / роли / auth mode

- **Team period status** — не влияет: экспорт доступен во всех статусах.
- **Auth mode / роль** — не влияет на доступность пункта меню; фактический доступ к данным
  ограничен tenant + scope на сервере (см. «Права доступа»).
- Ограничение проверяется на сервере, не только в UI.

## Тесты

- **`internal/export`** — табличные тесты: `short`/`full` × `goal`/`team`/`tree` ×
  `comments` on/off; KR-чеклист (done/not для BOOLEAN/NUMERICAL/PROJECT); детали NUMERICAL;
  дедуп общих целей в `tree`; экранирование пользовательского текста; заголовок периода.
- **Handler** — валидация всех параметров; scope-фильтрация (`404` вне scope/tenant);
  `scope=tree` отдаёт только доступные ветки; `scope=goal` — привязка цели к команде-контексту.
- **Service** — сборка данных по scope без N+1 (батчинг для tree).
