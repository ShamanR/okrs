# Публичный раздел «Обзор периода» (admin-only)

Дата: 2026-08-03

## Проблема и цель

Обзор периода (команды по статусам, ошибки весов, средний прогресс, массовые
операции) сейчас доступен только внутри админ-панели — в модалке «Управление
периодом» на `/admin/periods`. Админам удобнее видеть эту сводку в основном
приложении, рядом с трекером, не заходя в админку.

Цель: добавить в основное приложение (не админка) раздел «Обзор периода»,
видимый в сайдбаре только админам. Раздел визуально повторяет обзор периода из
админ-панели. Период, для которого строится обзор, **выбирается выпадающим
списком в сайдбаре** (переиспользуем существующий компонент), по умолчанию —
текущий активный период.

## Область (scope) и ключевые решения

- **Новых API не требуется.** Страница регистрируется под тем же
  `RequireTenantAdminMiddleware`, что и админ-эндпоинты, поэтому переиспользует
  готовые:
  - `GET /api/v1/admin/periods/{periodID}/overview` — данные обзора;
  - `POST /api/v1/admin/periods/{periodID}/teams/activate` — массовый перевод в «В работе»;
  - `POST /api/v1/admin/periods/{periodID}/teams/close` — массовое закрытие целей.
  - Список периодов — публичный `GET /api/v1/periods` (уже используется трекером).
- **Период выбирается выпадающим списком в сайдбаре** — переиспользуем
  существующий компонент `PeriodSelect` из трекера; по умолчанию выбран текущий
  активный период.
- **Общий презентационный компонент** для админ-модалки и публичной страницы —
  чтобы гарантировать визуальную идентичность и исключить дрифт (CLAUDE.md #13).

## Выбор периода

Период выбирается выпадающим списком в сайдбаре — тем же компонентом, что и в
трекере (`PeriodSelect`, отдаётся через слот `beforeSections` компонента
`Sidebar`, с подписью «Период»). Список периодов — `GET /api/v1/periods`. При
смене периода обзор перезагружается.

**Период по умолчанию** — текущий активный, определяется так же, как на сервере
(`FindPeriodForDate`, `internal/store/periods/periods.go`): среди неархивных
периодов, чей диапазон дат содержит сегодня, берём самый короткий (наименьший
`end − start`) — это текущий квартал, а не охватывающий год. Вычисляется на
клиенте из `GET /api/v1/periods` (`start_date`, `end_date`, `status`): фильтруем
`status == "active"`, выбираем период с наименьшей длительностью; при равенстве —
с более поздним `end_date`. Если активного периода нет — по умолчанию первый
период списка (как в трекере). Если периодов нет вовсе — пустое состояние.

### Переиспользование `PeriodSelect`

`PeriodSelect` и его хелперы (`TRK_PERIOD_STATUS`, `fmtPeriodDate`,
`fmtDateRange`) сейчас определены в `tracker.js`. Выносим их в общий файл
`internal/web/static/period_select.js`, подключаемый в `tracker-shell` и в новый
`period-overview-shell` (перед `tracker.js` / `period-overview.js`
соответственно). CSS-классы `period-select__*` и `sidebar__period` уже в
`tracker.css`/`sidebar.css`, которые оба шелла загружают, — верстка не
дублируется. `tracker.js` перестаёт объявлять эти символы и использует общий файл;
поведение трекера не меняется.

## Переиспользование вёрстки — общий компонент

Выносится презентационный компонент `PeriodOverviewContent` в новый общий файл
`internal/web/static/period_overview_view.js`, подключаемый и в `admin-shell`, и в
новый `period-overview-shell`.

Компонент рендерит (то, что общее для модалки и страницы):

- плитки «КОМАНДЫ ПО СТАТУСАМ» (5 плиток);
- плитки «КАЧЕСТВО И РЕЗУЛЬТАТ» (команды с целями / ошибки весов / средний прогресс);
- inline drill-down состава команд выбранной категории;
- карточки «МАССОВЫЕ ОПЕРАЦИИ» (активация / закрытие).

Интерфейс компонента:

```
PeriodOverviewContent({ data, busy, onApply })
```

- `data` — ответ `GET …/overview` (`{ period_id, summary, teams }`);
- `busy` — булево, блокирует кнопки во время операции;
- `onApply(ep)` — колбэк массовой операции (`ep` = `"activate" | "close"`),
  который контекст реализует сам (админ-модалка перезагружает список периодов;
  публичная страница — рефетчит overview).

Компонент самодостаточен по стилю: использует `ACCENT` из `ui.js` + инлайновые
стили + собственные мини-кнопку и бейдж статуса. Не зависит от `T`/`Btn`/
`PeriodBadge` из `admin.js`, чтобы работать в обоих бандлах. Превью-счётчики
массовых операций (`затронет N` / `пропустим M без целей`) считаются внутри
компонента из `data`.

### Рефакторинг админ-модалки

`PeriodOverviewModal` в `admin.js` оставляет свою шапку (имя/даты/статус +
«Редактировать»/«Удалить») и обёртку `Modal`, а тело (плитки + drill-down + bulk)
делегирует в `PeriodOverviewContent`. Дублирующая вёрстка плиток/drill/bulk и
локальные `STATUS_TILES` из `admin.js` удаляются. `onApply` в админ-контексте
выполняет тот же POST + рефетч overview + `reload()` списка, что и раньше.

**Единственное видимое изменение в существующей админ-модалке:** порядок плиток
статусов унифицируется в порядок жизненного цикла — Нет целей → Черновик →
К валидации → В работе → Закрыто (как на скриншоте публичной страницы), и
одинаковые цвета статусов в обоих местах. Всё остальное поведение сохраняется.

## Новый бандл и страница

- `internal/web/static/period-overview.js` — по образцу `activity.js`:
  - монтируется через `ReactDOM.createRoot(document.getElementById('root'))`;
  - грузит `GET /api/v1/me`, `GET /api/v1/periods`, `GET /api/v1/config`;
  - держит state выбранного `periodId`; по умолчанию — текущий активный период
    (см. выше), иначе первый период списка;
  - фетчит `GET /api/v1/admin/periods/{periodId}/overview` при каждой смене периода;
  - рендерит `<Sidebar user={me} active="period-overview"
    beforeSections={<div className="sidebar__period"><div
    className="sidebar__period-label">Период</div><PeriodSelect periods={periods}
    periodId={periodId} onChange={setPeriodId}/></div>} .../>` + шапку
    «`<Имя периода>` · `N` команд в вашем доступе» (`N = summary.total_teams`) +
    `<PeriodOverviewContent data busy onApply/>`;
  - `onApply(ep)` → `POST /api/v1/admin/periods/{periodId}/teams/{ep}` → рефетч overview.
- `internal/http/templates/period_overview_shell.html` — новый шелл (по образцу
  `activity_shell.html`): те же CSS (`tracker.css`, `components.css`, `sidebar.css`)
  и вендор-скрипты; грузит `api.js`, `storage.js`, `ui.js`, `sidebar.js`,
  `period_select.js`, `period_overview_view.js`, `period-overview.js`.
- `internal/http/templates/tracker_shell.html` — добавить `period_select.js`
  **перед** `tracker.js` (после выноса `PeriodSelect` в общий файл).
- `internal/http/templates/admin_shell.html` — добавить `period_overview_view.js`
  **перед** `admin.js`.
- `internal/http/server.go` — маршрут `GET /period-overview` внутри
  `registerAdminRoutes` (серверный admin-гейт), отдаёт `period-overview-shell`.
- `internal/web/static/sidebar.js` — новый пункт в `SIDEBAR_SECTIONS`:
  `{ id: 'period-overview', label: 'Обзор периода', href: '/period-overview', icon: '📊', adminOnly: true }`
  — вставить **перед** `activity-log`. На странице `active="period-overview"`.

## Ошибки и пустые состояния

- Нет ни одного периода → пустое состояние «Периодов пока нет».
- Нет активного периода, но периоды есть → по умолчанию выбран первый; селектор
  позволяет выбрать любой.
- Ошибка загрузки overview → ненавязчивое сообщение об ошибке, без падения страницы.
- Не-админ, открывший `/period-overview` напрямую → серверный `403`
  (`RequireTenantAdminMiddleware`); пункт сайдбара у него и так скрыт
  (`adminOnly` + `cfg.is_admin`).

- Backend не меняется — переиспользуемые эндпоинты уже покрыты тестами
  (`period_overview_test.go`, `period_overview` handler-тесты).
- `internal/http/templates_test.go` — добавить проверку, что новый шелл-темплейт
  `period-overview-shell` парсится и рендерится (по образцу существующих
  проверок шеллов).
- Frontend — проверка компиляции JSX затронутых бандлов
  (`period_overview_view.js`, `period-overview.js`, `admin.js`) и визуальная
  проверка в запущенном приложении: пункт сайдбара виден только админу, по
  умолчанию выбран текущий период, смена периода в выпадающем списке сайдбара
  перезагружает обзор, плитки/drill-down/массовые операции работают и совпадают с
  админ-модалкой. Отдельно — что трекер не сломался после выноса `PeriodSelect`.

## Вне scope

- Новые серверные эндпоинты или изменение доменной логики обзора/массовых операций.
