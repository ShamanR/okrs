# Обзор периода, массовые операции и иконочные контролы

Дата: 2026-07-30

## Проблема и цель

Раздел «Периоды целеполагания» (`/admin/periods`) даёт только базовое управление
периодами: создание, редактирование, вложенность, архив. Действия в строке —
текстовые ссылки (`+ вложенный`, `В архив`, `Изм.`, `×`), не выровнены и плохо
читаются. Нет сводной картины по периоду: сколько команд в каком статусе, у скольких
ошибки весов, средний прогресс. Нет способа массово перевести команды периода в
«В работе» или закрыть все цели периода.

Цель:

1. Заменить текстовые действия строки на консистентные иконочные контролы с
   подсказками, выровненные по правому краю.
2. Показать в строке периода метрики: сколько команд с целями, средний прогресс,
   число ошибок весов.
3. Добавить модалку «Управление периодом» с обзором (счётчики по статусам, ошибки
   весов, средний прогресс, drill-down состава команд) и массовыми операциями
   («перевести все команды с целями в В работе», «закрыть все цели периода»).

## Текущее состояние (что переиспользуем)

- `internal/web/static/admin.js` — `PeriodsSection`, `PeriodRow`, `PeriodAction`.
  Строка рендерит имя / даты / статус-бейдж / текстовые действия.
- `internal/http/dto/period.go` — `PeriodInfo` без метрик.
- `internal/service/healthcheckin.go` — уже грузит `PeriodData` (teams +
  goalsByTeam + statuses) за один проход и умеет считать ошибки весов
  (`weightSum != 100`) и прогресс целей (`CalculateGoalProgress`). Это база для
  агрегатора обзора.
- `internal/service/service.go:UpdateTeamPeriodStatus` — меняет статус команды в
  периоде и пишет **одну** запись op-лога (`recordActivity`,
  `ActivityStatus/ActionStatusChanged`).
- Одиночный переход статуса: `POST /api/v1/teams/{teamID}/status`.

## Подход к агрегации

Выбран вариант A: один общий сервисный агрегатор поверх существующего загрузчика
`PeriodData`. Причины: прогресс вычисляется в Go на чтении (не хранится в БД),
поэтому чисто SQL-агрегация невозможна без загрузки KR; периодов немного
(год + кварталы), это admin-страница; переиспользуем логику весов/прогресса из
healthcheck, не дублируем.

Отклонены: SQL-агрегат (раздваивает путь вычисления прогресса), ленивый догруз
метрик по одному запросу на строку (N запросов, против правила эффективности).

**Разделение по стоимости.** Список периодов (`GET /api/v1/admin/periods`)
остаётся лёгким и быстрым — он не тянет цели/KR всех периодов. Метрики строк
(средний прогресс, ошибки весов) считаются дороже (загрузка целей+KR), поэтому
запрашиваются **отдельным запросом** после отрисовки списка и домёрживаются в
строки асинхронно. Это не блокирует появление списка и не удорожает базовый
рендер. Один и тот же агрегатор обслуживает и batch-статистику, и полный обзор.

## Backend

### 1. Метрики строк — отдельный batch-эндпоинт `GET /api/v1/admin/periods/stats`

Список периодов **не расширяется** полем `stats`. Метрики отдаёт отдельный
эндпоинт — лёгкие сводки по всем периодам сразу (без состава команд):

```json
{
  "items": [
    { "period_id": 1, "total_teams": 22, "teams_with_goals": 19,
      "avg_progress": 56, "weight_error_count": 7 }
  ]
}
```

- `total_teams` — число видимых команд периода.
- `teams_with_goals` — команды с ≥1 целью в этом периоде.
- `avg_progress` — средний прогресс по командам с целями: невзвешенное среднее
  по командам от `okr.PeriodProgress(teamGoals)` (канонический прогресс команды в
  периоде, взвешенный по весам её целей). На скриншоте — «56% по 19 командам с
  целями».
- `weight_error_count` — число команд, у которых сумма весов целей ≠ 100
  (с допуском `WeightTolerance` из настроек, как в healthcheck).

Считается общим агрегатором (тот же, что и `/overview`), но без сериализации
состава команд. Admin-only. Батч по всем периодам — один HTTP-запрос вместо N.

### 2. Обзор периода — `GET /api/v1/admin/periods/{periodID}/overview`

Полный ответ для модалки:

```json
{
  "summary": {
    "by_status": { "in_progress": 15, "ready": 4, "forming": 0, "closed": 0, "no_goals": 3 },
    "total_teams": 22,
    "teams_with_goals": 19,
    "weight_error_count": 7,
    "avg_progress": 56
  },
  "teams": [
    { "id": 1, "name": "…", "path": ["…"], "status": "in_progress",
      "goals_count": 3, "progress": 72, "weight_sum": 100, "weight_error": false }
  ]
}
```

- `by_status` покрывает все команды периода; сумма счётчиков = `total_teams`.
- `validated` (редкий легаси-статус) считается в плитке `in_progress`.
- Фронт делает drill-down состава категории фильтрацией `teams` по статусу /
  флагу `weight_error` — без дополнительных запросов.
- Admin-only (под `/api/v1/admin`). 403 без tenant scope.

### 3. Массовые операции

Два эндпоинта:

- `POST /api/v1/admin/periods/{periodID}/teams/activate` — команды с ≥1 целью и
  статусом ≠ `in_progress` → `in_progress`.
- `POST /api/v1/admin/periods/{periodID}/teams/close` — команды с ≥1 целью и
  статусом ≠ `closed` → `closed`.

Ответ:

```json
{ "affected": 4, "skipped": 3 }
```

- `affected` — сколько команд реально сменили статус.
- `skipped` — команды без целей (не трогаем).
- Команды с целями, уже в целевом статусе, не входят ни в `affected`, ни в op-лог
  (идемпотентность).

Сервисный метод `BulkSetTeamPeriodStatus(ctx, scope, periodID, target, actorUserID)`:

1. Грузит данные периода один раз (teams + goalsByTeam + statuses) — переиспользуя
   загрузчик `PeriodData`.
2. Вычисляет набор затронутых: `goals_count > 0 && status != target`.
3. **Batch-update** статусов затронутых команд одним запросом
   (`INSERT … ON CONFLICT … WHERE team_id = ANY($…)` или batch).
4. **Batch-insert** активностей — по одной записи op-лога на каждую затронутую
   команду (`ActivityStatus/ActionStatusChanged`, payload `before/after`), одним
   запросом. Никаких `GetTeam`/`recordActivity` в цикле.

Перевод в `in_progress` автоматически блокирует редактирование целей (существующее
поведение статуса, отдельной работы не требует — остаётся обновление прогресса).

## Frontend

### Строки списка (`PeriodRow`)

- Блок метрик после имени/дат: `X/Y с целями`, тонкий прогресс-бар + `%`, бейдж
  `веса N` (нейтральный при 0, красный при >0). Данные приходят **отдельным
  запросом** `GET …/periods/stats` после отрисовки списка и домёрживаются в
  строки по `period_id`. До получения метрик блок либо скрыт, либо показывает
  ненавязчивый плейсхолдер — список отображается сразу, не дожидаясь статистики.
- Иконочные контролы вместо текстовых (общий компонент `IconBtn`):
  - шестерёнка — открыть «Управление периодом» (обзор);
  - «вложенный период»;
  - карандаш — редактировать;
  - корзина — удалить.
  Все иконки — inline SVG, `title`-подсказка при наведении, группа выровнена по
  правому краю, корзина всегда крайняя правая.
- Иконка «в архив» / «из архива» добавляется **слева группы** только для статусов
  `closed` / `archived`.
- Клик по строке — редактирование (как сейчас). Обзор открывает **только**
  шестерёнка.

### Модалка «Управление периодом»

- Шапка: имя, даты, статус-бейдж, кнопки «Редактировать» / «Удалить».
- Секция «ОБЗОР ПЕРИОДА»:
  - 5 плиток счётчиков по статусам (В работе / К валидации / Черновик / Закрыто /
    Нет целей);
  - 3 плитки «Команды с целями» (`teams_with_goals/total_teams`), «Ошибки весов»,
    «Средний прогресс».
  - Клик по плитке → drill-down списка команд категории (фильтрация `teams`).
- Секция «МАССОВЫЕ ОПЕРАЦИИ»:
  - карточка «Перевести все команды в В работе» — превью `затронет N · пропустим M
    без целей` (считается на фронте из overview), кнопка «Применить» →
    `…/teams/activate`;
  - карточка «Закрыть цели всех команд периода» — превью, кнопка «Применить» →
    `…/teams/close`.
  - После применения — перезагрузка данных.

Переиспользуем существующие общие компоненты интерфейса (Modal, Btn, PeriodBadge)
и держим стиль консистентным с текущей admin-панелью.

## Тесты

- Сервис `BulkSetTeamPeriodStatus`: пропуск команд без целей; идемпотентность
  (команда в целевом статусе не затрагивается и не логируется); один op-лог на
  затронутую команду; корректные `affected/skipped`.
- Агрегатор обзора: `by_status` покрывает все команды и суммируется в
  `total_teams`; `weight_error_count` и `avg_progress` совпадают с healthcheck-
  логикой; `validated` попадает в `in_progress`.
- Handler-тесты: `stats`, `overview` и bulk-эндпоинты — 403 без scope, 200 +
  корректные поля.
- `stats`-эндпоинт: сводки по всем периодам, корректный `avg_progress` /
  `weight_error_count`; список периодов остаётся без метрик.

`seed_demo.sql` обновляем только при изменении структуры таблиц — не планируется.

## Вне scope

- Массовые операции по другим статусам (черновик, к валидации) — не добавляем.
- Асинхронное выполнение / прогресс-бар долгих операций — периодов и команд мало,
  операция синхронная.
