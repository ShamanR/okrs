# Встроенные (вложенные) периоды — дизайн

Дата: 2026-07-03
Ветка: `nested-periods`

## Цель

Сделать периоды целеполагания **вложенными**: год → кварталы (произвольная глубина),
с автоматическим определением вложенности и статуса на основе дат. Управление
порядком вручную (`sort_order`, move up/down) упраздняется.

Референс визуализации:
- Селектор периодов на странице целей (grouped/nested dropdown со статус-бейджами).
- Админка `/admin/periods` — вложенная таблица «Периоды целеполагания».

## Ключевые решения

- **Архитектура (вариант А): считаем на чтении, персистим только ручной флаг архива.**
  Вложенность и три временных статуса — чистые функции от `start_date`, `end_date` и
  «сейчас». Единственное, что нужно хранить дополнительно, — момент ручной архивации.
  Это исключает cron/scheduler и рассинхронизацию между инстансами в K8s: каждый инстанс
  вычисляет одно и то же из дат. Стоимость пересчёта дерева из полного списка (десятки
  строк на тенант) пренебрежимо мала.
- **Вложенность**: строгое вхождение интервалов, глубина любая.
- **Статусы** (имена из постановки): `Будущий`, `Активный`, `Закрытый`, `Архивный`.
  Первые три — автоматически по датам; `Архивный` — ручной, только из `Закрытый`.
- **Порядок** периодов — полностью автоматический; ручное управление удаляется.

## Доменная модель

`Period` (см. `specs/020-domain-model.md`):

**Хранимые поля:**
- `id`
- `name` (уникально в пределах тенанта)
- `start_date`
- `end_date`
- `archived_at` (nullable timestamptz) — **новое**; момент ручной архивации
- `created_at`, `updated_at`

**Удаляется:** `sort_order`.

**Вычисляемые на чтении (не хранятся):**
- `parent_id` (nullable) — id родительского периода
- `depth` (int) — глубина в дереве (корень = 0)
- `status` — `future | active | closed | archived` (канонические значения в домене/API;
  в стиле существующего `TeamPeriodStatus`). UI показывает русские подписи:
  `future→Будущий`, `active→Активный`, `closed→Закрытый`, `archived→Архивный`.

### Enum PeriodStatus

```go
type PeriodStatus string

const (
    PeriodStatusFuture   PeriodStatus = "future"
    PeriodStatusActive   PeriodStatus = "active"
    PeriodStatusClosed   PeriodStatus = "closed"
    PeriodStatusArchived PeriodStatus = "archived"
)
```

## Правила вычисления

### Родитель (parent_id)

Для периода `C` кандидаты в родители — все периоды `A` того же тенанта, где:
- `A != C`;
- `A.start <= C.start` и `A.end >= C.end` (вхождение);
- `A` строго больше `C`: `A.start < C.start` **или** `A.end > C.end`.

Родитель — **самый узкий** (наименьший интервал) из кандидатов.
Тай-брейк при равном span: сначала более «плотный» (позднейший `start`, ранний `end`),
затем меньший `id` — детерминированно.

Два периода с **идентичным** интервалом `[start, end]` не вкладываются друг в друга
(строгое вхождение не выполняется) → они сиблинги/корни.

`depth` = число предков по цепочке `parent_id`.

**Инвариант дерева без противоречий:** так как интервал ребёнка лежит внутри интервала
родителя, невозможна ситуация «закрытый родитель с активным ребёнком». Активный
год может содержать закрытый (прошедший), активный (текущий) и будущий кварталы
одновременно — это корректно.

### Статус

```
если archived_at != null            → archived
иначе если now < start_date         → future
иначе если now > end_date           → closed
иначе                               → active
```

`now` — текущая дата (сравнение по дате, как `start_date/end_date` типа DATE).

### Порядок (сортировка на чтении)

DFS по лесу периодов:
- Корни делятся на две зоны: **актуальные и будущие** (`active`/`future`) — сверху,
  **прошедшие** (`closed`/`archived`) — снизу; `archived` — в самом низу.
- Внутри «актуальных и будущих» дети сортируются по `start_date` **по возрастанию**
  (ближайшие/текущие выше: Q1→Q2→Q3).
- Внутри «прошедших» дети сортируются по `start_date` **по убыванию** (свежие выше:
  Q4→Q3).
- Корни-годы: новые выше (по `start_date` убыв.).
- Дети идут непосредственно под своим родителем (обход в глубину).

## API

### `GET /api/v1/periods`

Публичный эндпоинт для страницы целей. **Архивные периоды не возвращаются** —
фильтрация на сервере (`archived_at IS NULL`), а не скрытие на клиенте. Каждый элемент
дополняется полями `parent_id` (nullable), `depth`, `status`; массив `items` возвращается
уже в порядке отображения. Поле `sort_order` **удаляется**.

Прямая ссылка `?period=<id>` на архивный период на странице целей не поддерживается —
такого периода нет в списке, селектор откатывается на дефолтный период.

```json
{
  "items": [
    { "id": 2, "name": "Y2026", "start_date": "2026-01-01", "end_date": "2026-12-31",
      "parent_id": null, "depth": 0, "status": "active" },
    { "id": 1, "name": "Q1 · 2026", "start_date": "2026-01-01", "end_date": "2026-03-31",
      "parent_id": 2, "depth": 1, "status": "active" }
  ]
}
```

### Admin CRUD (`/api/v1/admin/periods`)

- `GET /api/v1/admin/periods` — **новый**; отдаёт **все** периоды тенанта, **включая
  архивные**, с теми же вычисляемыми полями (`parent_id`, `depth`, `status`) и в порядке
  отображения. Админка (`admin.js`) переключается с публичного `/api/v1/periods` на этот
  эндпоинт, чтобы видеть и архивные тоже.
- `POST /api/v1/admin/periods` — `{name, start_date, end_date}` (без `sort_order`).
- `PATCH /api/v1/admin/periods/{periodID}` — `{name, start_date, end_date}`.
- `DELETE /api/v1/admin/periods/{periodID}`.
- **Удаляются** `POST …/move-up` и `POST …/move-down`.
- **Добавляются:**
  - `POST /api/v1/admin/periods/{periodID}/archive` — переводит в `Архивный`.
    `409 CONFLICT`, если текущий статус периода не `closed`.
  - `POST /api/v1/admin/periods/{periodID}/unarchive` — снимает `archived_at`; период
    возвращается к вычисляемому статусу (обычно `closed`).

Валидация дат create/update: `end_date >= start_date`; имя уникально в тенанте (как сейчас).
Вложенность не задаётся руками — она следствие дат; при пересечении без вхождения периоды
становятся сиблингами (это допустимо, отдельной ошибки нет).

### Прочее

`GET /api/v1/teams/{teamID}/overview` — объект `period` меняет `sort_order` на `status`
(+ при необходимости `parent_id`, `depth`).

## Фронтенд

### Админка — `PeriodsSection` в `internal/web/static/admin.js`

- Вместо плоской таблицы — **вложенная** таблица (год → кварталы с отступом): колонки
  `Период`, `Даты`, `Статус` (бейдж), действия. Колонки `Команд` **нет**.
- Бейдж статуса: `Активный` — зелёный, `Будущий` — синий, `Закрытый` — серый,
  `Архивный` — серый/приглушённый.
- Убрать кнопки move ↑/↓.
- Действие «Архивировать»/«Разархивировать» — доступно только для `closed`/`archived`
  соответственно.
- «+ вложенный» — удобная кнопка: открывает создание периода с преднаполнением дат
  внутри диапазона родителя (структура всё равно выводится из дат, ссылки не хранятся).

### Селектор периодов — `internal/web/static/tracker.js`

- Заменить плоский `<select>` на богатый grouped/nested dropdown (референс — скриншот 1):
  цветная точка статуса, диапазон дат, бейдж статуса, группа «АКТУАЛЬНЫЕ И БУДУЩИЕ»,
  отступ по `depth`.
- `Архивный` периоды в селектор **не попадают вовсе** — их не отдаёт публичный
  `/api/v1/periods` (фильтр на сервере). Клиенту не нужно ничего прятать.

## Миграция и seed

- Новая миграция `NNN_period_nesting`:
  - `ALTER TABLE periods ADD COLUMN archived_at TIMESTAMPTZ NULL;`
  - `ALTER TABLE periods DROP COLUMN sort_order;`
  - down-миграция реверсит (возвращает `sort_order INTEGER NOT NULL DEFAULT 0`,
    удаляет `archived_at`).
- `seed_demo.sql`: убрать `sort_order` из вставок; разложить демо-периоды в реальное
  дерево, чтобы воспроизводились оба скриншота:
  - текущий год + кварталы (часть активна/будущая/закрыта),
  - прошлый закрытый год + кварталы,
  - опционально один архивный период.

## Тестирование

- **Домен (unit):**
  - вложенность: строгое вхождение; произвольная глубина; тай-брейк; идентичные
    интервалы → сиблинги; пересечение без вхождения → сиблинги;
  - статус: `future/active/closed` по датам (граничные `now == start`, `now == end`);
    `archived_at` перекрывает вычисляемый;
  - порядок: DFS-сортировка соответствует правилам зон/направлений.
- **Repo:** персистентность `archived_at`; отсутствие `sort_order`.
- **Handlers:** `archive` → `409`, если период не `closed`; `unarchive` возвращает к
  вычисляемому статусу; удалённые move-эндпоинты недоступны; публичный `/api/v1/periods`
  не содержит архивных периодов, `GET /api/v1/admin/periods` — содержит.
