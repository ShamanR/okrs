# Связанные цели (дерево целей) — дизайн-док

Дата: 2026-08-14
Статус: черновик на согласование

## 1. Цель и контекст

Нужна возможность **наследовать цели друг от друга**, чтобы команда могла:

- декомпозировать цель руководителя на цели своей команды;
- иметь годовую цель и декомпозировать её на квартальные.

Для этого вводится **связь между двумя целями** отношением
«дочерняя → родительская»:

- цель можно сделать дочерней к любой другой доступной цели;
- родительская цель выбирается из любой доступной команды и любого периода;
- цель может ссылаться на **несколько** родительских целей (M:N).

Это **новая mutation-фича**. Связей цель↔цель в коде нет: у `domain.Goal` нет
поля родителя/ребёнка, в БД нет таблицы связей, во фронтенде (`mapGoal`) нет
соответствующих полей. Реализуется с нуля, переиспользуя существующие
компоненты (селектор периода `PeriodSelect`, поиск/список команд, popover
`UserInfo`, `InfoHint`).

### Отграничение от «общей цели» (share)

Связь **не** делает цель общей. Это разные механики:

- **Общая цель** (`goal_shares`, значок `⇄`) — одна и та же цель-идентичность
  становится **видимой нескольким командам**, со своим весом/порядком в каждой.
  Identity цели не меняется.
- **Связь** (`goal_links`, значок `↑`/`↓`) — соединяет **две разные цели**
  отношением «дочерняя → родительская». Идентичности две, связь —
  только отношение.

Тексты подсказки в UI прямо разводят эти понятия (см. §7).

### Отграничение от «Дерева целей» (страница `/goal-tree`)

В сайдбаре уже есть пункт «Дерево целей» (`/goal-tree`) — сейчас это
**заглушка** (`stub.js`). Полноценная страница-визуализация графа **не входит**
в этот change set (отдельная спека позже). Ссылка «🌳 дерево» в popover ведёт
**deep-link на связанную цель**, а не на страницу-дерево.

## 2. Терминология и семантика

- **Родительская цель (parent)** — верхнеуровневая цель, к которой привязана
  дочерняя. У дочерней в UI показывается лейбл `↑ N` (N родителей).
- **Дочерняя цель (child)** — цель, которая ссылается на родителя(ей). У
  родителя в UI показывается лейбл `↓ N` (N детей).
- **Связь (link)** — направленное ребро `child → parent` в таблице
  `goal_links`. Управляется со стороны **дочерней** цели (её владелец
  добавляет/удаляет родителей при редактировании цели).
- Граф связей — **направленный ацикличный (DAG)**: циклы запрещены на сервере.

### Что связь НЕ делает (важно, YAGNI)

- Связь **не влияет на расчёт прогресса**. Прогресс родителя по-прежнему
  считается только по его собственным KR; ребёнок не «вливает» прогресс в
  родителя. Никакого rollup по графу связей нет (согласовано).
  Расчёты прогресса (`internal/okr`) не меняются.
- Связь **не меняет видимость** цели командами (в отличие от share).
- Связь **не зависит от `team period status`** (см. §6).

## 3. Доменная модель

### Новая сущность `GoalLink`

Ребро графа связей. Хранится в таблице `goal_links`.

**Поля:**

- `tenant_id` (FK → tenants.id, ON DELETE CASCADE) — тенант; **обе** цели ребра
  всегда принадлежат этому тенанту;
- `child_goal_id` (FK → goals.id, ON DELETE CASCADE) — дочерняя цель;
- `parent_goal_id` (FK → goals.id, ON DELETE CASCADE) — родительская цель;
- `created_at`.

**Инварианты:**

- пара `(tenant_id, child_goal_id, parent_goal_id)` уникальна (PK);
- `child_goal_id <> parent_goal_id` (запрет самоссылки, DB CHECK);
- обе цели принадлежат одному тенанту (`goals.tenant_id = goal_links.tenant_id`
  для обеих) — проверяется в service-слое tenant-scoped запросами; кросс-тенантные
  связи невозможны;
- граф связей **ацикличен**: добавление ребра, замыкающего цикл, отклоняется на
  сервере (см. §5);
- связи каскадно удаляются при удалении любой из двух целей (`ON DELETE CASCADE`
  на обоих FK) — в т.ч. при `mode=move` переносе цели (жёсткое удаление
  исходной цели удаляет её связи);
- связи **не копируются** при `POST /goals/{id}/transfer` (аналогично тому, что
  шеры не переносятся) — новая цель создаётся без связей.

### Сводка связанной цели `GoalRef` (вычисляемая, не хранится)

Для лейблов и popover в списке целей на чтении собирается компактная сводка
каждой связанной цели:

- `id`, `title`, `period_id`, `period_name`, `team_id`, `team_name`,
  `team_type`, `progress` (0..100).

### Расширение `Goal`

`domain.Goal` получает два вычисляемых на чтении поля:

- `Parents []GoalRef` — родители (только видимые в scope читателя, см. §4);
- `Children []GoalRef` — дети (только видимые в scope читателя).

Оба поля заполняются **батчем** при загрузке доски (без N+1), поэтому счётчики
лейблов и данные popover приходят в одном ответе, без дополнительных запросов на
каждую цель.

## 4. Видимость и tenant-изоляция

### Tenant / namespace (сквозная изоляция)

- `goal_links.tenant_id` присутствует во **всех** запросах (anchor и recursive
  часть рекурсивного CTE в том числе); фильтрация по `tenant_id = $tenant`
  обязательна.
- Родительская цель при привязке валидируется **scoped-запросом** к `goals`
  (`WHERE id = ANY($ids) AND tenant_id = $tenant`) — привязать цель чужого
  тенанта нельзя (вернётся `VALIDATION_ERROR`), как и в `transfer` для целевой
  команды/периода.
- FK `tenant_id → tenants(id) ON DELETE CASCADE`: удаление тенанта чистит его
  связи.

### Scope (hierarchy grants)

Согласовано: **показываем только связи в scope**.

- В `Parents`/`Children` цели попадают только те связанные цели, чья
  **команда-владелец входит в доступный scope** читателя
  (`AllowedTeamIDsFromCtx`; администратор/`AUTH_MODE=disabled` — все команды
  тенанта). Связь на недоступную команду **не отображается** ни в счётчике
  лейбла, ни в popover — консистентно с остальной scope-моделью (цель
  недоступной команды = `404`).
- Пикер выбора родителя (`/goals/linkable`) отдаёт только цели доступных команд —
  привязать к недоступной цели изначально нельзя.
- Побочный эффект: связь, созданная владельцем ребёнка к родителю в команде A,
  видна в лейбле ребёнка только тем, у кого A в scope. Разные читатели видят
  разное число связей — это ожидаемо и совпадает с тем, как работает scope для
  всего остального.

## 5. Предотвращение циклов (без запросов в цикле)

Это ключевой риск фичи. Разбираем отдельно, т.к. цель может иметь несколько
родителей из любых периодов/команд — граф легко замкнуть (`A→B→A`, `A→B→C→A`).

### Правило

Граф `goal_links` (рёбра `child → parent`) должен оставаться **DAG**. Ребро
`C → P` замыкает цикл ⟺ `C` уже достижима из `P` вверх по цепочке родителей
(т.е. `C` — предок `P`). Такое ребро отклоняется: `409 CONFLICT`
(`GOAL_LINK_CYCLE`).

### Почему одной проверки достаточно при full-replace

Операция привязки — **полная замена** множества родителей дочерней цели `C`
(delete-all + insert-set в одной транзакции). Единственные изменяемые рёбра — это
исходящие рёбра `C` (её родители). **Удаление** старых родителей `C` цикл
создать не может. Значит, цикл может появиться только от **новых** рёбер
`C → Pᵢ`.

Новое ребро `C → Pᵢ` создаёт цикл ⟺ `C` достижима из `Pᵢ` по цепочке родителей
в графе, **из которого исключены исходящие рёбра самого `C`** (они как раз
заменяются). Отсюда — **одна** проверка на всю операцию:

1. одним рекурсивным CTE вычисляем множество **предков** всего набора
   `{Pᵢ}` (ancestor-closure по `goal_links`), исключив рёбра с
   `child_goal_id = C`, tenant-scoped;
2. если `C` ∈ этом множестве **или** `C` ∈ `{Pᵢ}` (самоссылка) — отклоняем весь
   запрос `409 GOAL_LINK_CYCLE`, транзакция откатывается;
3. иначе — коммитим replace.

**Никаких запросов в цикле** (CLAUDE.md §9): проверка — один CTE на всю
операцию, а не «по ребру». Вставка набора — один `INSERT ... SELECT unnest(...)`.

### Защита самого рекурсивного CTE от runaway

Данные поддерживаются ацикличными правилом выше, но CTE пишем defensively:

- используем `UNION` (не `UNION ALL`) — дедуп посещённых узлов;
- добавляем `CYCLE parent_goal_id SET is_cycle USING path` (PostgreSQL 14+) —
  встроенная детекция цикла обрывает рекурсию, даже если в данных внезапно
  оказалось замыкание (миграция/ручная правка);
- жёсткий предел глубины (`WHERE depth < 1000`) как дополнительный предохранитель.

Проверяем версию PostgreSQL в окружении; если `CYCLE`-клоза недоступна — резервный
вариант: рекурсия с массивом-путём (`path bigint[]`) и условием
`NOT parent_goal_id = ANY(path)`.

### Клиентские «циклические вызовы» (фронтенд)

Отдельно следим, чтобы не появилось бесконечных циклов на клиенте:

- popover-данные приходят **инлайн** в ответе доски → hover не запускает
  дозагрузку → нет петли fetch↔render;
- пикер (`/goals/linkable`) грузится только при открытии и по смене периода;
  `useEffect`-зависимости выверяем, чтобы смена периода не рекурсивно
  ретригерила загрузку;
- список кандидатов исключает саму редактируемую цель (`exclude_goal_id`), чтобы
  нельзя было выбрать себя.

## 6. Lifecycle-вопросы (обязательно по `050-permissions-and-lifecycle.md`)

Как любая новая mutation-фича, привязка отвечает на обязательные вопросы:

- **зависит ли от `team period status`** — **нет**. Привязка/отвязка родителя —
  метаданные цели; идёт независимо от статуса, как обновление прогресса.
- **разрешена ли в `validated`** — **да**.
- **разрешена ли в `closed`** — **да**.
- **проверяется ли на сервере** — **да**: доступ к команде-владельцу **дочерней**
  цели (`CanAccessTeamFromCtx`), принадлежность и scope-доступ каждой
  родительской цели, tenant-scope, запрет самоссылки и цикла. UI-ограничения —
  лишь удобство.
- **зависит ли от будущих permissions / roles** — **нет**; опирается на текущую
  модель tenant + hierarchy grants.

Обоснование «не зависит от статуса»: связь не является структурной правкой самой
цели/KR (не меняет состав целей команды, прогресс или веса) — это внешнее
отношение. Блокировать её в `in_progress`/`closed` не нужно; наоборот, полезно
уметь дособрать дерево уже в работе.

## 7. API-контракт

Все эндпоинты — под `/api/v1`, tenant-scoped, с проверкой scope. Формы ошибок
нормализованы (`VALIDATION_ERROR`/`NOT_FOUND`/`CONFLICT`/`INTERNAL`).

### 7.1. Чтение: встраивание связей в цель

`GET /api/v1/teams/{teamID}/okrs?period_id={id}` и
`GET /api/v1/goals/{goalID}` — каждая цель в ответе получает два массива
(scope-filtered):

```jsonc
"parents":  [ { "id", "title", "period_id", "period_name", "team_id", "team_name", "team_type", "progress" } ],
"children": [ { "id", "title", "period_id", "period_name", "team_id", "team_name", "team_type", "progress" } ]
```

- пустые массивы, если связей нет (или все вне scope);
- счётчик лейбла = длина массива;
- данные грузятся батчем (`goal_links` ⋈ `goals` ⋈ `teams` ⋈ `periods` по
  `ANY($goalIDs)`, фильтр по `tenant_id` + доступным `team_id`), без N+1;
- идемпотентность: read-only.

### 7.2. Чтение: источник пикера родителей

`GET /api/v1/goals/linkable`

- **method + path:** `GET /api/v1/goals/linkable`
- **query:**
  - `exclude_goal_id` (int64, опц.) — id редактируемой цели, исключается из
    выдачи (нельзя привязать себя);
  - `period_id` (int64, опц.) — фильтр периода; по умолчанию (отсутствует)
    трактуется клиентом как **текущий период**; специальное значение
    `period_id=all` (или отсутствие → клиент шлёт текущий) — все периоды.
    Сервер: если `period_id` задан — фильтр по нему; если `all` — без фильтра
    периода;
  - `q` (string, опц.) — регистронезависимый поиск по **названию цели**,
    **названию команды** или **имени лида** команды.
- **response (200, массив):**

```jsonc
[ { "id", "title", "team_id", "team_name", "team_type", "team_path", "lead",
    "period_id", "period_name", "progress" } ]
```

  Отсортировано по DFS иерархии команд (как в сайдбаре), внутри команды — по
  `sort_order` цели. Возвращаются только цели **доступных** команд текущего
  тенанта; администратор — все команды тенанта.
- **validation:** невалидный `period_id` (не int64 и не `all`) → `400
  VALIDATION_ERROR`.
- **idempotency:** read-only, без side effects, CSRF не требуется (GET).
- **side effects:** нет.

### 7.3. Запись: полная замена родителей (full-replace)

`POST /api/v1/goals/{goalID}/links`

- **method + path:** `POST /api/v1/goals/{goalID}/links`
- **request:** `{ "parent_goal_ids": [<int64>, ...] }` — полный целевой набор
  родителей дочерней цели `goalID`. Пустой массив → снять все связи.
- **validation rules:**
  - `goalID` не найдена / команда-владелец вне scope → `404 NOT_FOUND`;
  - `parent_goal_ids` содержит `goalID` (самоссылка) → `400 VALIDATION_ERROR`
    (`parent: self`);
  - какой-либо `parent_goal_id` не существует в тенанте или его команда-владелец
    вне scope вызывающего → `400 VALIDATION_ERROR` (`parent: not accessible`);
  - набор создаёт цикл → `409 CONFLICT` (`GOAL_LINK_CYCLE`);
  - дубликаты в массиве схлопываются (idempotent-набор).
- **success:** `204 No Content`.
- **idempotency:** идемпотентно — замена на текущий набор ничего не меняет и не
  пишет в журнал.
- **side effects:** строки `goal_links` для `child_goal_id = goalID` заменяются
  на новый набор; прогресс/статусы/веса не меняются. Журнал активности:
  раздельные записи `goal_linked` (добавленные) и `goal_unlinked` (снятые),
  категория `composition` (best-effort после успешной мутации). CSRF обязателен.

### Роуты (регистрация в `goals/routes.go`)

```go
r.Get("/api/v1/goals/linkable", h.HandleLinkableGoals)
r.Post("/api/v1/goals/{goalID}/links", h.HandleSetGoalParents)
```

(Порядок регистрации: `linkable` до `{goalID}`-подмаршрутов, чтобы chi не
трактовал `linkable` как `goalID`. Так как это отдельный путь `/goals/linkable`
без параметра — конфликтует только с несуществующим `/goals/{goalID}` GET на
корне; проверяем на этапе реализации.)

## 8. Слои реализации

Соблюдаем layered/clean architecture (CLAUDE.md §6, `010`):

- **domain** (`internal/domain/models.go`): типы `GoalLink`, `GoalRef`; поля
  `Parents`/`Children` на `Goal`.
- **store** (`internal/store/goallinks/goallinks.go`, новый пакет):
  `GoalLinkRepository` с полем `db *pgxpool.Pool`. Методы:
  - `ListLinksForGoals(ctx, scope, goalIDs, allowedTeamIDs) (parents, children map[int64][]domain.GoalRef, error)`
    — батч, scope-filtered, tenant-scoped;
  - `ReplaceParents(ctx, scope, childID int64, parentIDs []int64) (added, removed []int64, err error)`
    — транзакция: read текущего набора → cycle-check одним CTE → `DELETE`
    исходящих рёбер `childID` → `INSERT ... SELECT unnest($parentIDs)` →
    возврат diff для журнала;
  - внутренний `ancestorsExcludingChild(ctx, tx, tenant, childID, parentIDs) (map[int64]bool, error)`
    — рекурсивный CTE (см. §5).
  Регистрируется как `store.Store.GoalLinks` (composite в `store.go`,
  `store.New`).
- **service** (`internal/service`): интерфейс `GoalLinkRepo` в `service.go`;
  методы:
  - `SetGoalParents(ctx, scope, allowed, childID, parentIDs) error` — проверка
    доступа к команде-владельцу ребёнка, валидация принадлежности/scope/самоссылки
    родителей (scoped-запрос `GoalRepo.ListGoalOwnerTeamIDs` + пересечение с
    `allowed`), вызов `ReplaceParents`, запись в журнал (`ActivityRepo`);
  - `ListLinksForGoals(...)` — прокси для сборки `Parents`/`Children` при загрузке
    доски;
  - `ListLinkableGoals(ctx, scope, allowed, periodID *int64, excludeGoalID int64, q string) ([]domain.GoalRef+, error)`.
- **http/api/v1/goals**: `HandleSetGoalParents`, `HandleLinkableGoals`; сборка
  `parents`/`children` в существующих `response.go` доски и `GET /goals/{id}`.

Никакой бизнес-логики и SQL в handlers; расчёты прогресса не трогаем.

## 12. Тесты (Definition of Done, `010` §"Definition of done")

- **store** (`goallinks`):
  - full-replace: замена набора, снятие всех (пустой массив), идемпотентность;
  - **cycle**: прямой `A→B→A`, транзитивный `A→B→C→A`, самоссылка → отклонение;
    корректная замена, не создающая цикл, — проходит;
  - **scope-фильтрация** `Parents`/`Children`: связь на недоступную команду
    скрыта у одного читателя и видна у другого/админа;
  - **tenant-изоляция**: связь нельзя создать на цель чужого тенанта; связи
    одного тенанта не видны из другого; рекурсивный CTE tenant-scoped;
  - **каскад**: удаление цели и `mode=move` переносят/чистят связи; `copy` не
    копирует связи;
  - батч-загрузка без N+1 (кол-во запросов не растёт с числом целей).
- **service**: доступ к команде-владельцу ребёнка; валидация scope/принадлежности
  родителей; запись в журнал `goal_linked`/`goal_unlinked` (diff).
- **api**: контракт `linkable` (поиск, период, exclude, scope); `links` full-
  replace, коды `204/400/404/409`, CSRF; `parents`/`children` в ответе доски.
