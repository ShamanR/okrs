# Дизайн: комментарии как таски с ответами

**Дата:** 2026-07-17
**Статус:** утверждён к реализации

## Проблема и цель

Сейчас комментарий к цели (`goal_comments`) — плоская сущность: каждый комментарий
трактуется как замечание/таска с состоянием «решено / не решено». Диалога нет — ответить
на замечание нельзя, всё лежит одним списком.

Нужно превратить механизм в двухуровневый:

1. каждый комментарий первого уровня — замечание/таска (как сейчас, резолвится);
2. таски сортируются от самой старой к самой новой;
3. на таску можно ответить;
4. ответ таской не является (не резолвится);
5. свои таски и ответы можно удалять;
6. удаление таски удаляет и все её ответы (каскад);
7. счётчик выводит только число тасок (решённых и нерешённых); ответы не считаются;
8. ответы и таски попадают в журнал активностей, живут под одним фильтром (`discussion`),
   но имеют разные описания.

## Решения по продукту (утверждено)

- **Кто удаляет:** автор своей таски/ответа **ИЛИ** tenant-admin (модерация).
- **Журнал удалений:** удаление логируется отдельными событиями.
- **Глубина веток:** ровно один уровень — ответ только на таску, ответа на ответ нет.

## Модель данных

### Выбранный подход

Самоссылающийся `parent_id` в существующей таблице `goal_comments` (а не отдельная таблица
ответов). Даёт каскад удаления на уровне БД бесплатно, не плодит дублирование полей
author/text/created_at и сохраняет текущий батч-запрос без N+1.

### Миграция `040_comment_replies`

```sql
-- up
ALTER TABLE goal_comments
  ADD COLUMN parent_id BIGINT NULL REFERENCES goal_comments(id) ON DELETE CASCADE;
CREATE INDEX idx_goal_comments_parent ON goal_comments(goal_id, parent_id, created_at);

-- down
DROP INDEX IF EXISTS idx_goal_comments_parent;
ALTER TABLE goal_comments DROP COLUMN IF EXISTS parent_id;
```

### Сущность `GoalComment` (обновлённая)

- **Таска** — строка с `parent_id IS NULL`. Резолвится (`resolved_at` / `resolved_by_user_id`),
  как сейчас.
- **Ответ** — строка с `parent_id`, указывающим на таску (строку с `parent_id IS NULL`).

**Инварианты:**

- у ответа `resolved_at` и `resolved_by_user_id` всегда NULL — ответ не является замечанием
  с состоянием;
- `parent_id` ссылается только на таску того же `goal_id` и тенанта; глубина вложенности —
  ровно один уровень (ответа на ответ нет);
- каскадное удаление таски (`ON DELETE CASCADE`) удаляет все её ответы;
- остальные инварианты комментария (наличие автора, tenant-scoping, идемпотентность резолва)
  сохраняются.

## API-контракт

### Форма `comments[]` в `GET /api/v1/teams/{teamID}/okrs` и `GET /api/v1/goals/{goalID}`

`comments[]` содержит **только таски**; у каждой таски — вложенный `replies[]`:

```json
"comments": [
  {
    "id": 1, "text": "...", "author_name": "Ivan", "author_udid": "...", "created_at": "...",
    "resolved": true, "resolved_by_name": "Petr", "resolved_by_udid": "...", "resolved_at": "...",
    "replies": [
      { "id": 5, "text": "...", "author_name": "Anna", "author_udid": "...", "created_at": "..." }
    ]
  }
]
```

- ответ (`replies[]`) несёт `id`, `text`, `author_name`, `author_udid`, `created_at` — без
  resolve-полей;
- таски сортируются `created_at ASC` (старые → новые, требование #2); ответы внутри таски —
  тоже `created_at ASC` (порядок диалога);
- счётчик = `comments.length` (только таски, требование #7) — получается напрямую, раз ответы
  вложены;
- загрузка — тем же батч-запросом (`goal_id = ANY(...)`), без N+1; ответы группируются к таскам
  в памяти по `parent_id`.

### Эндпоинты

| Метод + путь | Назначение | Авторизация |
|---|---|---|
| `POST /api/v1/goals/{goalID}/comments` | создать **таску** (как сейчас) | любой в scope цели |
| `POST /api/v1/goals/{goalID}/comments/{commentID}/replies` | создать **ответ** на таску | любой в scope цели |
| `DELETE /api/v1/goals/{goalID}/comments/{commentID}` | удалить таску (каскад ответов) **или** ответ | автор ИЛИ tenant-admin |
| `POST .../comments/{commentID}/resolve` \| `/unresolve` | резолв/reopen — **только таска** | любой в scope цели |

**Валидация и ошибки:**

- `replies`: `text` непустой, иначе `400 VALIDATION_ERROR`; `commentID` должен быть таской
  (`parent_id IS NULL`), иначе `404 NOT_FOUND` (на ответ ответить нельзя);
- `resolve` / `unresolve`: если `commentID` — ответ, `404 NOT_FOUND` (ответ не резолвится);
- `DELETE`: `404`, если таска/ответ не найдены в scope; `403`, если вызывающий не автор и не
  tenant-admin; идемпотентность — повторный DELETE удалённого id → `404`;
- side effects: удаление таски каскадно удаляет ответы; счётчики/агрегаты целей от этого не
  зависят.

### Контроль доступа (для каждого comment/reply/resolve/delete эндпоинта)

Двухуровневая проверка, fail-closed на сервере, строго в порядке:

1. **Пространство (tenant):** `scope := TenantScopeFromContext` обязателен, иначе `403`. Каждый
   SQL несёт `tenant_id = scope.TenantID` в `WHERE` — сущность чужого тенанта не резолвится → `404`.
2. **Доступ к команде:** цель должна принадлежать команде из scope вызывающего **или** быть
   расшарена в такую команду (`canAccessGoal`: owner team ИЛИ любая shared team в scope).
   Недоступна → `404 NOT_FOUND` (не `403` — чтобы id цели не работал как оракул существования).
3. **Привязка сущности:** `commentID` пинуется к `goalID` и тенанту в
   `WHERE id=$comment AND goal_id=$goal AND tenant_id=$tenant` — нельзя удалить/ответить на
   комментарий из другой цели, подставив чужой `commentID`.
4. **Только DELETE, дополнительно:** автор (`author_user_id == текущий`) **ИЛИ** tenant-admin.
   Админ проходит шаг 2 автоматически (доступ ко всем командам тенанта). Не автор и не админ → `403`.

Цепочка применяется и к уже существующим `POST /comments`, `resolve`, `unresolve` (шаги 1–3 там
уже есть — сохраняем), и к новым `replies`, `DELETE` (реализуем ту же цепочку). Ни один шаг не
полагается только на UI.

## Журнал активностей

Все события — в категории `discussion` (один фильтр, требование #8), с разными `action` и
описаниями:

| action | Когда | Описание в ленте (RU) |
|---|---|---|
| `comment_added` | добавлена **таска** (как сейчас) | «оставил замечание к «{t}»» |
| `reply_added` (нов.) | добавлен **ответ** | «ответил на замечание к «{t}»» |
| `comment_resolved` / `comment_reopened` | резолв/reopen таски | без изменений |
| `comment_deleted` (нов.) | удалена **таска** | «удалил замечание к «{t}»» |
| `reply_deleted` (нов.) | удалён **ответ** | «удалил ответ на замечание к «{t}»» |

- при каскадном удалении таски пишется **одно** событие `comment_deleted`; отдельные
  `reply_deleted` при этом не пишутся (иначе лавина событий) — `reply_deleted` только при
  точечном удалении ответа;
- событие пишется best-effort после успешной мутации; журнал append-only, `comment_id` — не FK,
  поэтому старые `comment_added` / `reply_added` на удалённые комментарии остаются в ленте (это
  ожидаемо; deep-link на удалённый комментарий просто не сработает при скролле);
- `reply_added` кладёт `payload.text` (как `comment_added`), чтобы текст ответа рендерился в
  ленте markdown-блоком под строкой события.

## Фронтенд (tracker.js)

- **`CommentRow` (таска):** сохраняет резолв/reopen; добавляются:
  - кнопка **«Ответить»** → раскрывает компактный `MarkdownEditor` (переиспользуем тот же, что в
    `comment-compose`); submit → `POST .../comments/{id}/replies`;
  - список ответов под таской (отступ/ветка слева);
  - кнопка **«Удалить»** (иконка-ссылка в стиле `comment__link-btn`), видна если
    `c.authorUdid === me.udid` **или** `cfg.is_admin`; клик → inline-подтверждение (тот же паттерн,
    что у удаления цели) → `DELETE .../comments/{id}` → `onReload()`.
- **`ReplyRow` (новый, один уровень):** аватар + автор + дата + `Markdown`-текст; резолва нет;
  кнопка «Удалить» по тому же правилу (`authorUdid === me.udid || is_admin`). Ответ на ответ не
  предлагается.
- **Сортировка:** таски и ответы приходят с бэка `ASC` — клиент не пересортировывает. Визуальная
  группировка «открытые таски / Решённые · N» сохраняется, внутри групп — старые → новые.
- **Счётчик на футере карточки:** `💬 {comments.length}` = число тасок (требование #7); бейдж
  «N нерешённых» = `comments.filter(c => !c.resolved).length` (таски; ответы не в `comments[]`).
- **Данные:** маппинг goal → comment расширяется полем `replies` (shape таски минус resolve-поля);
  `is_admin` пробрасывается в `GoalCard` из конфига (бэкенд всё равно enforce'ит).
- **Консистентность (CLAUDE.md #12):** переиспользуем `MarkdownEditor`, `AvatarWithUDID`,
  inline-confirm и классы `comment__*`; новых паттернов управления не вводим.

## Разрешения и lifecycle (чек-лист specs/050)

- ответ и удаление таски/ответа **не зависят** от `team period status`: комментирование доступно
  во всех статусах (`in_progress` и `closed` — режим `comments_only` в UI), поэтому ответы и
  удаление своих комментариев доступны там же; серверных status-гейтов на комментарии нет и не
  добавляем;
- разрешено в `validated` и `closed` — да (как комментарии);
- проверяется на сервере — да (см. «Контроль доступа»), не только в UI;
- от будущих ролей не зависит; авторизация delete — авторство + текущая роль tenant-admin.

## Тесты

- **store:** `parent_id`, каскад удаления таски, сортировка тасок и ответов `ASC`, `resolved` не
  ставится на ответ, привязка `commentID` к `goalID`+тенанту.
- **service:** события `reply_added` / `comment_deleted` / `reply_deleted`; ровно одно
  `comment_deleted` при каскадном удалении таски.
- **handlers:** авторизация delete (автор / admin / чужой → 403); доступ по tenant + команде
  (чужой тенант / недоступная команда → 404); reply на ответ → 404; resolve ответа → 404;
  идемпотентность delete.
